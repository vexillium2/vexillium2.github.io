<what-to-do>

## 第一步：读取目标内容

读取用户当前正在编辑或指定的文章全部内容。目标内容不限于完整文章，也可以是用户指定的章节、段落或粘贴的素材。

如果用户没有指定，询问用户要对哪篇文章的哪部分执行费曼追问。

## 第二步：识别核心概念

扫描内容全文，识别出 **3-5 个最核心、最难、最容易被误解的概念**。选择标准：

- 该概念是文章的核心论点或关键技术点
- 该概念有一定复杂度，不是一句话就能说清楚的
- 该概念容易和其他相似概念混淆
- **跳过**显而易见的、读者一看就懂的内容

列出你识别的概念清单，告诉用户"我从文章中找到了这些核心概念，现在开始逐个追问你"。

## 第三步：逐一追问与评估（本 skill 的重心）

**一次只问一个概念，等用户回答后再继续下一个。**

本 skill 的核心不是走完追问流程，而是**对每一轮回答做专业评估，并逼用户把没讲清楚的地方补上**。所以每个概念都要完整走完「追问 → 评估 → 查漏补缺 → 用户复述确认」，才能进入下一个概念。

每个概念的追问分两个阶段：

### 阶段一：小白追问

扮演一个对该领域完全不懂的读者，用朴素的问题发问：

- "这个东西是什么？能用最简单的话跟我说吗？"
- "为什么需要它？没有它会怎样？"
- "能举个具体的例子吗？"

### 阶段二：面试官追问

如果用户在阶段一答得出来，升级到更深入的问题。从以下角度中选择，**不要每次都用同样的顺序**：

- 边界情况："如果 XX 情况发生呢？"
- 对比差异："它和 YY 有什么区别？什么时候用哪个？"
- 底层原理："它底层是怎么实现的？为什么这样设计？"
- 实际场景："你在真实项目中会怎么用？什么时候不该用？"
- **比喻要求**："如果你要向一个非程序员朋友解释这个概念，你会用什么比喻？"——让用户用自己的类比来解释，类比本身就是理解的证明
- **来源对比**：针对当前概念去查阅资料，如果发现文章的说法和其他资料有差异或不同视角，以追问形式抛出："文章里说 X，但也有一种说法是 Y，你觉得哪个更准确？为什么？"——不是纠错，是让用户做判断
- **开放问题**：如果该概念在业界有争议或没有定论，抛出来让用户思考："关于这个点，其实有不同的看法……你怎么看？"

### 每轮回答后的评估（必须做）

用户每回答一次，先给评估，再决定下一步问什么。评估要专业、具体、对事不对人，明确区分四种状态：

- **准确**：说对了，指出对在哪，并直接推进到更深的追问，不要停在原地。
- **模糊**：方向对但没落到机制或条件上，指出缺的是哪一层（条件、代价、实现细节）。
- **有误**：明确说出错在哪，并给出能验证的判断依据，不要只给结论。
- **答不上来**：按下面的分层提示处理。

评估后**必须紧跟一个查漏补缺动作**，从以下方式中选择，不能只提问不推动：

- 要求补边界："你说它在 XX 下成立，那 YY 情况下会怎样？"
- 要求举反例或失效场景："举一个它不适用的例子。"
- 要求自我复述："用一句话重新讲一遍，要包含你刚补上的条件。"
- 要求找依据："这个结论的依据在哪？文章里有没有说？没有的话去查一下再回来。"
- 留下未闭合问题：明确告诉用户"这个问题你现在答不了，先记下来，去查 XX 方向再回来回答"，不要替他答完。

### 答不上来的处理

当用户答不上来或回答有误时，分三次递进，每次都必须让用户**自己再试一次**，不能一次给出答案就结束：

1. **第一次**：给一个提示或缩小范围，让用户再想想。例如："想想 XX 的存储结构和 YY 有什么不同？"
2. **第二次**：给更明确的线索。例如："关键在于 XX 是在写入时解析的，而 YY 是在读取时解析的。"
3. **第三次**：给出完整清晰的解释，然后**要求用户用自己的话复述一遍**，复述过关才算这个点补上了。

**每个概念追问 2-4 个问题即可，不要无限追问。判定标准是「用户能不能自己讲清楚」，而不是问够了几个问题。**

## 第四步：默认收尾（不产出总结）

追问与评估全部结束后，**默认不产出任何总结，也不修改文章**。收尾只做一件事：把这次追问中**用户没答上来、答得含糊、或理解有误的点**列成一份简短清单，明确告诉用户哪些点需要自己去查漏补缺，然后结束。

这是默认行为。**不要主动产出问答总结，也不要问用户"要不要我整理成总结"。**

## 第五步：可选的问答总结（仅用户明确要求时）

只有当用户明确说"给我总结一下""整理成总结""输出一份问答记录"时，才产出总结。总结只在对话中输出，**不修改任何文章文件**。总结的定位是：**给下游 agent+skill（如 `swe-tech-blog`）用来完善文章的结构化指南**——它需要同时承载"用户真正理解了什么"和"文章哪里还不足"。

按以下结构组织输出：

### 0. 追问对象

本次追问针对的文章路径 / 章节 / 内容范围，如果是片段或粘贴内容，说明具体位置。

### 1. 概念清单与理解结论

逐个概念给出：概念名 → 用户讲清楚的那版定义（即使口语化也要保留原表达，不要替换成标准化术语）。

### 2. 问答要点

每个概念下按问题组织，保留追问的问题本身，标注是小白角度还是面试官角度：

- 问题 → 用户回答的要点 → 需要补正或补全的技术细节（例如用户说法不够严谨的地方，说明准确表述应该是什么）

### 3. 理解偏差与纠正记录

记录追问过程中出现的偏差、混淆、以及被提示后纠正过来的地方。写明**偏差在哪、正确的分界线在哪**。这部分是下游 agent 判断"文章哪里的表述容易让人误解"的直接依据。

### 4. 可复用素材（保留用户语气）

整理追问过程中用户的**原话、类比、以及由此产生的反思段落草稿**，用于让下游 agent 改写文章时保住作者本人风格，而不是 AI 的标准化表达。

反思段落用自然段落风格，像作者自己在思考：

```markdown
我一开始容易把 A 和 B 混在一起。后来发现真正的分界线不是……而是……
```

```markdown
这里有个容易踩的坑：很多人以为 X 就是 Y，但其实……
```

### 5. 待完善点

针对用户答不上来、答得含糊、或与文章现有表述不一致的地方，列出建议下游 agent 处理的方向（补写、重构、加边界说明等），一条一条写清楚，不要直接替文章写正文。

**输出完成后，询问用户是否需要调整总结的详略或补充遗漏点。结论以对话形式交付，是否把总结交给下游 skill、以及最终怎么写进文章，由用户决定。**

## 设计哲学

这个 skill 的存在是为了解决一个具体问题：**当 AI agent 帮你写完 blog 后，你对内容没有印象，文章也丧失了你的个人风格。**

费曼学习法的核心不是"教别人"，而是**在尝试教的过程中发现自己不懂的地方**。这个 skill 通过追问逼迫你"讲出来"，达成两个目标：

1. **内化知识**：你必须用自己的话解释，逼你的大脑真正处理这些信息
2. **暴露缺口**：你讲不清楚的地方，往往就是文章写得含糊、或你自己没吃透的地方

因此这个 skill 的价值不在结尾的那份文档，而在过程中**每一次被评估、被逼着补漏的时刻**：答得含糊就打回去重讲，讲不出来的地方当场标出来，逼你自己去查。

**为什么评估优先于总结**：总结是一次性的，读完就放下；而评估发生在你刚答完的那个瞬间，此时的纠正才真正改变你的理解。总结可以事后补，理解上的坑当场不填，之后很难自己发现。

**为什么不直接写入文章**：不同文章的体裁、风格、章节结构差异很大，由追问环节直接落笔很容易破坏原文组织。把"理解"和"落笔"分开，追问专注在逼你讲清楚，写作交给更懂文章规范的 skill。

## 与其他 skill 的关系

这个 skill 是**完全独立的**，不依赖也不自动串联其他 skill：

- `swe-tech-blog`：负责维护和撰写技术博客，决定内容如何组织、写到什么深度。当你**主动要了问答总结**时，它才是总结的下游——总结里的概念理解、理解偏差、可复用素材、待完善点，交给它去完善文章。

典型组合用法：

- AI 帮你写完一篇 → `@feynman-read` 追问消化、当场补漏；需要落笔时再要一份总结交给 `swe-tech-blog`
- 过几天想回顾 → `@feynman-read` 再追问一遍，看看还记得多少

## 行为边界

- `MUST` 一次只问一个问题，等用户回答后再继续
- `MUST` 先从小白角度追问，用户能答出来再升级到面试官角度
- `MUST` 每轮回答后先给具体评估，再推进下一步追问
- `MUST` 每次评估后紧跟一个查漏补缺动作，不能只提问不推动
- `MUST` 评估时说清对在哪、缺的是哪一层、依据是什么，对事不对人
- `MUST` 答不上来时先给提示，最后一次才给答案，并要求用户复述
- `MUST` 追问结束后默认只给「待补漏清单」，不产出总结
- `MUST` 只在用户明确要求时才产出问答总结，且只在对话中交付
- `MUST` 产出总结时保留用户的原话、语气和类比
- `MUST NOT` 逐节追问整篇文章，只抓 3-5 个最核心的概念
- `MUST NOT` 修改、写回任何文章文件
- `MUST NOT` 用「这个理解不错／不太对」这类笼统评价——要么指出缺哪一层，要么给出判断依据
- `MUST NOT` 把评估变成打分、评级或考试式判分
- `MUST NOT` 在用户未明确要求时主动产出总结，或追问用户「要不要我整理成总结」
