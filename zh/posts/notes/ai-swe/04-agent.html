Agent 智能体

vexillium2026/9/7大约 44 分钟后端开发人工智能

这一章把 Agent 当作一套需要自己搭建的运行时系统来分析，而不是某个现成框架的说明书。模型从"单次问答"变成 Agent，核心变化不在模型本身，而在它外面多出的那个循环：模型只负责每一步做出"下一步做什么"的决策，代码负责把决策变成真实的工具调用、把结果喂回去、判断该不该停。这个结构性变化会引出本章的主题——规划以什么模式展开、任务怎么拆、跨步骤与跨会话的状态（记忆）怎么存取、要不要让多个决策者协作、人在回路放在哪个节点、上下文窗口如何在循环中被反复组装、以及这套系统独有的失败方式。面试里关于 Agent 的高频问题，就地融入对应小节回答，不单独堆"面试题"章节。

Agent 的本质：从"生成答案"到"闭环执行"

Agent 是一个在"感知→规划→执行→反馈"闭环中反复调用模型、直到达成目标的系统，而不是"更聪明的单次回答"。单次问答只有生成；Agent 把生成嵌进循环：模型每次出场都基于当前状态决定下一步（规划），系统把这个决定翻译成真实动作——调用工具、读写文件、请求外部服务（执行）——再把动作结果（反馈）作为新感知注入上下文，进入下一轮决策。一个最小运行时的骨架：

while 未完成 and 步数未超限:
    决策 = llm(上下文)                    # 模型输出：终答，或"要调用某工具"
    if 决策是终答: return 决策.text
    结果 = tools.execute(决策.tool_call)  # 真实工具由代码执行，模型不直接碰环境
    上下文.append(工具结果)                # 观察注入，回到循环顶

这个骨架里的分工是整章的地基：模型只出"意图"，执行、校验、终止、恢复都由循环控制层负责。由此得到一条必须分清主次的工程判断——Agent 的能力上限由模型决定，但它的可靠性与安全性几乎全部由运行时决定：模型会选错工具、编造参数、原地绕圈，能不能拦住，取决于运行时有没有参数校验、步数上限与审计，而不是模型有多强。

四个构成组件各管一件事：

  • 决策内核（LLM）：产出"下一步动作"的结构化意图，不直接接触真实环境。
  • 行动接口（工具）：把意图翻译成真实副作用；权限、沙箱、幂等都锚在这一层，模型绕不过去。
  • 状态（记忆）：保存跨步骤、跨会话对任务与用户有用的信息，是闭环能否跨过单次会话的持久层。
  • 循环控制（运行时）：驱动循环、判定终止、检测卡死、维护轨迹——"感知→规划→执行→反馈"闭环真正存在的地方。

感知也不只是"用户的原始问题"。对 Agent 而言，感知 = 任务目标 + 当前轨迹 + 每一步工具返回的真实观察 +（需要时）人工修正或外部事件。闭环里的"反馈"因此分三层：工具结果（即时反馈）、人工修正（人在回路）、评测与复盘信号（离线反馈）。

决策者与控制流：Chain、Workflow 与 Agent 的真实边界

"什么算 Agent"常被名词之争带偏。与其从定义出发，不如看一个更本质的坐标：一次调用序列里，"下一步走哪条路"由谁决定、运行前能否被枚举。按这个坐标，三种形态是同一谱系上的不同位置：

形态决策者路径可否预先枚举可靠性与成本特征
Chain开发者写死，固定线性完全可枚举，无分支最可复现，最省
Workflow开发者写死分支/循环规则可枚举但非单线同输入同路径，可靠
Agent模型在运行时动态决策不可预先枚举有不确定性，成本最高
  • Chain 是一条写死的线性管线：Prompt → 解析 → 再 Prompt。适合步骤与顺序永不变化、中途无需判断的处理。
  • Workflow 的控制流写在代码里：有分支、重试、循环，但每个决策点往哪走由规则预先定义。RAG 管道、审批流、批处理都属于这一类。"Workflow 化"不等于"不智能"，它只是在决策确定处把控制权拿回代码，换来可复现与可测试。
  • Agent 在决策点上让模型说话：调哪个工具、要不要终止、是否换策略，都由模型根据上下文实时决定，运行前无法穷举所有轨迹。

判定边界一句话：控制流是否受模型影响。 模型只能影响单个节点的输出、不能改变后续走向的是 Workflow；模型能决定"下一步做什么"的才是 Agent。这条判据也解释了为什么同一系统可以在不同粒度上同时是两者——外层固定骨架、内层让模型决策的混合形态非常常见，往往是工程上最划算的形态。

实践取向：能用 Workflow 表达清楚的需求不要上 Agent。Agent 为系统的不可预测性付费——每个决策都是模型调用（成本），决策会出错（需要评测、重试与守卫），轨迹不可复现（排查更困难）。判断标准是决策空间是否开放：搜索调研、调试排障、需求不明确的改动这类开放式任务交给 Agent；ETL、审批流转、固定问答这类流程确定的任务写死成 Workflow。大量号称 Agent 的系统，收敛后其实是"骨架固定的 Workflow + 局部模型决策"，这不可耻，反而是工程收敛的正常形态。面试被问 "Workflow 和 Agent 的区别"，按"控制流由谁决定、路径是否可枚举"作答，再补一句"同一系统可以外层 Workflow 内层 Agent"，比背定义更有区分度。

规划模式：Agent 的"想"与"做"怎么组织

提示层面的范式（想一步做一步、先规划后执行）解决的是"决策如何组织"；到了运行时，要回答的是另一组工程问题：循环由什么信号驱动、每一步怎么调度模型与工具、如何判定终止与卡死、运行状态放在哪。先讲清楚运行时机制，再看各范式的差异落在哪里。

循环的驱动、调度与状态维护

Agent 循环以"模型输出是否携带工具调用意图"作为驱动信号。 每轮调用模型：若输出的是终答（不再要求调工具），循环结束；若输出工具调用，则经过参数校验后执行工具，把结构化结果作为 observation 追加进上下文，回到循环顶。终止判定因此是"模型信号 + 运行时兜底"的双保险——模型说"完成了"时，运行时要在 finish 前校验产物确实存在；模型一直不输出终答时，运行时用步数上限兜底。ReAct 就是"不预写计划、边走边决策"这类循环的原型，它成立的假设是每步动作高度依赖上一步的观察；它在运行时最脆弱的两个点，一是缺循环守卫会原地绕圈，二是模型会"脑补"观察结果。

运行状态要分两处存放：轨迹是一串带角色的消息（system / user / assistant / tool），其中 tool 消息承载真实观察、只能由运行时写入，绝不能允许模型自己生成"工具结果"；任务对象则保存不适合进上下文或模型不需要看的运行态——当前计划、已用步数、剩余预算、已完成子目标。这条切分的意义是：让模型做决策所需的信息进上下文，让系统做控制所需的信息留在运行时对象里。二者混在一起，循环就会既不可控也无法中断恢复。

Plan-and-Execute 在运行时的形态与 ReAct 不同：规划器先产出结构化步骤列表（每步可对应一个工具调用或一个子任务），执行器持有"计划 + 当前指针"按序推进，每步结束更新该步状态（完成/失败），步骤之间不允许自由发挥；计划与现实脱节时触发重规划——替换局部步骤或整段重排——而不是抱着旧计划执行到底。因此它把运行时的主要风险从"绕圈"转移到"计划质量"上：规划步骤写得不可执行，执行器只是把错误执行得更彻底。

Reflexion：把"这次失败"变成"下次的经验"

ReAct 的反馈来自外部观察，Reflexion（反思）补充的是内部反馈：在一条尝试（episode）结束后，让模型复盘"错在哪、根因是什么、下次该怎么做"，并把结论写下来供下一条尝试开始时加载。它把"单轮试错"扩展成"试错 → 复盘 → 带着教训再试"的跨轮循环，适合代码生成、搜索求解这类能试错、单次失败代价可控的任务。

实现上通常拆三块：Actor（干活的决策者）、Evaluator（判定这次结果好坏的评估器）、Self-Reflection（把失败原因与改进策略写成文本并存入记忆）。其中 Evaluator 的质量决定整套机制的上限——评估信号越客观越好：代码看测试是否通过、搜索看是否找到目标，这些可验证信号比"让模型给自己打分"可靠得多。如果评估只靠模型自评且没有外部反馈，反思很容易退化成自我合理化——模型写一堆"我太粗心了，下次要仔细"的空话，对下一次尝试毫无帮助。有效的反思要落到可执行的下一次策略上（"这个 API 需要先查文档确认参数名，再写调用代码"），而不是情绪化的检讨。

Reflexion 与同类的关键区别要分清：它改进的粒度是"跨尝试"，靠的是把反思写进外部记忆、下一条尝试开始时注入；这与"单次生成后立刻自我批评再改写"的做法不同——后者不跨轮，也没有持久化。代价上，Reflexion 把一条尝试的成本乘以 N（尝试轮数 + 每轮反思调用），只适合"答案有客观对错、试错成本可控"的任务；一次生成就要求正确的场景（如面向用户的低延迟交互）不该硬套。

LLM Compiler：把任务"编译"成可并行执行的图

LLM Compiler（源自 2024 年同名论文）把编译器思想搬进 Agent 运行时：规划器像编译器一样，先把用户请求"编译"成一张任务依赖图（DAG）——识别哪些工具调用相互独立、哪些必须等前置结果，而不是生成一串按顺序执行的步骤；执行器再像 CPU 一样调度这张图：独立的调用并行执行、有依赖的按序等待，并支持工具返回错误时对局部计划做重规划。

它针对的是 ReAct 串行循环的两个实际痛点：一是工具调用彼此等待，串行执行让延迟随调用数线性累加，而很多查询（查用户信息、查订单、查库存）明明互不依赖；二是每一步都要把完整轨迹喂回模型重新决策，token 消耗随轮数膨胀。编译成 DAG 后，规划只做一次，执行阶段按图并行推进、流式地把已完成的调用结果喂给后续步骤，不必每步都走一遍"全量上下文 + 模型决策"。

代价与边界同样明显：依赖分析正确性完全压在规划器身上——它误判两个调用相互独立并并行执行，结果就错了；真实世界副作用（写库、发消息）之间往往存在隐式依赖，编译器看不出来，所以并行化主要适用于只读/可并发的调用，带副作用的动作仍要串行并谨慎。它是对"执行效率"的优化，不是对"任务质量"的兜底，任务本身难、需要多轮探索时，ReAct/Reflexion 式循环比编译优化更对症。

规划模式的选择主线

把几种范式放在一起看，选择主线其实是三个变量：任务的不确定性、步骤之间的依赖形态、以及失败后能不能重来。任务开放、每步依赖上一步观察 → ReAct 式循环；步骤清晰、怕中途跑偏 → Plan-and-Execute；答案可验证、允许试错 → Reflexion 补上复盘；工具调用多且多为只读、想省延迟与 token → LLM Compiler 式并行调度。没有哪个范式"更高级"，它们优化的对象不同：有的省上下文、有的抗漂移、有的省延迟，选型要对着自己任务的成本瓶颈来。

任务拆解与子目标管理：把"一步到位"改成"步步逼近"

为什么必须拆

模型在单次决策里能同时盯住的约束是有限的：上下文里的步骤越多、信息越杂，每一步"想清楚再动"的质量就越差——目标漂移、漏步骤、中途忘了原始需求，大多不是模型笨，而是让一次决策背了太多它背不动的东西。拆解的实质是把"一个大的、开放的软约束问题"转成"一组小的、各自可验证的子问题"，让系统用多次低成本决策逼近一个单次高成本决策难以企及的结果。工程上拆解还有两个副产品收益：每个子任务的产物可被单独校验（错误能定位到子任务而不是整锅端）；相互独立的子任务可以并行执行、缩短总时长。

怎么拆、拆到什么粒度

  • 自上而下递归拆：目标 → 子目标 → 动作，直到每个叶子节点能对应一个具体工具调用或一次可完成的生成。递归拆到多深，以"子任务产出可被独立验证"为准——拆到"步骤无法被验证"或"再拆反而增加协调开销"就停。
  • 按依赖关系拆成结构而非清单：产物最好是一份结构化任务表（JSON：任务 ID、父任务、依赖、状态、产出），而不是散文式步骤。散文对模型友好，但对系统不可执行——子任务的状态、依赖、完成与否都要能机读，运行时才能调度、重试与续跑。
  • 按工具/数据边界拆：不同子任务需要的工具集、权限、知识上下文不同，这是天然的拆解边界。
  • 拆错的信号：拆出的子任务之间频繁共享临时结果、顺序根本无法预先确定、或两个子任务必须"挤在同一上下文里看同一份大材料"，都说明这个拆法制造了多余的协调成本，应该合并或改成执行中动态再决策。

子目标管理在运行时体现为一张任务状态机：pending / running / done / failed / blocked，配合依赖关系由运行时推进而不是由模型口头管理。每个子任务完成时把结果写回（结构化摘要进父任务上下文），父任务据此决定继续、跳过还是重规划——这是"系统控制 + 模型决策"分工在任务层的又一次体现。

双循环：任务循环与执行循环

生产级 Agent 普遍把上述逻辑实现为嵌套的双循环：外循环（任务级） 持有目标与全局状态，负责拆解、派发、收敛判定——子任务失败时决定重试、换策略还是降级，持有总预算；内循环（执行级） 对单个子任务做"决策→动作→观察"的快速循环，直到该子任务完成或放弃。这样设计的原因是两层失败的代价不同：内循环高频、失败廉价，要快失败、即时换招；外循环低频、持全局视图，负责不跑偏。内循环失败只影响一个子任务，外循环决定要不要换一条路甚至放弃整个任务——如果只有一个平铺的循环，一次局部失败会直接毁掉整条轨迹。

死循环检测与步数控制

模型驱动的循环天然会"绕圈"，守卫必须由运行时做、不能指望模型自觉。常用手段按检测对象分几类：

  • 步数与轮次上限：单条执行设 max_turns（常见几十步内），是最后兜底。到顶时不是硬失败——把"已用尽步数、请重新规划或换策略"作为反馈喂回，让它收敛或显式求助。
  • 成本与时间预算：单任务的 token/费用/墙钟时间上限。步数上限防"死循环"，成本预算防"活循环但贵到失控"——模型可能每步都在推进但绕了极大弯路，步数没超、预算先爆。
  • 重复动作检测：对动作做归一化签名（工具名 + 关键参数哈希），同一签名短时间内重复出现 N 次 → 判定震荡。注意区分"合法重复"（如轮询等待外部任务完成）与"无效重复"，轮询类动作要显式声明并允许。
  • 无进展检测：相邻若干轮观察内容高度相似、或每轮都在追加但没有任何新信息进入上下文 → 判定空转。
  • 震荡检测：在两个或几个动作之间来回切换、没有单向推进（A→B→A→B），往往意味着决策在"两瓶毒药"间徘徊，此时提示换策略比重试更有用。

守卫触发后的处理要分级：先提示模型换策略（低成本）；仍无效则触发重规划或回退到最近一个已知良好状态；再不行降级到人工或返回已获得的部分结果。关键是把"停止"设计成有产出的降级路径，而不是无声地切断——用户宁可拿到"我试了 X 步没走通，目前确认了 A 和 B，卡在 C"这样的部分结论，也不要一段被截断的空转日志。

记忆系统：Agent 的跨会话状态

这一节谈的记忆不是企业知识库问答——那是检索侧的职责。这里关心的是 Agent 自身怎么记住"对当前用户、当前任务有用的东西"，并让它在跨步骤、跨会话后被正确地想起：记什么、什么时候写、什么时候召回、怎么防止记错与记旧。核心矛盾一句话就能说清：上下文窗口是 Agent 的"工作台"，只放得下正在用的东西；工作台放不下的、未来还要用的，必须搬到记忆里去，用的时候再搬回来。

四类记忆的划分

按"生命周期 + 内容形态"，Agent 记忆工程上习惯分成四类：

记忆类型内容与载体生命周期典型例子
工作记忆当前任务进行中的执行状态（计划、待办、中间结果），在上下文/运行态中任务结束即清空正在执行的子任务清单、刚拿到的查询结果
短期记忆本次会话的对话历史与轨迹，消息列表随会话/窗口结束而失效多轮对话上下文、ReAct 轨迹
长期记忆（语义）关于用户的稳定事实与偏好，结构化库 + 向量库跨会话持久用户时区、术语偏好、项目约束、历史决策
情景记忆过去完整任务的经历与成败经验，结构化/文本库跨会话持久上次部署失败的原因、某类问题的标准解法

几个易混点要分清：工作记忆和短期记忆不是一回事——短期记忆是"原始发生过的对话"，工作记忆是"为完成当前任务而筛选出的可操作子集"（执行计划、关键约束、下一步待办）。会话越长，短期记忆越臃肿，而工作记忆应该始终精炼——这个差距正是靠持续的压缩与整理来弥合。情景记忆与语义记忆的差别在于是"一次经历"还是"一般规律"：Reflexion 的反思库就是典型的情景记忆，它记录的是"某一次任务里什么导致了失败"；当多条经历归纳出稳定偏好（"这个用户写代码偏好 Rust"）后，才值得沉淀成语义记忆。向量化适合语义记忆的相似召回；情景记忆更需要结构化字段（任务类型、结果、教训）支持按"同类任务"检索。

写入策略：宁缺毋滥

记忆写入的第一原则是克制——只有"跨会话仍有用"的信息才值得写。逐字记下对话、把工具输出全量入库、把一次性中间过程写成"长期事实"，都会让记忆库变成噪声池：召回时信噪比下降，注入上下文的内容不相关，反而污染每次决策。工程上可执行的判断标准：

  • 按信息类型分流。用户主动声明的偏好与事实（"我部署用 k8s"）、项目级约束、跨任务复用的流程经验——这些值得写；一次性的查询结果、情绪化表达、可重新检索到的公开信息——不写。
  • 写提炼，不写原文。落库前先让模型（或规则）把"这段对话里值得长期记住的要点"提炼成简短条目，而不是存对话本身。原文可留档用于审计，但记忆库只放提炼结果。
  • 带上元数据再落库。至少包含：类型、内容、来源会话/时间戳、置信度（用户明确说的 > 模型推断的）、有效期或"可能过期"标记。没有时间戳的记忆是事故的源头——后面冲突处理会用到。
  • 写入时机放在自然边界：会话结束、关键决策落定、任务里程碑处异步写入，而不是每轮对话都写；写入失败不能阻塞主流程。
  • 写前查重与冲突检测：新条目与库内既有条目语义相近时，先合并或标记，避免同一事实的多版本副本各自演化。

召回策略：该想起的时候才想起

写入克制解决"库太脏"，召回克制解决"上下文被无关记忆占用"。召回要回答三个问题：

  • 什么时候召回：两种时机——会话开始主动加载"核心事实"（用户画像、关键偏好、项目约束，注入 system 区域，量要小）；执行中途按需检索（当前任务涉及某个话题时，才把相关记忆向量召回到上下文）。
  • 召回到什么程度：宁少勿多，TopK 控制在几条且必须与当前任务相关。记忆注入是帮助决策，不是展示库存——塞 20 条"可能相关"的记忆和塞 20 条无关检索片段一样有害。
  • 召回后怎么用：每条召回内容带上来源与时间，供模型判断可信度与时效；对时效敏感的记忆（"用户上次说 X"）在注入时显式标注时间，避免模型把旧状态当现状。

陈旧、冲突与反例

记忆系统最隐蔽的故障是"记得但记错/记旧"，比"没记住"更难排查：

  • 无时间戳导致的陈旧：用户三个月前说"用 Java"，最近已切到 Go；系统若无时间与来源，仍拿旧偏好作答。对策是元数据里的时间与"确认状态"，会话开始时若检测到新旧矛盾，主动询问而不是静默选一个。
  • 冲突处理的优先级：明确的新指令 > 旧的长期事实 > 模型推断。永远不要静默覆盖——旧条目被推翻时，要么标记失效保留历史（可审计），要么在本次会话里显式向用户确认，而不是直接删除改写。
  • 多租户串记忆：同一套 Agent 服务多个用户/项目时，记忆必须按租户隔离，召回时带上归属过滤——这条与检索端的权限过滤是同一个道理，漏了就会把 A 用户的偏好答给 B。
  • 把"写得好"当"用得好"：记忆系统的验收标准不是库里有多少条，而是召回到的内容对决策正确率的提升——要像检索端一样建评测：构造"需要记忆才能答对"的任务集，对比开启/关闭记忆召回的端到端正确率，而不是数条目、看覆盖率。

Multi-Agent 协作：先回答"为什么要拆"

单 Agent 的天花板在哪

多 Agent 不是为了让系统看起来更聪明，而是单 Agent 存在几个结构性限制：一个上下文窗口装不下所有需要的知识与工具（塞进去要么超窗要么互相干扰）；一个决策者只能有一个目标与一种立场，角色切换会稀释约束；任务串行执行，无法利用并行；以及没有隔离——读取不可信内容与执行高影响动作共享同一上下文与工具集，安全上互相拖累。拆成多个 Agent，本质是用"上下文隔离 + 专业分工 + 并行"换这些限制的解除。判断要不要拆，先看单 Agent 到底被哪个限制卡住——卡住的是上面哪一条，才谈得上用哪种拆法去解。

五种协作范式

范式协作方式通信开销与主要风险适合场景
Orchestrator-Worker中心分解派发，worker 独立执行并返回结果，彼此不通信开销在拆解与汇总；中心是瓶颈与单点子任务相互独立的批处理式任务
Supervisor监督者动态决定由哪个专家 Agent 接手，循环直到完成每轮都要经监督者，会话越长越贵多个专长需要按序/按需接入的会话型任务
Group Chat多个 Agent 在共享频道平等发言、互相响应最高；token 随发言轮数膨胀，易发散不收敛头脑风暴、辩论、互相评审
Swarm / Handoff当前 Agent 把控制权与必要上下文转交给下一个，同一时刻只有一个活跃中；上下文随转移，易丢失责任边界客服转接、职责链式接力
Pipeline前一个 Agent 的输出作为后一个的输入，单向流动低但延迟累加；前段错误顺流放大阶段边界清晰、无需回退的流水线
  • Orchestrator-Worker：主 Agent 负责拆解与汇总，worker 各自拿一份自包含的子任务和所需上下文，完成后把结构化结果交回。通信是"请求-响应"式的，worker 之间没有对话——这让它开销可控、容易并行，也最容易做失败隔离。代价是拆解质量决定一切，worker 需要的信息如果没给全，它只能瞎猜。
  • Supervisor：监督者更像"对话主持人"，它不预先拆好全部任务，而是在会话中判断"现在该谁上"——把当前问题派给最合适的专家，听专家结果，再决定继续追问、换人还是收尾。与 Orchestrator 的差异在决策时机：Orchestrator 一次拆完再派，Supervisor 边走边派。它适合任务无法预先完全拆解的会话型场景，代价是每轮路由都要经过监督者，token 与延迟随轮数上涨。两者也可以嵌套：Supervisor 之下再挂一组 worker。
  • Group Chat：多个 Agent 在公共上下文里自由发言。收敛只能靠约定（指定主持人、限制发言轮数、设停止条件），否则会发散成无意义的互相客套。它最贵的不是"质量"，而是每轮发言所有 Agent 都要消费全部聊天记录——上下文按发言数二次方增长，这是它被滥用后最常见的成本事故。
  • Swarm / Handoff：一次只有一个 Agent 对用户负责，当前 Agent 判断"这事该转给谁"时，把控制权连同必要的会话摘要一起移交（handoff）。这与 Orchestrator 的区别是：没有始终存在的中央——每个 Agent 都可能成为"下一个中转站"，像接力跑。适合客服分流、意图逐步收敛的职责链；风险是转手时信息丢失，以及责任链无限延伸（A 转 B、B 转 A），需要移交深度上限。
  • Pipeline：本质上就是"每个节点是 Agent 的 Workflow"——步骤与顺序固定，前段输出喂后段。可靠、可测，但延迟累加、错误单向放大（后段无法回头修正前段错误），适合流水线本身就被业务定义清楚的场景（如文档 → 抽取 → 审核 → 生成报告）。

什么时候拆、拆多细：边界判断

拆分的收益来自隔离（上下文、工具、权限、失败域）与专业化（每个 Agent 的 system prompt 只需强调一件事，约束不被稀释）；拆分的代价是协调——每次跨 Agent 传递都要序列化上下文、花模型调用、引入"传话失真"。边界判断要落在两者的平衡上：

  • 拆的信号：需要的知识与工具集差异大且互不重叠；不同环节权限等级不同（读网页的 Agent 和发邮件的 Agent 必须隔离）；任务可并行；单一上下文已经因为塞了多角色约束而互相打架。
  • 不拆的信号：子 Agent 之间需要高频共享大量中间状态——这说明"隔离"没带来好处，反而制造了传话成本，合成一个 Agent（或共享一个工作存储）更优。共享越频繁越不该拆，这条可以直接当成反例判据。
  • 拆多细：拆到"每个 Agent 有清晰单一职责、自包含的上下文与工具集、产出可独立验证"为止。一个常见错误是把拆解当组织架构树来设计——三层 supervisor、八个专家，多数情况下两三个角色加一个协调者就够；每个拆出来的 Agent 都要额外花钱、额外引入一层出错可能，它不是免费的模块化。
  • 通信成本的估算口径：一次跨 Agent 交接 ≈ 一次"产出摘要 + 目标 Agent 重新消化"的模型调用，外加上下文里滞留的交接痕迹。所以交接时要传结论与必要上下文，不要传完整轨迹——这一点和记忆召回的原则一致：宁少勿多、传结构化摘要。
  • 认知上要破除的误区："多 Agent 更聪明"不成立——多数任务单 Agent + 工具更快更省更稳；多 Agent 只有在隔离与专长确实被需要时才划算，而且它的收益要用评测数据证明（同样的任务集，单 vs 多对比成功率与成本），不是架构上的自我感动。

Human-in-the-Loop：把人的判断放在关键节点

Agent 的自主度是产品决策，不是技术指标

一个 Agent 能全自动到什么程度，不是由模型能力决定的，而是由动作的风险与可逆性决定的：删库、转账、发公开邮件这类不可逆或高影响动作，即便模型有 99% 的把握做对，剩下的 1% 也足以让全自动上线成为事故。Human-in-the-Loop（人在回路）就是把人的判断插入 Agent 执行链的特定节点，用"人的成本"换"错误代价的兜底"。它的设计目标是让系统在安全与效率之间取到最优——人的介入点越少、越关键越好，而不是让 Agent 每步都请示。

审批节点（Approval Gate）挂在哪里、审什么

审批节点挂在动作执行之前：对工具调用层做拦截，凡是命中"需要审批"策略的工具，先暂停、把"动作 + 参数 + Agent 的理由 + 预估影响"打包给人确认，通过才放行，拒绝则把拒绝原因喂回模型让它换方案。设计要点：

  • 按动作分级，而不是一刀切。只读查询默认放行；写操作（改文件、写库）按策略允许或提示；不可逆/高影响动作（删除、对外发送、支付）默认拒绝，必须显式授权。分级表要配置化，能按租户、按用户调整。
  • 审批单要给人足够信息：人批准的不是"Agent 想干什么"，而是"它即将对真实系统做什么"——展示将要执行的命令/请求原文，而不是模型对动作的自然语言转述。否则人批的是模型的"解释"，不是实际的动作。
  • 审批超时的默认策略：拒绝比放行安全。审批请求挂起超时（如几分钟）应自动按拒绝处理并告知 Agent，而不是无限等待——无限等待会把"安全"变成"服务不可用"。

中断与恢复（interrupt / resume）

人介入必然打断 Agent 的执行，因此运行时必须支持在任意决策点暂停、把完整运行状态持久化、之后从暂停点继续的能力。可恢复的状态至少包括：完整消息轨迹、当前执行位置（在哪个步骤/哪条子任务上）、计数器（已用步数、预算消耗）、尚未执行的计划。实现上这要求状态全部走"可序列化"路径，而不是散落在进程内存或闭包里——这是把运行状态与决策上下文分开存放的实际回报：轨迹进存储，控制状态进持久化对象，暂停时一起落盘，恢复时原样装回。两个工程细节：恢复后要给模型明确提示"你之前执行到哪、刚被人为中断/修改了什么"，否则它会在不知情的情况下重复已做过的动作；大块工具结果落盘时考虑只存引用或摘要，避免把整个会话撑爆。

置信度触发人工介入

不是每个节点都值得挂人，更常见的做法是让系统自己判断"什么时候该叫人"。触发信号分几类：

  • 模型自评低置信：让模型在关键决策点输出置信度或"是否需要人工确认"标记，低于阈值转人工。
  • 校验失败：结构化输出解析失败重试仍失败、grounding 校验不通过、工具执行返回异常——这些是确定性信号，说明系统已经尽力但卡住，转人工。
  • 策略命中：动作属于高影响类别、涉及新用户/新域没有历史依据、轨迹出现异常模式（步数异常多、反复修改同一资源）。
  • Agent 主动求助：显式给模型一个"我搞不定，请人帮忙"的出口，比让它硬编一个答案强——这是对多种失败模式兜底的低成本设计。

关键认知：置信度触发是概率兜底，不是安全边界。模型自评的"低置信"并不可靠（它可能信心满满地错），所以高影响动作的安全不能押在"模型会主动求助"上，必须叠加审批门禁那类确定性拦截。

反馈回流：人的纠偏怎么变成系统的改进

人在回路的每次介入都是一条标注数据，浪费掉最可惜。回流有三条路径，粒度不同：

  • 本轮修正：人拒绝了某动作/修改了结果，把"为什么"作为反馈注入当前执行，让 Agent 换方案继续——这是即时路径，只影响当前任务。
  • 经验沉淀：把人的纠偏归纳成规则或记忆——"这个用户的所有对外发送都要先给人看""这类请求不要用 A 工具"，写入策略配置或长期记忆，让后续会话直接受益。注意区分"一次性的纠正"与"稳定偏好"，别把偶然纠正当成永久规则。
  • 评测回流：把人工介入点（尤其是模型犯错被拦下的案例）打标进评测集，成为后续回归与模型/提示词迭代的素材——这是把 HITL 从"安全机制"升级为"质量引擎"的关键一步。

反例：把 HITL 做成"人工执行"

最常见的设计失败是介入过频：每个子任务都要人点头，Agent 退化成"替人打字"，人的工作量没比全人工少，还多付了模型钱。判断介入点是否合理，看"人每次介入是否都发生在高杠杆处"——错误代价大、需要业务判断、超出系统能力的点值得介入；纯执行性步骤（查个文档、调个格式化工具）就该放行。另一个反例是介入但不给上下文：把模型原始输出甩给人，人看不懂前因后果只能瞎点通过——审批单、中断恢复提示都要为"人"而不是为"系统"设计。最后，反馈回流如果只做到第 1 条（本轮修正）而丢弃后两条，那么同样的错会在不同会话里反复让不同的人拦——HITL 的长期价值恰恰在第 2、3 条。

上下文工程：Agent 如何组装自己的窗口

Agent 上下文与单次问答上下文的差别

单次问答的上下文是一次拼好、用完即弃；Agent 的上下文则在循环中被反复重建——每执行一步工具，下一轮的输入就多一段真实观察，轨迹无限增长而窗口固定。这带来一个单次问答没有的约束：Agent 每轮都要决定"窗口里留什么、丢什么"，这个决定本身的质量直接决定后续决策质量。Context Engineering（上下文工程）处理的就是这个问题——把窗口当一块需要主动经营的预算来分配，而不是被动等它被轨迹撑爆。

窗口预算怎么分

一次 Agent 请求的窗口可以拆成几个构成块，按优先级从高到低分配：

  • 系统行为层：角色、任务规约、通用规则、安全边界。它是最重要的稳定前缀，量要克制——塞越多的"原则"，每一条被遵守的概率越低，规则之间还会打架。
  • 记忆层：会话开始时加载的核心事实（用户偏好、项目约束），只放本次任务真正相关的少量条目。
  • 工具定义层：本次循环可能用到的工具 schema 与使用说明。工具一多，这层最容易反客为主，成为窗口占用与不稳定性的主要来源。
  • 任务层：当前任务/子任务的说明、结构化计划、待办。它随任务推进而更新，是模型判断"我在哪、下一步该干什么"的锚点。
  • 轨迹层：历史决策与工具观察。它是滚动最剧烈的一层，也是压缩与裁剪的主要对象。

组装：静态稳定，动态靠后

组装原则承接一个基本事实：模型对序列开头与结尾的注意力系统性高于中间，且开头的内容充当"全局锚点"。所以稳定不变的构成块（系统行为、工具定义）放最前且顺序恒定，任务层紧随其后，最新最相关的轨迹放最后靠近当前决策点。顺序恒定还带来一个外部收益：稳定前缀能命中服务端的 prompt 缓存，长前缀的成本与延迟被大幅摊薄；反过来，在稳定前缀中间插入一句动态内容，会让整段前缀缓存失效，比不缓存更贵。工具定义层因此陷入一个真实的两难：全量注入占用窗口且保证稳定（缓存友好），按需加载省窗口但改变前缀（缓存不友好）——量少（约 20 个以内）全量注入，量多再谈分组常驻 + 冷门懒加载的折中，而不是无脑二选一。

压缩：浓缩而不是丢弃

轨迹增长到窗口边界时，第一反应是压缩——把信息浓缩，而不是把信息丢掉。三类手段：

  • 摘要化：把早期对话/早期轨迹递归压成一段摘要（"已完成 X、确认了 Y、用户要求 Z"），替代原始消息进入上下文。摘要会丢细节，所以决策结论、用户明确要求、关键编号这类高价值信息要么在摘要里显式保留，要么转入记忆库可随时取回——摘要 + 原文双轨：上下文只放摘要，精确信息需要时按引用回原文取。
  • 结构化提取：把散在轨迹里的决策、结论、待办抽成结构化字段（当前任务清单、已确认约束），比散文摘要更容易被模型和系统双方使用。
  • 工具结果瘦身：工具返回常是上下文膨胀的最大头。长结果只保留关键行/摘要进上下文，全文落盘存引用；同类的连续观察（重复的日志、重复的查询结果）只留最新。

判断该压缩谁，规则是按信息对未来决策的价值而非按时间新旧——被后续步骤反复依赖的早期结论，价值高于刚发生但不会再被用到的细节。这个判断可以交给模型（让它在每轮或定期输出"什么值得长期保留"），但系统要有兜底预算，不能指望模型自觉维护。

裁剪：预算驱动的取舍

压缩做不动或来不及做时，用裁剪控制总量。常用策略：

  • 滑动窗口：只保留最近 N 轮消息，最古老的直接丢弃。实现最简单，是最后的兜底；代价是早期结论可能被一起丢掉，需要摘要层先兜住。
  • Token 预算 + 分块淘汰：给每类内容（系统/记忆/任务/各段轨迹）定预算上限，超预算时按"对当前任务的保留价值"淘汰低优先级块。比滑动窗口精细，但要维护每块的元数据（角色、价值分、时间）。
  • 按需取回替代常驻：被裁剪掉的精确内容不销毁，转存外部（记忆库、落盘），模型发现需要时通过检索工具取回——裁剪不是删除，是"挪出窗口"。

工程上的配套习惯：每轮记录上下文占用与构成（哪一层占了多少），接近上限提前预警而不是等报错；把"本次用了多少窗口、压缩触发了多少次"作为指标纳入观测，看 Agent 是否在同一个坑里反复绕（压缩触发频率高往往意味着轨迹效率差，该改的是上游决策而不是加大窗口）。

反例与边界

反例一：只裁不压——直接滑窗丢掉早期结论，模型到任务后半段"失忆"，重复做已确认过的事。压缩层是裁剪层的上游，先压再裁。反例二：压过头——把还在用的关键上下文（如用户刚给的约束）也摘要化，摘要里没留原文引用，模型只能凭模糊印象行事。压缩前要判断"这段是否仍被当前任务依赖"。反例三：把所有工具输出都留全文直到爆窗——把可避免的膨胀拖成不可避免的裁剪，是最常见的上下文卫生事故。边界认知：上下文工程解决"窗口不够用"，不解决"模型不会用长上下文"——材料再多，模型对长上下文中段信息的利用仍有天然衰减，所以设计上永远优先"把窗口留给最重要的内容"，而不是"想办法装下更多"。

Agent 失败模式清单：多步执行如何放大单点错误

Agent 故障比单次调用故障难排查，有一个共同的放大器：每一步的输出是下一步的输入，单点错误会沿着轨迹传播甚至放大。单次问答答错了，错的是那一个回答；Agent 一步选错工具，后续所有步骤都基于错误结果继续推导，最终错误可能面目全非。所以排查 Agent 问题时，第一反应不该是"改提示词"，而是先定位错误发生在哪一层、是否已被放大。下面是生产里最高频的失败模式、成因与对策，按"错在工具层 / 错在目标层 / 错在传播层"分组。

幻觉工具调用：模型对"动作"撒谎

现象：调用不存在的工具名；参数凭空编造（把不存在的文件路径、ID、字段值传进去）；把工具能做的和不能做的搞混；更隐蔽的是观察幻觉——模型没有真正执行动作，却在轨迹里"脑补"出一个结果继续推理，等于把一个编造的事实当成依据，比不调用还糟。

成因：工具 schema 太多导致选择混淆；description 写得含糊（"何时用、何时不用"没说清）；参数描述缺失让模型猜值；以及模型天然会"补全"缺失的中间环节。对策分四层：

  • 工具侧：工具数量克制、命名规范、description 写明适用与不适用场景；参数用 JSON Schema 加 enum、格式约束并逐字段描述——给模型看的 API 文档质量，直接决定它调用得多准。
  • 运行时侧（最关键）：调用前做工具名白名单校验、参数 Schema 校验与业务校验（路径必须存在于白名单目录、ID 必须存在）；保证只有真实执行结果能进入上下文——模型输出的文本里夹带的"伪结果"一律剥离，observation 只由运行时写入。这一条是把"模型幻觉"与"系统事实"隔离的底线，做不到它，其余对策都是加固而非根治。
  • 错误反馈闭环：调用失败/参数非法时，把结构化错误原因喂回上下文让模型自我修正，而不是静默吞掉。
  • 观察侧：工具返回的长结果截断后注入，防止模型被无关细节带偏；对工具结果与模型后续声称做一致性抽查。

目标漂移：走远了，忘了为什么出发

现象：任务执行到中段，模型开始做与原始目标渐行渐远的事——用户要"总结这份文档"，它越做越深变成了"重写这份文档"；多个约束在长轨迹中先后被遗忘，只记得最近的一个。成因：任务越长，原始目标在上下文里的信噪比越低——被大量中间过程稀释后，模型对"最终要交付什么"的把握逐步衰减，而每步的局部合理性会掩盖整体跑偏。

对策：把任务规约做成常驻且独立的元素——最终目标、完成定义（done 的标准）、不可违反的约束单独成块放在上下文前部（系统层/任务层），并定期在关键节点让模型对照检查"当前进展与最终目标是否一致"；Plan-and-Execute 式地把计划当锚点、执行中对照计划位置，是抗漂移的结构性手段；中途用户新增需求时，显式合并进任务规约而不是让它混在对话流里。衡量手段：在评测里加入"目标保持率"——跑完长任务后检查产物是否忠于原始需求，而不只看单步正确率。

错误级联：一步错，步步错

现象：早期某步的错误结论被后续步骤当成既成事实继续使用，且没有回头的机会——检索到错资料 → 基于错资料写方案 → 方案又被拿去生成代码，错误层层加深，最终产物与事实完全脱节。成因：轨迹是单向累积的，模型默认"前面发生的就是真的"，除非有机制逼它质疑。

对策：在关键中间产物处设校验点，而不是只校验最终结果——数值类结论过计算器/工具、事实类结论做 grounding 校验、代码类结论跑测试，任一不过就回退到该步重来；为高影响步骤保留"回滚到最近已知良好状态"的能力（依托持久化的状态快照）；降低步骤间的耦合——相互独立的信息各自验证，别让一个中间值决定全局走向；让模型学会"标注不确定"：对没有把握的中间结论显式标记，后续步骤看到标记会警惕，而不是默默吞下。错误级联的根治思路是把"一次长链推理"改造成"多段短链 + 每段可验证"——每段短链的错误可以被当段拦截，这正是结构化任务拆解在可靠性上的回报。

兜底性失败：成本失控与虚假完成

两个模式虽不在"幻觉/漂移/级联"之列，但生产事故率同样高：

  • 成本与步数失控：模型陷入长而无意义的循环（反复尝试同一失败动作、无限扩大搜索范围），单任务 token 消耗超出预算几个数量级。对策是步数、费用、时间三重预算必须存在，且预算触发时要落到有产出的降级路径而不是无声截断。
  • 虚假完成：模型声称"已完成"，但产物不存在、格式不对或没满足完成定义——它把"我觉得做完了"当成了"确实做完了"。对策是在 finish 前由系统执行产物存在性 + 完成定义校验（文件在不在、schema 过不过、测试跑不跑得通），校验不过就不允许以"成功"收尾。

排查思路：先归因，再动手

面对一次 Agent 失败，按"轨迹回放 → 分层归因 → 针对性修复"的顺序走，比凭感觉改 prompt 高效得多：先重放完整轨迹看错误发生在第几步（这要求系统从第一天就记录完整轨迹——谁调了什么工具、传了什么参数、返回了什么、模型下一步怎么决策的）；再判断错误属于工具层（选错/参数错 → 改 schema 与校验）、目标层（跑偏 → 改任务规约与锚点）还是传播层（级联 → 加中间校验点与回滚）；最后只改对应层。多步系统里，80% 的"模型不行"最终定位出来是某一段的输入或校验问题——这个排查纪律，比任何单一防御手段都更能决定 Agent 系统能走多远。
