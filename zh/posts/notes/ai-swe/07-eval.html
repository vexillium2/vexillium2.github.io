Agent 评估

vexillium2026/9/7大约 23 分钟后端开发人工智能

这一章把"评估"当作 Agent 研发里的一等工程来写。传统模型评估解决"这个模型行不行"，Agent 评估要回答的问题复杂得多：不只是"任务完成没有"，还有"它是哪一步开始错的、是不是用危险路径完成的、换几次采样还稳不稳、改了一次 prompt 有没有偷偷弄坏别的事"。Agent 是模型、工具、上下文组装、循环控制的组合系统，任何一层变动都可能影响整体表现，而没有评估体系的团队，每一次升级都是在盲改。本章从"为什么难"讲起，给出分层评估、LLM 裁判、benchmark 的正确用法，再落到自建评估集与 CI 化落地。凡是会随榜单与版本变化的内容，按"该看什么维度、如何自测"处理，不写死结论。

为什么 Agent 评估比传统模型评估难

传统评估的基本盘是"固定输入 → 单一正确输出"：数据集给 query 和 gold answer，算准确率。Agent 评估的输入输出都不再是这种形状，难在三个结构性原因上：

非确定性：同一条输入，每次跑结果都可能不同

传统模型推理本身是概率的，但单轮生成"一次给一个答案"，评估还能容忍。Agent 是一串决策的累积：每一步的采样温度、工具返回顺序、上下文的微小差异都会改变后续走向。同一条任务，这次 5 步成功，下次可能 20 步绕圈甚至失败。单次通过不能代表能力，必须多次采样看通过率与稳定性。这是 Agent 评估与传统评估最直观的差异——一个 case 跑一遍通过了，什么都证明不了。

轨迹长且错误会累积：失败难以归因

传统评估里"答错"基本发生在一次推理内部。Agent 的端到端结果是几十步决策的复合产物，错误可能在任何一个环节种下：目标理解错、工具选错、参数填错、工具结果读错、下一步策略判断错。越到后面的步骤，前面埋的错误被放大得越厉害——这导致两个后果：一是端到端失败几乎无法凭结果反推错在哪一步；二是组合空间爆炸，靠人工一条条看轨迹去猜测，效率极低。所以 Agent 评估必须分层，把"整条链路失败"拆成"每一环节单独打分"，才有工程上可用的归因信号。

没有标准答案：任务成功有多种等价路径

Agent 处理的是开放式任务（"帮我重构这个模块"、"调研一下行情"），不存在唯一正确的输出。就算有可判定的结果（测试通过、文件生成），通往结果的路径也千差万别。评估必须回答的不是"跟标准答案一不一样"，而是"目标是否达成 + 达成方式是否可接受"。后者需要人工或 LLM 做语义/功能等价判断，无法用字符串匹配自动化。

除此之外，Agent 评估还有一个传统评估完全没有的维度——过程合规性。传统评估只看结果对不对；Agent 的结果对，不意味着过程可接受：它可能为了达成目标调用了被禁止的工具、越过了权限边界、把敏感数据外发了。端到端成功率高但合规率低的 Agent，比完成率低更危险。因此合规（是否做了不该做的）必须作为独立评估轴，与完成度分开记录——这正是 Agent 与普通模型在评估哲学上的分水岭。

综上，Agent 评估的目标不是打出一个总分，而是输出一套"分层 + 多维"的信号：完成度、路径质量、单步正确性、合规性各自独立可查，任何一次改动都能定位到"哪个分数变了、为什么变"。

评估分层：单步、轨迹与端到端各管一段

Agent 评估的分层逻辑，跟代码测试的分层是同构的：单测定位到函数、集成测定位到模块、端到端测回答"整体能不能用"。三层评估各自回答不同问题，缺了任何一层，另一层都会失真。

层评估对象回答的问题典型方法
单步（unit）一次模型决策这一步选对工具/填对参数了吗？程序校验 + 与 gold 决策对比
轨迹（trajectory）一整条决策序列路径合理吗？绕圈了吗？该停时停了吗？LLM-as-Judge 或规则判据
端到端（task）任务最终结果目标达成了吗？产出可用吗？程序验证 + 人工/LLM 复核

单步评估：把 Agent 拆成"每一步的判断题"

单步评估的输入是"某一步的上下文"，输出判据是"这一步模型的决定是否正确"。可判定的内容有两类：

  • 工具调用正确性：该不该调工具、选对工具没、参数填对没、工具结果读对没。程序能校验一部分（参数是否合法、调用的工具是否在 gold 集合里），但"该调 A 却调了 B"这种语义错误需要跟 gold 决策对比或交给裁判。
  • 决策合理性：这一步是继续执行还是该停下来问人？该终止时还在空转，属于单步就能抓出来的问题。

单步评估的工程难点在于复现上下文：模型这一步看到什么，取决于前几步的工具返回与压缩策略。离线评估时必须"重放"到这一步的完整输入，而不是只拿当前指令去测——这也是为什么单步评估集要与可观测的轨迹存档绑定。

轨迹评估：判断"路径本身"而非"结果"

轨迹评估把一整条决策序列当作对象，回答"这条路走得漂不漂亮"。它和端到端的区别必须想清楚：结果是偶然的，路径是能力的体现。一个 case 结果碰巧对了，但轨迹在绕圈、在反复试错、踩了一次高危操作，这是端到端分数反映不出来的；反过来结果错了，但轨迹判断每一步都合理（工具结果本身不可用），那问题大概率在工具或数据，不在 Agent 决策。

轨迹评估没有程序可写的黄金判据，几乎都靠 LLM-as-Judge 或人工按规则打分。常见的轨迹判据：是否围绕目标推进而非发散、有没有明显的空转循环、面对失败是否合理换策略、是否在证据不足时过早下结论。

端到端评估：用户真正在乎的那一层

端到端评估回答最终问题：任务完成没有。方法取决于任务有没有"可判定的成功信号"：

  • 有硬判据（测试是否通过、文件是否生成、接口是否返回预期）——程序验证最可靠，这也是为什么编码类 benchmark 可信度高。
  • 无硬判据（写一段总结、给一份方案）——需要人工或 LLM 做质量复核，且要给出评分细则而不是"感觉好不好"。

三层如何配合使用

  • 日常迭代（改 prompt、换模型、调工具描述）先看单步 + 轨迹：它们定位快、成本低、能指出"具体哪步退化"。
  • 发布前看端到端：回答"整体是否可用"。三层是配合关系，不是替代关系——只跑端到端，出问题无从归因；只跑单步，局部都对、整体发散也发现不了。这正是"分层"在工程上的全部意义：每层分数独立，改动后对比每层分数变化，就知道问题出在决策层、路径层还是任务层。

一个高频误区：把"可复现的通过"当成"能力"

Agent 的非确定性意味着评估结果本身有方差。写评估脚本时最常见也最隐蔽的错误，是用固定 seed 跑一遍、把所有 case 标记为 pass，就认为系统是好的。固定 seed 只能证明"在这条采样路径上能过"，不能证明能力。负责任的报告至少要给出多次采样的通过率（如跑 3-5 次统计 pass 比例）而不是单次 pass/fail——尤其在单步与端到端两层。

LLM-as-Judge：让模型当裁判的工程，而不是一句"让 GPT 打分"

单步里的程序校验（参数是否合法、gold 是否匹配）不依赖 LLM；但轨迹是否合理、端到端产出质量这类无程序判据的判断，人工标不完、规则写不出，只能请另一个 LLM 当裁判。LLM-as-Judge 的工程本质是：把"主观质量判断"做成一份有评分细则的评估 prompt，并对裁判本身做质量管控——裁判也是模型，它会偏、会漂、会自圆其说。跳过管控直接"让 GPT 打个分"，得到的分数只能感动自己。

评估 Prompt 的设计要点

  • 给评分细则（rubric），不给自由发挥。"按 1-5 打分，5 分最好"等于让裁判凭感觉；细则要落到可观察的行为描述，比如每档写明"答案引用了上下文且引用正确"与"答案脱离上下文编造"的差别。裁判对照细则打钩，而不是综合感受打分。
  • 一次只评一个维度。把"忠实度、相关性、完整性"塞进同一个 prompt 让模型一次评完，维度之间会互相污染（模型常把"长而全"误判成"质量高"）。一个评估任务一个维度，拆成多次独立调用。
  • 要求先给依据再给分数。裁判输出先引用被评内容里的具体证据（"答案第 2 句声称 X，上下文无 X 支撑"），再落分数。有了依据链，分数可复核、可审计——这比一个裸分数有用得多，也是发现裁判自身幻觉的手段。
  • 结构化输出。要求裁判输出固定字段（各维度分 + 一句理由 + 依据引用），便于批量解析与后续一致性统计。

裁判会犯的典型偏差，及对策

  • 位置偏差：让裁判比较两个答案时，排前面的容易赢。对策是调换顺序各评一次、只取两次一致的结论；或干脆用逐项打分而非两两比较。
  • 长度与华丽度偏差：越长的、修辞越漂亮的答案越容易被判高分，哪怕信息量低。对策是在细则里明写"冗余要扣分、只按要点覆盖评分"。
  • 自肥偏差（self-preference）：裁判偏好与自身同源（同一厂商/同一代）模型的输出风格。对策：跨厂商裁判、必要时对答案匿名化（去掉能暴露模型身份的措辞风格）。
  • 裁判本身的漂移与幻觉：裁判在读很长的被评内容时也会丢信息、会引用不存在的证据。对策是控制单次被评内容长度，并定期用"已知正误的校准集"抽测裁判——裁判分数与人工结论的偏差超过阈值时，先修裁判，别急着信分数。

与人工的一致性校准，是不可省略的一步

LLM-as-Judge 上线前必须回答一个问题：它的判断和人的判断一致吗？做法是抽一批样本（含容易分歧的边界 case）做人工标注，与裁判结果对比，算一致性（一致率或相关系数），并重点看分歧样本长什么样——如果分歧集中在某类 case（比如"答案信息正确但风格差"），说明裁判漏了该维度或细则没覆盖，需要补细则而不是调温度。

校准后的使用原则：裁判只在高置信区自动放行，低置信（分数贴线、裁判自评不确定）的 case 必须转人工。不要追求"全自动评估"——那是把低置信样本的风险转嫁给了分数。

反例清单

  • 细则缺失的"让 GPT 打分"，分数方差大且不可复核。
  • 把多个维度塞进一次 judge 调用，维度互相污染。
  • 裁判与生产用同一个模型，自肥偏差被系统性放大，评估结果虚高。
  • 从不做人工一致性校准，分数自洽但与人脱节。
  • 把 judge 分数当精确度量直接进发布门禁，而不看置信区间与分歧样本。

Benchmark 怎么读：测什么、怎么判分、坑在哪

公开 benchmark（如 SWE-bench、GAIA、AgentBench、τ-bench）是行业公认的横向参照，但读法比分数重要。背一个具体分数毫无意义——榜单会变、模型会在训练时见到这些题（污染）、你的业务场景跟它差很远。真正要读的是三个维度：它测什么能力、用什么方式判分（判分方式决定分数可信度）、我的场景跟它哪里不像。

Benchmark测什么怎么判分读懂的关键
SWE-bench真实 GitHub issue → 改代码跑隐藏单元测试，程序自动判定测"代码改对没有"，有硬判据，可信度高；但只覆盖编码且环境与真实开发差异大
GAIA多步真实世界问题（查资料、算数、组合推理）对最终答案字符串/断言匹配测"综合工具使用 + 推理"，但判分偏松（答案匹配），高分不代表路径合规
AgentBench把多种环境（操作系统、数据库、网页游戏等）统一成 agent 任务各环境自带成功判据测"跨环境通用能力"，覆盖广但单环境深度有限
τ-bench模拟业务环境（客服、零售 API）里按指令调工具完成任务判分含"任务是否完成"与"是否违规调用工具"双轴少见的把"合规"纳入判分，贴近 Agent 评估的过程合规维度

读 benchmark 时的三个通用提醒：

  • 判分机制决定可信度。程序化验证（跑测试、跑代码）比"字符串匹配答案"可信；字符串匹配比"LLM 打分"可信。一个 benchmark 若靠 LLM 自评，它的分数自带裁判偏差，横向对比时要打折扣。
  • 注意数据污染。模型训练语料可能包含 benchmark 的题与解，尤其热门 benchmark 存在"记住答案"的可能。这不代表模型能力变强了，只代表它见过题。自查办法：在你的私有 case 上对比，而不是只信公开分数。
  • benchmark 分数是"能力下限证明"，不是"业务上线依据"。它的题是公开的、静态的、与你的领域数据无关。业务评估必须回到自建评估集——benchmark 回答"这个模型/这套 Agent 架构在通用任务上有没有基本盘"，自建集回答"在真实任务上能不能用"。两者配合，缺一不可。

检索型能力的评估：Agent 里 RAG 环节的专项指标

当 Agent 内置了检索类工具（查知识库、搜文档），它的表现除了看整体任务完成度，还要对"检索这个动作"做专项评估。常用指标归成三个口径：上下文精度（context precision） 衡量检索回来的内容里有多少是真正相关的（检索端）；忠实度（faithfulness） 衡量最终回答的每个断言能否在被检索到的上下文里找到支撑（生成端是否忠于材料）；答案相关性（answer relevancy） 衡量回答是否切中用户问题。三者拆开的原因和 Agent 分层评估同构：检索没召回相关材料、召回了但生成没用对、回答偏题，是三个不同环节的病，必须分别归因。指标得分可用工具约定口径，也可人工抽检复核，但注意这类自动分数衡量的是"与材料的一致性"，替代不了"对业务是否真正有用"的判断——后者仍需业务视角的人工评估。对 Agent 而言额外要盯一条：检索工具本身要按 Agent 决策链被评估——它是否在恰当的时机被调用、检索失败后有没有合理换路，而不只是看返回内容命中率。

构建自己的评估集：黄金样本、bad case 回流与回归测试

公开 benchmark 是"别人的题"，自建评估集才是"自己的考场"。一套自建 Agent 评估集要同时回答三层问题，所以它的结构天然不是"一堆问题和答案"，而是分层的样本：既有端到端任务样本，也要有带轨迹标注的单步样本（用于单步评估与回归）。

黄金样本从哪来

  • 真实任务优先，不要凭空造。从线上真实会话里采样高频任务、典型场景与边界场景，而不是让工程师脑补"用户可能会问什么"。脑补的样本容易是"我们以为系统会遇到的"，与真实分布脱节。
  • 标注要多份、判据要收敛。端到端任务多数没有唯一正确答案，标注要给"可接受的结果特征清单"而非一个标准答案；多个人标同一批样本后要校准一致性，标注口径不一致的样本要么改判据、要么剔除。
  • 单步样本要带着轨迹上下文。单步评估需要"重放到这一步"的完整输入，所以黄金样本应保留当时轨迹的关键上下文，而不是孤零零一句"下一步该做什么"。

bad case 回流：让评估集跟着线上长

评估集最忌讳"一次建好就再也不动"。正确做法是建立回流闭环：线上失败案例（用户投诉、质检拦截、人工修正过 Agent 产出的会话）自动进候选池 → 人工筛选确认值得守护 → 补进评估集 → 跑回归。这样评估集永远在覆盖"最近暴露的问题"，防止同一类错误反复上线。回流也有反向价值：某类 bad case 若长期不再复现，可以归档而不是让评估集无限膨胀——评估集要持续演进，size 不是资产，覆盖率才是。

回归测试的工程要点

  • 每次改动（prompt、模型、工具定义、harness 逻辑）都要能在分层评估集上跑回归：单步集定位"哪一步退化"，端到端集回答"整体是否变差"。
  • 回归的基线要留档：改动前的分数曲线要能回查，否则"这次是不是它搞坏的"永远说不清。
  • 测试要快得能天天跑。Agent 端到端样本贵又慢，全部进回归会拖垮迭代速度——把评估集按成本分层：便宜的单步样本每次提交都跑，昂贵的端到端样本做夜间或按需回归，这是评估能融进持续集成的前提。

反例：自建评估集的常见失效模式

  • 黄金样本全部来自"系统已经能答对"的题——评估集变成对现状的确认，分数永远好看，退化测不出来。必须强制纳入已知失败与边界样本。
  • 标注只有一份、没有一致性校准——判据其实很主观，换个人标可能全变，分数自洽但不可信。
  • 评估集只增不减、从不演进——线上分布早变了，你还拿半年前的题当准绳。
  • 把端到端分数当唯一指标，bad case 回流了却不知道该看单步还是轨迹层——回流样本要带上分层标注，而不是只记一句"这个任务失败了"。

在线评估：离线分数永远不够，真实流量才是终审

离线评估集再完备也是"历史快照"：样本分布会漂移、真实用户问题永远有评估集没覆盖的形态。上线后的在线评估才是对 Agent 的终审。在线评估的工程问题不是"看什么指标"，而是三个容易想当然的环节：对照组怎么设、用户信号怎么定义、灰度怎么放量。

A/B：在真实流量上比版本

A/B 的核心纪律是同一时刻同一用户只接触一个版本，否则版本间串扰会让信号没法归因。Agent 场景有两个额外的麻烦：

  • 非确定性放大样本量需求。Agent 同任务多次跑结果不同，要分辨"版本 A 比 B 好"还是"纯属随机波动"，需要比传统 A/B 大得多的样本量。样本不够时先别下结论，至少按统计显著性来判断，而不是凭感觉看趋势线。
  • 成本是实验的约束。Agent 每一步都是真金白银的模型调用与工具执行，长尾任务一次就可能烧掉可观预算。实验组别设计与样本量预算要在设计实验时就定好，而不是跑完发现对照组成本失控。

用户反馈信号：显式很少、隐式易偏

  • 显式反馈（点赞、点踩、打分）信号强但稀疏且有偏——愿意点踩的用户本来就带着情绪，样本不代表全体。
  • 隐式信号（是否采纳产出、是否复制、是否继续追问、是否中止会话、是否点击引用）量大，但每个都是间接代理指标，定义时要想清楚它代理的是什么：用户继续追问可能意味着"没答好"，也可能意味着"答得不错想深入"。隐式信号必须清洗与交叉验证，不能单点当真。
  • 对 Agent 还有一种关键信号：安全与合规事件（触发了权限拦截、访问了被禁止资源、产出需要人工修正）。这类信号量极少但权重极高——在线评估不能只盯"完成率"这类正向指标，护栏指标（事故数、越权次数）是发布门禁里最硬的一条，宁可拦错不可放过。

灰度与回滚：让问题只在可控半径内发生

新版本不要全量上线，按风险递进放量：内部小流量 → 低风险用户群 → 百分比逐步放大。灰度期间同时盯两组指标：功能指标（完成率、用户反馈）与护栏指标（成本/请求、延迟、失败率、安全事件）。任何护栏指标异常都应触发自动或快速回滚——回滚的决策标准要在灰度前写死，不要上线后再"开会讨论要不要回"，那通常已经晚了。Agent 版本回滚还有一个特殊性：要连同评估基线一起回退，否则"代码回滚了、prompt 没回滚"会让问题以另一种形态复现。

反例：在线评估的常见误区

  • 用 A/B 结果直接做发布决策，却不看统计显著性与样本量。
  • 只统计显式反馈，把"没点踩"当成"满意"——沉默不是赞许，绝大多数不满根本不会变成点踩。
  • 灰度只看转化/完成指标，不盯护栏指标，危险操作在放大到全量后才被发现。
  • 回滚只回代码不回配置（prompt、工具描述、评估基线），问题换个样子回来。

把 Agent 评估接进 CI：慢而贵的测试怎么守门

Agent 测试与普通单元测试最大的冲突在成本与速度：一次端到端样本可能跑几十步、烧几千 token、耗时以分钟计。把这类测试当成普通单测塞进每次提交的门禁，结果是开发者被拖到失去耐心，最后选择绕过门禁——评估形同虚设。CI 化 Agent 测试的关键不是"把评估跑起来"，而是设计一套与改动类型匹配的分层守门策略。

快与慢：给不同层级的测试分配频率

  • 每次提交都跑的快集：单步评估样本（单次模型决策判定，快、便宜）加上一小撮固定 seed 的端到端冒烟样本。它们的作用是快速暴露"这改动是不是把基本盘弄坏了"。
  • 合并/夜间跑的慢集：完整端到端集、轨迹评估、大样本统计。它们慢而贵，但对"整体是否退化"的判断才是充分的。
  • 快集要足够短才守得住门，慢集要足够全才守得住质量——两者职责不同，别混成一个超大门禁。

改动类型决定跑哪一层

按改动内容定向触发评估，是控制成本的关键：

  • 改了 prompt 或工具描述 → 跑单步与轨迹层，重点看决策质量是否波动。
  • 改了工具实现或 schema → 跑涉及该工具的单步样本 + 相关端到端场景。
  • 换了模型 → 全套慢集，模型是横切改动，影响所有层。
  • 改了 harness（权限、上下文压缩、状态恢复）→ 安全与合规样本优先，再跑回归。

处理评估固有的不稳定性

Agent 评估天然带方差，CI 里要区分真退化与随机波动：

  • 固定 seed 缩小方差，但固定 seed 的通过可能只是运气好——快集用固定 seed 保可复现，慢集用多次采样看统计。
  • 对偶发失败做有限重试（比如同 case 跑 3 次取多数），但要记录重试率——重试率持续上升本身就是退化信号，说明稳定性在变差，别用重试把它藏起来。
  • 门禁的阈值要有人工校准的余地，不能定死一个分数就再也不动；同时阈值校准要留痕，防止"为了让门禁过、悄悄调低阈值"这类无声腐化。

反例：Agent CI 化的典型失败

  • 把所有端到端样本塞进每次提交的门禁，一次提交跑半小时，团队最后选择"跳过 CI"或"提交后再补跑"——门禁失效。
  • 门禁只看端到端总分，不在分层上归因：分数掉下来，却不知道是单步、轨迹还是任务层的问题，排障无从下手。
  • 用无限重试把偶发失败"洗绿"，掩盖了稳定性退化。
  • 上线一个 Agent 改动，评估只在本地跑过一次"看起来不错"，没有形成可重复的 CI 回归基线——下一次改动时，没人知道这次是不是破坏了什么。

收束：评估是一条数据回路，不是一套脚本

把整章串起来看，Agent 评估的工程本质是一条持续的回路，而非一堆一次性脚本：分层评估给出可归因的信号 → bad case 回流让评估集覆盖真实弱点 → 在线信号与 A/B 补上离线集覆盖不到的分布 → CI 门禁在每次改动时守护这些基线。环上的每一段都在回答同一个问题：这个 Agent 是不是比上一版更值得被信任。模型的改进决定能力上限，评估回路决定的是你敢不敢把能力放上线——后者才是工程上真正决定交付质量的环节。
