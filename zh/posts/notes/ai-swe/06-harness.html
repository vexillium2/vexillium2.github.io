Agent Harness 工程

vexillium2026/9/7大约 25 分钟后端开发人工智能

这一章讨论模型循环外面那一圈工程外壳——Agent Harness。模型只负责"下一步做什么"的决策，可决策产生之前与之后的所有事情，都需要 harness 兜住：动作在哪执行、越权怎么办、跑到一半断电怎么恢复、上下文怎么在不失真的前提下省着用、烧钱失控了谁来踩刹车、被恶意内容诱导时最后一道闸在哪、出问题后凭什么复盘。编码类 Agent（如 Claude Code、Codex、OpenHands）是观察 harness 结构最好的样本——它们把同样的循环包装进沙箱、权限与状态体系里，差异只在取舍。凡是会随版本变化的厂商细节，一律按"该看什么维度、如何自测"处理，不写死结论。

一、Agent Harness 是什么：模型之外的那台"机器"

Agent 的决策内核（LLM）、行动接口（工具）与循环控制构成了运行时；但光有循环，一个 Agent 还不能上生产。Harness 是把"会决策的循环"变成"可被约束、可恢复、可审计、可预算化的产品"的全部工程外壳。判断一件事是否属于 harness 的职责有一条简单的判据：把模型拿掉，这件事是否依然必须存在——沙箱必须存在（动作要执行），权限必须存在（越权要拦截），状态必须存在（中断要恢复），预算与观测必须存在。凡是"模型没了就不需要"的东西（如何规划、如何反思），不属于 harness。

以编码类 Agent 为样本，可以拆出 harness 的六块骨架，它们之间是串行拦截而非并列关系：

  • 执行环境：模型声明的动作（shell 命令、文件编辑、网络请求）落在哪里——本机裸跑还是隔离沙箱，读写权限边界怎么划。
  • 权限裁决：每次动作执行前，按"动作名 + 参数"判定放行、拒绝还是请示，裁决独立于模型输出，模型无法绕开。
  • 状态与恢复：把对话上下文、运行中计划、已产生副作用的工作区落盘，支持中断续跑与多会话隔离。
  • 上下文管理：在窗口有限的前提下决定什么进上下文、什么外置、何时压缩——这是 harness 对模型最直接的"照料"。
  • 资源治理：给每一步决策设定 token、时间与成本上限，保证失控时可被硬性终止。
  • 可观测与安全：记录每一步决策与动作的痕迹，既用于排障复盘，也是安全审计的依据。

一个典型的编码 Agent 运行时，模型输出"读文件"或"跑测试"的结构化意图后，harness 依次做四件事：先过权限裁决（允许/拒绝/问人），再在沙箱内执行，把结果连同这次动作的审计记录写进会话状态，随后做上下文管理（这段结果要不要压缩）。这四道工序每一步都可能让一次"模型很自信的调用"被拦下或改写——harness 的本质是给模型的自由上边界，边界内模型说了算，边界外模型碰不到。

工程上最常见的方向性错误，是把 harness 环节当成"可后补的增强"：先把模型循环跑通、再把权限和状态随手一贴。但沙箱、权限、状态、压缩这些机制是耦合设计的——沙箱决定权限能在哪一层生效，权限决定恢复时能放行什么，压缩决定状态里要留哪些原始信息。harness 必须从第一天就按产品约束设计，而不是模型能跑之后再打补丁；否则等到要上生产时会发现，安全与恢复能力不是"加一个模块"能补上的，而是需要重构执行路径本身。

二、沙箱执行：动作发生在哪，决定了风险有多大

为什么需要隔离

Agent 的动作有两类来源，风险差异极大：一类是结构性工具（读文件、查库、调 API），动作边界由工具代码写死；另一类是自由执行（跑 shell、执行生成的代码、安装依赖），模型输出什么就执行什么，动作边界几乎不存在。自由执行是 Agent 能力强的来源，也是事故的来源——模型可能因推理错误、上下文被污染或目标漂移，执行一条它自己都意识不到后果的命令。隔离的目标不是"防止模型作恶"，而是"限制模型出错时能造成的最大损失"。隔离粒度决定一件事：一次越界动作，毁掉的是当前工作目录、整个容器、还是宿主机。

隔离技术的取舍：容器 / 微虚拟机 / WASM

方案隔离边界启动与性能开销兼容性典型角色
容器（如 Docker）内核共享，靠 namespaces/cgroups 隔离极低，毫秒级高，近似原生默认选择，隔离的是"路径"而非"内核"
用户态内核（如 gVisor）系统调用被用户态拦截、改写中，syscall 密集场景明显较高需要比裸容器更强的边界又不愿付虚机成本
微虚拟机（如 Firecracker）硬件虚拟化，独立内核较高，启动百毫秒级中，内核/驱动差异多租户、不可信代码、强隔离诉求
WASM 沙箱语言/运行时级，无系统调用面低低，只能跑编译到 WASM 的程序插件体系、内存安全优先的场景

选型的关键不是"哪个更安全"，而是你的威胁模型里，对手与受害者的距离有多近：同一个人自己的开发机、只防"模型手滑删库"，一层容器 + 文件权限就够；要承接不可信代码或多租户隔离，容器共享内核这个事实本身就不可接受，必须上到内核隔离。反过来，为所有任务一律套微虚拟机，启动开销与镜像维护成本会抵消 Agent 快速试错的收益。隔离强度应当与"动作能访问的资产价值"匹配，而不是统一拉满——跑测试用的沙箱与跑生产部署的沙箱不应是同一个配置。

文件系统与网络的策略，才是沙箱的真正边界

技术选型只决定"隔离壳有多厚"，真正决定事故半径的是壳内可见的资产：

  • 文件系统默认只读，按需挂载可写目录。模型唯一能写坏的是显式交给它的工作区，其余路径（系统目录、其他项目、用户主目录）只读或不可见。把整个主目录可写地挂进去，等于没隔离。
  • 网络默认关闭或出向白名单。很多高危事故的链路是"模型读到了密钥 → 发出网络请求外带"，网络层是最后一道拦截。本地开发全放开、生产执行收紧是常见分级，但没有"外发即审计"的地方，文件泄露出去你都无从知道。
  • 临时环境一用即弃。每次任务用全新沙箱，任务结束销毁；复用"上次的沙箱"会把上次的残留文件变成这次的攻击面或错误源。
  • 时间与资源同样属于隔离维度。无限制的 CPU/内存配额会让一次失控循环拖垮宿主机——这属于资源治理的职责，但配额要在沙箱层声明。

结构性工具（读文件、编辑文件）也应在沙箱内以受限身份执行，而不是在宿主机上以进程所有者权限直跑——否则沙箱只挡住了 shell，没挡住同样危险的工具调用。隔离的是"执行者身份"而非"调用方式"，这个认知比具体技术选型更重要。

三、权限系统：把"默认拒绝"变成可执行的裁决

沙箱管住"能碰什么"，权限管住"能做什么"。编码类 Agent 的权限系统几乎都是同一套裁决模型，值得拆开看：

  • 动作命名空间与白名单。Agent 可调用的不是"任意 shell 命令"，而是一个受限命令集合（文件读、文件写、执行测试、跑构建……）。白名单在 harness 层声明，模型只能看到白名单内的工具，看不到的连"尝试"都无从发起。这比"事后发现越权再拦截"安全一个量级——不存在于可见范围内的动作，天然不可能被调用。
  • 参数级裁决，而非命令级。命令名允许不等于命令安全：rm 是合法工具，rm -rf / 与 rm -rf ./dist 风险天差地别。裁决必须落到参数：删除命令作用在项目目录内才放行，越出边界进入询问或拒绝。只看命令名放行、不校验参数，等于把"危险"的判断外包给了模型。
  • 分级策略：自动放行 / 询问 / 拒绝。低危高频动作（读文件、只读查询）按规则自动放行；中危（写文件、跑测试）按路径与内容匹配自动放行或弹确认；高危（删库、外发网络、安装全局依赖）无论参数如何都进人工确认或直接拒绝。分层是为了把人工注意力留给真正需要判断的动作——确认框本身是稀缺资源，滥用会让用户闭眼点允许。
  • 最小权限的落地形态。进程以最小必要身份运行：不 root、不带凭据、只有当前任务需要的目录可写。session 结束时身份与凭据随之销毁，不让权限残留到下一个任务。

权限系统设计的反例与陷阱

  • 把权限写进 prompt 而不是裁决器。在系统提示里写"不要删除生产库"毫无约束力——模型可能因注入或幻觉输出删除命令，而提示只是一段文本。权限是运行时行为，不是模型约定。凡安全要求必须落到裁决代码。
  • 白名单只圈命令、不圈来源。命令白名单 + 允许 Agent 执行任意脚本内容（bash <(curl ...)、eval）会把"你审过的命令"绕过成"模型现场编的命令"。要禁的是"执行未经过滤的输入"，而非某一串命令。
  • 全自动放行 + 无审计。为了不打断 Agent 把每件事都自动放行，等于放弃了权限层全部意义，只剩沙箱兜底。即使自动放行，也必须给每次放行留审计轨迹——否则出了事故，权限层无法回答"那次危险命令是谁批的"。
  • 权限与沙箱分离配置。沙箱内可写目录和权限系统允许写的目录不一致时，会出现"裁决允许了、沙箱没给路径"或"沙箱给了、裁决没审"的裂缝。两者应共享同一份路径白名单定义。

权限系统与"人工在环"的关系是：机器能可靠裁决的交给规则，规则判不了的交给人，但人只做二选一的判断题（放行/拒绝 + 是否记住），不做填空题。

四、会话与状态管理：checkpoint、断点续跑与多会话隔离

状态到底包含什么

一次 Agent 会话产生的状态远比"聊天记录"多。至少分三层：

  • 对话上下文：消息序列（含工具调用与结果），模型继续推理的依据。
  • 运行态对象：当前计划、待办列表、已用步数与预算、目标定义。这些不一定都进上下文，但必须被持久化，否则恢复后模型不知道自己进行到哪。
  • 工作区副作用：沙箱里被创建/修改的文件、安装的依赖、启动的进程。这是最容易漏的一层——只恢复对话、不恢复文件，Agent 续跑时面对的是一个"失忆的世界"。

checkpoint 要同时覆盖这三层才算完整。编码类 Agent 普遍采用"每个工具动作边界落一次 checkpoint"的策略：动作前记录状态、动作后确认落盘，这样任意一步失败都能回退到上一个一致性点。

断点续跑的正确姿势与难点

续跑不是"把消息塞回去重新问一次"。正确的恢复顺序是：恢复工作区（文件回到 checkpoint 状态）→ 恢复运行态对象 → 恢复对话上下文 → 提示模型"你正在继续之前的任务"。其中最大的工程难点是副作用的一致性：

  • 文件类副作用可以通过快照/补丁栈回滚，相对可控；
  • 外部副作用不可回滚：已经发出的网络请求、已经写入远端数据库的数据、已经发送的消息，checkpoint 恢复不了。对这类动作，harness 只能靠"幂等设计 + 恢复时明确告知模型哪些动作已实际生效"来兜底，而不是假装时间倒流。
  • 恢复后要给模型一个明确信号：哪些步骤已完成、哪些结果不可信需重验。模型自己从消息历史推断，往往会重复执行已完成的外部副作用。

多会话隔离：并行与冲突

一个 harness 上可以同时跑多个会话：同一任务多开对比、不同任务并行。隔离的两个层次：

  • 状态隔离：会话 A 的上下文、计划、checkpoint 对会话 B 不可见。这个靠"状态按 session id 分桶"实现，模型是共享的还是独立的都无所谓——状态边界必须清晰。
  • 工作区隔离：两个会话改同一份文件，冲突与互相覆盖不可避免。要么每会话独立工作副本（成本高但安全），要么共享工作区 + 变更锁。现实产品多采用"工作区 + 变更应用前先 diff 确认"的策略，让冲突暴露在裁决层而不是静默覆盖。

反例与常见失败

  • 只存对话不存运行态：恢复后模型有上下文却丢了目标与计划，续跑变成"重新开始"。
  • checkpoint 频率过低：每 10 步存一次，第 9 步崩溃就丢 9 步的推理与副作用。步级 checkpoint 是成本与安全的默认平衡点。
  • 恢复时把外部副作用当没发生：以为恢复到了过去，实际外部世界已经变了——恢复的只是"你的状态"，不是"世界的状态"。
  • 会话之间共享工作区却无锁：并发 Agent 互相覆盖文件，产出的代码无法合并，排查时归因到"另一个会话改了它"。

五、上下文管理工程：让上下文"长跑不胖、坏了能修"

上下文窗口是 Agent 最稀缺的资源。组装"什么进窗口"是运行时的话题，harness 要解决的是窗口装不下的工程机制：窗口满了怎么办、大内容怎么喂、哪些内容根本不该进窗口。

Compaction 与 Summarization：窗口满了怎么办

长会话必然逼近窗口上限。粗暴做法是截断：丢掉最旧的消息。它的致命缺陷是丢的是"最早的目标设定与用户约束"，而这恰恰是最不能丢的——模型截断后会在没有目标的情况下继续执行，目标漂移由此而来。

harness 采用的主流机制是 compaction（压缩）：把已经执行过的、不再需要逐字保留的旧内容压缩成摘要，腾出空间。它与截断的区别在于摘要保留了信息语义。工程上的三个关键决策：

  • 触发时机：到达 token 阈值自动触发、每 N 轮主动触发、还是模型或用户手动触发？纯自动压缩的坑是"压缩发生在推理中途"，摘要本身会引入偏差。多数成熟产品支持手动 + 阈值结合。
  • 哪些内容可压缩、哪些必须保真：用户原始指令、系统级约束、当前任务目标必须原样保留；工具往返的历史可以摘要化。摘要模型自己做的判断不可全信——压缩后的内容会作为后续决策依据，摘要错了，后续全错。因此压缩结果要尽量由独立于主决策的一次调用产生，并保留"压缩发生在第几步、原始内容存哪"的索引，供需要时回查。
  • 压缩不是删除，是移动：原始完整轨迹应落盘（进 trace/审计存储），上下文里只留摘要。这样调试时仍能拿到原始证据，只是不在模型窗口里。

大文件读取：别把整个代码库塞进窗口

Agent 处理代码任务时最大的上下文黑洞是"读文件"。三个工程原则：

  • 先定位后读取，能不全量就不全量：先用搜索/索引确定相关符号与行号，再按需读片段；而不是把整个文件甚至整个项目 cat 进上下文。
  • 分块读取 + 行号续读：超出单次可读上限的文件分段读，每次带行号范围，让模型知道"我看的是 100-200 行，前面还有"。没有行号与边界的分块，模型会误以为读到的是全文。
  • read 工具与 shell 的差异：文件读取走专用工具（返回结构化内容、受大小限制与权限控制），而不是让模型自由 shell cat。shell cat 无大小护栏、无权限裁决、无审计——大文件读取策略首先要在工具层面堵死这条自由路。

Todo 列表外置：什么不该进上下文

Agent 的执行计划、待办清单这类运行态，如果放在上下文里让模型"记着"，会占窗口且在压缩时被改写。harness 的做法是把它们外置成文件，通过文件工具读写。好处是：不占上下文、压缩不丢失、断点续跑时直接恢复、还能被其他进程（比如 UI 展示、审计）读取。模型需要时读当前 todo，更新后写回。注意这里的坑：外置 todo 与模型"口述"的进度可能不一致——模型说"做完了"但 todo 文件没更新，要以文件为准做一致性校验，而不是信模型口头汇报。

六、资源治理：给不确定的循环装上保险丝

Agent 是不确定系统：同一个任务，可能 5 步完成也可能 50 步绕圈；可能一次调用就够，也可能在同一个错误上反复重试。没有资源上限的 Agent 循环，成本与耗时都是无界的。harness 的资源治理就是给这个不确定系统设定各种上限，并在超限时强制执行——注意"强制执行"，写在提示词里的软预算（"请尽量少用几步"）模型会无视。

几个必须有的维度

  • 单次调用上限：一次 LLM 调用的最大输出 token、最大耗时。超时后重试或降级，避免一次卡死的调用挂住整个任务。
  • 单步执行上限：一次工具调用的超时与重试次数。工具卡住不该拖死 Agent，工具失败不该无限重试（尤其是副作用操作，重试前要考虑幂等性）。
  • 整任务预算：总步数上限、总 token 预算、总成本上限。这是防"Agent 陷入循环无法自拔"的最后手段——模型层可能永远不主动喊停，只有 harness 能数着步数强制终止。步数与 token 的双重预算比单一维度可靠：步数少但每步烧大量 token 的路径，单看步数发现不了。
  • 并发与限流：同一会话内并行工具数、同一账号并发会话数、对上游 API 的速率。模型倾向于一次开很多并行调用，harness 要按成本与上游承受力约束。

预算与"目标完成"的关系

预算用尽时不能只报"超预算了"就完事——要区分两种情况：正常推进中预算用完（可恢复：加预算续跑）与空转耗尽预算（不可恢复：说明 Agent 在绕圈，恢复也白烧钱）。判断依据是最后 N 步是否有实际进展（文件变更、外部调用、状态推进）。预算耗尽报告里应该带上"最后在做什么、卡在哪"，让人能决定是续跑、换策略还是放弃——这是资源治理从"计数器"变成"决策支持"的关键一步。

反例与陷阱

  • 只设单次超时，不设整任务预算：一次调用不会卡死，但任务会无限步数空转到天价账单。
  • 预算用提示词约束："请尽量在 10 步内完成"没有任何强制力。预算必须由循环控制层计数并在代码里硬性终止。
  • 所有重试都无上限且立即重试：瞬时错误可以重试，但同一个错误反复出现说明策略错了，应该停下来换路径而不是继续烧钱。
  • 预算超限直接杀掉会话：没有把中间产物落盘就杀，恢复成本反而更高。资源治理要与 checkpoint 机制配合：预算告警时先做一次状态落盘，再决定终止与否。

七、Agent 安全：内容进上下文之后的攻防

Agent 与普通程序最大的安全差异是它会把不受信任的内容读进上下文并据此行动：网页、文档、代码仓库、工具返回、邮件都可能包含诱导指令。提示层面的防御（告诉模型"忽略注入"）只是第一层且可被绕过；harness 层面的安全是把"模型可能被诱导"当作前提来设计——既然内容不可信、模型可能被操控，那就让被操控的模型也做不成坏事。

工具注入的现实攻击面

最典型的攻击链：恶意内容混在 Agent 读取的资料里 → 模型被诱导调用工具 → 工具产生真实副作用（读敏感文件、改代码、外发数据）。harness 的防御不依赖模型识破诱导，而是依赖执行层机制：

  • 工具只暴露最小必要集：Agent 根本看不到的敏感操作，注入内容再强也无法触发——白名单机制是这一点的执行载体，敏感操作从可见范围内消失，比事后拦截可靠。
  • 参数白名单校验：即便模型被诱导调用"删除文件"工具，参数也要过路径边界校验，删不到白名单外。诱导只能让模型"在规则允许的范围内"动作。
  • 外部副作用默认高成本：凡是会离开沙箱的动作（网络外发、远端写入、安装全局依赖），默认进人工确认或直接禁止。网络外发尤其要拦——敏感数据泄露大多不是靠删库，而是靠悄悄外带。
  • 敏感内容标记与污染追踪：读入的文件标注来源（"这是用户上传的不可信文件"），让模型与后续裁决知道内容信任等级；工具结果若来自不可信输入，追加来源标记而不是让它冒充系统权威内容。

沙箱逃逸与权限提升

沙箱隔离本身不是银弹，逃逸面主要在配置错误：

  • 挂载泄漏：把宿主敏感目录（/、~/.ssh、docker socket）挂进沙箱，等于亲手打开门。挂载前问：模型真的需要读写这里吗？
  • 特权与内核共享：容器内 root + 共享内核 + 未禁用危险 syscall，就退化为"带目录限制的普通进程"。容器要配 non-root、capability drop、seccomp/用户态内核。
  • 资源耗尽型逃逸：沙箱内无限占 CPU/内存拖垮宿主机，需要配额兜底。

审计日志：安全事件的真相来源

安全机制总会失效，审计日志是"失效后还能查清"的保障。Agent 审计日志的核心字段：会话与用户标识、时间线、每一步的完整决策链（模型输入摘要 → 模型输出 → 工具调用名与参数 → 裁决结果 → 执行结果）、批准人。工程要点：

  • 记全不记糙：工具调用的参数必须记录——事后追查"那条命令到底干了什么"，参数比命令名有价值得多。敏感参数（密钥）要脱敏，但脱敏规则不能把关键证据一起抹掉。
  • 审计与可观测共用一份事件源：安全审计和排障 trace 是同一份运行时事件的不同视图。分开记录会导致"安全日志里没有上下文、trace 里没有裁决信息"，出事故时两边对不上。
  • 日志可写保护：沙箱内进程不能改写自己的审计日志，否则被攻破后日志会被清洗。日志要写到沙箱外的独立存储。

八、可观测性：把"黑盒决策"变成可回放、可归因的记录

Agent 的每一步都是模型决策，失败时最常见的困局是"看结果知道错了，但不知道是哪个决策、哪条上下文导致的"。可观测性解决的就是这个问题：把每一步的输入、决策、动作、结果完整记录，让任何一次失败都能被回溯到具体一步。

记录什么：决策轨迹而非结果

  • 每次 LLM 调用的完整输入与输出：system + 当时上下文（或至少其标识与摘要）+ 模型输出。没有调用输入，事后无法判断"当时模型看到了什么导致它这么选"。
  • 每次工具调用的声明与结果：工具名、参数、裁决结果、真实执行结果、耗时。工具调用是模型与世界的唯一触点，这条链是归因的主干。
  • 决策与决策之间的因果：为什么走到这一步（上一步的哪个结论触发了这次调用）。把工具结果与后续决策关联起来，才能区分"是工具返回错"还是"模型用错了结果"。

用 trace 把事件串成链

单条日志无法支撑归因，需要把一次会话的所有事件组织成带层级与顺序的 trace：一次任务 = 一个 trace；一次 LLM 调用与其触发的工具执行 = 其中的 span。每个 span 携带开始/结束时间、父子关系与结构化属性。这样排查时能回答三类问题：这条链路花了多少时间（在哪一步最慢）、在哪一步开始偏离预期（对比成功案例的路径）、哪一步产生了实际副作用。

工程上常踩的坑：

  • 只记结果不记决策：日志里只有最终产物，模型中间改了多少次主意、试过哪条死路全部丢失——这是 Agent 排障最痛的点。中间轨迹比结果有信息量。
  • 全量记录导致存储爆炸：每一步 LLM 调用的完整输入可能上万 token，任务一长就存不下。策略是"结构化必存 + 内容分级存储"：必存的是工具调用与裁决等小体积高价值事件；大体积的上下文快照按需抽样（如每 N 步存一次、失败会话必存）。
  • 丢失关联标识：没有统一的会话 ID / 请求 ID 贯穿 trace、审计、应用日志，事后无法把"这笔账单""这条命令""这次模型调用"对应到同一件事。

Replay 与调试：让失败可复现

有了完整轨迹，就能做真正有效的调试：把记录下来的某一步输入原样重放给模型，验证"同样的输入是否稳定产出同样的错误"——若是，问题在模型或上下文；若重放不复现，问题在运行时（状态错乱、竞态）。更高阶的用法是离线修改轨迹做对照实验：同一段任务，换成不同的上下文组装、不同的工具描述，重放对比哪条路径收敛。这把 Agent 的调试从"对着日志猜"变成"可重复的实验"。采集 bad case 的标准动作因此是：失败时连同完整轨迹一起归档（含当时的上下文、工具链与裁决记录），而不是只留一句错误信息——没有轨迹的 bad case，等于一个无法复现的 bug 报告。

九、收束：六块骨架如何咬合成一台机器

回看整个 harness，六块机制不是各管一段，而是共享同一套事件与状态基础：checkpoint 复用 trace 的步骤边界，审计复用工具调用的事件记录，权限裁决结果同时进入审计与可观测，预算耗尽报告引用最后几步的轨迹。判断 harness 成熟度的试金石只有一件事：一个任务失败或越界之后，你能不能回答"它每一步看到了什么、做了什么、谁批准的、花了多少钱"——能回答，harness 就在正常工作；缺了任何一块，都会在某类事故里变成查无可查。

这一章从上到下走的是同一套设计逻辑：先定义边界（沙箱划清能碰什么），再定义裁决（权限决定能做什么），再定义连续性（状态保证中断后可恢复），最后用治理（预算）、安全（兜底）与可观测（留痕）把整个循环包成可上生产的产品。Harness 不改变模型的能力，它改变的是模型能力可以被信任的程度——这正是"能跑通的 Agent"与"能交付的 Agent"之间的全部距离。
