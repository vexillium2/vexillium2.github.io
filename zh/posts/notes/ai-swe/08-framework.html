AI 应用开发框架

vexillium2026/9/7大约 26 分钟后端开发人工智能

这一章不回答"哪家框架最好用"，而是把框架当成工程来读：当你在框架里写 Agent 时，框架究竟替你做了什么、做得牢不牢、又锁定了哪些自由。模型的推理能力来自模型本身，不来自框架；框架解决的是另一摊事——把"模型 + 工具 + 上下文 + 控制流"编成可运行、可中断、可恢复、可审计的程序。先把生态按协议层 / 框架层 / 平台层切成三层地图，再看具名产品时就会过滤掉营销话术，只剩机制与边界：LangChain/LangGraph 代表的显式编排、LlamaIndex 代表的数据优先、OpenAI/Anthropic 官方 SDK 代表的最少封装运行时、AutoGen/CrewAI 代表的多 Agent 协作、以及把框架再包成托管服务的低代码平台。框架与版本更迭极快，本章对具名产品一律按"机制与边界"而非"当前特性清单"来讲，选型时请自行复核现状。章末用手写一段极简 Agent 反推框架的增值点，把选型落成决策树。

一、生态三层地图：协议、框架与平台各自解决什么

三层不是并列的技术，而是三档"抽象与托管"深度

Agent 应用可以按对开发者的暴露程度分成三层，每一层锁定的是不同的可变化点：

层解决的核心问题典型产出使用者
协议层"双方怎么接"——模型怎么调用工具、Agent 之间/Agent 与宿主之间用什么报文互通函数调用协议、MCP、A2A 一类接口规范工具方与框架方共同遵守
框架层"一次任务怎么被写成代码"——运行循环、状态、工具注册、记忆、中断恢复、权限钩子可 import 的编程库与运行时写应用的工程师
平台层"整套系统怎么被运维与协作"——UI 编排、知识库管理、成本与密钥、审批与审计、监控发布可托管的服务或可自部署的平台非工程师搭建者与平台运维

协议层把接口定成标准，本身不提供任何编排；框架层在标准之上给出编写 Agent 的骨架；平台层再把骨架变成点鼠标就能搭的托管系统。三层的边界不是技术高低的边界，而是"你希望把可变性控制在自己代码里，还是交给上层产品"的边界——协议最底层，锁死最少；平台最上层，交付最快但抽象最深。

框架层真正卖的不是"Agent 能力"，而是六个机制

宣传语总在暗示"用了 XX 框架 Agent 就更聪明"，这是错觉——框架不产生能力，只放大工程。同一个模型套在不同框架里，聪明程度不变；框架间拉开差距的是下面六件事做得多牢：

  • 运行循环：模型调用与工具执行如何交替、何时算结束、失败怎么重试。
  • 状态管理：整段任务的上下文状态放在哪、如何流转、如何持久化。
  • 工具调度：工具如何注册、入参如何校验、结果如何回灌给模型。
  • 记忆与上下文：历史如何截断/压缩、外部记忆如何读写。
  • 中断与恢复：执行能否真正挂起（等人批准、等外部事件）再精确续跑。
  • 可观测与权限：每步决策是否有迹可循、工具与数据访问能否被治理。

读到具名框架时，可以逐个对照它把这几项做到什么程度。判断一个框架"厚不厚"，就看它替你代管了这六项里的几项、代管时留下的自定义钩子有多宽——这也直接决定你将来为"例外需求"写多少绕过代码。

两个清醒点：地图会过时，抽象有成本

框架生态是最善变的软件层：头部项目一年内可能被重写命名空间（AutoGen 从对话 API 演进到事件驱动内核即一例），小项目则可能停更。两条务实态度：其一，把框架当"机制样本"去读，而不是当"API 说明书"去背——理解了它替你做的六件事，换版本换框架时迁移的是心智不是语法；其二，做选型记录并定期复审，写清楚"当初选它换来了什么、锁定了什么"，每半年重读一次，比追最新榜单可靠得多。真正的锁定成本也不在框架本身，而在你写的业务代码依赖了它的哪一层抽象：只用了标准工具循环，迁移成本低；把状态 schema、持久化方案、恢复语义全压在上面，迁移就是重写。

二、LangChain 与 LangGraph：编排思想的"链"与"图"两代实现

LangChain 的原始命题：把 LLM 调用拼成可复用的管道

LangChain 起步要解决的问题很朴素：写 LLM 应用有大量重复样板——接各家模型 API、拼 prompt、解析输出、连向量库。它给的答案是一套组件 + 管道抽象：ChatModel 统一各家模型接口，prompt | model | parser 的链式语法把"模板 → 调用 → 解析"声明成一条管道，并统一暴露同步、流式、批量等标准接口，外围再挂 retriever、tool、memory 等组件。链（Chain）适合流程固定、分支确定的多次 LLM 调用——比如"先总结再翻译再提炼要点"，写成链清晰且好测。

但链在结构上是 DAG，表达不了"让模型自己决定下一步"的循环：Agent 的本质是"决策 → 执行工具 → 观察结果 → 再决策"的自环，不是单向管道。早期 LangChain 用 AgentExecutor 这类高层封装硬塞这个循环，代价是抽象过厚：内部用隐式 Prompt 和魔法字符串控制模型行为，参数一换、模型一升级，Agent 的行为就悄悄变，出了错又很难从黑盒里定位。这也给行业上了一课：高层 Agent 封装把"行为可控性"外包给了 Prompt 和隐式约定，调试成本会成倍转嫁给应用开发者。今天写这类应用，更值得学的教训是把它拆回"显式的循环 + 显式的状态"，这正是 LangGraph 出现的理由。

LangGraph：把 Agent 重写成"带状态的图"

LangGraph 的思路是放弃把循环藏起来，把整个 Agent 显式建模成一张有状态的计算图：

  • 状态（State）：全图共享一份带类型的 state 对象，每个节点读取它并返回增量更新。状态是显式的，任务做到哪一步、积累了哪些中间产物，一眼可查。
  • 节点与边：节点是执行单元（一段代码，或"调模型 + 执行工具"）；边可以是条件边，根据当前状态把执行路由到不同节点，从而自然构成循环和分支。
  • Checkpoint 持久化：每个节点执行完落一次状态快照，让执行变成"可持久化的长跑"——进程崩溃后可从最近的检查点续跑，也可以把历史状态回放出来做调试（time-travel）。这回答了 Agent 上线后"跑到一半挂了怎么办、怎么排查"这类最现实的问题。
  • 中断与恢复（interrupt / resume）：节点可在任意位置把执行真正挂起，序列化状态后退回控制权；外部（人类审批、另一个服务）审核或修改后，再从挂起点精确恢复。这是 HITL 从"对话里问一句"升级为"运行时原语"的分界：对话式问询不保证执行被暂停，模型可能边问边往下跑；interrupt 保证的是执行确实停在边界上、状态一致、恢复点明确，适合放到"下单、删库、发消息"这类需要强审批门的动作前面。

图上还能嵌套子图（subgraph），把多个 Agent 组织成层级协作；一条"执行 → 评估 → 不达标就重跑"的反射流程，也能用条件边直白地画出来。代价也随之而来：图式编排把复杂度前置了——所有可能路径都要先想清楚并画出来，流程频繁变化时改图结构不便宜；state 设计与检查点频率也影响性能和存储成本。所以取舍很清晰：需要精确控制、断点恢复、强审批的确定性流程，图式框架（LangGraph 是其中代表，同思路产品还有 Temporal 式编排与自研状态机）是合适选择；任务高度开放、路径完全不可预知、想用最少代码先跑起来，官方 SDK 那类"自带循环的 runner"反而更省事。

三、LlamaIndex：数据接入与索引优先的框架

它的命题不是"更会编排"，而是"把数据变成可查询的知识"

LlamaIndex 与通用编排框架功能有重叠（也能接模型、也能做 Agent），但它的核心抽象压在一件事上：外部数据如何被接进来、结构化、并针对特定查询模式建索引。它对工程师最大的价值是数据侧的现成工程：几十种数据源的加载器（connectors）把异构文档统一成 Document → Node（含元数据） 的结构化单元，再进入不同索引。

索引抽象的本质："结构即查询策略"

LlamaIndex 最值得理解的设计是把"索引类型"当成一种查询策略选择，而不是"存向量的地方"：

  • 向量索引：适合语义相似召回，问题是只有 TopK 相似，天然回答不了"全局归纳、多跳关系"类问题；
  • 摘要/树索引：把语料按层次聚合成摘要，回答"整库在讲什么"这类全局问题；
  • 知识图谱索引：把实体与关系建成图，支持多跳关系查询，解决向量检索"跨片段推理"的盲区。

选索引前先问查询模式，再选结构，而不是默认"上向量库"。索引之上是查询引擎（Retriever + 后处理 + 答案合成 的组合），它把"检索 → 拼上下文 → 生成"封装成可复用的接口；而查询引擎又能被包装成工具交给 Agent 调用，形成"检索当工具用"的常见形态。框架还内置检索质量与回答质量的评估工具，属于少见的"把评估接口当一等公民"的设计。

边界：数据链路脏时，框架不会替你兜底

LlamaIndex 把"接入到查询"的管道搭好，但它不会把脏数据变干净——切块不合理、元数据缺失、文档本身就是垃圾时，换任何索引与查询引擎都救不回来。它也不以通用 Agent 编排见长：任务主线如果是多工具、多步骤的自主决策而非数据检索，把它当主框架就不如通用编排顺手。务实的用法是各取所长：数据密集的 RAG 部分让 LlamaIndex 负责，把它的查询引擎封装成工具，挂到擅长编排的框架上。

四、OpenAI / Anthropic 官方 SDK：厂商把"推荐运行时"打包给你

共同形态：Agent 就是"模型 + 工具 + 一个内置循环"

图式框架要你亲手画状态与分支；官方 SDK 走相反的路：把"模型决策 → 执行工具 → 结果回灌 → 再决策"的标准循环直接做成内置运行时，把开发者要写的代码压到最少。开发者声明 Agent 的指令、可用工具与模型，runner 替你循环到任务收敛。OpenAI Agents SDK 与 Anthropic Claude Agent SDK 机制骨架一致，差异主要在厂商对运行时的定型重点：

  • OpenAI Agents SDK：以 Agent 对象为核心（instructions + tools + model），Runner 负责执行循环。两个代表性机制值得理解：Handoffs（交接）把一个 Agent 的控制权在能力边界交给另一个更专门的 Agent——实现上是一次特殊的"交接"工具调用，而不是嵌套两个循环，这让分工在结构上很便宜；Guardrails（护栏）在输入进入主 Agent 前、输出返回用户前挂独立校验，把不该放行的内容挡在门外。
  • Anthropic Claude Agent SDK：脱胎于 Claude Code 这套在真实编码任务里打磨过的运行时，特点是把"会话工程"做进运行时：面向长任务提供上下文压缩与续跑（session 持久化、长会话自动整理），并把权限策略做成显式门（对某类操作 allow / deny / ask，ask 即循环真正停下来等用户拍板），辅以工具执行前后的 hooks 让开发者插入自定义逻辑。

取舍：最少抽象的另一面是厂商绑定

官方 SDK 的价值一句话概括：与自家模型同源演进、新能力第一时间可用、抽象层最薄——调试时看到的就是真实的调用与报文，没有中间层替你做决定。它是"以单一厂商模型为主、不想多垫一层、信任厂商把循环调到最稳"时的默认选择。代价同样明确：

  • 运行时与模型深度绑定，换模型几乎等于换运行时。交接、护栏、权限、压缩这些机制都是围绕该厂商模型定制的，跨厂商复用度低。
  • 官方 runner 是"好用的既定循环"，不是"可任意裁剪的编排画布"。流程需要精确多分支状态机、或要把某一步换成自研调度时，在图式框架上改更容易。
  • 两者因此不是竞争而是取向差异：前者默认"循环已足够好、别让我操心"，后者假设"循环只是起点、我要亲手接管"。折中做法也常见：以官方 runner 为主干，只在关键动作上通过权限/hook 语义插入人工审批与续跑——让"人等审批"成为运行时契约的一部分，而不是对话层的口头确认。

五、AutoGen 与 CrewAI：多 Agent 协作的两种取舍

AutoGen：对话式起步，事件驱动内核托底

AutoGen 的成名形态是对话式多 Agent：多个 Agent 像群聊一样轮流发言协作解决任务（经典的 UserProxy + Assistant 配对、由管理者分配发言权的 GroupChat）。把协作建模成对话，好处是角色只需用 System Prompt 区分、搭建极快；坏处是决策轨迹是隐式的——谁该插话、何时该停，很大程度靠模型临场发挥，确定性与可审计性差，token 消耗高。

AutoGen 随后的演进给出了双层架构：上层保留对话式 API 方便快速搭建，下层换成事件驱动的运行时内核（Agent 是收发消息的 actor，传输层可插拔）。这个分层本身就是值得抄的架构示范：高层 API 负责"写得快"，低层内核负责"跑得稳、接得住自定义"。理解 AutoGen 别只停留在"能聊天协作"，它的真正贡献是证明了对话协作只是多 Agent 的一种实现，不是唯一形态——要上生产，把业务从对话层下沉到事件层、自己控制消息流，才是可控的路径。

CrewAI：把协作包装成"组织分工"的项目结构

CrewAI 把多 Agent 协作组织化成直观的角色分工：定义 Crew（团队），给每个 Agent 设 role/goal/backstory（岗位），把任务拆给角色，再用 Process 决定协作方式——顺序执行（一个角色干完传给下一个）或层级执行（manager Agent 动态分配任务），另有 Flows 提供事件驱动流程、记忆组件辅助角色回忆。相比画图，这种抽象让"任务像项目一样被拆解"的上手门槛低很多。

代价在于：角色的靠谱程度被押在 Prompt 与分工设计上，框架本身不提供角色间协调的强保证——某个角色理解偏了、产出质量差，下游会照单全收；角色增多后，沟通开销、token 与错误传播非线性上涨。所以角色化抽象适合把"组织化任务"快速跑成原型，但要当生产编排层用，质量闸门与审计必须自己补。

横向对比与一个共同陷阱

框架取向编排模型状态与恢复上手成本适合阶段
图式框架（LangGraph 等）显式状态图 + 条件边强：checkpoint / 续跑 / interrupt高确定性流程，生产化
官方 Runner SDK内置循环 + 交接/护栏中：会话级持久化低单模型应用快速落地
对话式多 Agent（AutoGen 高层）群聊式轮流发言弱：依赖对话记录低原型验证
角色式多 Agent（CrewAI）角色分工 + 顺序/层级中：自带记忆低组织化任务原型
事件驱动内核（AutoGen Core 类）消息驱动 actor中到强：取决于实现高需自定义的多 Agent 生产形态

贯穿这些取向的高频陷阱只有一个：用多 Agent 解决单 Agent 的事。多 Agent 换来的是并行、专业分工与角色上下文隔离，代价是复杂度、成本与不确定性整体上移。要不要上多 Agent，得先有单 Agent 失败的证据（上下文互相污染、需要并行执行互不干扰的子任务、单一上下文装不下多个专业角色），而不是为了架构好看。另一个隐蔽坑在对话式高层 API 上：看似在协作，实则把大量决策交给模型临场发挥，改一次 Prompt 整个"团队行为"就会漂移——从原型迈向生产时要主动下沉到更可控的底层，而不是继续在对话层叠 Prompt。

六、低代码平台：把默认路径交给画布，把例外路径留给代码

平台层的共同机制

低代码平台是三层地图里的最上层：把"框架 + 托管 + 协作"打包成可视化产品。它们的共同机制是——画布式编排（节点即模型调用、工具、知识检索、条件分支）、内置知识库与数据接入、一键发布为对话应用或 API、平台统一管密钥/成本/日志/权限。工程团队看待它们的位置应当是"一套内置了运行时与运维的受限编排器"，而不是"写代码的对立面"。

三个代表性产品的定位差异主要在闭环程度与集成半径：

  • Dify：开源、可自部署，主打 LLMOps——应用编排 + 知识库 + 工作流，可发布 API。对需要数据不出域、要自托管的企业是最常被选的那一类。
  • Coze：字节系的闭环平台，强在插件生态与渠道集成（发布到 IM、小程序等），Bot 商店让分发路径现成；换来的是自定义能力与私有化受平台约束。
  • n8n：本质是通用工作流自动化（集成编排），几百种外部系统的节点（webhook、OAuth、数据库）是它的主场，AI/Agent 节点只是其中一类——强项是把 LLM 步骤嵌进企业既有自动化链路，而非只做对话应用。

边界：什么时候该写代码

判断标准不是"会不会写代码"，而是你的需求落在平台"默认路径"内还是外：

  • 默认路径内的需求：常见模型 + 常见工具组合、知识库问答、流程固定、需要 UI 与运维省心、需要快速接多个渠道 → 平台合适，尤其是团队里有非工程师成员或要一周内出可演示产物时。
  • 超出默认路径的需求，就该回到代码。高频触发条件包括：需要细粒度权限与审计（平台策略模型兜不住）、需要自定义上下文工程（自己的压缩/记忆/检索后处理策略）、要把 Agent 嵌进自有状态机与领域事务、需要版本化回归评估与灰度发布的 CI 语义、需要自定义工具沙箱与网络隔离、以及需要 interrupt/续跑这类精确恢复语义而画布算子集里没有。
  • 反例要特别警惕两类：其一，"画布就是有限算子集"——复杂控制流在可视化里要么表达不出，要么画成意大利面，调试难度远超同等代码；其二，迁移锁定——从平台导出的一般只是该平台格式，业务逻辑、权限、运维全在平台上时，"换"几乎等于"重写"。平台加速了前 80% 的搭建，剩下 20% 的例外往往要花 10 倍力气去绕过——所以选平台前先确认例外需求的比例，而不是被演示视频打动。

七、国产与场景化框架：Qwen-Agent、MetaGPT 的机制启发

具名产品可能更新，讲机制更耐久。这一梯队有两个方向值得拆开看：

  • Qwen-Agent（阿里系）代表"模型 + 运行时垂直整合"的方向：围绕 Qwen 模型族提供代码解释器（在沙箱里写代码执行）与浏览器类工具等一等能力，目标是让"模型、工具执行、联网、部署与合规"在一个体系里闭环。它对国内工程环境的启发是：当应用必须部署在境内云、模型必须是国产合规模型时，与其跨多个开源组件拼装，不如接受一个把模型与运行时绑定的全家桶——用厂商一致性换组装自由。
  • MetaGPT 代表"SOP 驱动的多 Agent 流水线"方向：把软件开发拆成需求→设计→编码→测试的标准作业流程，每个角色产出结构化文档/代码，下游读取上游的"产物"而非自由对话。这个机制的启发比产品本身值钱：多 Agent 通信质量差，根源常是聊天式消息太随意；用带格式的产物做角色间交接，能把噪声和歧义压下去。适合能被"剧本化"的任务（软件工程类最典型），对完全开放的任务则受制于上游产物质量。

除此之外还有大量"知识库 + 工作流 + 对话"一体化的中文场景产品（如 FastGPT 一类），机制大致相同：把 RAG 的常用路径与对话 UI 打包成可私有化部署的盒子，适合中小团队快速做内部知识助手。选这类框架的反例只有一条：拿"是否国产/是否热门"当选型依据，而不看机制是否匹配。开源界常出现"套壳 LangChain 早期 API"的替代品，维护与更新滞后——评估时同其他框架一样看三件事：核心机制、活跃度与版本演进、以及它锁定了你的哪些数据与部署形态。

八、选型决策树：先定义你真正要解决的"变化点"

把这些具名产品当成"机制样本"后，选型就能去掉品牌噪声，变成对三个问题的顺序回答。

第一问：任务主线是什么

主线决定首选层的方向，先把这一个问题答对，答案自然会收敛：

  • 流程相对确定、要精确控制、要断点恢复与强审批（业务编排、需要"执行到一半等人拍板"）→ 图式框架（LangGraph 一类）。
  • 主线是数据接入与检索（企业文档问答、多知识源查询）→ 数据优先：LlamaIndex，或自带知识库的低代码平台；注意检索在这里是手段不是目的。
  • 以单一厂商模型为优先、要最少封装与最新特性 → 官方 SDK。
  • 任务是明确的多角色分工协作，且你能举出单 Agent 失败的证据 → 多 Agent 框架，并按确定性需求选择形态：原型用对话/角色层，生产下沉到事件驱动或图式。
  • 团队含非工程师、一周内要可演示、渠道与知识库组合常规 → 低代码平台。
  • 境内部署 + 国产合规模型 + 强数据约束 → 国产垂直整合型全家桶优先于跨组件拼装。

第二问：工程约束是否会砍掉候选

框架选型先于部署形态想，几乎必然返工。约束按优先级过一遍：私有化/数据不出域会直接排除纯 SaaS 平台；既有基础设施（向量库、消息队列、监控、服务网格）决定你该选"能接入现有件的代码框架"而不是"自带一套的平台"；需要 CI/回归评估/灰度则要求运行时可编程、可挂评估钩子，平台与对话式高层 API 天然吃亏；合规审批审计要求权限模型与审计日志可见，框架层的钩子宽度决定这事能不能落地。

第三问：对候选跑一遍"六问体检"

选定一两个候选后，用贯穿本章的六个机制逐一提问，任何一项答不上来或需要大量绕过代码，都是红灯：

  1. 状态与恢复：进程崩溃后任务从哪继续？状态 schema 是你可定义的吗？
  2. 中断与审批：HITL 是"对话里问一句"还是真正的挂起/恢复原语？恢复点精确吗？
  3. 工具扩展与审计：新增一个工具要动几处代码？工具调用有留痕吗？
  4. 上下文与记忆：压缩/截断/外部记忆策略能自定义，还是被写死？
  5. 可观测与评估：单步决策能否追踪？能不能接入回归评估？
  6. 升级与迁移：你的业务代码钉在它的哪层抽象上？升级会不会破坏它？

别忘了决策本身要留痕、要定期复审——框架生态一年一变，当初的取舍理由要写下来，半年后重读一遍再决定要不要动。选型输出的不是"某个框架"，而是一句话的取舍记录：我为了换取哪几项机制的成熟，接受了它的哪层抽象与锁定。

九、手写一个极简 Agent：看懂框架在替你写什么

放下框架，先把"一个 Agent 运行起来的最小骨架"写出来。给定模型与工具后，骨架其实只有四件事：一条消息列表当状态、一张能按名执行的工具表、一个"决策 → 执行 → 回灌"的循环、一组终止与护栏条件（步数上限、审批门）。

"""极简 Agent 骨架：模型 + 工具表 + 消息列表 + 一个循环。
刻意不引入任何框架，只保留运行所需的最小结构。"""
from typing import Callable

# ---- 1. 工具注册表：工具调度的最小形态 ----
TOOLS: dict[str, tuple[str, Callable[[dict], str]]] = {}

def register(name: str, desc: str):
    def deco(fn: Callable[[dict], str]) -> Callable[[dict], str]:
        TOOLS[name] = (desc, fn)
        return fn
    return deco

@register("calc", "计算四则运算，入参 expr")
def calc(args: dict) -> str:
    return str(eval(args["expr"]))          # 仅演示；生产应换成安全沙箱

@register("search", "检索内部知识库，入参 query")
def search(args: dict) -> str:
    return f"<知识库片段> 命中 {args['query']}（模拟）"

# ---- 2. 模型调用：伪代码，实际是请求推理端点 ----
def call_model(messages: list[dict]) -> dict:
    """返回两种形态之一：
      {"kind": "final", "content": "..."}   收敛，输出最终答案
      {"kind": "tool", "name": ..., "args": {...}}  请求执行工具
    与真实端点的交互细节此处省略。"""
    raise NotImplementedError

# ---- 3. 循环主逻辑 ----
def agent_loop(user_input: str, max_steps: int = 8) -> str:
    messages = [{"role": "user", "content": user_input}]   # 状态 = 消息列表
    for _ in range(max_steps):                              # 护栏一：步数上限
        decision = call_model(messages)                     # 1. 决策
        if decision["kind"] == "final":
            return decision["content"]                      # 护栏二：模型收敛即止
        name, args = decision["name"], decision["args"]
        if name not in TOOLS:
            messages.append({"role": "tool", "name": name,
                             "content": f"错误：未知工具 {name}"})  # 错误回灌
            continue
        try:
            result = TOOLS[name][1](args)                   # 2. 执行工具
        except Exception as exc:                            # 异常也回灌给模型
            result = f"工具异常：{exc}"
        messages.append({"role": "tool", "name": name, "content": result})
        # 真正的 HITL 应发生在这里：把执行挂起、序列化状态，
        # 等人审批后再从断点续跑；而不是在对话里口头问一句。
    return "达到最大步数仍未收敛"                             # 护栏三：预算耗尽

对照这个骨架，前面所有框架的抽象就都有了落点：

  • 手写循环最写不牢的地方在边角：进程崩溃续跑、并行工具调用、流式输出、工具间并发一致性。LangGraph 的 checkpoint 与 interrupt，正是把"循环 + 挂起/精确续跑"补成可靠原语——骨架里那段审批注释只是玩具，图式框架让"停在哪、从哪继续、状态是否一致"变成可保证的语义。
  • 消息列表是裸状态：上下文超长时的压缩、会话持久化、用户间隔离都无人管。官方 SDK 把这一层做成 session 与上下文管理，省掉的是"自己维护一套消息生命周期"的活。
  • 工具注册表只管"能按名执行"：入参校验、权限策略、审计留痕、沙箱隔离都缺席。框架与平台各自在不同深度补这层，而如果你的场景确实不需要它们，裸工具表反而更干净。
  • call_model 那一行伪代码背后藏着流式、重试、限流、成本统计——厂商 SDK 把这"一行"做成了最扎实的运行时。
  • 想让 search 这个工具从模拟变成真实检索，LlamaIndex 补的就是数据接入、切块、索引与查询引擎那一整套；协作角色一多，MetaGPT 式的"传结构化产物而非随意对话"解决的则是消息本身该长什么样。

于是全章收束成一句话：框架的价值 = 它把"循环、状态、恢复、审批、审计、上下文"这些你自己写容易写错、写不牢的边角做扎实的程度；框架的成本 = 你的业务代码钉在它抽象上的深度。手写极简骨架的目的不是让你复刻框架，而是让你保有"退回自己写"的判断力：当某层抽象开始挡路时，你看得懂它在替你做什么，也就知道该在哪里绕过它、或直接接管它。带着这把尺子去评估任何新框架——无论它叫什么名字——都能很快判断它值不值得进你的技术栈。
