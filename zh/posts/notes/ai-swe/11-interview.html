AI 应用开发高频面试题

vexillium2026/9/7大约 25 分钟后端开发人工智能

一、面试题

1. Agent Loop 的双循环怎么设计的，外循环和内循环分别负责什么？

答：Agent 的双循环是任务级与步骤级的双层嵌套结构。外循环是任务循环，负责整体任务的规划与收敛：接收任务、拆解成子任务、调度执行、校验结果，决定重试、回滚还是结束，持有全局状态和目标。内循环是执行循环，负责单个子任务的执行与修正：典型实现是 ReAct，即 Thought、Action、Observation 循环，直到子任务完成，负责工具选择、参数生成、结果解析和单步重试。设计成双循环的原因：内循环高频、快失败、即时修正，保证单步正确率；外循环低频、有全局视图，保证任务不跑偏。两者通过状态解耦，内循环失败后外循环可以换策略重试，而不是从头再来。实现上要注意：内循环要设最大迭代次数防止死循环，外循环要设重试预算防止成本失控，内外循环状态需要持久化以支持断点续跑。

2. Agent 的权限控制怎么做？如何约束 Agent 对高风险操作的行为？

答：核心原则是最小权限、分级审批、全程审计。权限分层：只读操作默认放行；写操作如修改文件、写库需要策略允许或提示；高风险操作如执行命令、删除、网络请求、支付默认拒绝，必须显式授权。具体实现机制：工具级 ACL，每个工具注册时声明所需权限，调度层调用前做匹配校验；策略文件，把允许、询问、拒绝规则化，比如 Claude Code 的权限配置；Human-in-the-loop 门禁，高风险调用前暂停等人工确认；执行环境隔离，用容器或沙箱运行，即使 Agent 越权影响也可控；Hooks 拦截，工具调用前后挂校验脚本，PreToolUse 校验参数，PostToolUse 校验副作用。约束高风险行为还有几个工程手段：参数校验，禁止危险路径、限制路径白名单；操作可回滚，执行前备份；临时凭证按任务发放用完即回收；审计日志记录谁在什么会话做了什么。

3. Agent的上下文管理，怎么做压缩和裁剪的？Claude Code 怎么做的？

答：上下文管理的目标是在窗口有限的情况下保留最关键信息，手段分为压缩和裁剪两类。压缩是浓缩而不是丢弃：摘要压缩，把早期对话递归总结成摘要保留要点；提示压缩，用专门的压缩模型剔除与任务无关的 token；结构化提取，把对话转成决策、结论、待办等结构化要点。裁剪是按策略丢弃：滑动窗口只保留最近 N 轮；token 预算按角色和消息重要性打分，超预算按优先级裁剪；LRU 或时间衰减淘汰不常用的内容。Claude Code 的做法：会话接近上下文上限时自动压缩，把早期对话总结成摘要后继续，支持 --continue；提供手动 /compact 命令；把长期事实写入 CLAUDE.md 和项目记忆文件，避免反复注入。设计原则：压缩发生在缓存边界之外的位置，避免破坏 prompt 前缀缓存；每轮记录 token 占用提前预警；原始消息和摘要双轨存储，需要精确信息时还能从外部存储取回。

4. 什么是 Harness？讲讲思想，还有 Agent 中怎么去实现？

答：Harness 直译是缰绳或鞍具，指的是模型能力之上、业务逻辑之下的一层运行时外壳，把裸模型、工具、记忆、策略、观测组装成可以安全使用的 Agent，本质是 LLM 的工程化封装层。核心思想：模型只负责决策，Harness 负责行动，工具调用、文件读写、网络请求都由 Harness 兜底执行并返回结果；安全可控，权限、沙箱、审计都在 Harness 层完成，模型绕不过去；可观测，所有推理和工具步骤被记录；能力外接，把模型不具备的实时数据、代码执行、系统 API 以工具形式注入；模型无关，同一个 Harness 可以换不同模型后端。DeepSeek 的 Agent 计划里强调 Harness 是模型推理能力与世界之间的桥梁。实现要点：模型适配层统一接口并抽象出工具调用；工具注册表负责 schema 管理、路由、参数校验、错误规范化；上下文引擎负责消息组装、历史管理和压缩裁剪；策略引擎负责权限、最大迭代、成本预算和人工审批；执行环境负责沙箱和进程隔离；观测管道负责结构化日志、轨迹和指标。LangGraph 提供的是 Harness 的流程骨架，Claude Code 是 Harness 思想的成熟产品化实践。

5. 如果 MCP 工具（SKILL）过多，如何让 Agent 检索的效率更高？调用工具的准确性更高？工具过多怎么优化上下文窗口的占用？

答：这个问题拆成三个层面：召回、路由、压缩。提升检索效率：用工具选择器，把工具描述做 embedding，用户意图做向量检索，只把 Top-K 工具注入上下文；两级路由，先让模型判断任务域，再在域内细选；工具分组和命名空间，比如 docs:search、code:edit 这种结构化命名利于检索。提升调用准确性：写高质量 description，说明何时用、何时不用、输入格式和边界，冲突工具在描述里互相排除；参数 schema 精简并用 enum、format 约束；给 few-shot 示例，展示什么问题选什么工具；失败反馈闭环，把调用失败原因写回上下文让模型下次选对。优化上下文占用：渐进式加载，不一次性注入全部 schema，按需加载，常用工具常驻、冷门工具检索后再加载；schema 瘦身，省略冗余描述、合并参数；工具定义放稳定前缀以复用缓存；工具结果截断，长结果只保留摘要或关键字段。核心权衡：工具全量注入准确率高但占窗口，渐进式加载省 token 但多一跳路由还可能破坏 KV 缓存。一般按数量分档，少于 20 个全量注入，20 到 50 个按域分组注入，超过 50 个必须检索注入。

6. 有没有对 Token 的消耗做过一定的优化？怎么做的？

答：做过，主要在三个方向。Prompt 侧：压缩指令措辞；few-shot 少而精；固定前缀复用 provider 的 prompt caching，缓存命中价格更低。上下文侧：历史转摘要；工具结果裁剪只保留关键行，超长结果落盘给引用路径；RAG 的 Top-K 动态化，简单问题少检索。推理侧：模型路由，简单任务用小模型、复杂任务用大模型；用 JSON schema 约束结构化输出减少废话；限制 max_tokens 防止模型输出过长；语义缓存，相似请求直接命中不重复调用。配套的是监控，对每次调用的输入输出 token 和成本埋点，异常暴涨告警，并给单会话设 token 预算上限。

7. CLI 和MCP 之间有什么区别？你怎么做选型的？

答：CLI 是进程内直接调用的可执行程序，MCP 是标准化的 Client-Server 协议。CLI 的优点是实现简单、无协议开销、调试直观可以直接在终端试；缺点是缺乏标准能力描述，Agent 难以自动发现和编排，跨语言跨平台复用差，远程调用要自己包装。MCP 的优点是能力声明标准化，Tools、Resources、Prompts 三要素，跨模型跨客户端复用，支持 stdio 和远程 HTTP+SSE 传输，生态丰富；缺点是有协议和序列化开销，实现复杂，调试依赖 MCP 工具。选型：只在单应用内部使用选 CLI；需要跨应用、跨 Agent 复用、对外提供服务选 MCP；需要远程标准接入选 MCP。实践上常组合，CLI 工具作为底层能力，外面包一层 MCP Server，一个 Server 封装多个 CLI，既拿到 CLI 的简单可靠，又获得 MCP 的标准接入。

8. MCP 网关和传统的后端网关有什么区别？需要多关注什么问题？

答：两者都做路由、鉴权、限流、观测，但关注点差异很大。协议上传统网关是 HTTP、gRPC、REST，MCP 网关是 JSON-RPC，需要协议转换和桥接；路由对象上传统网关是 API 端点，MCP 网关是工具和资源；能力管理上传统网关是静态路由表，MCP 网关要动态发现、聚合多个 Server、做 schema 合并去重；鉴权粒度上传统网关是应用或用户级，MCP 网关要精确到工具级，不同工具不同权限；数据面传统网关是请求响应，MCP 网关有 SSE 长连接和双向推送；另外 MCP 网关对模型有感知，要把工具描述注入 LLM 上下文，还要关心 token 成本。MCP 网关要特别关注的问题：多个 Server 提供同名工具的 schema 冲突，需要用命名空间、别名或冲突策略；工具级鉴权与审计，敏感操作必须留痕；超时与幂等，工具调用可能很慢或者有副作用不能重放，需要超时策略和去重；提示注入防护，工具返回的不可信内容可能污染模型；成本控制，网关是 token 消耗的汇聚点，要做预算和配额；流控，SSE 长连接数量、背压、并发限制。

9. Agent 出现幻觉的话，怎么优化？

答：幻觉是模型生成与事实或上下文不符的内容，从输入端、生成端、输出端全链路治理。输入端：RAG 检索增强给出可核对的依据，上下文只放高置信度内容，把引用来源直接拼进 prompt。生成端：指令约束，要求不确定就明说不确定，禁止编造、只能基于给定上下文回答；用 JSON Schema 约束结构化输出减少自由发挥；降低 Temperature；用 CoT 或自我反思让模型先推理再下结论。输出端：做 Grounding 校验，答案里的关键事实必须在上下文中能找到证据，找不到就拒绝回答或标注未证实；代码类任务直接跑测试验证，数值类任务用工具验证；高风险场景强制人工审核。还要建立评估闭环，构建事实一致性的评测集，上线前回归、上线后抽样，用 LLM-as-Judge 检测答案对检索文档的忠实度。如果幻觉高频，按链路排查：检索质量、上下文组织、提示约束、基座模型能力，逐层定位根因。

10. 如何提升 Agent 的缓存命中率？渐进式加载工具或技能会不会导致KV 缓存失效？

答：LLM provider 的 prompt caching 是前缀匹配，请求开头一段 token 完全一致时，这段的 KV 可以被复用。提升命中率的方法：把稳定内容放最前，系统提示、工具 schema 全量按固定顺序放在前缀；动态内容追加在后，对话历史和检索片段只追加不修改，旧消息绝不能改；工具定义顺序固定、描述不随会话变化；同一会话的请求尽量共用同一前缀。渐进式加载会导致 KV 缓存失效。因为工具定义位于稳定前缀中，第二次请求注入更多工具就改变了前缀，前缀缓存全部失效，失效后重算长前缀甚至比不缓存更贵。缓解方案：分两层，稳定层放全部工具 schema 但压缩到极简，只留名字和一句话描述，动态层把详细描述和示例按需追加到对话尾部；或者用固定插槽预先占位，新增工具只填占位位；务实做法是接受冷门工具加载时失效一次，把高频工具长期固定在前缀，用缓存命中率和失效次数统计来动态决定哪些工具常驻。一句话总结：渐进式加载省的是 prompt token，赔的是前缀缓存，要做的是把加载动作控制在缓存边界之外，或者用缓存统计决定常驻集。

11. 怎么评估 Agent 效果的好坏？Agent 上线之后遇到过什么问题？

答：评估分几个维度。任务成功率是端到端完成率，通常用 Pass@k，同一任务跑 k 次；执行效率看工具调用次数、重试率和步数，越少越好；成本看 token 消耗、单任务成本和延迟 P50、P95；安全性看越权操作次数、敏感信息泄漏、破坏性命令触发率；质量看输出正确性和用户主观评分。评估方法：构建 Golden Set 评测集，覆盖典型、边界、失败场景；用 LLM-as-Judge 强模型打分，配合人工抽检校准；做轨迹评估，不只评结果还评过程，看有没有绕路或滥用工具；每次改动后跑回归测试，防止修一个 bug 坏三个功能。上线后常见问题：工具调用不稳定，选错工具、参数格式错，靠加强描述、few-shot 和失败反馈解决；上下文超限和成本失控，靠压缩和预算上限；模型升级后行为漂移，需要固定版本和回归评测；安全事件比如误删和越权，靠权限收紧和沙箱；长尾任务失败，评测集没覆盖，要把生产日志回流打标扩充评测集。

  1. 场景类问题：让你设计一个写 PPT 的SKILL，你会怎么设计？

答：按拆解任务、定义工具、设计流程、质量闭环来设计。输入定义：主题、受众、篇幅页数、风格偏好、参考素材。工具清单：大纲生成，输出标题、分节、要点和备注；渲染工具，把结构化内容渲染成 PPT，比如 python-pptx 或幻灯片服务；配图生成，AI 生图注意尺寸和版权；模板应用，套用配色字体版式；质量校验，检查页数、字数、图片存在性和内容溢出。执行流程：先规划，分析主题和受众生成大纲；再逐页生成结构化内容，标题加三到五条要点加演讲备注，一页一主题控制信息密度；然后渲染，模板化渲染、图表用数据可视化、关键页配图；最后校验，逐页检查溢出、错别字、数据一致性，超页数自动合并；支持对单页局部修改重渲染，不必整份重做。质量原则：每页不超过五条要点，用短语不用长句；数字和结论必须有来源；风格统一；输出演讲备注，而不是把正文堆进幻灯片。设计核心是把内容创作和视觉呈现分离，LLM 产出结构化数据，渲染器负责排版，避免让模型直接生成格式脆弱的文本。

13. 开放类问题：Pi Agent 的设计哲学，DeepSeek Harness 的设计哲学？不同Agent 之间的区别？优势？

答：开放题没有标准答案，考察的是对 Agent 系统的整体认知和设计品味，可以按框架回答。先给分析框架，从五个维度拆解任意 Agent：决策与执行边界，模型决策自主还是框架流程主导；上下文管理，全量注入还是渐进加载，怎么压缩和缓存；安全策略，权限模型、审批流、沙箱强度；能力扩展，工具、Skill、MCP 的组织方式；可观测与评估，轨迹记录和评测体系。然后举例对比。Claude Code 的哲学是深度融入开发环境，读写文件、执行命令、Git 操作一体，用 Hooks 做安全门禁，CLAUDE.md 注入项目规范，Skills 封装可复用流程，优势是工程开发场景开箱即用、MCP 生态丰富。DeepSeek Harness 的哲学是模型推理能力与世界之间的桥梁，把推理、工具、检索、记忆编排成可插拔的 harness，重视长上下文和缓存优化、成本控制，优势是推理能力和成本。AutoGen 和 CrewAI 的哲学是群体智能，多角色对话或角色扮演协作，优势是任务分解与协作。不同 Agent 的差异本质是面向场景不同：单智能体工具型适合代码和办公，多智能体协作型适合研究和流程编排；控制粒度不同，LangGraph 细粒度可控但复杂，Claude Code 开箱即用但定制受限；成本模型不同，自研 harness 可以深度优化 token 和缓存，现成框架上手快但可能浪费 token。收尾给出结论：选型是场景、团队能力、成本三者权衡，先用最小可行验证，再决定自研还是用框架。

14. Agent 的长期记忆和短期记忆怎么设计的？长期记忆存在冲突怎么办？

答：短期记忆就是当前上下文窗口内的内容，设计上是一份带 token 预算的消息列表，配合压缩裁剪，按角色标记 system、user、tool 结果，特点是快准但易失。长期记忆存用户偏好、项目事实、历史决策、学到的技能。存储介质按类型选：向量库存语义可检索的事实；KV 或数据库存结构化偏好，比如时区配置；知识图谱存实体关系，适合多跳；文件或笔记存人可读可审计的内容，比如 CLAUDE.md。写入策略：重要的跨会话信息才记，写前去重，带时间戳和来源；检索策略：相关性召回加置信度过滤，会话开始主动加载核心事实。长期记忆冲突的处理：写前做相似度检测识别矛盾，然后按优先级处理。时间优先，新事实覆盖旧事实；显式确认，矛盾时问用户，之前你说过什么，现在要改成什么；分级保留，置信度高的压过置信度低的；无法判定时共存并标注来源和场景，检索时都返回让模型判断。关键原则是永远不静默覆盖，冲突解决要留痕可审计。

15. Agent 的历史记忆怎么做淘汰策略？

答：淘汰目标是在有限空间里保留未来最可能用到、信息价值最高的记忆。常见策略：按 token 预算滑动窗口，只保留最近 N 轮，是最常用的兜底；按重要性打分，决策结论高于中间推理高于寒暄，低分优先淘汰；按时效衰减，旧信息降权，但长期事实类不衰减；LRU 或 LFU，访问频率低的淘汰，适合工具使用习惯这类；摘要替代最推荐，不是删除而是把一批旧记忆压缩成摘要保留，细节丢失但要点还在，实现无损降级。配套做分层存储：L1 工作集存最近和高频，放上下文内；L2 近时记忆存本周内容，放结构化存储可按需检索；L3 归档存不常访问但重要的，放文件或向量库按需召回。触发时机是达到 token 阈值、会话切换或定期异步整理。淘汰策略上线后要对比召回命中率，避免把真正重要的记忆淘汰掉。

16. 如果有多个 Agent 进行协作，不同 Agent之间的通信是怎么做的？

答：有三种主流通信模型。消息传递，Agent 之间直接收发结构化消息，典型是 AutoGen 的对话式交互，适合讨论、质疑、迭代；共享状态或黑板，所有 Agent 读写同一个 State，典型是 LangGraph 的全局 State，适合分工写同一份产物；编排器模式，主 Agent 派任务收结果，子 Agent 之间不直接通信，适合任务分解型场景，比如代码生成和研究。消息设计要用结构化消息，包含 from、to、type、task、payload、refs 字段，用 JSON Schema 约束；内容带任务指令、上下文引用，传 ID 或路径不传全文，带期望产出格式；带回执语义，结果、错误、进度，便于编排器决策。工程问题：进程内走内存，跨进程走消息队列，比如 Kafka 或 Redis PubSub；子 Agent 卡死要有超时熔断；失败消息进死信队列由编排器重派；上下文隔离，子 Agent 只拿自己需要的上下文，防止共享窗口爆炸，这是多 Agent 的核心优势；安全上子 Agent 之间有信任边界，敏感操作统一走编排器审计。

17. RAG 怎么做分片？向量数据库的选择，原理？了解 Graph RAG吗？

答：分片策略的选择取决于文档类型和检索粒度。固定字符加 overlap 是通用兜底；递归切分按标题和代码结构，适合技术文档；语义切分按句子向量相似度断点，适合长文章；父子分块用小块检索、大块送 LLM，兼顾召回率和上下文质量。参数心得：chunk_size 取决于检索单元粒度和 LLM 上下文预算；表格和代码要整块保留防止切断；多级索引比单一切法灵活。向量数据库选型：FAISS 是内存库，快且轻，适合单机和原型；Milvus 分布式、支持亿级和过滤，适合大规模生产；Qdrant 用 Rust 实现、过滤强、API 友好，适合中等规模需要复杂过滤的场景；Chroma 轻量、Python 友好，适合原型和小项目；pgvector 是 PostgreSQL 插件，有事务一致性，适合已有 PG 生态需要 SQL 联合查询的场景。原理：向量化后相似度就是向量距离，用余弦、内积或 L2；大规模用 ANN 近似最近邻，HNSW 是分层跳表式图索引，查询快但内存高；IVF-PQ 是倒排聚类加量化压缩，省内存但精度略降。Graph RAG：先对文档做实体和关系抽取构建知识图谱，检索时从命中实体沿图扩散多跳邻居，再聚合生成答案。和传统 RAG 的区别是检索粒度从局部文本块相似度变成实体加关系网络，擅长多跳推理和全局聚合性问题，比如总结所有方案；但图谱构建贵，需要 LLM 抽取，延迟高。选型建议：单点事实问答用传统 RAG 就够，需要跨文档关联或全局综述时上 Graph RAG，也可以混合，向量召回加图扩展。

18. Agent 的自进化，自我学习了解吗？

答：自进化是指 Agent 从自己的经验中持续改进，而不是每次从零开始。主流技术路线：Reflexion，失败后反思，把错在哪、下次怎么做写入记忆，后续回合加载，实现跨 episode 改进，是最简单实用的；Self-Refine，一次生成后自我批评再修正，迭代到质量达标；从轨迹学习，收集成功轨迹做成 SFT 数据微调模型，提升工具使用能力；可验证奖励强化，数学和代码这类可自动判分的任务用 verifiable reward 做 RL，模型自我提升推理，类似 R1 的自我训练；LLM 合成数据回炉，用强模型生成数据、过滤后训练弱模型，不断循环。落地注意事项：当前主流是半自动闭环，失败样本回流、人工打标、定期微调或更新记忆，不要盲目全自动；防 reward hacking，奖励函数被钻空子，比如只求通过测试不写正确逻辑；防分布漂移和遗忘，自学习要保留原始能力，回放旧数据；评估先行，每次进化都要回归评测。

19. Agent的可观测怎么做？都做了什么？

答：可观测是日志、轨迹、指标三件套，围绕 LLM 调用和工具调用展开。记录内容：LLM 调用记录输入输出、token 数、延迟、模型版本、采样参数；工具调用记录工具名、参数、截断后的结果、耗时、错误、重试次数；决策轨迹记录每一步思考、路由结果，为什么选这个工具；会话维度记录 session_id、任务、成本累计、上下文占用曲线。工具：LangSmith、Langfuse、W&B Weave、Arize Phoenix，大厂常自建以控制数据不出网。关键指标：任务成功率、平均步数、工具错误率、token 和成本、上下文利用率，接近上限要预警、缓存命中率、幻觉检测分数。实践细节：结构化日志 JSON 全量落盘，支持按 session、工具、模型检索回放；会话回放最重要，能按时间轴重放一次任务的完整轨迹，是排查 Agent 问题的主要手段；告警覆盖成本突增、连续失败、越权尝试；安全审计对敏感操作完整留痕，谁、何时、调了什么、效果如何。

20. 模型的 Temperature,Top-k，Top-p 有什么用？

答：三者都控制解码的随机性和多样性，作用在 Softmax 之后、采样之前。Temperature 缩放 logits 再 Softmax，T 越小分布越尖锐、输出越确定，T 等于 0 就是贪婪解码取最高概率 token；T 越大越随机，是整体锐度控制器。Top-k 只从概率最高的 k 个 token 中采样，其余置零，是硬性截断，防止长尾低概率 token 干扰；缺点是 k 固定，分布平坦时截断过多、尖锐时截断过少。Top-p 也叫核采样，从累积概率达到 p 的最小 token 集合中采样，集合大小动态自适应，分布尖锐时集合小、分布平坦时集合大，比 Top-k 更灵活。配合关系：常用组合是 temperature 0.7 加 top_p 0.9，两者可以同时用，先 Top-k 截断再按 Top-p 收缩，也可以只用其中一个。任务建议：事实、代码、结构化输出用低 temperature 甚至贪心；创意写作用 0.8 到 1.2；Agent 工具调用对一致性要求高，temperature 调低避免 schema 输出飘。

21. AGENT.md 和 SKILL 文件的区别？

答：AGENT.md 也叫 CLAUDE.md，是项目级行为规范，内容是项目结构说明、代码风格、约束和工作流约定，加载方式是会话开始时自动注入常驻上下文，作用是告诉 Agent 在这个环境里怎么行为，是守则。SKILL 文件是可复用的能力模块，内容是完成某类任务所需的提示词、工具调用步骤和校验逻辑，加载方式是按需触发，Agent 判断任务匹配时加载，作用是给 Agent 能做什么、怎么做某件事，是技能。核心区别：AGENT.md 是规则约束，SKILL 是能力流程；AGENT.md 对整个项目会话生效，SKILL 特定任务触发；AGENT.md 常驻，SKILL 惰性加载；AGENT.md 是声明式规范，SKILL 是指令加步骤加工具编排。关系上两者互补，SKILL 生成代码时要遵守项目的 AGENT.md 规范，SKILL 触发策略也可以在 AGENT.md 里声明。AGENT.md 管底线，SKILL 管能力上限。

22. Plan-and-Execute 和 ReAct 的区别？怎么选择？

答：ReAct 是边想边做，Thought、Action、Observation 交替循环，每一步根据观察结果决定下一步。优点是适应动态变化，中间出错能即时修正换路径；缺点是可能跑偏，因为每步只看局部，步骤多时推理和工具调用轮次多，token 开销大，缺少全局计划。Plan-and-Execute 是先规划再执行，Planner 先生成完整计划，Executor 逐步执行。优点是全局视角方向稳定不易跑偏，无依赖步骤可并行执行，token 开销低，因为规划阶段不调工具；缺点是对环境变化不敏感，计划过时不会自动调整，计划质量依赖模型能力。选择建议：任务可预先拆解、步骤稳定，比如批量处理文件，用 Plan-and-Execute；任务需要边做边看结果，比如调试报错、搜索加汇总，用 ReAct。最佳实践是混合，外层 Plan-and-Execute 管全局大步骤，内层 ReAct 管单步微操作，这正是双循环的落地形态，外循环负责计划与收敛，内循环负责执行与修正。
