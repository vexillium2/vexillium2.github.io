工具调用与 Tool Engineering

vexillium2026/9/7大约 32 分钟后端开发人工智能

这一章讲模型"如何触碰真实世界"。单靠参数里的静态知识，模型既无法拿到实时数据，也无法产生真实副作用；工具调用（Function Calling / Tool Use）就是那个接口——模型不再输出纯文本，而是输出"我想调用哪个工具、用什么参数"的结构化意图，由你的代码去真正执行。本章从最底层的调用机制写到工具设计方法论，再进入围绕工具的生态协议：MCP 把工具标准化成可跨应用复用的服务，Agent Skills 把"怎么用工具做完一类事"的方法沉淀成可加载的知识，A2A 解决 Agent 与 Agent 之间的任务委派，AG-UI 类协议则统一 Agent 与前端界面的流式交互。这些协议层内容演进很快，所以行文只落架构模型、原语与选型边界，不写死具体版本结论——凡是会过时的细节，都按"该看什么维度、如何自测"处理。

工具调用机制：模型如何"声明意图"

为什么需要工具调用，而不只是"让它输出一段命令"

模型天生只会生成文本。如果想让它在对话里触发真实动作（查数据库、发请求、执行代码），最原始的做法是让它"用文字描述想干什么"，再由代码解析这段文字——这条路的脆弱在于解析。模型不会稳定遵守一套自造的调用格式，它会换措辞、漏参数、在命令前后夹带解释。Function Calling 的本质是把"动作意图"从自由文本里提出来，变成模型被训练过、以结构化字段输出的协议消息：模型的输出分成两段——它要对你说的正文，以及一个带工具名与参数 JSON 的调用块。代码不再解析自然语言，而是读取结构化字段。它和"只要求输出 JSON"的差别在于：调用块携带的是可执行的语义（调用哪个函数、传什么值），并且协议层保证这段输出的稳定性。

一次完整调用在消息流里怎么走

工具调用协议（以事实上的 OpenAI 兼容格式为例，各家厂商字段名不同但语义一致）由四个消息阶段构成一个闭环：

1. user      : "查一下订单 10086 的物流状态"
2. assistant : 正文("好的") + tool_calls=[{ id: "call_1",
               name: "query_logistics", arguments: '{"order_id": "10086"}' }]
3. tool      : tool_call_id="call_1"  内容=真实执行结果
4. assistant : "订单已于今天上午 10:20 签收。"
  • 阶段 2 的 assistant 消息只是"意图声明"。模型并没有执行任何东西，它只是在可调用工具列表里选了一个、填了一组参数。执行权始终在应用代码手里——这一点决定了工具调用的安全边界：模型越权的前提不存在，因为动作根本没被它执行。
  • 阶段 3 必须有 tool_call_id 回指。多轮循环中模型可能先后发起多个调用，结果必须能对号入座，否则上下文里的"哪个结果对应哪次调用"就乱了。工具结果以独立角色（tool）追加进消息历史，随后的 assistant 请求会携带完整上下文。
  • 阶段 2→3→2 的循环会一直重复，直到某次 assistant 输出不再带 tool_calls——那一刻模型的输出才是最终回答。判断"这轮要不要执行工具"，依据是最后一条 assistant 消息里有没有 tool_calls，而不是它正文说了什么；模型可能一边说着"好的我这就查"，一边根本没发起调用。

不同厂商的线格式不同（Anthropic 是 tool_use / tool_result 结构，Gemini 是 functionCall / functionResponse），但两阶段语义（模型声明意图 → 宿主执行并回填）完全一致，网关/适配层做的就是把各家格式归一成一套内部消息模型。

并行调用

模型可以在一次 assistant 输出里携带多个 tool_calls——这是"我判断这几件事相互独立，可以同时做"的信号。宿主收到后可以并行执行，把各结果分别以 tool 消息回填（各自带自己的 tool_call_id），再让模型基于全部结果继续。工程上必须清醒几点：

  • "并行"是模型对独立性的判断，不是保证。模型可能把两个本有先后依赖的动作（先创建订单再查询订单）一起发出——宿主并行执行就会拿到错的第二个结果。带副作用的写操作不要盲信并行，按语义人工排串行或显式声明依赖；只读查询类（查天气、查文档、查库）才是并行的安全区。
  • 各厂商对并行调用的支持强度与开关（能否禁掉并行）不同，且版本间会变化——需要按官方文档实测，别假设所有模型默认都并行。
  • 并行执行要做好超时与部分失败的处理：一个调用失败不该让整批结果丢弃，把各自的成功/失败都结构化回填，让模型自行决定是重试失败的、还是基于成功的继续。

流式与工具调用的关系

对话走流式（SSE 逐块吐 token）时，工具调用也要能流式：assistant 消息里的 tool_calls 字段不是一次性到达，而是随流分片到达（arguments 以增量片段形式出现）。客户端需要：把每个 tool_call 的 name/arguments 增量分别缓存累积，等流结束（finish_reason 表明是 tool_calls）时拼出完整 JSON 再解析，而不是收到第一片就去执行。拼装中的 arguments 经常是"半个 JSON"，提前解析必然报错。这是流式接入时最高频的坑之一。是否流式只是传输方式的区别，不影响两阶段语义——即使每个 token 都实时推给前端，工具是否执行仍要等整个调用块收齐。

错误处理：把失败也当成模型的输入

工具调用的错误几乎不可避免（参数非法、工具内部异常、业务不成立），关键是设计处理链路而不是祈祷不出错。按错误的产生位置分层：

  • 协议/解析错误：arguments 不是合法 JSON、字段缺失或类型不对。源于模型生成漂移，通常重试一次或让模型参考错误信息重新生成即可。
  • Schema 校验错误：字段类型对但值越界（传了不存在的 ID、非法枚举）。代码侧校验挡下，把校验错误回填。
  • 执行错误：工具本身抛异常（网络失败、权限不足）。需要判断可否重试——只读/幂等工具可安全重试，副作用工具的重试要幂等设计支撑，否则宁可不重试而报错。
  • 业务语义错误：语法全对但业务上不成立（查询已删除的订单）。这种错误模型无法通过"重新生成一遍格式"修复，需要给它更多上下文或换路径。

最有效的通用做法是"错误回灌"：把结构化的错误信息（错误码 + 可读描述 + 如果可能给出修正建议）作为 tool 结果回填给模型，让它看到"为什么失败"后自行修正调用——通常一两轮内能修复大部分偶发错误。和所有模型循环一样，要设重试轮次上限，防止模型在同一个错误上反复打转烧 token。回填的错误信息本身是给模型的输入，要写得对模型友好：是"参数 order_id 不存在"，而不是堆一屏服务端堆栈。

常见反例

  • 把工具说明写在 prompt 正文里而不是 schema 里。只靠文字描述工具时，模型会"发明"不存在的工具名——工具必须以结构化 schema 提供，代码侧还要有工具名白名单兜底。
  • 忽略 finish_reason / tool_calls 边界，把"这轮该执行工具"误判成"该返回最终答案"，或反过来。
  • 让模型自己执行动作：把工具结果让模型"复述"而不是以 tool 角色回填，导致上下文里没有真实的执行记录，后续决策建立在模型转述上。
  • 解析失败就硬失败：不做错误回灌自修复，一次参数拼错就整轮报废。
  • 对副作用工具盲目重试：网络超时重发一次"转账"请求，造成的不是报错而是重复扣款——重试策略必须按工具的幂等性分别设计。

工具设计：把工具当成"给模型用的 API"

视角转换：工具的用户不是人，是模型

写 REST API 时你在为工程师写文档；写工具时，读"文档"的是一遍遍读 schema 与 description 的模型。它看不到你的实现、猜不到你的隐含约定、记不住你没写进描述里的限制。所以工具设计的全部工作可以归结为一句话：把工具应该被"如何使用、何时使用、何时不该使用"表达成模型能稳定解析的信息。判断工具写得好不好，标准不是代码优雅，而是模型能否在真实调用中稳定地：选对工具 → 填对参数 → 正确处理返回。

粒度：拆到什么程度算"刚好"

工具切多细不是代码层复用性的问题，而是模型要做几次决策的问题。一条经验基线：一个工具对应一个模型能独立判断的"动作意图"——它先判断"现在该不该做这件事"，再带着明确参数调用它。把多个意图并进一个工具，模型就得靠参数组合表达"哪种场景填哪几个字段"，schema 越复杂、字段间约束越多，填错率越高；反过来把一个意图切成多个工具，模型被迫串行调多次，每多一次调用就多一个失败点、多一轮上下文开销。

拆分时盯三条边界：

  • 读与写分开。查询类工具可并行、可安全重试、可放心审计；变更类工具带副作用，要幂等设计与显式确认。混在一个全能工具里，安全边界和重试策略都没法按类设计——模型可能拿一个只读场景去执行带副作用的动作，而你在运行时无法从工具粒度上拦截。
  • 按业务动作拆，不按实体拆。对订单提供 query_order / create_order / cancel_order，而不是一个 order 工具加 action 参数让模型自己拼。action 一旦是自由字符串，等于把"选工具"问题平移成"在参数里写对动作"，比前者更难稳定。
  • 相近动作宁可共存。search_users 与 get_user_by_id 同时暴露是常态，靠 description 区分；不要为了"少几个工具"合并它们——选错工具的损失通常小于逼模型做两跳（先查列表再逐条定位）的损失。

反向信号：如果某个工具的 description 要写好几行才能讲清"什么时候别用它"，多半是吞了多个意图，该拆。还要记得每个工具定义都在占输入 token——schema 总长直接吃上下文预算，工具数量与复杂度应当跟真实调用频率成正比，冷门的细分操作别全部平铺，用参数展开或按场景分组暴露。

命名：让模型"望文生义"

工具名是模型做初筛的第一信号，多数模型会先按名字过滤再读 description。命名约定：

  • 动词开头 + 具体宾语：query_order_status、create_crm_contact、send_slack_message。名词裸名（order、file）不传达动作，模型难以判断调用它会产生什么。
  • 动词用模型语义最熟的词：search / query / get / create / update / delete / send / approve，避免自造动词。
  • 同一业务族共享前缀、命名体系化：让模型识别"这是一族工具"，避免跨族调用时配错参数风格。
  • 避开歧义缩写与随机后缀（t1_qry、util_02）。模型对缩写与编号的语义把握不可靠，纯属给它增加无信息量的记忆负担。

自测方法：把工具名单独贴给模型问"这个工具干什么"，如果必须看 description 才能猜对行为，名字就该改。

description：写"什么时候用、什么时候别用"

description 是模型决定"选哪个工具、怎么填参数"的主要依据。它的重点不是解释内部实现，而是讲清三件事：这个工具做什么、什么情况下该用它、什么情况下不该用它。第三点最常被省略，也最常导致用错工具——模型看到 search 就用来查一切，即使你希望它优先走 get_by_id。

一个可复用的结构模板：一句话功能（做什么、返回什么）→ 触发条件（当用户需要……时使用）→ 排除条件（当只是要……时不要用，XX 场景请用相邻工具）→ 关键参数与边界（枚举含义、格式示例、默认行为、失败时返回什么）。

常见反例：

  • 写实现细节："内部通过 HTTP 调用外部服务并自动重试"——模型不需要知道，也帮不上选型。
  • 不写限制：get_weather 不说明"仅支持国内城市"，模型对任意城市都自信调用，拿到错误结果后可能开始编数据圆场。
  • 相似工具描述雷同：lookup_user 与 search_users 都只写"查找用户"，模型只能随机挑一个，等于把区分工作全推给名字，而名字又不够具体。
  • 参数不留示例：不给枚举含义、不给日期格式（"2026-09-07"还是时间戳）、不给单位，模型每个没写清的字段都是编造的候选。

模型不会"常识性"地知道你的数据约定，description 的投入产出比远高于堆更多工具——同一批工具，描述重写前后的调用准确率可能差异显著，值得当接口文档一样写。

返回值：设计"模型的下一跳输入"，而不是给人看的输出

工具结果会以 tool 消息回到模型手里，作为它继续决策的依据被再读一遍。它和给人看的界面文本有本质区别：

  • 返回机器可解析的结构，别返回排版文本。JSON 优先。结果要被模型继续加工（取字段、算总和、判断状态）时，结构化字段比"第 3 行第 2 列"式的文本可靠得多——模型处理结构化数据的稳定性远高于从散文里抠信息。
  • 只留决策所需信息，控制体积。模型上下文有限，一段 50KB 的原始日志、一整页 HTML 照单全收，只会稀释模型对关键字段的注意力并烧掉预算。能摘要的摘要、能剪裁的剪裁（列表返回前 N 条加 total 计数），别把"人可能想看全部"默认成"模型需要看全部"。
  • 把"边界"暴露给模型。带分页的查询要返回 total 与 next 线索，否则模型不知道还有没有下一页、该不该继续翻；空结果要明确返回"空"，而不是成功码加空 body——后者让模型无法区分"没数据"和"出错了"。
  • 留下可继续动作的线索。返回订单对象时带上可用的后续操作提示（如可取消、可改地址），减少模型对"接下来能做什么"的猜测。它不会像人一样从业务上下文里推断，只会从你给的信息里找。

错误返回同样按可读结构设计：错误码 + 一句人话描述 +（可能的话）修正建议，例如"参数 order_id 不存在，可先用 query_order 确认订单号"。模型读得懂才能自我修正；只回一个状态码或一整屏堆栈，它只能原地瞎试，最终浪费的是你的 token。

迭代工具设计的信号

工具好不好不能靠"人觉得顺手"，只能靠回放真实轨迹看两类错误率：选型错误（该用 A 工具却调了 B）与参数错误（工具对但参数填错）。从调用日志里找三类信号并反推 schema 问题：

  • 某个工具几乎从未被选中：可能 description 有歧义、和相邻工具没区分开，也可能暴露得太晚被埋没在长列表里。
  • 某参数频繁填错：缺枚举含义、缺格式示例，或参数名与 description 用语不一致。
  • 调用成功后模型还要追问补充信息：返回缺了下一步决策所需的字段。

按这三类信号迭代 schema 与返回结构，比凭感觉打磨更快收敛。测试对象是模型不是人，这是"工具是给模型用的 API"这条原则的最终落点。

MCP：把工具从"应用内私有"变成"可复用服务"

它在解决什么：N×M 的集成重复

没有标准协议时，每个模型应用接入一套外部能力都要自己写一遍：能力从哪发现、怎么调用、怎么鉴权、怎么把结果塞回模型上下文。应用（IDE、桌面工具、网页应用、你自己的服务）与能力提供方（数据库、内部系统、第三方 API）之间的集成是 N×M 的重复劳动，而且每对集成都是私有实现——换一个应用，同一个工具要重新适配一遍。MCP（Model Context Protocol）把"应用如何获取并使用外部能力"定成标准协议：能力提供方实现一次 server，任何支持 MCP 的应用（host）都能接入。注意它的定位边界：MCP 解决的是"应用 ↔ 工具/数据源"的横向集成，不负责 Agent 之间怎么协作、也不约束模型怎么思考——那分别属于 A2A 与运行时的话题。

架构：Host / Client / Server 三段

  • Host：用户所在的模型应用，负责维护会话、把模型上下文组装起来，并对工具调用做授权决策。
  • Client：host 内部与某个 server 一一对应的连接。一个 host 里可以有多个 client，各连一个 server。
  • Server：能力提供方，声明并实现可用的原语（tools / resources / prompts），通过协议暴露给 host。

连接层有两个经典形态：stdio 与 HTTP。stdio 模式由 host 把 server 作为子进程拉起，通过标准输入输出交换消息，生命周期随 host 启停、权限继承自父进程，适合本地一对一场景，也最常见。HTTP 模式（早期走 SSE，后收敛为流式 HTTP）让 server 常驻并可被多个 host 复用，适合远程部署、需要经过网关鉴权与审计的形态。选哪个看两件事：server 与 host 是否在同一可信域，以及server 是否要被多个 host 共享。消息本身走 JSON-RPC，两边无需知道对方实现语言——这也是它做"标准"的底气。

三种原语：Tools、Resources、Prompts

server 向外暴露的能力分三类，语义与风险完全不同：

原语语义对模型的影响风险特征
Tools可执行的动作（查库、发消息、改配置）触发副作用，改变外部世界高，需授权/确认
Resources可读取的数据（文件、代码、文档片段）作为上下文内容被读入中，只读但可能含敏感信息
Prompts可复用的提示模板注入一套完成某类任务的指令低，但可携带引导性内容

三者错位是常见设计错误：把"读数据"实现成 tool、把"触发动作"实现成 resource。前者让只读数据访问也走上授权路径，徒增确认噪音；后者等于让模型"读"出一个副作用。设计时的默认问法是：这个东西是要执行的动作（tool），还是要进上下文的内容（resource），还是一套做事方法（prompt）？

安全模型：授权在 host，不在协议

MCP 协议本身不裁决"这次调用允不允许"——它负责传输意图，授权决策留在 host（用户确认、策略引擎）。这与工具调用的模型一脉相承：模型始终只是"声明意图"的一方。工程上最容易踩的坑，是 host 把工具调用全部自动放行，等于把权限判断完全交给模型和 server 的自觉——恶意或受损的工具描述、注入到上下文里的内容，都能驱动模型去调用危险动作。协议侧的现实是：server 只声明能力与权限诉求（capability / 所需 scope），是否授予由 host 侧的用户或策略决定；远程 server 还要经鉴权（OAuth 一类）与最小权限授权，stdio 本地进程则继承父进程权限、天然受沙箱限制。落地上该盯的维度是"谁在批准每一次真实副作用"，而不是指望协议替你挡。提示词侧的文本注入防御是另一套方法，这里不展开；协议层的主战场在权限路径——所有副作用调用都必须落在显式的授权决策上。

写一个 MCP Server：别自己造 JSON-RPC

实现 server 时最容易犯的错是手搓协议细节。消息帧格式、握手、能力协商这类东西用官方 SDK 现成的——协议字段对不上是接入失败的第一大来源，而你调试它的成本远高于依赖维护成本。剩下真正要你花心思的，是工具设计方法论在 server 里的落地，以及三个 server 侧特有决策：

  • 传输按部署形态选，别默认。本地、单 host、和宿主同生命周期 → stdio 最省事；要跨机器、被多个 host 共享、走网关 → 上 HTTP。中途改传输的代价不小，先想清楚 server 是"附属于某个应用"还是"独立服务"。
  • 工具的实现要自带防御。MCP 帮你把意图传进来，但参数校验、鉴权、限流、审计都得 server 自己守。工具描述写"给模型看"，工具实现按"可能被任何人以任何参数调用"来写——这两套视角在 server 里第一次同时出现，最容易顾此失彼。
  • 资源与提示也要当成产品设计。很多人只暴露 tools 就交付了。要不要把常用数据源暴露成 resources、把高频任务流程固化成 prompts，决定 server 对 host 的"可用深度"——但每多一类原语就多一层授权与维护面，按真实使用场景加，不为了齐全而齐全。

企业里为什么需要一层 MCP 网关

server 一多，混乱就开始了：谁负责发现有哪些 server？谁做统一鉴权？调用日志归谁？这层职责应该收拢到网关（gateway）而不是散落在每个 host 或 server 里。网关的典型职责分四块：

  • 目录与发现：登记内部 server、声明每个暴露了哪些工具/资源/权限诉求，host 通过网关按需订阅，而不是各自硬编码 server 地址。
  • 统一鉴权与审计：身份在网关统一校验，工具调用全量留痕——谁、何时、经哪个 host、调了哪个工具、传了什么参数。没有这层日志，出问题连"发生了什么"都答不上来。
  • 治理与限流：对高成本或高风险的调用做策略控制（哪些工具需要人工审批、哪些调用频率受限），把"按动作危险程度分级审批"的思路落到协议接入面。
  • 统一的运行时观测：调用成功率、token 消耗、响应延迟集中可观测，供持续调优。

要不要上网关，看规模与风险面：个人开发、server 就两三个、全是本地 stdio，网关是过度设计；一旦涉及敏感系统（财务、生产库、对外接口）或多个团队共享 server，网关几乎是强制项——工具接入企业系统的关键不在协议本身，而在它外面那圈"谁能调、调了留痕、超限怎么管"。评估现成网关产品时，按上述四块职责逐一对照，别被"多少种 server 兼容"这类宣传指标带偏。

Agent Skills：把"怎么做完一件事"沉淀成可加载的方法

Skill 与 Tool 的本质区别："脑"与"手"

Tool 是一只手——一次原子动作（查天气、改文件）；Skill 是一套完成某类任务的方法：需要调哪些工具、按什么顺序、中间怎么判断、遇到什么情况怎么处理、成品的验收标准是什么。同一句话能更本质地概括：Tool 回答"能做什么"，Skill 回答"这件事该怎么做完"。Skill 里可以编排工具、可以内嵌领域判断、可以带示例，但它不写死在代码里——它以文本（通常一份 Markdown 说明 + 若干支持文件）的形式存在，需要时被加载进模型上下文，指导模型"像老手一样干活"。所以它落在"脑"这一侧：真正执行靠的还是 tool，Skill 改变的是模型做事的方式。

为什么要单独搞一层，而不是把方法写死在 prompt 里？因为方法的知识量与调用频率不匹配：几十个 Skill 的方法细节不可能常驻上下文，多数时候也用不上。于是需要"按需加载"——这正是它与静态 system prompt 的分界。

SKILL.md：一份约定俗成的"说明书格式"

围绕 Skill 形成了事实上的规范形态（典型代表如各类编码 Agent 的 skills 目录）：一个 Skill 是一个目录，入口是一份 SKILL.md，内含：这个 Skill 解决什么问题、何时该用/何时不该用、核心步骤与判断准则、常见陷阱与反例、必要的示例。它的结构和工具 description 同构——同样回答"做什么、何时用、何时别用"——但粒度大得多，是一份可以展开为多轮操作的说明书，而不只是一个 schema 条目。

写 SKILL.md 的本质是给模型写"领域 SOP"，不是给人写文档。判断标准同样是模型拿到它之后，能否在没有你实时指挥的情况下，独立完成一整类任务。反过来说，一个 SKILL.md 如果只是罗列"步骤 1 做 A、步骤 2 做 B"，而没有写清"什么迹象说明方向错了、什么时候该停下来问人"，它就是一份残缺的 SOP——模型照做能完成顺风局，遇到边界情况就开始瞎发挥。

渐进式加载：上下文成本决定的加载策略

Skills 的方法要进上下文才生效，但所有 Skill 全量加载会瞬间撑爆预算。现实策略是渐进式（progressive）加载：只把"当前任务明确需要"的 Skill 头信息先放进上下文；模型判断需要时，再按需读取某个 Skill 的完整 SKILL.md 与支持文件。头信息要足够模型判断"这事归不归这个 Skill 管"，正文才负责指导具体执行。判断 Skill 粒度与数量的尺度，仍然是频率与成本的平衡：热门的、每次任务都要用的方法直接写进 system prompt；次热门的做成 Skill 按需加载；一年用一次的连 Skill 都不必做——文档就行。

编写与复用的要点

  • 从真实轨迹里沉淀，别凭想象写。先让模型在人工指导下把任务做几遍，把"哪些环节它反复出错、你在哪里不得不介入纠正"记下来，这些正是 SKILL.md 最该写的部分——不是顺利路径，而是纠偏知识。
  • Skill 是可复用资产，命名与目录即索引。数量上来后，模型靠名字和头信息做初筛，命名含糊（"优化.py"、my_task）等于让 Skill 永远不被选中。
  • Skill 内嵌工具调用规范，但不替代工具实现。它描述"何时调 A 而非 B、参数怎么定"，真正执行仍走工具与权限路径——别把危险动作写进 Skill 正文绕过审批，那等于把安全降级成文本自觉。
  • 版本与实验：方法会随工具、模型、业务变化而失效。Skill 是文本，天然可 diff、可 review、可回滚——把它当代码管（评审、版本、灰度），而不是当"某个人的笔记"。

A2A：Agent 与 Agent 之间的任务委派

它解决什么问题：MCP 不管的那一半

MCP 打通了"应用 ↔ 工具/数据"，但一个 Agent 想请另一个 Agent（由不同团队开发、跑在别的系统里）帮忙完成一件事，目前没有统一办法——双方该怎么互相发现、用什么格式表达"请你帮我做 X"、结果与进度怎么同步、中途要不要问人。A2A（Agent2Agent 一类协议）的目标就是为 Agent 之间的任务级协作定标准：不是我调你暴露的某个函数，而是我委托你完成一个有明确目标的任务，你在自己的环境里用自己的工具去做，再把结果交回来。一句话切分两者边界：MCP 是"Agent 伸手够工具"，A2A 是"Agent 把活派给另一个 Agent"——前者让模型的能力半径变长，后者让协作边界变宽。

Agent Card：让 Agent 可以被发现与被判断

跨系统协作的前提是"能被找到 + 能被判断合不合适"。A2A 用 Agent Card 解决：一份机器可读的元数据，声明这个 Agent 是谁、擅长什么任务、接受什么样的输入、产出什么、有哪些能力约束、支持哪些交互模式。它的作用类似服务注册中心里的服务描述——别的 Agent 或编排方先读 Card，判断"这个任务该不该派给它"，再发起委派。Card 写得含糊（"全能助手"），等于把判断责任推给调用方去试错。

任务委派：从"调用"到"委托"的语义变化

A2A 把协作的最小单元定义为任务（task），而不是请求-响应。一次委派的生命周期：发出任务（目标 + 输入 + 约束）→ 接收方确认接受或拒绝 → 执行中回报状态（进行中/需补充/要人工确认）→ 完成并交付结果。这里有几个和函数调用完全不同的工程语义，容易踩坑：

  • 任务不是同步调用。一个 Agent 干一件事可能要很久，期间还可能主动向你询问补充信息或请求人工介入。协议层需要的是"任务状态可查询 + 中途消息可往返"，而不是一把同步 RPC——把 Agent 协作当成微服务调用来设计，超时与失败模型都会错。
  • 结果质量靠验收，不靠信任。对方是一个独立系统，你无法假设它的输出可靠。拿到结果要校验、要按领域标准验收，必要时把"再加工"继续作为新任务派出去。跨 Agent 协作的第一课是降低信任假设。
  • 委派粒度决定耦合。任务拆得越细、来回越多，通信与状态同步成本越高；拆得太粗，接收方无法判断该不该接。权衡点是"对方能否独立完成的最小完整目标"。

跨平台协作的现实与反例

A2A 想通的场景是异构系统：不同技术栈、不同组织、不同信任域的几个 Agent 协同完成一个端到端目标（一个 Agent 查资料、一个 Agent 跑流程、一个 Agent 出报告）。但协议能标准化"消息格式"，标准化不了"双方对任务目标的理解一致"——真正的协作难度从来不在传输，而在语义对齐：你说"整理一下"和对方理解的"整理"可能差很远。跨系统协作的反面教材是把 Agent 编排塞回 A2A：如果你的多个 Agent 同进程、同信任域、共享记忆，那是内部 Multi-Agent 编排问题，用 A2A 反而把内部细节暴露成外部协议，白白背上网络与鉴权成本。A2A 的适用前提是"边界真实存在"（不同团队、不同部署、不同信任域）；边界不存在时，别为协议而协议。

边界与选型：MCP vs A2A 一句话

协议协作单元回答的问题典型形态
MCP工具/资源怎么触达能力与数据Agent ↔ 工具服务
A2A任务怎么把活派给别人Agent ↔ Agent

两者不是竞争而是互补：一个 Agent 往往通过 MCP 拿工具、再通过 A2A 把超出自己能力的任务委派出去。选型别按"哪个更流行"，按你要打通的那条边界属于哪种协作单元。

AG-UI 一类协议：Agent 与前端界面的流式对话

前端要的从来不只是"打字机效果"

Agent 跑在前端背后时，UI 层需要知道的东西远超"逐个 token 的文本"：Agent 当前在哪个阶段（思考中 / 正在调工具 / 卡住要问人）、调了哪个工具结果如何、需不需要用户补充输入、某项操作要不要用户确认。传统做法是把这一切糊进一条 SSE 流或轮询，前端收到后自己猜语义——于是每家前端都写一套脆弱的解析：靠"内容里出现问号就弹输入框"之类的启发式。AG-UI 一类协议的目标，是把 Agent ↔ UI 之间的消息按语义结构化：定义明确的消息类型（用户的输入、Agent 的文本、一次工具调用、一次需要用户介入的请求、状态变化），让前端不用猜，而是按类型渲染与响应。

需要关心的原语，与"过时版本"无关

这类协议演进很快、各家命名不同，背消息枚举没有意义；值得吃透的是四个稳定的交互原语：

  • 结构化消息流：流里的每个事件都带类型与结构化载荷（工具调用、工具结果、状态、文本块），而不是一行裸文本。前端据此决定是打字、是画工具卡片、还是收起输入框等待。
  • 会话与状态：一次 Agent 交互是一次有状态的会话，流式连接断掉后要能恢复或续接。UI 协议真正难的不是"推得快"，而是状态一致——前端展示的进度和后端 Agent 的真实状态不能是两套。
  • 请求用户输入：Agent 在执行中途需要用户补充信息（一个选择、一段澄清）时，要能结构化地"暂停并向 UI 请求输入"，而不是把问句混在正文里让用户碰运气回复。
  • 确认/审批回传：危险动作的授权在 UI 上做确认时，确认结果要以结构化消息回传给 Agent，形成闭环。

什么时候需要它，什么时候不需要

判断要不要引入这类协议，看你的前端要不要感知 Agent 的内部节奏并参与决策：如果只是"文本流进来、用户发一句进去"，一条 SSE 加文本解析就够；一旦 UI 要渲染工具过程、要插话、要拦下操作做确认，就值得结构化。别把"有打字机效果"当成上协议的理由——打字机只是把文本切碎，和结构化交互是两回事。同样，UI 协议与 MCP/A2A 面向的边界不同：MCP/A2A 是"Agent 到系统"，这类协议是"Agent 到人所在的那块界面"，它关心的是把 Agent 的内心活动翻译成人能看懂、能介入的界面语义。

协议选型自查清单

从裸 Function Calling 到 MCP 到 A2A 到 UI 协议，它们解决的边界逐层外扩。选型时按边界自问，而不是按流行度站队：

  • 只有自己的应用在调自己的几个工具？ 用裸 Function Calling 直接接。加协议层只会徒增一层适配，工具都长在你进程里时，MCP 是多余的。
  • 工具要跨应用复用、跨系统共享、需要鉴权与审计？ 上 MCP。判断信号是"同一个工具是否被多个 host 需要"和"是否有工具服务要独立于调用方部署"。此时把工具设计方法论的 schema/description/返回规范一起搬进 server，否则协议只解决传输、没解决质量。
  • 要和一个真实独立的 Agent（别人团队、别家系统）协作完成任务？ 才考虑 A2A。自问一遍：这个协作边界是不是真的存在（不同信任域/部署）？两个 Agent 能不能直接合并成一个？不能才委派。
  • 前端要渲染过程、要介入确认？ 考虑 AG-UI 类结构化交互协议。只在"文字流 + 输入框"不够用的时候上。
  • 所有选择前先问：这次集成的边界到底在哪一端？ 边界在能力与数据 → 工具/MCP；边界在"整件活" → 任务委派/A2A；边界在人机界面 → UI 协议。协议不生产智能，它只决定你的模型与工具、与人、与别的 Agent 之间那根线怎么画——线画错了，任何协议都救不回来。
