RAG 检索增强生成

vexillium2026/9/7大约 44 分钟后端开发人工智能

这一章把 RAG 当作一条数据管道来讲：从"用户问了什么问题"到"模型拿到了什么证据"，再到"答案有没有钉在证据上"。模型参数里的知识是静态的、会过时的，RAG 的思路是把回答的依据从"参数记忆"挪到"可检索的外部知识库"——知识更新时改库而不是改模型。贯穿全章有一条主线：RAG 的输出质量上限由检索到的证据质量决定，模型生成只是把这份证据"如实翻译"成回答。所以数据侧（解析、切块、清洗、索引）和检索侧（改写、召回、精排）的投入，决定了一个 RAG 系统能走多远；真正工程化 RAG 的人，日常打磨的也主要是这两端，而不是模型的提示词。沿着"架构总览 → 选型 → 查询端 → 检索端 → 证据端 → 向量化与存储 → 数据处理 → 高级形态与评估"推进，各小节的面试高频点就地讲清。

一、RAG 全景：从朴素到模块化的演进

标准三段式：Indexing → Retrieval → Generation

RAG 的基础形态是一条固定的离线/在线流水线：

离线：文档 → 切块 → 向量化 → 建索引入库
在线：用户问题 → 向量化 → 向量检索 TopK → 拼入 Prompt → LLM 生成

三段的职责分别是：Indexing 把知识库切分成"检索单元"并转成可检索的形式；Retrieval 在查询时召回与问题最相关的片段；Generation 基于召回片段生成有据可依的回答。这个"朴素 RAG"能跑通，但上线后会暴露三组典型问题：切块和向量化做得糙，召回的全是不相关的；TopK 拉得大，上下文里噪声比信号多，反而干扰生成；检索到的证据是对的，模型却没照着说。业界后来的演进，本质上都是围绕这三个失败点做工程修补。

Advanced RAG：把三个环节各自做精

Advanced RAG 不是在朴素流程上另起炉灶，而是在 Retrieval 的前后分别加了"预检索"和"后检索"处理：

  • 预检索（查询端）：改写用户的短 query、补全对话指代、扩展多路查询，让"问法"更贴近"文档的写法"，提高召回命中率。
  • 检索本身：从单一稠密向量检索扩展为混合检索（词法 + 语义）、元数据过滤、父子切块等，让"召回的候选"更准更全。
  • 后检索（精排与压缩）：对召回结果用更精细的模型重新排序，把 TopK 压缩到"够用且不脏"的量级再送进上下文。

一句话概括：朴素 RAG 的假设是"向量检索 TopK 就是好证据"；Advanced RAG 承认这个假设经常不成立，于是把证据质量变成被显式优化和治理的对象。

Modular RAG：从固定管道到可编排模块

再往后，RAG 的实践形态从"一条写死的管道"走向模块化编排：检索、改写、精排、记忆、路由、融合各自成为可插拔模块，按任务自由组合。这一步真正的变化是"检索"从"必然发生"变成"按需发生"——系统开始判断这个问题到底要不要查、查哪一类知识源、查完要不要再查。路由（轻量分类或 Agent 决策）、自适应检索（检索结果不满意就纠偏）都是这一阶段长出来的能力。它不再是一个固定的技术方案，而是一套可以被编排的检索增强体系，Agentic RAG 就是这条线进一步演化的产物，后面单独展开。

理解演进要避免一个误区：阶段升级不是名词升级。朴素 RAG 最典型的失败不是"没用上 Advanced 技术"，而是数据管道（解析、切块、Embedding）本身是脏的。工程上先按"数据 → 召回 → 精排 → 生成"的顺序逐段查漏，比急着堆最前沿的模块化框架有效得多。

二、RAG / 长上下文 / 微调：知识接入的三条路线怎么选

三条路线各自在改什么

面对"模型不知道某些知识"的需求，有三条路线，先想清楚它们各自的杠杆在哪个位置：

维度RAG长上下文微调
修改对象模型输入：检索证据注入上下文模型输入：整本文档塞进窗口模型参数
知识更新换库/重建索引即可，几乎实时换输入即可需要重新训练，成本高
可溯源性强，答案能挂到具体文档中，能引用但不保证用对弱，知识进了参数无法举证
主要成本检索/索引工程 + 每轮 token大窗口的 token 与 KV 成本GPU 训练 + 数据
生效条件知识可被"切成片段"检索文档量小、可整体装入需要的是行为/风格而非知识
  • RAG 适合"知识量大、经常变、要求可引用"。它把知识的读写都放在库上：更新知识 = 更新索引，答案可以追溯到具体文档。代价是引入了整条数据管道，检索质量不佳时反而帮倒忙。
  • 长上下文适合"一次性、文档量小、需要跨文档整体把握"。它是"不过滤的输入"：没有检索，就不会有检索错误。但窗口"放得下"不等于"用得好"，超长内容里关键信息常常被淹没，且每次请求都要为整段上下文买单。
  • 微调适合"改变行为范式"而不是"注入新知识"。模型的回答风格、输出格式、交互协议这类"行为"，用微调定型是最稳的；但用微调去灌大规模事实性知识是低效的——知识会被压缩进参数、会忘、无法更新，性价比远低于 RAG。

决策要点与反例

  • 知识会频繁更新、或来源需要审计 → RAG。
  • 一次性的长文档（如读一份 500 页的合同），更新低频 → 长上下文更直接。
  • 要的是"像我们团队那样说话、按我们的格式输出"→ 微调。
  • 任务依赖对整库的全局归纳而非片段检索（"过去一年文档里提到了哪些架构风险"）→ 向量检索的单片段召回天然不擅长，考虑图谱/全局方案或专门的聚合策略。

最常见的选型反例有两个：指望微调把私有知识库灌进模型——训练贵、会遗忘、无法更新，还会侵蚀通用能力；把长上下文当 RAG 的免费替代——语境里资料一旦超过几十万 token，中间内容被稀释，成本与延迟也一路走高。三条路线不是互斥的，生产系统里 RAG + 微调（RAG 供知识、微调定风格）是常见组合，别把自己锁死在单一选项上。

三、Query 理解：先让"问法"配得上"文档的写法"

检索对不上的根源在表示不对称

用户的问题和文档的表述之间存在天然的鸿沟：query 常常很短（"那个授权咋弄"）、充满指代（"上一条里说的方案"）、口语化，而文档用的是完整规范的书面语。稠密检索又依赖"问法"和"文档写法"在语义空间里足够接近——差距越大，召回越差。Query 处理的目标不是把问题变"漂亮"，而是把它翻译成更可能命中文档的那种表述。顺着这个目标看三个手段就都清楚了。

Query Rewrite（改写）

用 LLM（或规则）把原始 query 改写成更适合检索的形式，常见操作：

  • 指代消解：把多轮对话里的"它、这个方案"替换成具体指代对象，使每轮检索都自包含。
  • 补全与扩写：给过短的 query 补上任务上下文（"授权"→"xxx 系统的权限授权流程"）。
  • 纠错与术语统一：把口语、错别字、中英混写归一成文档里的规范术语。

改写要在"贴近用户意图"和"贴近文档词表"之间取平衡——纯按用户原话检索经常命中不了，改得太发散又会检索到无关内容。

多查询扩展（Multi-Query Expansion）

思路最简单：同一个问题，让 LLM 生成多个不同角度、不同措辞的变体查询，各自检索，合并去重后统一进精排。它直接提高的是召回率（recall）——用户问法没覆盖到的表述，可能被某个变体覆盖到。代价是成倍的检索调用与噪声引入，因此通常只在"召回不够、宁可多捞再精排"的场景使用，且后面必须跟 Rerank 把扩出来的噪声压下去。

HyDE：用"假设答案"去检索

HyDE（Hypothetical Document Embeddings）的原理很反直觉但很有效：先让 LLM 针对问题生成一段假设性的答案文档（hypothetical document），再用这段假答案的向量去检索真实文档。动机是缓解"query 侧表示"与"文档侧表示"的不对称——假答案说的是"文档话"，它和真实文档在向量空间里的距离，往往比原始问题更近。

HyDE 有两个必须知道的坑：生成假答案本身是一次 LLM 调用，引入额外成本与延迟；更关键的是假答案质量差时会带偏检索——模型知识不足或生成跑偏时，假答案里的错误方向会把检索引向无关文档。实践中可以保留"原 query 检索 + 假答案检索"两条路做融合，而不是让假答案完全取代原查询。它适合 query 极短、领域表述差异大的场景；query 本身已经足够规范时收益有限。

小结与误区

  • 召回差先分清"是问法问题还是索引问题"：改写只解决表示不对称，救不了脏数据导致的检索失败。
  • 三种手段都增加一次或多次 LLM 调用，属于"用成本换召回"，别对每个请求无脑全开；按 query 类型做路由（短口语 query 才改写、复杂问题才多查询）比全量堆叠更划算。
  • 面试被问"HyDE 和多查询有什么区别"，答"多查询扩大的是 query 侧的覆盖，HyDE 改变的是 query 侧的表示域"，再加一句"多查询靠 Rerank 收口、HyDE 靠双路融合兜底"，就比背定义完整得多。

四、检索召回：稠密、稀疏与混合融合

两条互补的召回路线

检索层负责从索引里把"可能相关"的片段捞出来，主流是两个互补的家族：

稀疏检索（以 BM25 为代表）做的是词法匹配。它基于倒排索引，按 query 词在文档中的统计特征打分——核心是 IDF（词越稀有越有判别力）与词频饱和（一个词出现很多次收益递减）、再按文档长度归一化。它的优势恰好是稠密检索的短板：对精确 token 敏感，型号、编号、代码、人名、法律条文这类必须逐字命中的查询，BM25 稳准且可解释；缺点是"词汇鸿沟"——换个说法（同义词、改写）就匹配不上。

稠密检索把 query 和文档各自编码成一个向量，用向量相似度召回。它把"词面不同但意思相近"的文本拉近，弥补了词法检索的词汇鸿沟；代价是它对精确 token 不敏感、领域外文本表现不稳，而且结果难以解释——你不知道它"因为什么"觉得相关。

为什么几乎总是需要混合

两类检索的失败模式正交，因此混合检索（词法 + 稠密并行召回、再融合排序）在实践中几乎总是优于单用任何一类：用户问法里同时混着精确实体（"Bug 报表里那个 INV-203 的工单"）和语义成分，只靠一路都会漏。融合方式里最常用的是 RRF（Reciprocal Rank Fusion）：不直接比较各路分数的绝对值，而是按排名位置折算：

score(d) = Σ_retriever 1 / (k + rank_retriever(d))，k 通常取 60

RRF 用排名而不是分数做融合，因为不同检索器的分数尺度根本不可比（BM25 的十几分和余弦相似度的 0.8 没有换算关系），而"排在第几名"是跨检索器可比的信息。工程实现上，把各路 TopK（一般各取 100~200）合并，按 RRF 分重排，必要时对不同路加权重（词法准确率高就多给词法一点权重），再做文档级去重。

反例与工程要点

  • 只有稠密检索的 RAG，遇到精确匹配需求（ID、编号、专有名词、代码符号）时召回系统性拉胯，这是最常见的第一档事故。
  • RRF 不是万能胶：某一路检索器质量很差时会把噪声名次抬上来，融合前要先保证各路自身质量；混合检索解决"两路互补"，不解决"两路都烂"。
  • 召回与过滤的顺序：权限、时间、来源这类硬过滤（不属于语义相关性）应在检索阶段就生效（如按元数据过滤后再算），不要在生成端才发现材料不可见或过期。
  • 面试主线：稀疏检索讲 BM25 的词频-逆文档频率与词汇鸿沟，稠密检索讲语义匹配与精确词短板，混合检索讲"失败模式正交 + RRF 用排名消掉分数不可比"。

五、精排与压缩：Rerank 在做什么

双编码器召回与交叉编码器精排的分工

召回阶段用的是双编码器（bi-encoder）：query 和文档各自独立编码成向量，相似度是一次向量运算——快，而且文档向量能提前算好、离线索引。精排阶段换成交叉编码器（cross-encoder）：把 query 和候选文档拼接成一个序列喂给模型，让两者的 token 在全注意力下充分交互，再输出一个相关性分数。

交叉编码器更准，是因为它让 query 与文档的每个词都发生了细粒度交互，而不是把两边各自压成一个向量再比较；它也更贵——文档无法预索引，必须在查询到达后对候选逐条实时打分。所以 RAG 的标准架构是两段式：向量库粗召回一个较大的 TopK（如 100~500），再用交叉编码器精排，截断到真正送入上下文的小 TopK（3~10）。粗召回要"宽"，宁可多捞，把精确排序交给精排，因为交叉编码器在几千个候选项上逐条跑是延迟灾难。

Top-K 压缩与上下文卫生

Rerank 的另一个作用是上下文压缩。生成端上下文里有用的证据通常只有几条，塞 20 条"可能相关"的片段进去，噪声反而干扰生成、也白烧 token。压缩的基本原则是：送入生成端的证据量，以"足够回答"为准，而不是"尽量多"。精排后截断、必要时再做片段合并去重（同一文档的多条命中先归并），再交给生成。

反例与边界

  • Rerank 救不了召回：漏在召回阶段的文档，精排永远看不到。定位线上问题时先看"正确答案在不在召回列表里"，不在就去改数据与召回，而不是加更贵的 Rerank。
  • 把双编码器当 Rerank 用是常见的偷懒：两者本质都是打分，但双编码器没有 token 级交互，精排增益有限——想省成本可以接受，但别指望它带来真正的精排提升。
  • 交叉编码器有长度截断：模型有最大输入长度，超长候选要截断，而关键证据可能被截在窗口外；长文档可以先切成候选段落再精排。
  • Rerank 分数只在同一 query 内可比，不要拿它跨请求比大小或设全局阈值。

召回决定答案的上限，Rerank 决定能在多大程度上逼近这个上限——排查质量问题永远从"证据是否被召回"查起。

六、证据与引用：让答案钉在材料上

RAG 场景的幻觉要拆成三个来源处理

模型为什么会在有材料的情况下还说错，机制层面的成因是通用的，RAG 工程里更值得关心的是把它拆成三个可定位的故障点：

  1. 没证据：该查到的内容没被召回（召回失败），模型只能硬答——错误来自检索端。
  2. 有证据但不照着说：材料是对的，模型没忠实于材料，自由发挥——错误来自生成端。
  3. 多份证据矛盾时选错：召回了几条互相冲突的片段，模型挑了错的那条——错误来自证据组织与去噪。

三个来源的处理手段完全不同：第 1 类去修数据与召回；第 2 类靠"证据组织 + 输出约束 + 校验"压住；第 3 类靠提示词要求模型识别矛盾并说明、必要时做多片段一致性处理。排查 RAG 幻觉的第一步是归因，而不是一律去改提示词。

证据组织的两个工程要点

  • 片段编号化：给送入上下文的每个片段一个稳定的编号（如 [1]、[2]），提示词里要求"只能基于方括号编号的材料作答，并在相关句尾标注引用编号"。编号让"模型引用了谁"变成可追踪的结构，而不是散文里说不清出处的转述。
  • 去噪优先于堆料：把明显不相关的命中在生成前滤掉（Rerank 截断、冲突片段降权），比把 TopK 全塞给模型更有效——噪声越多，模型越容易被带偏，也越难做到忠实。

引用与校验：把"看起来对"变成"可验证对"

引用本身也会被幻觉：模型可能编造格式正确但根本不存在的片段编号或来源。所以引用必须做成闭环，而不是"让模型自己标个序号就完事"：

  • 每个 chunk 在索引时携带来源元数据（文档 ID、标题、页码/章节、URL），引用编号能反查到具体 chunk。
  • 生成后做 grounding 校验：解析答案里声明的引用编号，核对"该句子声称的内容是否确实出现在对应片段中"。对关键断言（数字、结论、实体），做"断言在证据中可定位"的检查，找不到就拒答、降级或触发一次补充检索。
  • 展示层的引用（给用户看的来源链接）必须做真实性与可达性校验后再展示，别把模型输出的"假引用"直接渲染给用户。

拒绝与降级的度

把"没把握就拒答"调得太狠，会换来高拒答率伤体验——用户问的是正常问题却被反复告知无法确认。工程上按场景设策略：内部知识助手可以严格（宁可不说错），C 端问答要更激进地兜底（给出最接近的资料并标注不确定）。RAG 的目标不是"零幻觉"，而是让每个答案都能被追到材料、没材料时明确说不知道——前者靠校验与拒答，后者靠提示词与产品策略共同实现。

七、Embedding：句向量是怎么训出来的

先分清 token 向量与句向量

模型内部给每个 token 一个上下文向量，那是"词在句中的表示"；检索用的 句向量（sentence/document embedding） 是另一回事：它把整段文本压成一个固定维度的向量，让"语义相近的文本在向量空间里距离也近"。两者常被混为一谈，但用途完全不同——句向量是专门为"相似度比较与检索"这一件事优化的产物，它不是对文本的完整理解，而是把文本映射成可用于比较的坐标。理解了这一点，就不会对句向量的"丢信息"大惊小怪：压缩成单个向量本来就会丢细节，这是它与生俱来的取舍。

双塔结构与训练方式

检索型句向量模型的标准结构是双塔（bi-encoder）：query 与 document 分别经编码器处理，取池化结果（[CLS] 或均值池化）并归一化，检索时算两者内积/余弦。query 塔和 document 塔可以共享参数，也可以各自独立。

它靠对比学习（contrastive learning）训练：目标是让"相关的（query，文档）对"向量靠近，让"不相关的对"远离。训练数据来自搜索点击日志、LLM 生成的问题-文档对、人工标注的相关性数据等；损失函数是带温度系数的 InfoNCE 式损失——给定一个正样本，把同 batch 里其他样本当作负样本拉开。决定最终质量的两个关键工程细节：

  • 难负样本（hard negative）挖掘：只用随机负样本，模型很快学会"表面差异"就够区分；用检索器（如 BM25/初版向量模型）召回"看起来很像但实际不相关"的样本当负例，才能逼模型学到真正的语义判别。
  • query 侧的指令前缀：很多开源检索模型训练时给 query 加指令前缀（"为这个句子生成表示以用于检索相关文章"），给文档不加。使用时必须与官方做法一致，query 漏加前缀或给文档也加，检索质量会明显下降。

两个必须有的工程认知

  • 通用 Embedding 有领域落差。通用模型是在通用语料上对齐"通用语义"；法务、医疗、代码、内部黑话这类垂直语料，通用模型经常"看着相关却检索不对"。垂直领域优先用领域内微调的模型，或在自己语料上做领域适配，而不是拿通用榜单冠军硬扛。
  • 表示质量有上限，但训练方向要匹配使用方向。句向量表征空间存在"各向异性"（向量挤在狭窄锥形区域，退化到按词频区分），很多模型通过后处理（如白化）缓解。对使用者来说更现实的提醒是：评估 Embedding 必须放在自己的数据上测召回，而不是背榜单分数。

八、Embedding 选型与评测：榜单之外看什么

MTEB / C-MTEB 是什么、该怎么看

MTEB（Massive Text Embedding Benchmark） 是目前事实上的句向量评测基准，覆盖检索（Retrieval）、语义相似度（STS）、分类、聚类、重排等多类任务；C-MTEB 是其中文版。面试里被问"Embedding 怎么选型"，报出这两个基准是入场券，但真正的功力在于会看榜单：

  • 榜单是多个任务的平均，而你的业务可能只用其中一类（比如只做检索）。要按任务子榜看：做 RAG 就看 Retrieval 类的分数，而不是总分。
  • 看语言匹配：中文业务重点看 C-MTEB 以及中文检索子任务，很多模型中英表现不均衡。
  • 榜单分数衡量的是"通用分布"，垂直领域（代码、法律、医疗、内部文档）的分数要自己在领域数据上测。

选型时按这个清单过一遍

  • 任务类型：你是做检索、相似度判重、还是分类聚类？不同模型在不同任务上各有侧重，别只看一个分。
  • 最大输入长度与切块匹配：句向量模型有长度上限（如 512/8192 token），超长文本会被截断。长文档做 RAG 时，要么选支持长输入的模型，要么让切块长度配合模型上限——这是检索失败的一个隐蔽来源。
  • query/文档前缀要求：是否需要对 query 加指令前缀（见上节），两端编码是否要区分，跟官方用法保持一致。
  • 维度、精度与成本：输出维度决定索引体积与带宽；是否支持量化（int8/binary）；API 还是自部署——这些直接影响大规模检索的工程成本。模型与价格迭代很快，这类结论不要写死，按当时实测为准。
  • 相似度度量一致性：模型的向量是按"内积"还是"余弦"训练的（通常二者等价，只要两边都做了归一化），向量库检索的度量必须与训练一致，混用会拿到错误的相似度。

反例与自测方法

  • 只盯总分榜一，拿通用冠军模型直接上垂直检索——领域落差会让它输给领域微调的小模型。
  • query 和文档用同一种处理——该加指令前缀的模型，给文档也加前缀或给 query 漏加，检索质量静默下降。
  • 不测就上线。选型的最后一步永远是在自己的"问题集 + 文档集"上测召回：构造几十到几百条真实 query 与其对应的 gold 片段，对比候选模型的 Recall@K，再叠加成本与延迟做决定。生产里的 bad case 持续回流进这个评测集，让选型跟着业务走，而不是一次定终身。

九、向量检索的载体：ANN 索引与向量库

为什么检索必须是"近似"的

对几百万、上千万条向量做检索时，精确的最近邻需要全量扫描比对，代价不可接受，所以生产环境都用 ANN（Approximate Nearest Neighbor，近似最近邻） 索引——用一点点召回损失，换来几个数量级的检索加速。召回与速度之间的取舍，由索引参数显式控制。主流的两个家族是图索引与倒排索引。

HNSW：分层小世界图

HNSW（Hierarchical Navigable Small World） 把向量建成一张分层的邻居图：顶层图连接稀疏、每条边"跳得远"，用于快速定位大概区域；越往下层边越密、越精细。查询从顶层入口开始，逐层向下做贪心搜索逼近最近邻；插入新向量时按概率决定它出现在哪些层。

  • 优点：查询延迟低、召回率在同量级索引里最高，对"查询量大、数据量中到较大"的场景几乎是最佳默认。
  • 代价：索引全驻内存（图结构 + 向量本体），内存占用大；构建耗时长；增量删除会逐渐劣化图质量，频繁增删需要重建或留 tombstones 处理。
  • 三个关键参数控制取舍：图邻居数 M（越大越准越费内存）、构建期搜索宽度 efConstruction、查询期搜索宽度 efSearch（越大召回越高、延迟越高）。

IVF：倒排 + 量化

IVF（Inverted File） 走的是聚类路线：建索引时用 K-means 把向量空间聚成 nlist 个桶，每个向量只属于离它最近的桶（并记录与桶中心的残差）；查询时只进最接近的 nprobe 个桶里精确比对。它和"先分类再搜索"是同一个思想，nprobe 越大召回越高、越慢。

  • IVF-PQ 是处理超大规模的关键组合：把每个向量切分成若干子向量，分别做乘积量化（PQ），压缩成极短的码——向量本体可以压缩几个数量级，内存从"全量向量"降到"短码 + 质心表"，代价是检索精度下降。适合亿级、内存受限的场景，本质是用精度换内存。

HNSW 与 IVF 家族怎么选

维度HNSWIVF-FlatIVF-PQ
检索速度快，稳定的低延迟随 nprobe 增大而变慢快（配合查表）

召回率高且稳定高（nprobe 够大时）受量化损失影响

选型不是二选一：向量库通常允许同一份数据建多个索引，或用 efSearch/nprobe 之类的参数在召回与延迟之间现场调。

实践里有几个高频翻车点：度量选择必须与 Embedding 训练一致（余弦/内积混用，相似度语义就错了）；带过滤的检索性能——先做元数据过滤（权限、时间）再在过滤集上 ANN 搜索，过滤太狠时候选集太小、图索引退化，需要按过滤场景设计索引或接受全扫描；规模增长后索引参数没有跟着调——百万级时 efSearch=16 的召回可能不够，要用自己的评测集实测。最后一条提醒：向量库解决的是"存与搜"，解决不了"该存什么"——数据侧（解析、切块、Embedding 质量）才是检索效果的上游瓶颈，很多团队在库选型上花大量精力，却对自己的索引内容质量一无所知，这是本末倒置。

十、多向量与 Late Interaction（ColBERT）

双编码器的压缩损失

稠密检索有个结构性损失：整段文档被压成一个向量，token 级别的细节全被平均掉了。文档里只有一句话真正相关、其余都是铺垫时，单向量表示可能把关键信息"稀释"得检索不出来；长文档尤其严重。多向量检索就是针对这个问题的补强方案。

ColBERT：保留词级交互，又保持文档可预索引

ColBERT 的思路介于双编码器（快但不精细）与交叉编码器（精细但无法预索引）之间：query 和文档各自编码后不压缩成一个向量，而是每个 token 保留一个向量。打分时用 Late Interaction——query 的每个 token 向量去和文档的所有 token 向量算相似度、取每个 query token 的最大相似度再加总：

score(query, doc) = Σ_query_token  max_doc_token  cos(q_i, d_j)

这个设计的精妙在于两个"既要又要"：query 与文档的 token 之间发生了细粒度交互（精度接近交叉编码器）；而文档向量仍然可以离线预计算并索引进向量库（不需要像交叉编码器那样查询时才实时编码）。代价是索引与查询的计算量都远大于单向量：每个文档要存一串 token 向量而不是一个向量。工程上靠向量压缩（如 ColBERTv2 的残差压缩）与剪枝（只对候选部分 token 算 MaxSim）把它压到可用。

什么时候值得上 ColBERT

  • 检索质量要求高、术语/局部表述匹配重要（代码、法律、科研文献），单向量检索明显漏召回时。
  • 长文档场景，单向量的"稀释"问题严重。
  • 一般做第二路检索器与 BM25、单向量混合使用，而不是全线替换——它贵，换来的是更高的召回上限。

反过来说，简单相似度任务、数据量小、或预算敏感的场景，不值得为 ColBERT 的索引开销买单。面试问"ColBERT 和双编码器/交叉编码器什么关系"，答"它用 Late Interaction 在'可预索引'与'词级交互'之间取了折中"，就抓住了它存在的全部理由。

十一、文档解析：从原始文件到干净的文本

解析的目标不只是"抽文本"

RAG 的输入往往是 PDF、Word、扫描件、网页这类原始文档，而索引需要的是干净、顺序正确、带结构标记的文本。解析要同时交付三样东西：

  • 正确的文本流：正文按阅读顺序输出，页眉页脚、目录、批注等噪声剔除。
  • 结构信息：标题层级、章节、页码——这些是后续结构感知切块和引用溯源的原料。
  • 复杂元素的保真表示：表格、公式、代码块如果被拍平成乱序文本，切块和 Embedding 都会被毒化。

处理路径与技术栈

  • 文本型 PDF：直接从 PDF 提取文本层即可，但要注意文本层 ≠ 正确顺序——多栏排版、跨页表格、页眉页脚会让提取结果乱序或混入噪声。
  • 扫描件/图片型文档：必须走 OCR，先做版面分析（layout analysis）识别标题/正文/表格/图片的区域，再对文本区域做文字识别。中文与公式的 OCR 错误率明显高于英文，是质量瓶颈的高发区。
  • 表格：转换成结构化的 Markdown/HTML/CSV，而不是拍成一行行散文本——结构丢失后表格的语义（哪列是什么）就没了。
  • 公式：识别成 LaTeX，而不是 OCR 成乱码字符。
  • 工具：MinerU、Docling、Unstructured 这类开源解析器都能把 PDF 转成带结构的 Markdown/JSON；OCR 引擎可选 PaddleOCR 等。它们的能力（尤其中文、公式、复杂表格）和输出格式差异很大、迭代又快，不要背工具结论，要按自己的文档抽样实测：找一批代表性 PDF，对比各工具在版面顺序、中文准确率、表格/公式还原、输出结构化程度上的表现，再算批量处理成本。

三个高频事故

  • 把"能抽出文字"当"解析完成"。丢掉标题层级、页码、表格结构，后续结构感知切块做不了、引用溯源的页码也没了——解析阶段省的事，后面全都要还。
  • 格式噪声直接入库。页眉页脚、重复的模板文字、导航栏文本进入 chunk，embedding 被这些高频噪声带偏，检索时反复命中"模板片段"。
  • 公式表格乱码毒化索引。公式识别成乱码、表格拍平后，包含关键数据的检索命中率断崖式下跌——复杂元素需要专门的保真处理，不能靠通用解析糊弄过去。

抽样质检是解析环节的标配：人工抽查每批文档的解析结果（文本顺序、结构、复杂元素），把错误率控制在可接受范围再进索引。

十二、切块（Chunking）与 Overlap：决定检索粒度的设计

切块为什么是检索效果的枢纽

Embedding 把整段文本压成一个向量，文本越长信息越被稀释；反过来，如果切得太碎，一个完整的语义单元（一段论证、一个表格、一条操作步骤）又被拦腰切断，检索命中了也答不完整。切块的本质是决定"检索单元"和"答案单元"的对齐程度——理想情况下，一次回答所需的信息应该尽量落在同一个 chunk 里。这是 RAG 里性价比最高、也最常被参数化糊弄过去的环节。

从粗到细的切块策略谱系

  • 固定大小切分：按 token 数硬切。简单可靠，是基线方案；但它无视语义边界，是最容易切碎句子的方案。
  • 递归结构切分：按分隔符层级（段落 → 句子）递归切到目标长度附近。比硬切尊重语义，是最常用的通用默认。
  • 结构感知切分：对 Markdown/HTML/代码这类有结构的文档，按标题层级、代码块、表格行切——chunk 天然带着章节语义，检索命中还能直接定位到小节。
  • 语义切分：用 embedding 检测文本间的语义断点（或让 LLM 判断断点），切出的块语义更完整，但需要额外计算，量大时不便宜。
  • 父子切块：小块负责检索（命中精准），命中的小块向上映射到包含它的父块送进上下文（语义完整）——缓解"小块命中但信息不全"的矛盾，是实践中很有效的组合。

两个关键参数

  • 块大小：要和 Embedding 的长度上限与任务的"答案粒度"匹配。常见几百 token 是经验区间，但具体值取决于文档形态，要在自己的数据上验证。代码、表格、法律条文这类"信息密度高"的内容，比散文更适合更小的块。
  • Overlap（重叠）：把切分边界附近的文本在相邻块间重复一段，缓解"语义正好跨过切点被切断"的问题。典型取块长度的 10%~20%。overlap 不是越大越好：重叠过多会让相邻块高度重复，索引冗余、检索去重变难、向量被重复内容稀释。

反例清单

  • 整篇文档当一个块：超长文本被压成一个向量，什么都检索不出来——这是把 Embedding 当全文存储用的经典错误。
  • 照抄默认参数不验证：500 token + 50 overlap 只是起点，不同语料的最优解差异很大，拿真实问题集测 Recall@K 才是判断依据。
  • 中文按字符硬切：把句子、术语拦腰切断，检索质量断崖下跌；切分要以能识别的语义单位为准。
  • 切完丢了溯源：每个 chunk 要能指回来源（文档 ID、章节、页码），否则后续引用与去重都无从谈起——切块不是终点，是索引元数据的起点。

十三、元数据与增量更新：把索引当有生命周期的数据来管

每个 chunk 该带什么元数据

检索命中的 chunk 不只是要送给模型的文本，还是一条需要溯源、过滤、展示的记录。索引时建议为每个 chunk 维护的元数据：

  • 来源：文档 ID、标题、章节路径、页码/位置、来源 URL——支撑引用溯源与展示。
  • 版本与时间：文档版本号、入库/更新时间——支撑增量更新与时效过滤。
  • 内容指纹：文档内容哈希、chunk 哈希——支撑去重与变更检测。
  • 权限/范围：可见性标签（部门、用户组、机密级别）——权限过滤要在检索阶段就生效，而不是生成后才发现。

增量更新要以"文档"为粒度

知识库是活的：文档会新增、修订、下架。增量更新最容易犯的错是按 chunk 管理生命周期——文档改了，旧 chunk 散落各处，删不干净，检索里全是过期内容。规范的做法是以文档（doc）为粒度做版本化：

  • 新增：解析 → 切块 → 写入，幂等（同一 doc_id 重复写入不产生双份）。
  • 更新：一个 doc 的任何 chunk 变化，都在事务里"删除该 doc 的全部旧 chunk → 写入新 chunk"（或带版本号并靠检索过滤只留最新版）。保证要么全旧、要么全新，不留新旧混杂的中间态。
  • 下架/删除：按 doc_id 删除其全部 chunk，并清理不再被引用的元数据。

一致性风险与对策

  • 更新期间的瞬时不一致：文档 A 已换新版，但某次检索仍命中旧 chunk。低风险可接受（下一次检索即新）；敏感场景给检索加时间/版本过滤。
  • 全量重建与增量的选择：量级小、结构简单时周期性全量重建最省心（索引一致性最好保证）；量大、更新频繁才需要增量管道，此时"变更检测"（靠文档哈希判断哪些 doc 真变了）是省算力的关键——不是每次同步都全量重embedding。
  • 孤儿数据：删除文档后忘删其 chunk，是知识库最常见的"幽灵答案"来源——把 chunk 的写入/删除做成与文档生命周期绑定的自动化，而不是靠手工脚本。

一句话：切块是检索的单元，文档才是生命周期管理的单元——所有增删改都锚定在 doc 上，索引才不会在长期维护中腐烂。

十四、数据质量工程：清洗与去重

RAG 是典型的 GIGO 系统

检索的上限由数据质量决定，这一点怎么强调都不过分——脏数据进索引，检索侧做再多优化也只是把垃圾翻得更准。数据管道在上线前最值得投入的环节，就是清洗与去重。

清洗：把噪声挡在索引外

进入切块之前的原始文本要过一遍清洗，主要处理：

  • 模板噪声：页眉页脚、网站导航、免责声明、重复的模板段落。这类文本高频出现，embedding 很容易被它们"带偏"——检索常命中模板而不是正文。
  • 格式残留：HTML 标签、转义符、OCR 错字。OCR 错字对精确匹配（BM25、术语召回）伤害尤其大，识别准确率低的数据宁可修复或标注也不硬上。
  • 无信息内容：过短碎片、纯符号、乱码块。
  • 敏感信息：脱敏要在数据管道里做，别等模型把密钥或隐私拼进答案再补救。

去重：分三个层次

重复内容会让检索结果被同一份知识的多个拷贝占据 TopK，还稀释精排的有效候选。去重要分三层处理：

  • 精确重复：文档级或 chunk 级的哈希碰撞，直接去重，最简单可靠。
  • 近似重复：同一文档改了几个字、或同源转载——用 MinHash/SimHash 这类局部敏感哈希做 near-duplicate 检测，阈值内的归并。
  • 语义重复：表述不同但内容相同（如多份文档描述同一套流程）。语义层去重最贵也最需要谨慎，通常只在特定业务语义（同一产品、同一政策的多份说明）下做，避免误伤真正不同的内容。

质量过滤与验证

  • 对入库单元做质量打分过滤：乱码比例、停用词密度、长度异常、垃圾概率这些信号可以筛掉明显低质的块。
  • 数据管道要带抽样质检：人工抽查 + 检索效果回归，保证清洗规则没有误伤（把有价值的文档过滤掉了）。
  • 质量治理是持续过程不是一次性动作——新接入的数据源要过同一套清洗与质检流程，数据管道和检索评测集一起持续演进，索引才不会边用边烂。

十五、GraphRAG 与 KAG：把关系变成可检索的知识

向量检索的盲区：只见片段，不见全局

向量 RAG 的检索单元是"语义相似的片段"，它对两类问题结构性失效：跨文档聚合问题（"这份技术方案里提到了哪几种鉴权方式，各自什么场景？"）和关系多跳问题（"A 模块的改动会影响哪些依赖它的服务？"）。这类问题需要的是知识之间的关系网络，而不是某一段话——这是图谱增强检索登场的理由。

GraphRAG：从文本中构建知识图谱再检索

GraphRAG（以微软的方案为代表）的管线分两段：

  1. 离线建图：用 LLM 从文档里抽取实体（人、系统、术语、指标）与它们之间的关系，构建知识图谱；再做社区检测（把图切分成关系紧密的社区），并为每个社区生成摘要。
  2. 检索回答：对"全局性问题"在社区摘要上做由粗到细的聚合回答；对"局部性问题"从相关实体出发沿图扩展补充上下文。

它真正解决的是"问题横跨大量文档、需要在更高层面归纳"的场景——把"在哪几段话里找"升级为"在哪些实体与关系上找"。代价也相当大：LLM 抽实体建图很贵，图的质量、Schema 设计、更新维护都需要持续投入。

KAG：领域知识图谱与 LLM 的双向增强

KAG 走的是另一条强化路线：以结构化的领域知识图谱为骨架，让 LLM 与图谱互相补位——图谱负责精确的实体关系与逻辑约束，LLM 负责理解开放性问题、并把非结构化文本里的信息与图谱对齐。它的定位更偏向"专业领域（医疗、金融、政务）里把知识图谱真正用起来"，适合领域本体清晰、对准确性与可解释性要求高的场景。相比通用 GraphRAG 的"文档聚合"，KAG 更强调用既有知识体系约束回答、支持推理，工程上需要领域本体设计，起步成本更高。

该不该上图谱：决策要点与反例

  • 问题确实以"全局归纳、跨文档关系、术语体系固定"为主，图谱增强才有账可算。
  • 反例 1：把 GraphRAG 当"更高级的 RAG"。语料以事实性片段问答为主时，向量 RAG 足够，图谱只是徒增建图与维护成本。
  • 反例 2：文档量小也上图谱。图谱的收益来自"关系网络"的密度，几十篇文档的关系网络撑不起建图成本。
  • 反例 3：对图谱质量不设防。LLM 抽出的实体关系有噪声，错的关系会像错的知识一样被传播——建图质量要纳入质检，别把"抽出来了"当"抽对了"。
  • 现实中的常见组合是向量 RAG 打底 + 图谱只在关系/聚合类问题上兜底，而不是全线替换。

十六、Agentic RAG：让检索策略从"固定管道"变"按需决策"

固定管道的天花板

经典 RAG 对每个 query 走同一条固定管道：先检索、再生成。但真实问题形态差异极大——简单事实问答可能不需要检索（模型自己知道）；时效性问题需要联网；多跳问题需要"先查 A、再根据 A 查 B"；聚合问题需要图谱。用一条固定管道服务所有问题形态，本质上是用同一把钥匙开所有的锁：检索冗余时浪费成本与延迟，检索不足时答案缺料。

Agentic RAG 在决策什么

Agentic RAG 把"检索策略"本身交给模型按需决策，围绕几个决策点展开：

  • 要不要检索：问题简单且模型有把握时不查，省掉无效检索；不确定再查。
  • 查什么：在多个检索源之间选路——向量库、网页搜索、数据库、图谱、某个具体 API。
  • 怎么查：自主改写 query、拆成子问题逐一查、决定查几轮。
  • 查完怎么办：评估检索结果是否够用——不够就换检索器/换问法再来一轮（纠偏式检索），而不是把不满意的结果硬着头皮交给生成。
  • 生成前验证：对答案做 grounding 校验，不扎实就再查或拒答。

对应地，业界有几个代表性思路：Self-RAG 训练模型在生成中输出反思信号，自主决定"该不该检索、检索结果可不可信"；CRAG（纠偏式检索） 给检索结果打分，质量差就触发修正（分解 query 或换检索源）。这些都属于"检索由 Agent 编排"的家族，区别在决策的自主程度与实现成本。

工程上怎么落地：先路由，后 Agent

Agentic RAG 听着优雅，代价也明确：每一步都是模型调用，成本与延迟成倍上涨，且多了一步"模型决策错误"的新失败模式（该查的没查、不该查的乱查、检索结果不会用）。工程上的务实路线是阶梯式引入：

  1. 先做检索路由：用轻量分类（规则或小模型）把 query 分流——简单问答不检索、片段事实走向量、时效走搜索、聚合走图谱。绝大多数线上流量用固定路由就能解决，稳定且便宜。
  2. 只有路由覆盖不了的长尾（复合问题、多跳、跨源）才交给 Agent 做动态编排。
  3. 保留校验兜底：无论路由还是 Agent，生成前对答案做证据校验，防止模型"忘记检索直接凭记忆答"——这是 Agentic RAG 里最需要警惕的失败模式。

反例：把每个请求都丢给 Agent 全权处理——简单问题被绕了远路，成本与延迟失控，还引入决策不确定性。Agentic RAG 的价值在"把灵活留给真正需要灵活的问题"，而不是让所有问题都变得更复杂。

十七、RAG 评估：先把问题定位到环节

为什么 RAG 的评估必须分环节

RAG 是一条管道，任何一个答案出错，都可能源自两个完全不同的环节：检索没找到证据，或者找到了但生成没用对。如果只用一个端到端正确率打分，你只知道"错了"，不知道"该修哪"——这是 RAG 评估与普通模型评估最本质的差异。所以 RAG 评估的基本方法就是两层分开测、各自归因，这里给出定位与要点：

  • 检索层：看证据是否被召回。指标用 Recall@K、命中率（gold 片段在不在 TopK 里）、MRR/NDCG 这类排序指标。需要一份标注集：真实 query → 其对应的 gold 片段（哪些文档才算是相关证据）。检索层不过关，改的是数据管道与召回策略，而不是提示词。
  • 生成层：看证据是否被忠实使用。核心是忠实度（faithfulness）——答案里的断言能否在给定上下文中找到依据；再辅助看答案相关性与完整性。生成层不过关，才去动证据组织、提示词与输出校验。
  • 端到端：在两层之上看整体答案质量、引用正确率与拒答是否合理，用于验收与竞品对比，但不能替代分层评估做归因。

落地的要点与提醒

  • 评测集要跟着业务长：从生产 bad case、真实高频问题、边界场景里持续回流构建 query-gold 标注集，而不是造一批"看起来像"的样例测一次就完。选 Embedding、定切块参数、调 TopK，都要在同一套评测集上做回归。
  • RAGAS 等框架的价值在"约定指标口径"：把忠实度、上下文相关性这类概念标准化成可计算的分数，可以作为参考实现，但生产归因仍然要靠分层抽检与人工复核，别让自动分数替代判断。
  • 自动分数的边界：忠实度这类"答案是否忠于上下文"可以较可靠地自动判；但"答案对业务是否真正有用"必须回到业务视角的人工抽检。
  • 反例：只跑端到端正确率，出了问题在"改提示词"和"改数据"之间反复横跳；或者只测检索（Recall@K 好看）却忽略生成端根本不忠实——两层缺一不可。

到这一节为止，一条完整的 RAG 工程链路已经走通：数据管道决定检索上限，检索与精排逼近这个上限，生成用证据与校验把答案钉在材料上，图谱与 Agent 化解决固定管道覆盖不了的问题，分环节评估保证每一次改动都能定位到该修的那一环。
