多模态应用

vexillium2026/9/7大约 18 分钟后端开发人工智能

这一章把多模态当成一组新的输入通道来工程化，而不是把每种模态都讲成独立领域。文本应用要解决的问题是"怎么把问题与资料变成模型能推理的 token"；多模态只是把同样的工程问题扩展到像素、音频与视频：如何把非文本信号编码成模型可推理的表示、如何采样控制 token 与成本、如何与既有文本链路（Agent、检索、文档解析）对齐。全章按"底座 → 接入 → 场景"推进：先讲 VLM 的架构范式与三条技术路线（CLIP 对齐 / LLaVA 投影 / Qwen-VL 原生多模态），再讲把视觉接进 Agent 的 GUI 操作与截图理解、把图文接进检索的多模态 RAG、文档侧的 OCR 选型、以及时序约束最硬的实时语音链路，最后对视频理解与生成式多模态做概览定位。具名模型与产品一律按"机制与取舍"描述，易过时的能力清单按"该看什么维度、如何自测"处理。

一、把"看懂"变成输入通道：VLM 的架构范式

一切多模态应用共享同一个问题

无论输入是图片、PDF 扫描件、屏幕截图还是视频帧，落到应用层的问题只有一个：把它变成 LLM 能参与推理的表示。文本天生是 token，图像不是——所以 VLM（视觉语言模型）的架构几乎都长成同一副骨架：视觉编码器（把图像变成视觉特征）→ 投影层（把视觉特征映射进语言模型的表示空间）→ LLM（跨模态推理）。理解了这副骨架，就能解释多模态应用里的绝大多数工程现象：为什么高分辨率图那么贵（视觉 token 多）、为什么模型"看得懂但数不清"（视觉编码的粒度问题）、为什么图文混合任务表现不稳（对齐质量问题）。后面谈 Agent、RAG、OCR，本质都是围绕这个骨架做取舍。

三条技术路线的机制差异

路线对齐/训练方式强项主要代价
CLIP 类对比对齐图文对比学习拉近配对表示表示对齐好，检索/零样本分类强不直接产出生成，缺细粒度文本理解
LLaVA 类投影微调现成编码器 + 投影层 + 指令微调训练轻、易复现、生态基线多视觉与语言融合深度有限
Qwen-VL 类原生多模态视觉 tokenizer 与 LLM 联合设计图文交错、多图、定位/文档能力均衡训练与数据成本最高

三条路线不是版本高低，而是"视觉表示与语言推理融合到什么程度"的取舍：

  • CLIP 类解决的是"图文对齐"：用海量图文对做对比学习，让配对的图与文在向量空间里靠近。它产出的是表示而非生成，天然适合检索与零样本分类；单靠它做不了开放式问答，但它作为视觉编码器被广泛复用。
  • LLaVA 类是工程上最容易复制的范式：拿一个训练好的视觉编码器和一个现成 LLM，中间加一层投影（线性层/Q-Former/MLP 等），再用指令数据微调，让 LLM"学会看"。它的价值在于把"做多模态"从预训练级成本降到了指令微调级成本，大量开源模型与垂直方案走这条路。
  • Qwen-VL 类原生多模态不再把视觉当"外挂编码器"：视觉 tokenizer 与语言模型联合设计、支持图文交错输入与多图推理、对高分辨率与文档类图像专门处理，能力上限最高，但训练与数据成本也最高。

两个贯穿应用的工程事实

第一，分辨率与细节是视觉侧的"上下文长度"。图像切成 patch 后，视觉 token 数量随分辨率上升，高分辨率文档/截图会带来与长文本同源的 token 与成本问题——于是出现动态分辨率、分块输入（把大图切成多块再聚合）等工程手段。第二，模型"看得到"不等于"读得准"：视觉编码是 patch 级模式，对"逐字逐像素"的内容（小字号、密集表格、精确坐标）会犯错。因此凡是要求精确文本/结构输出的任务（文档提取、截图点按），工程上都要叠加解析层或结构化输入，而不是裸调 VLM——这个判断会在文档与 GUI 场景里反复出现。

二、视觉接入 Agent：屏幕、截图与新的"观察通道"

GUI 操作（Computer Use）的机制：像素当观察，动作当工具

GUI 操作类 Agent 的目标是让模型像人一样操作界面：观察屏幕 → 决定动作（点击哪里、输入什么、滚动多少）→ 观察结果 → 继续下一步。它的循环骨架与文本 Agent 一致，差异集中在两端：观察是高密度的像素与界面状态，动作是带坐标的离散操作。因此工程上的核心问题不是"模型能不能看懂截图"，而是"用什么样的表示喂给模型、动作如何校验"，业界实践收敛出清晰的优先级：

  • 结构化界面优先：能拿到可访问性树（accessibility tree）、DOM 或平台控件树时，优先用它——它直接给出元素的语义、角色、名称与坐标，模型据此决策远比"看像素猜位置"稳，token 成本也低一个量级。
  • 像素作兜底：只有纯图像界面、远程桌面、无结构树的自研客户端等场景才需要截图 + VLM 定位，代价是更高的 token 成本与"看错坐标"的风险。
  • 混合形态：结构化树为主干、截图提供视觉上下文（判断布局、颜色、选中态），是多数复杂产品的常态。

GUI 操作真正的难点在"动作的可靠性"，不在"视觉理解"

用视觉操作界面的产品最容易翻车的地方不是模型没看见，而是动作缺少前后校验：点没点上、点错了、页面还没加载完就执行下一步、长任务里误差一步步累积导致整体漂移。对应的工程手段全部落在运行时：点按前先做状态断言（元素存在且可点、页面稳定），点按后再校验是否产生预期变化，长任务定期回到"当前在哪、目标是什么"做一次自检。动作工具的参数也要设计成"元素标识或语义优先、坐标作后备"，而不是让模型裸输出像素坐标——界面一变，坐标全废，语义却仍然可解析。

失败模式里最常见的是三类：坐标精度问题（点偏了），用元素框中心 + 命中区域容错缓解；界面二义性（一堆相似按钮不知道该点哪个），补充 DOM 上下文或让模型先描述意图再选元素；长任务漂移（前一步的微小错误被后续步骤放大），靠中途自检与断点恢复来止损。

截图理解与文档 VQA：视觉问答的任务形态

把一张图或截图交给模型回答，是视觉应用最轻的形态：图 + 问题 → VLM 生成，覆盖用户贴图提问、图表/页面截图问答、文档页问答。这类任务要分清"看图说话"与"精读文字"的边界：

  • 需要引用原文、还原表格、逐字提取时，前端应先把图像过一遍 OCR / 文档解析，把文本与结构交给模型，而不是让模型对着像素硬读——对着小字号像素读文字，是视觉模型幻觉的高发区。
  • 需要图表大意、位置关系、颜色与版式判断这类"看整体"的任务，才适合纯视觉问答。
  • 图表与截图还有两个常见技巧：表格先转结构化（markdown/CSV 进上下文），关键区域裁剪放大再提问（规避小字号与细节丢失）。

反例集中提醒一句：让 VLM 对着原始分辨率整图做"逐字引用型"问答，或对一屏十几个小图表不做切片就问细节，模型会一本正经地编——这不是模型笨，是输入粒度配错了任务。

三、多模态 RAG：当"文档"里不只有文字

文档成分决定入库策略

文本 RAG 的检索单元是"切出来的文字块"；一旦文档里有表格、图表、扫描件，问题就从"怎么切"变成"这个成分该以什么形态入库"。按文档成分划分，业界收敛出三类入库策略：

文档成分入库策略适合的查询
纯文字/扫描正文OCR / 文档解析转文本，走常规切块索引文字内容检索
表格解析成结构化（markdown/CSV），保留表头与行列关系"某行某列的值"型精确查询
图表（趋势图/柱状图等）生成结构化摘要或数据表入库，必要时保留原图"趋势怎么样、哪年最高"型粗粒度查询
图文混排页切块时保住图与所属段落的关系需要"图 + 上下文"一起理解的查询

核心判断是：图表的信息密度不在像素里，而在"布局与数值的关系"里。把一张趋势图"文本化"成图注与坐标轴标签，就丢掉了趋势本身；把它原样存图，文本检索又命中不了。因此图表类文档的工程惯例是先做结构化抽取——表格转 markdown/CSV、图表用描述模型生成摘要与数据表——让"可检索的文本"承载图里的信息，查询需要细节时再回到原图用视觉理解兜底。

图文混排的两条硬规矩

  • 别把图从它的上下文里切走。解析图文混排文档时，图片要与其所属段落/章节保持关联（合并进同一检索单元，或保留引用关系），否则图成了"孤儿"，查到时缺语境，语境里又缺图。
  • 文本索引与视觉索引分工。让检索命中的主力永远是文本与摘要（便宜、准、可控），多模态 embedding 只做补充通道：先用 caption/文本召回，需要视觉细节时再把原图喂给 VLM。把图片裸塞进文本向量库（向量化时图片被丢弃或转成乱码），是这类系统最常见的返工原因。

多模态 Embedding 的机制与边界

多模态 embedding 与对比学习路线同源：把图像与文本映射进同一个向量空间，让"内容相关的图与文"在空间里靠近。它解决的问题是跨模态的粗粒度召回——"有没有一张讲 XX 的图/报表"，这种 query 用文本索引确实难命中，多模态 embedding 是合理补充。但它的边界也要说清：向量对齐是"整体相似"，不是"细粒度理解"，回答不了"这张表里 2023 年的值是多少"这类问题——那需要结构化抽取而非 embedding。工程上把它当"第二路召回"与文本通道合并去重，而不是替代解析层。

四、OCR 技术选型：先问版式，再挑方案

OCR 的职责是把图像里的文字变成机器可用内容。选型第一个动作不是比较各家识别率，而是定义清楚输出需求——不同需求对应完全不同的技术档位。

三档方案与各自机制

档位机制强项主要代价
传统 OCR版面分析 + 文本检测 + 逐字识别批量便宜、可控、可私有化，输出带坐标与置信度复杂版式（表格/公式/多栏）结构易丢
VLM 直接看图像进多模态模型"理解式"读出高泛化、带语义纠错、能直接问答token 贵、无稳定版面结构输出、表格易幻觉
文档解析管道版面检测 + 阅读顺序 + 表格/公式结构化，输出 markdown/JSON复杂版式转结构化最稳，RAG 入库首选管道搭建/调校成本高，弱于开放域理解
  • 传统 OCR（PaddleOCR、Tesseract 一类）走"检测 + 识别"的分步管道，输出文本框、文字与置信度，胜在便宜、批量、可私有化；短板在"结构"——双栏、表格、公式这类版式若不做版面分析，文字按行吐出，行列关系与阅读顺序全丢。
  • VLM 直接看的优势是理解式识别：结合上下文把模糊的字按语义猜对，能直接回答"这一页在讲什么"；代价是每次调用都烧视觉 token、输出没有可靠的版面坐标与阅读顺序保证、密集表格容易一本正经地看错行。
  • 文档解析管道（MinerU 一类）是为"复杂版式转结构化文档"而生：版面检测确定区域与阅读顺序，表格识别成表格结构、公式识别成可编辑形式，最终输出 markdown/HTML/JSON。它是扫描件进 RAG 前最稳的预处理形态，代价是需要搭建与调校。

选型决策的四个维度

  1. 版式复杂度：纯文本印刷体 → 传统 OCR 即可；学术论文/财报/书籍这类含表格、公式、多栏的 → 必须版面分析与结构化。
  2. 输出要求：只要纯文本 → 传统 OCR；要保留阅读顺序与表格结构 → 管道；要"理解语义 + 能问答" → VLM。
  3. 规模与成本：十万页批量离线 → 传统 OCR 或管道，逐页喂 VLM 会同时爆成本与时间预算；在线单页、量小 → VLM 可接受。
  4. 隐私与部署：数据不能出域时，优先可私有化部署的传统 OCR 与自托管管道，而不是云端 VLM。

生产系统常见的不是单选而是组合：结构化解析负责"把版式变成可检索的数据"，VLM 负责语义问答与低置信区域复核——解析层保准确，视觉层补理解。

三个反例

  • 十万页扫描件逐页调 VLM：识别率再高也扛不住成本与延迟，批量离线永远先走解析管道。
  • 用传统 OCR 硬啃复杂表格：行列关系会被抹平成一段文本，"第二行的第三列"从此无法回答。
  • 忽略阅读顺序直接抽文本：双栏论文、报纸页面直接按行拼接，抽出的文字顺序错乱，下游检索与问答一起变差。另外警惕"单字识别率 99%"的营销数字——单字准 ≠ 版式对 ≠ 结构对，评测要以端到端任务（检索命中、表格还原、问答正确率）为准。

五、语音链路：实时语音 Agent 是"时序工程"，不是"模型堆叠"

从异步到实时的难度跃迁

语音应用最简形态是一条异步管道：ASR 把整句转文本 → 文本交给模型处理（对话、检索、Agent 都能复用）→ TTS 播报。它没有新概念，语音只是入口与出口。难度跃迁发生在"实时对话"：用户边说、系统边听边想边答，这时所有问题都变成时序与状态问题——什么时候该听、什么时候算说完、回答能不能被中途打断、端到端延迟分给哪一段。

实时语音链路的标准组件只有四个，但每个都藏着工程细节：

  • VAD（语音活动检测）：判断用户是否在说话、何时开始何时结束，灵敏度与"拖尾"设置直接决定丢字还是吞静音。
  • 流式 ASR：边听边产出文本，输出分"部分结果（partial）"与"最终结果（final）"两档。
  • 模型决策：可以在句尾触发，也可以随文本流持续更新。
  • 流式 TTS：把回答"边生成边播放"，追求的是首字延迟而不是整句生成完再放。

轮替、句尾判定与打断：交互状态的三个坎

  • Turn-taking 判定：系统何时认为自己该停止听、开始答，靠静音阈值 + 语义完整性共同决定；判定过早会抢话，过晚显得迟钝。
  • Barge-in（打断）：用户正在说话时系统要能立刻停掉自己的 TTS 并转回收听。做不好打断，产品表现就是"我说话它还在播"的机器人感。
  • 半双工与全双工：轮替式（半双工）实现简单但体验僵硬；全双工允许真并发，但要额外处理回声消除（AEC）、环境降噪与"两个人同时说"，工程复杂度上一个台阶。

全双工最隐蔽的坑：系统会听见自己

让语音 Agent"自言自语"的经典事故链是：TTS 播放回答 → 麦克风把播放的声音又收进去 → 没做回声消除时 ASR 把系统自己的话当成用户输入 → 模型又回应自己。全双工音频如果没有 AEC/回声消除兜底，就会形成自我对话死循环。这是语音链路独有的、文本系统永远不会遇到的故障类型。

工程上的四条硬经验

  • 别拿 ASR 的部分结果当最终决策。partial 是会被改写的中间态，用未确认文本去触发不可逆动作（下单、转账）会造成错误操作；以 final 为准，partial 只作"正在听"的提示。
  • 端到端延迟要拆段预算。"用户说完到听到回答"由 ASR 尾延迟 + 模型首 token + TTS 首字共同构成，逐段设预算、逐段测量，而不是整体拍一个目标。
  • 文本中间层会丢掉副语言。语气、情绪、语速在"语音→文本→模型→文本→语音"的链路里被压扁；产品若需要情感维度，要有专门的音频特征通道，而不是指望文本层保留。
  • 选型按可测指标走：ASR 看领域词错率与口音鲁棒性、流式首结果延迟；TTS 看自然度与首字延迟；整链路用真实语句测"停止说话 → 开始听到回答"的时延与打断反应，而不是背产品参数表。

六、视频理解与生成式多模态：概览与定位

视频理解：视觉模型加一条时间轴

视频是"连续帧 + 时间"，它的工程本质是采样问题：逐帧全量喂给模型既烧 token 又充满冗余（相邻帧信息高度重复）。常用策略有三类，按任务挑选：

  • 均匀抽样：固定间隔取帧，适合内容分类、粗粒度内容识别；
  • 关键帧/场景切分：按画面变化取代表性帧，适合事件检测与内容梗概；
  • 窗口化理解：把一小段连续帧作为一个单元交给模型做时序推理，适合动作、过程类任务。

成熟的工程链路通常先把视频"降维"：抽帧 + 必要时配上 ASR 字幕，逐段用 VLM 生成片段描述，再把"片段描述 + 字幕"拼成文本做全局归纳或检索——视频问答最终常落在文本层，视觉只在片段理解那一步出场。成本上要记住帧就是图像，视频时长会把 token 线性放大，先想清楚"理解到什么粒度就够"，再决定采样的密度。

生成式多模态：另一族模型，另一种工程

文生图、图生视频这类生成模型与理解型 VLM 是不同模型族：前者从噪声/条件生成内容，后者做判别与推理。应用侧的主要工程形态是调用服务与 API，关心的问题集中在四类：提示词与条件的可控性（纯文本之外，参考图、布局、蒙版等条件输入的边界）、一致性与风格保持（同一角色/画风在多张图之间不漂移）、成本与异步批处理（生成任务往往秒级到分钟级）、以及内容合规与版权。评测以主观 + 任务指标（相关性、一致率）为主，不做像素级可复现的假设——生成天然不确定，不能当确定性函数用，凡是对输出精确性有硬要求的环节，都不该把生成模型放在"必须正确"的位置上。

收束：多模态工程的同一根主线

把全章压成一句话：每一种新模态都是一条输入通道，反复出现的只有四件事——表示（怎么编码进模型）、对齐（怎么与文本和任务接上）、采样与预算（分辨率、帧率、时长与 token 的交换）、结构化优先（能拿结构就不靠像素硬读）。遇到任何多模态需求，先回答一个判断题："这个信息在像素里，还是在结构里？" 在结构里（DOM、可访问性树、表格、字幕、版面）就先解析成结构；只在像素里（视觉布局、趋势、位置关系）才值得动用直接视觉理解。这一个判断能挡掉多模态项目里的大部分返工。
