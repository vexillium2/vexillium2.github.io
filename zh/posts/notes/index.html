01 概念设计：从需求描述到关系模式

需求描述是用自然语言写的，关系模式是用键和外键写的，两者之间隔着一整套转换。这套转换里有几步是不可逆的设计决策：一只宠物是不是弱实体、一条联系是完全参与还是部分参与，都会决定后面哪些业务规则能被数据库强制、哪些必然落空。

所以概念设计要回答两个问题：从这段需求里能读出哪些实体、联系和约束，以及读出来的东西映射成关系模式之后，还剩多少能被强制。第二个问题比第一个更容易被忽略，但它才是设计质量的真正分水岭。

02 表设计：从函数依赖到反范式边界

表设计要回答的问题不是"该建几张表"，而是这组业务规则允许出现哪些数据状态、不允许哪些。函数依赖和范式是回答这个问题的工具：它们把业务规则翻译成对属性的约束，再推导出什么样的结构不会产生异常。

工具只解决一半。生产中有大量表并不满足第三范式，它们同样正确——因为它们用一致性成本换取了读取成本，而这个交换是有条件的。判断条件是否成立，比记住范式定义更重要。

全文用一个供应链场景贯穿：产品由大部件构成，大部件又可以由其它部件或基本零件构成；每个基本零件可以由多个供应商供货，价格随供应商不同。

03 InnoDB 与索引：一条 SQL 的数据路径

一条 SQL 从接收到返回，会在四层结构上留下痕迹：磁盘上的页、按主键组织的 B+ 树、内存里的缓冲池、顺序追加的日志。这四层各自解决一个物理问题——数据放哪、怎么快速定位、怎么避免随机 I/O、怎么保证掉电不丢。

理解它们的顺序是"从底往上"：先看数据在磁盘上长什么样，再看索引如何在一堆页里定位，再看内存如何把磁盘访问变少，最后看日志如何把随机写变成顺序写。把四层拼起来，就是一条 SQL 的真实路径。

这条路径也解释了索引的边界：索引存在不等于会被使用，而"不被使用"有时是优化器的正确决策，有时才是设计错误。

04 查询优化器：从关系代数改写到你看到的执行计划

你写下的 SQL 不是执行计划，只是一个待优化的表达式。优化器会重写它、为每一步选择算法、最后输出一份计划——你看到的 EXPLAIN 是这份计划的摘要。

这个链条上有三个问题值得分别回答：改写凭什么保证结果不变、算法按什么选、我怎么从计划里读出真实成本。第一个问题只有关系代数能回答，第二个问题要靠代价模型与统计信息，第三个问题是纯工程——把 EXPLAIN 的每一列对应回它想表达的成本。

三者都指向同一个结论："这条 SQL 慢"很少是 SQL 本身的问题。它可能是估算失真、可能是搜索空间被剪枝、也可能是优化器做了一个正确但与你预期相反的决定。

05 事务、MVCC 与锁：并发正确性的判据与代价

并发正确性有一个硬性判据：并发执行的结果，必须与按某个串行顺序执行这些事务的结果相同。这条判据叫可串行化，它不关心实现，只关心结果。

在这个判据之下，数据库有两条腿去实现它：多版本让读不必等待写，锁让写之间互相排斥。理解这两条腿各自能做什么、以及在什么情况下失效，就能回答绝大多数并发问题的提问：这段代码在隔离级别 X 下会不会错、锁会等在哪。

06 复制、备份与高可用：故障时到底会丢什么

数据最终落在磁盘上——这是所有数据库机制的前提。而复制、备份与高可用要回答的是另一个问题：当磁盘、机器、机房出问题时，这个前提还成立多少。

这三个话题表面上各说各的，实际上共用同一个坐标系，横轴是故障类型，纵轴是丢失边界：

故障类型 谁负责兜住 丢失边界
进程崩溃、断电 崩溃恢复 已提交事务不丢
磁盘损坏 备份 从最近一次备份到故障点之间的数据
整机 / 机房不可用 复制与故障切换 取决于复制模式：从"可能丢失"到"不丢"
