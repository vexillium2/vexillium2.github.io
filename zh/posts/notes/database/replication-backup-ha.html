复制、备份与高可用：故障时到底会丢什么

数据最终落在磁盘上——这是所有数据库机制的前提。而复制、备份与高可用要回答的是另一个问题：当磁盘、机器、机房出问题时，这个前提还成立多少。

这三个话题表面上各说各的，实际上共用同一个坐标系，横轴是故障类型，纵轴是丢失边界：

故障类型谁负责兜住丢失边界
进程崩溃、断电崩溃恢复已提交事务不丢
磁盘损坏备份从最近一次备份到故障点之间的数据
整机 / 机房不可用复制与故障切换取决于复制模式：从"可能丢失"到"不丢"

所以判断一套架构是否可靠，只需要问三个问题：崩溃后能不能自动起来、备份能不能恢复出指定时间点、切换时会不会丢已提交的事务。

二进制日志：复制的唯一数据源

binlog 的三种格式：ROW 为什么成为默认

二进制日志记录"数据发生了什么变化"，它有三种记录方式：

格式记什么优点代价
STATEMENT记原始 SQL 语句日志最小非确定性语句会导致主从数据不一致
ROW记每一行修改前后的镜像结果确定、可审计批量更新时日志量巨大
MIXED默认记语句，遇到非确定性语句改记行折中判断规则不透明，仍可能踩到不一致

ROW 成为默认格式，核心原因不是性能，而是正确性：只要记录的是行的变化，从库重放的结果就一定与主库相同，与语句里有没有时间函数、随机函数、有没有隐含顺序都无关。STATEMENT 格式下这些问题都会变成主从数据漂移。

ROW 的代价要具体看：一次影响一百万行的 UPDATE，会产生一百万条行事件。日志膨胀、网络传输、从库重放都会因此变慢。缓解手段是只记录变化的部分（而不是整行），但这条路径的优化空间有限——批量更新在大表上本身就应该分批做，这也是为什么"改数据要小批量"在复制架构下更加重要。

位点与 GTID：复制的两种定位方式

从库要告诉主库"我从哪里开始接"，有两种定位方式：

  • 基于位点：用 binlog 文件名加偏移量。它简单直接，但有个致命弱点——位点是文件内的物理位置，换一个主库或换一个文件就失去意义。故障切换时，运维需要人工找出各从库执行到哪个位点、选最靠前的那个来提升，这个过程容易出错。
  • 基于 GTID：每个事务在主库上被分配一个全局唯一的标识。从库记录"我执行了哪些标识"，切换时只需把它指向新主库，两边会自动算出缺哪些事务并补齐。它还带来一个附带好处：重复投递同一个事务会被识别并跳过，重放天然幂等。

所以 GTID 的价值不在日常运行，而在故障切换与拓扑变更这两个最容易出错的时刻。它把"人工计算位点"换成了"自动补齐差值"，这是可靠性上的实质提升，不是便利性上的小改进。

代价也有：开启 GTID 后，某些语句形态会受限（在语句格式下尤其明显），并且跳过某个事务需要特殊手段——因为"跳过"与"全局唯一序列"在语义上是冲突的。

binlog 保留策略：删早了会发生什么

binlog 会持续增长，必须清理，但清理策略直接决定了从库和备份的可行性：

  • 删得太早：一个落后的从库需要的日志已经不存在了，它无法继续增量追赶，只能重新做一次全量。对大数据量实例，这意味着数小时的不可用。
  • 留得太久：磁盘被吃满。磁盘满会导致写入失败，是比"从库落后"更严重的故障。

判断依据是最坏情况下的追赶窗口：从库最长可能落后多久（维护窗口、网络中断、误操作恢复），就至少要保留那么久的日志，并留出余量。有备份体系时，这个窗口还可以与"最近一次全量备份的时间"取较大值——因为从备份恢复需要的日志，正是从备份那一刻开始的。

复制链路：延迟是怎么产生的

复制链路的四个环节

开启复制后，一次写入要经过四段：

  1. 主库把事务写进 binlog；
  2. 主库的发送线程读取 binlog 并推给从库；
  3. 从库的接收线程把它落到中继日志；
  4. 从库的重放线程执行中继日志里的内容，真正改动数据。

这四个环节里，只有第 4 段决定"从库的数据是否可见"。也就是说：即使第 2、3 段完全实时，只要第 4 段跟不上，从库读到的就是旧数据。理解这一点是排查延迟的前提——延迟不是"网络慢"，而是"重放慢"，绝大多数情况下如此。

延迟的四个来源与并行复制

延迟的来源按发生频率排：

  • 主库并发写、从库单线程重放。这是经典矛盾：主库可以同时用几十个工作线程，而从库默认只有一条重放链路。主库写入越并发，从库越跟不上。
  • 大事务。一个事务是一个不可分割的重放单位——它要么全部执行完，要么全部没执行。所以一个跑了十分钟的批量删除，会让从库在这十分钟里什么都追不上。大事务在复制架构里的危害远大于在单机上的危害。
  • 从库上的其它负载。在从库上跑备份、大查询、DDL，都会与重放线程抢 CPU、IO 与锁。
  • 硬件与网络差异。从库规格低于主库时，重放能力天然落后；跨地域复制则叠加了网络往返。

针对第一个来源，数据库演进出了并行复制：先按库并行（只在多库场景有效），再按组提交并行（同一批提交的事务可以并行重放），再到基于写入集合的并行（把"改动的行集合不冲突"作为并行依据）。它的效果取决于主库的写入冲突程度——如果主库的写入都集中在同一批行上，并行度无法提升，因为冲突是真实存在的。

对第二个来源，只能靠工程纪律：把大批量操作拆成小批。它同时缓解延迟、减少锁持有时间、降低回滚成本。

Seconds_Behind_Master 为什么不可信

大多数延迟监控都盯着一个指标，而它恰恰是最不该单独依赖的那个。它的计算方式是"从库当前时间减去正在重放的那个事件的时间戳"，这带来几个结构性缺陷：

  • 主库没有新写入时它会掉到 0，看起来完全同步，但此时即使从库的接收链路断了也不会体现；
  • 它只反映重放进度，不反映接收进度。接收已经落后很远、但中继日志里的内容被追平了，它依然显示 0；
  • 大事务重放期间它长时间不动，然后突然跳变，无法用于判断"还要多久"；
  • 它依赖两台机器的时钟，时钟不同步时数值直接失真。

更可靠的判断方式有三类：比较主从的 GTID 集合差异、读取重放线程的逐工作线程统计、或者在主库定期写入心跳记录再在从库读它的时间戳。最后一种最接近"业务真正感受到的延迟"，因为业务能看到的正是它。

复制的一致性：数据为什么会漂移

非确定性语句：主从数据为什么会不一样

复制从设计上就假设"同样的输入产生同样的输出"。任何打破这个假设的语句都会让主从分叉：

  • 依赖当前时间的函数：同一个语句在主库与从库执行的时间不同，结果就不同；
  • 依赖随机数的函数；
  • 依赖自增分配的插入：在没有指定主键的插入里，自增值可能不同；
  • 没有排序的分页查询：LIMIT 不写 ORDER BY 时选哪些行是不确定的，用它来更新就会改错行；
  • 依赖会话状态的语句：用户变量、会话参数不同，执行结果不同。

这是 ROW 格式成为默认的根本原因：它把"重放语句"换成了"重放行的变化"，从源头上消灭了这类分叉。反过来说，如果还在使用语句格式，就必须保证所有语句都是确定性的——而这件事在业务迭代中是守不住的。

从库被误写与复制过滤

第二类漂移来源更朴素：有人在从库上写了数据。

它通常由三种原因造成：应用配置错误把写流量打到了从库、运维做数据修复时连错了实例、只读保护没有真正生效。

这里有一个容易踩的坑：普通的只读设置拦不住拥有高权限的账号——它只约束普通权限的用户。要真正防止误写，需要用更高一级的只读开关（连高权限账号也拒绝写），并把这项设置作为从库的初始化规范。

还有一类隐蔽的漂移来自复制过滤规则：只复制部分库或部分表的配置，会让从库长期处于"数据不完整"的状态。它在功能上线时不报错，只在某天需要用从库切换时暴露——那时才发现从库缺表。过滤规则应当被禁止，或者至少被显式记录在架构文档里。

数据校验：怎么发现已经漂移的数据

漂移不会自己报警，必须主动比对。常见手段按代价排序：

  • 逐表校验和比对：对表算一个整体校验和，主从对比。它快，但对大表需要分块，且要求比对时两边数据静止（否则会误报）。
  • 按块逐行比对：把表按主键切成块，逐块比对行数与内容摘要。它最可靠，代价最高，适合定期抽检。
  • 业务侧对账：对关键指标（金额合计、订单数）在主从分别统计并比对。它最贴近业务影响，也最容易说服人去修。

比"怎么比对"更重要的是比对之后做什么：发现漂移后往往需要以主库为准重建从库，而重建期间这台从库不能承担读流量——所以校验的频率应该与它能承受的重建成本相匹配。

崩溃恢复：数据为什么没丢

恢复的三个阶段：分析、重做、回滚

崩溃恢复不是"把日志从头读一遍"，它有明确的三段：

  1. 分析：从日志里找到最近一次检查点，确定从哪里开始重做，并找出崩溃时尚未提交的事务；
  2. 重做：从检查点开始，把日志里记录的页修改重新应用一遍。注意这一步包括未提交事务的修改——因为要先把数据页恢复到崩溃瞬间的状态；
  3. 回滚：用回滚日志把所有未提交事务的修改撤销掉。

顺序不能颠倒：先重做所有修改，再回滚未提交的。中间那段时间数据页上存在未提交的数据，这是正常的——它们还没有对任何事务可见。

已经提交的事务为什么一定不丢：提交成功的标志是"日志已经落盘"（而不是"数据页已经落盘"），所以重做一定能把它的修改补回来。这就是持久性的全部机制。

恢复时间由什么决定

恢复时间几乎完全由检查点之后累积了多少日志决定。而检查点推进的频率又与"允许积压多少脏页"相关。

于是出现一个必须权衡的对子：

  • 日志容量大、检查点稀疏：日常写入性能更好（不必频繁强制刷脏页），但崩溃后要重放的日志更多，恢复更慢；
  • 日志容量小、检查点密集：恢复快，但日常写入更容易被强制刷脏页打断，出现周期性的性能抖动。

这个权衡没有普适答案，它取决于能接受多长的不可用时间。关键在于：这个数字应该是被主动设置过的，而不是默认值决定的。很多"崩溃后恢复花了很久"的事故，根因是没人算过这笔账。

日志能救的和不能救的

有一个边界必须划清：重做日志保障的是"内存中已提交的修改不丢"，它不能替代备份。

原因是重做日志与数据文件同处一个存储介质上。磁盘损坏时，日志和数据页一起没了——靠日志能恢复的前提是日志本身还在。所以：

  • 进程崩溃、机器断电、异常重启 → 日志能救，且能救到崩溃前的最后一个已提交事务；
  • 磁盘损坏、文件被误删、数据被误改 → 只能靠备份。

还有一类日志救不了的情况需要在设计时避免：页写入过程中断电导致的部分写。重做日志记录的是"在某个页上做了什么修改"，前提是这个页有一个可用的基础镜像；如果页本身被写坏了，光重放日志无法还原。这类问题由页级的写入保护机制来兜住，它牺牲一次顺序写换取页的写入原子性——这是"能恢复"这个承诺的一部分，不是可选优化。

备份：能恢复才算备份

逻辑备份与物理备份：四个维度的取舍

备份方式可以按四个维度分类，实际选择通常是在前两个维度上做决定：

维度选项影响
内容逻辑（导出语句）/ 物理（复制文件）可移植性与恢复速度
范围全量 / 增量备份时间与恢复步骤数
状态冷备（停机）/ 热备（在线）对业务的影响
方式单线程 / 并行备份窗口

两组典型选择：

  • 逻辑备份：把数据导出成 SQL 语句。优点是能跨版本、跨平台恢复，能只恢复某几张表，内容可读可审计；缺点是恢复慢——它要重新执行所有语句并重建索引，一个几十 GB 的库可能恢复几小时。
  • 物理备份：直接复制数据文件。优点是恢复快（接近文件复制速度）；缺点是与版本、平台、页大小绑定，粒度粗，不能只挑一张表。

这两者的差别在恢复时刻才体现出来，而恢复时刻恰恰是压力最大的时刻。所以选择依据应该是"我希望多快恢复"，而不是"我希望多快备份"。

一致性快照：热备成立的前提

在线备份必须在某个时间点取到一份一致的快照，否则备份出来的是一个跨越了多个时间点的拼盘——它无法恢复成一个可用的数据库。

  • 逻辑热备依赖数据库自身的一致性读能力：在一个可重复读的快照里导出全部数据。这个能力对支持事务的存储引擎有效，对不支持事务的表不成立——混用引擎的表在被备份时可能不一致。
  • 物理热备需要处理"备份期间数据页仍在被修改"的问题，同时必须记录备份开始时刻的日志位点，否则后续无法增量补齐。

"记录位点"这一步是热备的关键动作，也是最容易被漏掉的一步：没有位点，这份备份只能恢复到备份完成的那个模糊时刻，时间点恢复就无从谈起。

时间点恢复：全量加日志怎么拼

时间点恢复的思路很简单：用一个全量备份回到过去某个确定时刻，再用日志把它推进到目标时刻。

具体是三件事：

  1. 恢复最近一次可用的全量备份；
  2. 从这份备份记录的位点开始，重放日志；
  3. 在到达目标时刻时停下。

第二步里有两个易错点：位点必须取备份开始时的位点（而不是结束时），并且日志必须一直保留到"下一次全量备份成功"为止。而第三步本身也是一种能力：能停下来，才意味着"误删了一张表"可以恢复到删除前一秒——这是全量备份单独做不到的。

备份的验收标准是恢复演练

判断备份是否有效，唯一可靠的标准是恢复演练。原因在于备份失败的方式非常安静：

  • 备份进程退出码为 0，但备份文件不完整；
  • 备份内容完整，但缺少位点，无法做时间点恢复；
  • 备份与位点都对，但恢复流程本身没人跑过，真出事时才发现步骤缺失、依赖缺失、耗时远超预期；
  • 备份文件在，但存放位置与数据库在同一个故障域，一次机房故障两边一起没。

所以备份的工程要求不止"定期跑备份"，还包括：定期做一次完整恢复演练、记录恢复耗时、并确认备份不与被保护的数据共享故障域。

备份放在从库上是常见做法——它把备份的资源开销与主库隔离开。但要记住两点：这份备份反映的是从库的位点（从库落后时，备份也是落后的），以及在大事务重放期间做备份会进一步加重延迟。

高可用与故障切换：切换会丢什么

异步、半同步与多数派：数据丢失的边界

复制模式的差别，最终都体现为"提交成功"意味着什么：

模式提交成功的含义切换时的丢失边界
异步主库本地日志落盘即返回可能丢失尚未传到任何从库的已提交事务
半同步至少一个从库确认收到日志后才返回日志已在一台从库上，提升它则不丢；提升别的从库则仍可能丢
多数派多数节点确认后才算提交已提交事务不丢，代价是少数派分区不可写

异步模式的丢失边界不是一个固定值，而是"在故障瞬间还没被任何从库接收的那部分"。它平时为零、故障时突然变成几分钟——这正是异步复制最危险的地方：它的代价只在最坏的时刻集中兑现。

半同步把边界收窄到"日志已到从库、但未重放"这一段，因为日志已经在从库的磁盘上，提升它可以把这些事务补完。但它有两个必须监控的失效点：确认延迟超过阈值时会自动退化为异步，而退化通常是静默的——如果没人盯着状态变量，你以为还在半同步，实际已经在裸奔；另外，确认只保证"收到"，不保证"已重放"，所以切换时必须选择日志最完整的那台，而不是随便一台。

多数派复制（组复制这类）通过共识协议做到"提交即多数派持有"，因此可以承诺已提交事务不丢。代价是写延迟上升（至少一次跨节点往返），并且网络分区时少数派一侧会拒绝写入——牺牲可用性换一致性，这是那个古老权衡的具体形态。

分区时的一致性与可用性

网络分区是分布式的常态而非异常。分区发生时只有两种选择：

  • 保可用：两侧都继续接受写入 → 一定出现分叉，之后要人工决定保留哪一侧的数据，被丢弃的那一侧的已提交事务就是丢失量；
  • 保一致：少数派一侧拒绝写入 → 业务受损但不产生分叉，恢复后数据自动收敛。

选择依据是业务对这两种损失的相对容忍度："几分钟不可写"和"丢掉一部分已提交数据、且要人工介入"哪个更糟。 对交易与账务类业务，答案几乎总是后者更糟。

需要警惕的是第三种情况：以为自己选了保一致，实际是保可用。典型表现是异步复制加自动切换——自动切换给的是可用性的形式，底层的异步复制决定的却是一致性的实质，而两者并不匹配。

脑裂与 fencing：切换必须解决的问题

故障切换里最危险的不是"选不出新主库"，而是"选出来了，但旧主库还活着并在接受写入"。一旦发生，两个节点都认为自己可写，数据分叉，之后无论怎么切都会丢东西。

所以切换的核心动作是隔离旧主库（fencing），手段从强到弱：

  • 强制关机或断电：最彻底，代价是可能误杀；
  • 摘除网络入口（虚拟 IP、负载均衡摘除、防火墙）：见效快，但需要确认旧主库无法通过其它路径被写入；
  • 置为只读并阻止高权限写入：最轻量，但依赖旧主库本身还能响应——如果它是"假死"（进程活着但没有响应），这个手段可能失败。

fencing 必须发生在提升新主库之前，顺序错了，切换本身就成了故障。判断标准应该写成"旧主库已确认不可写"这样一个可验证的条件，而不是"已经执行了摘除操作"这样一个动作。

故障切换的四个阶段与验收

一次完整的切换包含四段，每段都有它特有的失败方式：

  1. 检测：判断主库是否真的不可用。太敏感会产生误切换（把一次网络抖动变成一次数据分叉），太迟钝则延长不可用时间。常见做法是多次探测加人工确认，在自动化与安全之间取舍。
  2. 决策：选出新主库。依据必须是数据完整性（日志最全、GTID 集合最接近），而不是机器规格或机房位置——先保证不丢数据，再谈性能。
  3. 执行：隔离旧主、提升新主、把其余从库指向新主、切换应用入口。这一步的自动化程度决定恢复时间。
  4. 收尾：处理旧主库（重建后作为新从库加入）、校验数据一致性、确认所有应用已重连、核对新旧主库的 GTID 集合差异是否为零。

第四段最容易被跳过，而它是唯一能回答"这次切换到底丢了没有"的阶段。收尾时至少要做两件事：把新旧主库的日志集合做一次差异比对（差异就是丢失量），以及确认没有任何应用还连着旧主库。

与备份同理：没有演练过的切换方案不算方案。演练要覆盖的不只是"主库宕机"，还包括更麻烦的几种形态——旧主库假死（进程在、响应无）、网络分区（两侧都活着）、以及切换过程中再次故障。这几种才是真实事故的样子。
