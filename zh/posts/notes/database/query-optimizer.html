查询优化器：从关系代数改写到你看到的执行计划

vexillium2026/9/21大约 24 分钟后端开发数据库查询优化

查询优化器：从关系代数改写到你看到的执行计划

你写下的 SQL 不是执行计划，只是一个待优化的表达式。优化器会重写它、为每一步选择算法、最后输出一份计划——你看到的 EXPLAIN 是这份计划的摘要。

这个链条上有三个问题值得分别回答：改写凭什么保证结果不变、算法按什么选、我怎么从计划里读出真实成本。第一个问题只有关系代数能回答，第二个问题要靠代价模型与统计信息，第三个问题是纯工程——把 EXPLAIN 的每一列对应回它想表达的成本。

三者都指向同一个结论："这条 SQL 慢"很少是 SQL 本身的问题。它可能是估算失真、可能是搜索空间被剪枝、也可能是优化器做了一个正确但与你预期相反的决定。

关系代数：优化器改写的语言

关系代数：为什么它是改写的语言，而不是历史符号

关系代数用一组封闭在关系上的运算描述查询。所谓封闭，是指每个运算的输入和输出都是关系——所以运算可以任意嵌套、任意重排，这正是"改写"能够成立的前提。

它只有五个基本运算：

运算符号含义
选择σC(R)\sigma_{C}(R)σC​(R)挑出满足条件 CCC 的元组，操作在行上
投影πA(R)\pi_{A}(R)πA​(R)只保留属性组 AAA，操作在列上
并R∪SR \cup SR∪S属于 R 或属于 S 的元组，要求属性结构相同
差R−SR - SR−S属于 R 但不属于 S 的元组
笛卡尔积R×SR \times SR×S每个 R 的元组与每个 S 的元组配对，结果行数是两者行数之积

另外三个是派生运算，可以由基本运算定义出来：交 R∩SR \cap SR∩S 等于 R−(R−S)R - (R - S)R−(R−S)；连接等于笛卡尔积加选择；除用一个"对所有"的形式，下面单独说。

SQL 与它们的对应关系很直接：WHERE 对应选择，SELECT 列表对应投影，UNION / INTERSECT / EXCEPT 对应并、交、差，FROM A, B 对应笛卡尔积，JOIN ... ON 对应连接。

把笛卡尔积当基本运算、把连接当派生运算，这个顺序不是数学上的偏好，而是要解释一件事：连接条件不是"额外的过滤"，它是让笛卡尔积有意义的那一步。少写或写错连接条件时，数据库不会报错，它只是忠实地执行了笛卡尔积。

连接与除：两个派生运算在 SQL 里长什么样

连接的定义就是：

σC(R×S)=R⋈CS\sigma_{C}(R \times S) = R \bowtie_{C} S σC​(R×S)=R⋈C​S

右边是连接，左边是"先做笛卡尔积，再按条件筛选"。两种写法的结果完全相同，成本却可能相差几个数量级——这中间的差额，正是优化器存在的理由。

关系代数里的连接有几种变体：等值连接要求连接条件是相等比较；自然连接是它的特例，按所有同名列自动匹配并去掉重复列；外连接在结果之外保留没有匹配上的元组（悬浮元组），未匹配的位置补空值。

自然连接看起来最省事，但它有一个必须警惕的性质：连接条件是"同名列"这件事本身，而不是你的意图。两张表都有 create_time 时，自然连接会把它也算进连接条件。所以它只适合在同名列语义确实一致的场合使用。

除表达的是一种"对所有"：

R÷SR \div S R÷S

它的结果是 R 中那些"与 S 中每一个元组都搭配得上"的元组。用供应链场景举例：供货(零件号, 供应商号) ÷ 供应商(供应商号) 的答案是所有供应商都能供应的零件——这是典型的"全称量词"需求。

函数依赖语境里的投影要单独说明一次，因为它和关系代数的投影是同一个动作、不同的对象：把一组依赖投影到某个关系上，就是只保留左部和右部都落在这个关系属性集里的那些依赖，其余丢弃。它回答了"拆完之后，原来那些规则还剩几条能被强制"。

等价变换：改写凭什么保证结果不变

优化器的改写必须保证结果不变，可依据的规则集就是从关系代数推出来的等价变换。常用的几条：

  • 选择串接：σC1∧C2(R)=σC1(σC2(R))\sigma_{C_1 \wedge C_2}(R) = \sigma_{C_1}(\sigma_{C_2}(R))σC1​∧C2​​(R)=σC1​​(σC2​​(R))，一个复合条件可以拆成多次筛选；
  • 选择下推：当 CCC 只涉及 R 的属性时，σC(R×S)=σC(R)×S\sigma_{C}(R \times S) = \sigma_{C}(R) \times SσC​(R×S)=σC​(R)×S；
  • 选择对并、差、连接的分配；
  • 投影下推：投影可以提前到子表达式的输出上，甚至可以沿连接树向下传播；多个投影可以合并；
  • 连接交换律与结合律：R⋈S=S⋈RR \bowtie S = S \bowtie RR⋈S=S⋈R，(R⋈S)⋈T=R⋈(S⋈T)(R \bowtie S) \bowtie T = R \bowtie (S \bowtie T)(R⋈S)⋈T=R⋈(S⋈T)；
  • 选择与笛卡尔积合并：σC(R×S)=R⋈CS\sigma_{C}(R \times S) = R \bowtie_{C} SσC​(R×S)=R⋈C​S。

这些规则的共同点是：它们只改变运算的顺序和位置，不改变运算的语义。所以优化器可以在一个巨大的表达式空间里自由腾挪，而不用担心算错——真正要担心的只有成本。

逻辑优化：不改变结果，只改变顺序

选择下推：为什么"先过滤"几乎决定一切

上面那条选择下推的规则，是整个优化过程里收益最大的一条。理由不在数学，在成本：

每一层运算的成本，取决于它的输入有多少行。 过滤越早发生，后续所有步骤处理的行数就越少——扫描少、连接少、排序少、内存占用少。反过来，如果先连接再过滤，中间结果会按连接的规模膨胀，可能几百倍于最终结果。

所以"选择运算尽可能先做"不是一条经验口诀，它是"中间结果行数决定总成本"的直接推论。这也是为什么优化器宁可多花时间分析条件、把它尽量拆开往下推。

投影下推与 SELECT * 的代价

投影下推的收益比选择下推含蓄，但同样真实：提前裁剪列，等于提前缩小了每一行的大小。行变小，同一页能装更多行，同样的 I/O 能搬更多有效数据。

SELECT * 恰好把这条优化掐死了。它的代价有两层：

  • 无法提前裁剪列，中间结果比需要的宽；
  • 让覆盖索引失效——覆盖索引的前提是"查询需要的列都在索引里"，而"所有列"几乎不可能都在，于是每一次查询都必须回表把整行取出来。

所以 SELECT * 的影响不只是"多传了几个字段"，而是把一条本可以在索引里完成的查询降级成必须回表的查询。

连接顺序：阶乘级的搜索空间与剪枝

连接交换律与结合律意味着连接顺序可以任意重排，但可选顺序的数量增长得极快：只考虑左深连接树，3 张表有 6 种顺序，10 张表超过 360 万种。

优化器必须剪枝。它用的是带剪枝的贪心搜索：先把连接顺序的搜索深度限制在一个范围内，再按"当前部分计划是否已经明显比另一个差"来剪掉分支，避免穷举。

这直接解释了一个常见困惑：优化器给出的不一定是全局最优计划。在多表连接里，它找到的是"在它能承受的搜索范围内，看起来最便宜的计划"。表一多，贪心与剪枝的影响就明显起来——这不是 bug，是复杂度上的必然妥协。

物理优化：用代价选算法

代价模型：I/O 主导，统计信息决定成败

逻辑优化决定"做什么"，物理优化决定"怎么做"。选择依据是总代价，通常拆成几项：

总代价 = I/O 代价 + CPU 代价 + 内存代价 + 通信代价

其中I/O 代价占绝对主导——它比 CPU 代价高好几个数量级，所以"少读一个页"几乎总是比"少算一次比较"更值钱。内存代价体现为是否要落临时表、排序能不能在内存里完成；通信代价只在数据被分发到其它节点时才出现。

代价要靠行数估算算出来，而行数估算完全依赖统计信息。这是整条链路上最脆弱的一环：统计信息有两类失真来源——它可能是过期的，也可能是采样估出来的。一旦某一步的行数估错一个数量级，后面的每个决策都会跟着错，而且错得自洽——优化器会理直气壮地选一个糟糕的计划。所以排查计划异常时，检查统计信息的新鲜度应该排在很前面。

MySQL 实际有哪几种连接算法

教科书里常列的连接算法有三种或四种，但实际实现的集合比教科书窄：

  • 嵌套循环连接：外层表逐行取出，内层表按连接条件查找。如果内层有可用索引，就是索引嵌套循环——这是 MySQL 里最常见、通常也最便宜的形式。
  • 块嵌套循环：内层没有可用索引时，把外层的一批行放进连接缓冲区，再批量与内层比对，减少内层的重复扫描次数。它在 MySQL 8.0.20 之后已被弃用，由哈希连接取代。
  • 哈希连接：MySQL 8.0.18 引入。用于有等值连接条件但内层没有可用索引的场景：把小表建成内存哈希表，再扫大表去探测。它的价值在于把"没有索引时的 O(n×m) 比对"降到接近 O(n+m)。

这里有一个必须纠正的印象：排序合并连接在 MySQL 里没有实现。它是其它系统的算法，特征是利用输入已经有序来减少比较，适合"两个输入都已在连接列上有序"的场合。MySQL 在需要顺序的场合是用排序加嵌套循环替代的，并不会切换到排序合并。

选哪种算法由代价决定，而代价又取决于：连接条件是否是等值、内层有没有可用索引、两个输入的规模、连接缓冲区够不够大。所以给连接列建正确的索引，往往同时改变了算法选择和成本量级。

子查询怎么被改写：半连接与物化

IN、EXISTS 这类写法在逻辑上表达的是"存在性"，优化器通常不会为每一行都真的执行一次子查询。它会尝试把子查询改写为半连接，即在连接过程中一旦找到匹配就停止对该行的搜索，并可以选择不同的执行策略：先匹配即停、松散扫描去重、把子查询物化后再连接等。

改写失败时，子查询会退化为物化：先把子查询结果算出来存成临时表，再去连接。这个选择会直接体现在执行计划里，也能解释"为什么这条 SQL 多了一步临时表"。

对写法的实际影响是：IN 与 EXISTS 的性能差异不能一概而论，它取决于优化器是否成功改写，以及子查询能不能被去重。与其记"哪个更快"，不如记住两条更稳的规则：

  • 子查询里的去重（DISTINCT）如果能被优化器识别并消除，成本差一个量级；
  • NOT IN 与 NOT EXISTS 在语义上并不等价——子查询结果里有 NULL 时，NOT IN 会返回空集，而 NOT EXISTS 不受影响。

执行计划的读法：EXPLAIN 各列对应什么

type 的等级与它的真实含义

type 描述这一行如何访问表，常见取值从好到差大致是：

system → const → eq_ref → ref → range → index → ALL

  • system / const：最多只需要读一行。主键或唯一索引上的等值查询落在这里——注意它是在优化阶段就能确定结果的。
  • eq_ref：连接中内层按唯一索引等值匹配，每个外层行最多匹配内层一行。
  • ref：按普通索引等值匹配，可能匹配多行。这是最常见的"用上索引"的形态。
  • range：索引上的范围扫描。
  • index：全索引扫描。它读的是整棵索引树而不是全表，但仍然是全量扫描，通常只比 ALL 略好——不要因为"看到了 key"就以为它很便宜。
  • ALL：全表扫描。

对 index 的误判是最常见的：type = index 意味着索引被"用"了，但代价是读完整棵索引，而不是定位到一小段。

key_len：怎么算出联合索引用到了前几列

key_len 是实际用于查找的索引长度，它最有价值的用途是回答"联合索引用上了前几列"。

算法是按用到的每一列累加其存储长度：

  • 定长类型加自己的字节数：整数类型、日期时间类型都有固定长度；
  • 变长类型额外加 2 字节（长度前缀）；
  • 允许为 NULL 的列额外加 1 字节（NULL 标志位）。

举一个可以手算的例子。联合索引建在 (a, b) 上，a 是 INT NOT NULL，b 是 VARCHAR(20) NOT NULL，字符集是 utf8mb4（每字符最多 4 字节）：

用到了哪些列key_len推算
只用 a4INT 定长 4 字节
a 和 b 都用到864 + 20 × 4 + 2，变长列加 2 字节长度前缀

如果 b 允许为 NULL，第二个数字会变成 87——多出来的 1 字节就是 NULL 标志位。所以同一个索引的 key_len 会因为列是否允许为 NULL 而不同，比较两条 SQL 的 key_len 之前，先确认列定义一致。

rows 与 filtered：估算的扫描量在哪里失真

  • rows：优化器估算这一步要扫描多少行。它是估算值，不是实测值。
  • filtered：这一步的条件过滤之后，剩余行数占扫描行数的百分比。

两者相乘才是"这一步会向上传递多少行"。这个乘积是估算的，所以会失真，常见的失真来源有三种：

  • 统计信息过期或采样不足，导致 rows 与真实行数差一个数量级；
  • 条件的选择性估算不准，导致 filtered 偏离——多个条件组合时的相关性、函数条件、LIKE 模式都会让它失准；
  • filtered 在某些形态下（尤其涉及连接的内层）会偏乐观，让上层以为拿到的行很少。

所以读计划时不要只看 rows。rows 很大但 filtered 很低，说明扫描量虽大、条件的选择性还不错，要解决的是"扫描能不能缩小"；rows 很大且 filtered 接近 100，说明这一步几乎没有有效过滤，扫描多少就会向上传多少，后面每一步都要为这些行付账——这才是必须先处理的形态。

Extra 的高频取值各意味着什么

Extra 是信息量最大的一列。高频取值与它们的含义：

取值含义成本信号
Using index覆盖索引，不需要回表好——查询在索引里就完成了
Using index condition索引条件下推，过滤发生在存储引擎层好——减少了回表次数
Using where存储引擎返回的行还需要在服务层过滤中性——要看产生了多少行
Using filesort需要额外排序，无法直接利用索引的有序性差——排序是 CPU 与内存的大户
Using temporary使用了内部临时表差——常见于分组、去重、并集，可能要落盘
Using join buffer连接时内层没有可用索引，用了连接缓冲区差——连接算法退化了
Using MRR多范围读，把随机回表整理成较顺序的批量读好——是优化生效的标志

需要特别澄清一点：Extra 为空或显示 NULL，并不意味着发生了回表。Extra 描述的是"额外的处理动作"，回表与否要看查询的列是否被索引覆盖。把 NULL 读成"回表"是一个流传很广的误读。

走一遍：三个表的连接计划怎么读

EXPLAIN
SELECT p.part_name, s.supplier_name
FROM part p
JOIN part_supplier ps ON ps.part_no = p.part_no
JOIN supplier s ON s.supplier_no = ps.supplier_no
WHERE ps.price > 100;
+----+-------+------+---------------+---------+---------+-------------------+------+----------+-------------+
| id | table | type | possible_keys | key     | key_len | ref               | rows | filtered | Extra       |
+----+-------+------+---------------+---------+---------+-------------------+------+----------+-------------+
|  1 | ps    | ALL  | NULL          | NULL    | NULL    | NULL              | 8421 |    33.33 | Using where |
|  1 | p     | ref  | PRIMARY       | PRIMARY | 130     | db.ps.part_no     |    1 |   100.00 | NULL        |
|  1 | s     | ref  | PRIMARY       | PRIMARY | 130     | db.ps.supplier_no |    1 |   100.00 | NULL        |
+----+-------+------+---------------+---------+---------+-------------------+------+----------+-------------+

逐行读：

  • 第一行是驱动表 ps，type = ALL，possible_keys 为空——说明 price 上没有可用索引，只能全表扫描 8421 行，filtered 33.33% 意味着大约 2800 行会进入后续连接。
  • 第二、三行是被驱动表，都在主键上做 ref 查找，rows = 1，各查一次。这两步很便宜。
  • 两行的 key_len 都是 130。如果 part_no 是 VARCHAR(32) NOT NULL、字符集 utf8mb4，按前面的算法就是 32 × 4 + 2 = 130——估算出来的数字可以用同一套算法反推回去，这是验证"索引用到了哪几列"最直接的办法。
  • 整条计划的成本几乎全部落在第一行：一次全表扫描 + 约 5600 次主键查找。

现在结论变得具体了：这条 SQL 的优化点不在连接，而在 ps 的扫描。给 ps.price 建索引、或者改写成先用索引取出这批 part_no 再关联，都会让第一行的 type 从 ALL 变成 range 或 ref。但要留意一件事——如果 price > 100 命中了这张表的大部分行，优化器可能仍然选择全表扫描，因为顺序读完整张表比"索引查找 + 逐行回表"更便宜。那种情况下它不是没找到索引，而是算过账后主动放弃了。

计划为什么会变

统计信息：估算错了，整条计划就错了

统计信息的来源决定了它必然有误差：InnoDB 通过随机采样索引页来估算索引的基数（不同值的个数），采样页数是可配的，默认只有二十页左右。表越大，二十页的样本越难代表整体分布。

由此产生三类典型失真：

  • 索引基数是采样估出来的，在数据分布倾斜时偏差很大（例如某个状态值占了 90% 的行）；
  • 非索引列没有统计信息，条件的选择性只能靠默认经验值猜——这是函数条件、范围条件估算失准的主要原因；
  • 统计信息会过期。批量导入、大批量删除之后，表的数据分布已经变了，但统计信息可能还是旧的。

可以做的干预有三件：手动触发统计信息重新计算；调高采样的页数（代价是统计更慢）；对没有索引、却常出现在条件里的列建立直方图，让优化器知道它的值分布。第三件是较新的能力，对那些"始终没有被索引覆盖、估算长期偏离"的列收益明显。

同一条 SQL 为什么今天换了计划

计划翻转通常不是优化器"变了心"，而是输入变了。按发生频率排：

  • 数据量跨过了阈值。表从几万行涨到几百万行之后，原本不划算的索引变得划算、原本划算的索引变得不划算。这是最经典的一种：同一个索引在小表上不划算、在大表上划算，所以"表长大后计划翻转"和"加索引后计划改变"其实是同一个机制在不同规模下的表现。
  • 数据分布变了。新增了一类占比很高的值，让某个条件从"高选择性"变成"低选择性"。此时旧的索引确实不该被用了。
  • 统计信息刚被重新计算。同样的 SQL，在统计信息刷新前后可能给出不同计划。
  • 查询参数不同。同一条带参数的 SQL，用不同的常量值会得到不同的选择性估算，可能走完全不同的计划。这种"参数敏感"现象在数据倾斜时尤其明显。
  • 版本升级。优化器的能力集合会变：新的连接算法、新的扫描方式、新的统计结构都可能改变计划。升级前后对比计划，是发布前值得做的一步。

排查思路是把顺序倒过来：先确认数据有没有变，再确认统计信息有没有变，最后才怀疑优化器。

干预手段与它们的风险：USE / FORCE / IGNORE INDEX

索引提示可以让优化器用或不用某个索引：

  • USE INDEX：把候选索引缩小到指定范围，是建议；
  • FORCE INDEX：在 USE INDEX 的基础上，进一步让优化器认为全表扫描代价极高，是强制；
  • IGNORE INDEX：把指定索引排除出候选。

它们的共同风险是把优化器的判断权永久交出去了。优化器之所以"今天不选这个索引"，通常是因为在当前数据分布下它不划算。把索引强制上去，意味着下次数据分布变化时，这条 SQL 会继续沿着一个已经不合适的选择走，而且不会有人告诉你——它只是变慢。

因此索引提示只应该用在两种场合：数据分布稳定且可预期、并且有实测证明强制后确实更快。它不该被当作"让计划符合我预期"的工具。

慢查询治理：从症状到干预的顺序

先定位：慢日志与按 digest 聚合

定位慢查询有两条互补的路：

  • 慢查询日志：记录执行时间超过阈值的语句。它的价值是保留了完整的原始 SQL 文本，方便重现；缺点是只记录超过阈值的那部分，且同一类 SQL 会反复出现。
  • 按语句摘要聚合的统计表：performance_schema 里的语句摘要统计表（如 events_statements_summary_by_digest）会按语句摘要（把常量替换成占位符之后的规范化形式）聚合执行次数、总耗时、平均耗时、扫描行数等。它覆盖全部语句，不只超时的那些，所以更适合回答"哪一类 SQL 吃掉了最多的时间"。

两者的分工很清楚：先用聚合统计找"总时间最贵的语句"，再用慢日志拿到具体那一条。只看平均耗时容易漏掉"平均很快但调用量极大"的语句——它们往往是总耗时的主要来源。

深分页：LIMIT 的代价与两种解法

LIMIT 带上大偏移量时性能会突然变差：

SELECT * FROM part ORDER BY part_no LIMIT 100000, 10;

原因在语义上：这条语句要求的是"排序后的第 100001 到 100010 行"，而数据库无法跳过前 100000 行——它必须真的取出 100010 行，丢掉前面 100000 行。偏移量越大，白读的行越多。如果排序列没有合适的索引，还要额外承担一次全量排序。

两种解法，代价和适用范围不同：

延迟关联——把"取哪些行"和"取完整行"拆开：

SELECT a.* FROM part a
JOIN (SELECT part_no FROM part ORDER BY part_no LIMIT 100000, 10) b
  ON a.part_no = b.part_no;

子查询只需要 part_no 一列，可以走覆盖索引，于是"白读的 100000 行"只读索引项而不读整行；真正回表只发生在那 10 行上。它把成本从"读 100010 个整行"降到"扫 100010 个索引项 + 读 10 个整行"。但偏移量继续增大时，扫描量仍然线性增长——它只是把常数降低，没有改变量级。

游标分页（也常叫键集分页）——记住上一页的最后一个键，从它之后继续取：

SELECT * FROM part WHERE part_no > '上一页最后一个值' ORDER BY part_no LIMIT 10;

这才能把复杂度从"偏移量越多越慢"变成"每页成本恒定"，因为它根本不需要跳过任何行，直接靠索引定位到起点。代价是它只能顺序翻页，不能跳到第 N 页——如果产品上要求显示页码跳转，就得用延迟关联或改造交互。

选哪种取决于产品需求，不是性能数字：能接受"只能下一页"就用游标分页，必须支持跳页就用延迟关联并限制最大页数。

批量写入与在线 DDL 的工程手段

写入侧的优化手段与读取侧不同，它们主要围绕"减少事务次数"和"减少索引维护的随机 I/O"：

  • 批量插入而不是逐条插入，并把批量控制在合理范围——过大的单条语句会带来解析与回滚日志的额外压力；
  • 显式控制事务，把多条语句放进一个事务，避免每条语句都经历一次提交；
  • 按主键顺序插入，让插入落在索引树的右侧而不是随机位置；
  • 大批量导入优先用专用的批量载入通道（如 LOAD DATA），它跳过了逐行 SQL 解析与部分约束检查，比等价的 INSERT 快得多。

表结构变更的代价则取决于变更类型：只改元数据的变更可以瞬间完成（例如纯新增列的某些形式）、需要重建表的变更会读写全表（例如改列类型、改字符集）。后者在线上要特别小心：如果只能以重建的方式完成，整个过程会阻塞写入。这类需求通常会借助外部工具来做：先在影子表上完成变更、再把增量同步过去、最后原子切换，把"长时间重建"变成"短时间切换"。

干预的顺序：先改写，再索引，最后强制

同一个慢查询，干预手段的收益与风险差异很大。建议按这个顺序试：

  1. 改查询写法。最便宜、最可逆。常见的几类：去掉不需要的列（让覆盖索引有机会生效）、把列上的函数移到常量一侧、补上引号避免隐式类型转换、把深分页换掉。这一步不需要改数据库结构，改动可以随时回滚。
  2. 补或调索引。收益通常最大，但代价是长期存在的：每个索引都要在写入时维护，还要占缓冲池。所以补索引的依据应该是实测的扫描量下降，而不是"看起来这个列该有索引"。
  3. 更新统计信息。如果计划明显与真实数据分布不符（例如 rows 与实测差一个数量级），先重算统计信息再看，可能不需要动任何结构。
  4. 索引提示。最后一步，且必须留下记录：写明它解决的是哪个具体问题、以及在什么数据量下应该重新评估。
  5. 改表结构。这一步本身有风险，应该放在"已经确认前四步解决不了"之后。

有一个反面模式值得单独提：加索引之后查询没变快。这时不要急着再加一个索引，先确认慢的原因是不是扫描——它也可能是回表次数、排序、临时表，或者根本不在数据库里（网络往返、行数过多导致的序列化开销）。前面那个三表计划的例子就是这类排查的模板：先在计划里指出成本落在哪一行，再决定动什么。
