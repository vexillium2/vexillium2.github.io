00 数据库笔记导览

vexillium2026/9/21大约 4 分钟后端开发数据库

这个页面不承载知识本身，它只回答两件事：遇到问题该翻哪一份笔记，以及几份笔记之间的边界在哪。边界写清楚，以后新增内容才不会写重。

七份笔记各自回答什么

笔记层次一句话定位
概念设计需求层从需求描述里读出实体、属性、联系、弱实体与参与约束，把 ER 图映射成关系模式，并说清键与外键表达不了哪些约束
表设计设计层从函数依赖推到范式与模式分解，落到什么时候故意反范式、以及哪些完整性约束该由数据库强制
InnoDB 与索引存储层数据在磁盘与内存上的形状：行与页、B+ 树与聚簇索引、缓冲池、redo/undo/binlog，以及索引在哪些情况下帮不上忙
查询优化器执行层关系代数如何成为改写语言、代价模型与统计信息、EXPLAIN 每一列怎么读、以及同一条 SQL 的计划为什么会变
事务、MVCC 与锁并发层以可串行化为判据，讲清版本链与 ReadView、隔离级别的实现差异、锁为什么加在索引上、死锁怎么查
Java 数据访问应用层JDBC 的三段成本、连接池参数的依据、事务边界、ORM 的 N+1，以及应用层在哪里抵消了数据库侧的优化
复制、备份与高可用可靠性层故障时到底会丢什么：binlog 与复制链路、数据漂移、崩溃恢复、备份与切换各自的丢失边界

边界判据

新增内容时先过这几个问题，答案决定它写进哪一份笔记：

判据问题去处
它在回答"业务世界里有哪些实体与联系、它们怎么变成表"？概念设计
它在回答"表该拆到什么程度、约束该放在哪一层"？表设计
它在回答"数据在磁盘和内存上的形状、索引与日志的结构"？InnoDB 与索引
它在回答"一条 SQL 会被改写成什么计划、代价怎么估、计划怎么读"？查询优化器
它在回答"并发会不会出错、锁会等在哪"？事务、MVCC 与锁
它在回答"应用代码怎么写才不会让数据库白优化"？Java 数据访问
它在回答"机器、磁盘、机房出问题时还剩多少数据"？复制、备份与高可用

同一个名词出现在多份笔记里不算重复，只要角色不同。数据库这边几组常见的分工：

  • 索引：存储层讲它的结构与代价（页、B+ 树、回表、Change Buffer），执行层讲"为什么用不上、为什么优化器主动不用"，应用层讲"ORM 生成了几次查询"。
  • 锁：并发层讲加锁规则与死锁排查，"为什么这条 UPDATE 锁了这么多行"由存储层的索引结构回答。
  • 连接：设计层用它论证反范式的收益，执行层讲它的等价变换与代价，可靠性层讲批量写入对重放的影响。
  • 事务：并发层讲语义与机制，应用层讲边界该划在哪里，可靠性层讲"提交成功"在复制场景下意味着什么。
  • NULL：设计层讲它在约束上的漏洞（唯一索引不唯一），存储层讲它与索引的行为，执行层讲它让 NOT IN 返回空集。
