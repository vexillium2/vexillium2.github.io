Java 数据访问：JDBC、连接池与 ORM 的边界

数据库侧做了很多优化：页的大小、索引的结构、执行计划的代价、锁的范围。它们全部可能被应用层的一次错误写法抵消——很多性能问题在数据库内部根本看不到，因为它根本没有变成一条慢 SQL：它变成了很多条快 SQL，每一条都快到不会进慢查询日志。

这篇文章按"从下往上"的顺序看应用层：JDBC 是唯一的真实通道，连接池是它的复用与限流层，事务决定连接的持有时间，ORM 决定生成了什么 SQL、生成了几条。最后回到一个可验收的判据：应用层有没有在做数据库本该做的事。

JDBC：连接、语句与结果集的三段成本

连接的成本：为什么必须池化

建立一个 JDBC 连接要经历 TCP 握手加数据库认证，还要在服务端为它分配会话状态。如果每个请求都新建、用完就关，会带来三重代价：

  • 网络层：大量短连接反复握手、关闭，留下大量处于等待关闭状态的连接，占用系统资源；
  • 数据库层：为每个连接建立与销毁会话相关的数据结构，这是纯开销；
  • 应用层：连接的创建与回收产生大量短命对象，把 GC 压力推高。

这三重代价与"这条 SQL 本身快不快"完全无关。所以连接池不是性能优化选项，是必需的——它把"每个请求付一次建连成本"变成"整个进程付一次，之后复用"。

PreparedStatement：预编译与参数化的双重作用

JDBC 有三种语句对象：普通语句、预编译语句、存储过程调用。其中预编译语句带来两件不同的事，值得分开看：

  • 参数化：参数通过占位符传入，不参与 SQL 文本拼接。这从根本上消除了 SQL 注入（前提是参数永远走占位符，而不是拼字符串）；
  • 预编译：语句模板在数据库侧解析一次、复用执行计划，省掉重复的解析成本。

这里有一个容易误解的细节：驱动默认可能并不使用服务端的预编译。以 MySQL 驱动为例，服务端预编译需要显式开启，默认走的是客户端参数替换。所以"我用了预编译语句，所以数据库侧一定复用了执行计划"这个推断并不成立——参数化带来的安全性是必然的，预编译带来的性能收益是条件性的。

还有一件相关的错：把能用参数的场景写成字符串拼接，然后再靠转义来防注入。参数化是结构性的防护，转义是文本层面的对抗，后者迟早会有遗漏。

结果集太大：一次性、流式与游标三种读法

这是应用层最容易被忽视的一段成本。查询返回的数据要从服务端搬到客户端，这一段的内存与时间开销不受索引和计划的影响。

默认行为是把整个结果集一次性读进客户端内存。行数少时它最简单也最快；行数上万之后，问题不在数据库而在应用——内存峰值、长时间的对象分配、以及 GC 停顿。轮询或数据修复类任务经常在这里出事故。

另外两种读法改变的是数据传输的粒度：

  • 流式读取：让驱动逐行或小批地从服务端取数据，不在客户端堆积。代价是这条连接在结果集被读完之前被独占——如果处理逻辑很慢，连接池里的可用连接会持续减少。它适合"边读边处理、且处理不慢"的场景。
  • 游标读取：在服务端建立游标，客户端按批取回。它在服务端保存了查询状态，对复杂查询更友好，但同样占用连接与数据库侧的临时资源。

选哪种取决于结果集的规模与处理方式，不是性能偏好：几百行的报表用一次性读取最省事；百万行的导出必须用流式或分页，否则迟早会因为内存问题挂掉。

连接泄漏：池化之后最贵的错误

连接池让"忘记归还"变成了一个必然耗尽的资源问题：池里的连接是有限的，只要有一条代码路径在异常时没归还连接，池的可用量就会以每次调用的速度减少，直到全部占满，然后整个应用的所有数据库操作一起挂住。

避免方式是结构性的，不是靠仔细：用自动关闭的语法块管理资源，让连接、语句、结果集在作用域结束时一定被释放；在池上开启泄漏检测（超过阈值未归还就打印持有者堆栈），让问题在耗尽之前暴露出来。

// 自动关闭的语法块：无论正常返回还是抛异常，三个资源都会按相反顺序释放
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(SQL);
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        // 处理每一行
    }
}

要记住的是：池化把"连接用完即走"的容错性换掉了。以前漏一个连接只影响那个请求，现在漏一个连接会累积成全局故障。

连接池：参数不是随便填的

池解决的是复用与限流两件事

连接池做两件事，第二件常被忽略：

  • 复用：把建立连接的成本摊到多次使用上；
  • 限流：为应用对数据库的并发量设置一个上界。

第二件事的意义比第一件大。数据库能承受的并发是有限的，它由 CPU 核数、磁盘 IO 能力、锁竞争程度共同决定。连接池把"无限并发"截断成"可控并发"，让超出部分在应用侧排队，而不是冲进数据库把锁竞争与上下文切换推到失控。没有池，应用能对数据库发起的并发就没上限。

连接数不是越多越好：从服务能力反推池大小

这是连接池最重要也最反直觉的一条：把池调大通常会让系统更慢。

原因是数据库的并发处理存在一个饱和点。超过它之后，每个请求都要分享 CPU 时间片、抢同一批锁、争同一份缓冲池，结果是每个请求都变慢、总吞吐反而下降。连接数只是把等待从应用侧搬到了数据库侧，代价还更高——因为等待期间数据库仍在为这些连接做调度。

所以正确的推导方向是从数据库能承受的并发反推池大小，而不是按应用的线程数或用户数去配。经验上，一个较小的池（与 CPU 核数同量级、再按磁盘并行能力上浮一些）往往比一个过大的池吞吐更高。

同时必须核对一个乘法：所有应用实例的池大小之和，必须明显小于数据库的最大连接数。忘了这一步，扩容应用实例就会变成打垮数据库——这是"扩容反而更慢"最常见的原因。

另外，应用线程数与池大小也应当协调：线程数远大于池，大量线程会卡在"等连接"上，问题表现为应用超时而非数据库慢；线程数远小于池，池里会有大量闲置连接白占数据库资源。

生命周期与保活：为什么 maxLifetime 要小于 wait_timeout

数据库服务端会对空闲连接设一个超时（wait_timeout），到期就单方面关闭它。问题在于这个关闭是静默的：池里的连接对象还在，应用以为它是好的，直到拿它发请求才报错——表现为"偶发的、无法复现的连接异常"。

标准做法是把池的最大生命周期设得比服务端的空闲超时更短，让池主动在服务端清理之前把连接换掉。同时配置保活检测（拿连接时验证、或定期验证），把已经失效的连接提前淘汰。

这两个参数的关系是必须成立的不等式，不是可调优的选项：maxLifetime 小于 wait_timeout（并留出余量）。调错方向的后果不是变慢，而是随机失败。

连接泄漏的定位

泄漏排查不要从代码审计开始，先从数据看：

  • 池的活跃连接数是否只升不降——这是泄漏最直接的信号；
  • 泄漏检测打出的堆栈指向拿连接的那一行，这才是根因位置；
  • 结合数据库侧的当前连接数与状态，确认这些连接是"空闲但未归还"还是"真的在执行"。

这三者能区分开三种完全不同的病因：泄漏（拿了不还）、长事务（还不了）、慢查询堆积（还没来得及还）。它们都表现为"连接数打满"，但修法完全不同。

事务：应用层最容易把并发搞坏的地方

事务边界：注解失效的三种常见情况

用声明式事务时，"我加了注解"不等于"事务真的生效了"。失效有三种典型来源：

  • 同类内部自调用。声明式事务靠代理实现，类内部直接调用自己的方法不经过代理，事务注解被跳过。这是最隐蔽的一种，因为代码看上去完全正确。
  • 方法可见性不满足代理要求。基于代理的实现对方法可见性有要求，不符合时注解不会生效。这条的具体边界随框架版本变化，遇到"注解没生效"时应把它列入排查项。
  • 异常类型不在回滚范围内。默认只在非受检异常时回滚，受检异常不会触发回滚——事务已经执行了一部分，然后提交了。这类 bug 不会报错，只会留下坏数据。

第三条的正确做法是显式声明回滚条件，不要依赖默认行为。事务里捕获异常后"吞掉不抛"也会产生同样的后果：异常被消化了，事务却以为一切正常。

事务里不该做的事：远程调用与循环

事务的生命周期等于锁的生命周期，也等于连接的持有时间。所以放进事务的每一件慢事，都会成倍放大成并发损失。

三条明确不该进事务的操作：

  • 远程调用：网络抖动是秒级的，而事务里的锁在等它。一次下游超时就能把上游的写并发全部拖住。
  • 消息发送：它应该发生在事务提交之后。在事务内发送，会出现"消息发出去了但事务回滚了"的经典不一致。
  • 循环里的单条读写：一次事务里发 N 次查询，往返成本乘以 N。这类逻辑应该改成批量操作，让一次往返处理一批数据。

与之相关的是只读事务：如果一段逻辑只读，明确标记为只读，框架与数据库都可能省掉不必要的开销，也不会误占写锁。

长事务如何耗尽连接池

这是一个跨层的因果链，值得单独走一遍：

事务不结束 → 它绑定的连接不归还 → 池的可用连接减少 → 其他请求开始排队等连接 → 应用超时。

它的表现极具误导性：数据库侧的慢查询日志可能是干净的（每个语句都很快），CPU 与 IO 都不高，但应用大面积超时。根因是"事务开得太多、活得太久"，而不是"SQL 太慢"。

所以定位"连接被打满"时，一定要先分清是三种里的哪一种：泄漏、长事务、还是慢查询堆积。把长事务当成连接数不够去扩容池，只会让更多长事务同时存在，情况更糟。

ORM 的代价：抽象换走了什么

N+1 查询：应用层最典型的性能陷阱

ORM 最擅长的事是"把对象关系映射成表关系"，而它最容易出错的地方也在这里。看一个典型形态：查出一批订单，然后遍历它们取每个订单的客户名。

如果关联属性是懒加载的，实际发生的 SQL 是：一条语句查出 N 个订单，然后每条订单各发一条语句查它的客户——总共 N+1 次往返。

它的危害不在任何单条语句：每一条都走了主键索引，都很快，都不会出现在慢查询日志里。它的成本全在往返次数上：N+1 次网络往返、N+1 次解析与优化、N+1 次取连接。N 是 100 就是 101 次往返，而它本可以是一次连接查询。

// N+1：一条语句查出订单，再为每个订单各查一次客户
List<Order> orders = orderMapper.selectByUser(userId);              // 1 次往返
for (Order o : orders) {
    o.setCustomerName(customerMapper.selectById(o.getCustomerId())  // N 次往返
            .getName());
}

// 显式批量查询：先收集主键，一次取回，再在内存里组装
Set<Long> ids = orders.stream().map(Order::getCustomerId).collect(toSet());
Map<Long, Customer> byId = customerMapper.selectByIds(ids).stream()
        .collect(toMap(Customer::getId, c -> c));                   // 1 次往返
orders.forEach(o -> o.setCustomerName(byId.get(o.getCustomerId()).getName()));

四类对策，按适用性排序：

  • 一次连接取回：用连接抓取（join fetch）把关联在一条语句里带出来。它最直接，但要注意：当一对多关联被连接时结果会膨胀，去重与分页都要重新考虑。
  • 批量抓取：把懒加载按批合并，一次取一批关联（例如每 100 个主键发一条查询），把 N+1 降到 1+N/100。它改动最小，通常是最实用的第一步。
  • 显式批量查询：先收集关联 ID，再用一次带 IN 的查询取回，然后在应用侧组装。控制力最强，代价是要自己写组装逻辑。
  • 用缓存承接：如果关联数据变化不频繁，把它放进本地或分布式缓存。它把问题从"查询次数"变成"缓存命中率"，但引入了失效逻辑。

检测手段比对策更重要：开启 SQL 日志，统计单个请求产生的语句条数。N+1 不会自己暴露，必须主动去数。

懒加载与事务边界

懒加载把"取数据"这个动作推迟到了属性被访问的那一刻。这带来两个后果：

  • 访问发生在事务之外时会失败。会话已关闭，ORM 无法再发起查询，于是抛异常。很多"偶发报错"来自这里——事务内没用到的属性，在事务外被序列化时被触发了。
  • 访问发生在事务之外、但会话尚未关闭时会反复申请连接。每次懒加载都是一轮独立的取连接、查询、归还，一个逻辑操作因此产生多次连接往返，在连接池紧张时表现为难以解释的等待。

处理方式有两种取向：要么在事务内一次性把需要的数据取全（明确声明抓取策略），要么把实体转成不含懒加载的传输对象再往外传。两者都比"靠事务边界恰好包住"更可靠。

批量操作与分页在 ORM 下的真实形态

ORM 的抽象会掩盖两类操作的真实成本：

  • 批量更新/删除。ORM 的"批量"有时只是"在循环里逐条执行"，实际是 N 条语句、N 次往返。真正的批量应该落成一条语句，或者至少是分批的多值语句。
  • 分页。分页通常伴随一条额外的计数查询；深分页在 SQL 层的代价（要取出并丢弃前面所有行）不会因为换成 ORM 的分页组件而消失。分页组件的方便程度和分页查询的成本是两件事。

判断方法还是同一个：看日志里实际生成了几条什么 SQL。ORM 的 API 无法告诉你这件事。

让 ORM 生成的 SQL 可见

ORM 的收益是开发效率，它的代价是SQL 不再由你直接控制。代价本身没问题，问题是很多人不知道代价发生在哪里。

所以有一条几乎是硬性的工程要求：ORM 生成的 SQL 必须可观测。具体是三件事：

  • 开发与测试环境打开语句日志，让每条生成的 SQL 都看得见；
  • 生产环境让这些 SQL 进入慢查询统计，而不是绕过它；
  • 对关键接口统计每个请求的语句条数，把一个隐性的性能指标变成可监控的指标。

一句话总结这一节：ORM 不是"不用懂 SQL"，它是"用开发效率换走了对 SQL 的直接控制"，换来的东西你必须能用日志补回来。

读写分离与多数据源

读写分离的三种实现位置

读写分离把读流量分到从库，实现位置有三种，代价不同：

位置做法主要代价
驱动层在 JDBC 层按语句类型路由到不同数据源对应用透明，但路由规则只在当前进程内有效
代理层应用连代理，由代理转发到主库或从库对应用完全透明，多一跳网络与代理的运维成本
应用层用注解或 AOP 显式指定走主库还是从库控制力最强，但每个开发者都要记得标注

三种都能用，选择依据是团队愿意把复杂性放在哪里：驱动与代理把复杂性集中在一个组件里，应用层则把它分散到每次调用上。

主从延迟：读己之写为什么会失败

只要用了从库，就必须面对一件事：复制是异步的，延迟总是存在。典型症状是"我刚保存，再查却查不到"。

这属于读己之写（read-your-writes）的破坏，标准补偿有几档：

  • 写后一段时间内强制走主库。实现简单，代价是把一部分读压回主库，需要设定时间窗口；
  • 按标记路由。写入后把这个请求（或这个会话）标记为"必须读主"，直到它成功读到自己的写；
  • 在同一次业务操作内不切从库。凡是与写属于同一逻辑单元、且需要看到该写的读，直接走主库。

要划清的边界同样重要：事务内的读必须走主库。如果在事务里把读路由到从库，会出现"事务内的读看不到本事务的写"这种更严重的错乱。

多数据源与事务的边界

引入第二个数据源时，最先要接受的事实是：本地事务无法跨越两个数据源。这不是实现问题，是本地事务的定义决定的——它的事务上下文属于某一个连接。

由此产生几种选择，代价逐级上升：

  • 避免跨源写：让每个事务只写一个数据源，跨源的一致性改由最终一致获得（本地事务写业务数据加一张待发送记录表，事务提交后再异步投递，由重试保证送达）。
  • 两阶段提交：由协调者保证原子性，代价是持锁时间变长、性能下降，且需要额外组件。
  • 补偿型事务模式：把一个分布式事务拆成若干本地事务加补偿动作，代价是必须为每一步写出补偿逻辑，并且要接受中间状态对外可见。

选择依据是业务对中间状态的容忍度，而不是对"强一致"这个说法的偏好。能接受最终一致就不要引入两阶段提交——后者带来的性能与可用性代价，通常在业务上换不到对应的收益。

把数据库的能力还给数据库

应该下沉到数据库的：过滤、排序、聚合、约束

有一条判据可以覆盖大部分情况：如果一件事能在数据库里用一条 SQL 表达，就应该在数据库里做。

  • 过滤：把条件写进 WHERE，让索引有机会用上。把整表读进应用再筛选，等于主动放弃索引、放弃下推、放弃只读需要的那部分数据。
  • 排序：只有数据库知道索引的有序性，应用侧排序意味着先把数据全部搬过来。
  • 聚合：计数、求和、分组由数据库做，只返回结果行；应用侧做聚合意味着把明细全部搬运一遍。
  • 约束：唯一性与存在性尽量下沉，因为应用层的校验会被绕过——数据修复脚本、手工 SQL、另一个服务都会绕过它。

应该在应用层做的：跨服务聚合与业务规则

反向也要说清，否则会走向另一个极端：把所有逻辑塞进存储过程。以下三类更适合留在应用层：

  • 跨服务的聚合。数据在不同的服务或数据库里，数据库的 join 做不到，只能由应用组装。
  • 需要外部系统的判断。调用风控、调用配置中心、调用第三方，"是否允许下单"这类规则依赖数据库之外的信息。
  • 频繁变化的业务规则。规则用代码表达可以测试、评审、快速发布；写进存储过程会让它的变更流程与代码脱节。

所以边界不是"哪边更强"，而是数据在哪里、变更频率如何、以及谁负责它的测试。

一个可验收的判据：返回行数与扫描行数的比值

把上面这些结论压缩成一个可以在代码评审和监控里用的判据：

核对每一次查询的"扫描行数"与"返回行数"的比值。 扫描很多、返回很少，说明过滤没有下沉；扫描很多、返回也很多，说明分页或聚合没有下沉——这两类都能在数据库侧被消除，而现在它们消耗的是网络、应用内存与 GC。

这条判据的好处是它不依赖任何框架知识，也不需要在评审时读懂 SQL：只要看一个比值，就能判断这段数据访问是在利用数据库，还是在绕过它。 而它恰好也是那些"数据库侧看不到的性能问题"最可靠的检测手段——因为它们不会变成慢 SQL，只会变成很多条快 SQL。
