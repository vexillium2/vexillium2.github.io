软件测试笔记

vexillium2026/7/8大约 13 分钟后端开发测试

一、测试基础理论

1.1 测试的核心目的

测试的目的不是证明没有 Bug，而是发现风险。

  • 缺陷发现：在发布前识别代码逻辑错误、边界条件遗漏
  • 质量保护：作为回归防护网，防止新代码破坏现有功能
  • 设计反馈：可测试性差往往意味着设计耦合度过高
  • 文档价值：测试用例是最鲜活的功能规格说明

1.2 经典测试原则

原则说明
测试穷尽不可能只能基于风险选择测试范围，而非追求 100% 覆盖
尽早测试缺陷修复成本随阶段呈指数级增长（单元 < 集成 < 线上）
杀虫剂悖论同一组测试用例反复执行会逐渐失效，需定期补充新用例
上下文依赖医疗软件 vs 营销网站的测试策略天差地别
Absence-of-errors Fallacy没有 Bug 不代表产品有价值，需结合业务目标

1.3 测试金字塔（Test Pyramid）

        ▲
       /▲\        E2E / UI 测试（少量、关键路径）
      / ▲ \       集成测试（服务间、模块间）
     /  ▲  \      组件测试
    /   ▲   \     单元测试（大量、快速、稳定）
   /________\    基础设施（静态检查、类型系统）

核心思想：越底层的测试，数量越多、速度越快、成本越低；越上层的测试，数量越少、覆盖越全、维护成本越高。

💡 SWE 的主要职责集中在金字塔底部和中部：单元测试 + 集成测试。E2E 通常由 QA 或 SDET 主导。

二、核心测试类型详解

2.1 单元测试（Unit Test）

定义与边界

  • 测试对象：最小可测试单元（函数、类、模块）
  • 隔离原则：不依赖数据库、网络、文件系统，外部依赖全部 Mock
  • 执行速度：单测毫秒级，全量单测应在分钟级完成

SWE 必会要点

1. FIRST 原则

  • Fast（快速）：慢的单测会被开发者跳过
  • Independent（独立）：用例间无依赖，可任意顺序执行
  • Repeatable（可重复）：同一结果不受环境影响
  • Self-validating（自验证）：断言自动判定，无需人工检查
  • Timely（及时）：与生产代码同步编写或先于代码（TDD）

2. 命名规范（推荐）

[被测单元]_[场景/条件]_[期望结果]
例：calculateDiscount_WhenUserIsVIP_ShouldReturn20PercentOff

3. 断言设计

  • 避免过度断言：一个用例聚焦一个行为
  • 优先断言业务结果而非实现细节（否则重构会破坏大量用例）
  • 异常场景要断言异常类型和消息

4. 典型反模式

  • ❌ 测试私有方法（私有方法应通过公有接口被间接测试）
  • ❌ 一个用例包含多个 if/else 分支（拆分为多个用例）
  • ❌ 单测中出现随机数、时间依赖（注入可控的 Clock）

2.2 白盒、黑盒、灰盒测试

维度白盒测试黑盒测试灰盒测试
视角已知内部实现未知内部实现部分已知
设计依据代码结构、逻辑分支需求规格、用户场景接口定义 + 核心逻辑
常用技术语句覆盖、分支覆盖、路径覆盖等价类、边界值、决策表API 测试 + 关键代码路径验证
执行者开发 SWEQA / 产品SWE / SDET

🎯 对 SWE 的意义：单测是白盒，集成测试往往是灰盒（知道接口定义 + 部分内部逻辑），验收测试是黑盒视角。

2.3 集成测试（Integration Test）

定义与分类

  • 狭义：模块间接口调用测试（如 Service 调用 Repository）
  • 广义：服务间协作、第三方依赖集成（如调用支付网关）

策略模式

  1. Big Bang：所有模块开发完一次性集成（适用于小型项目）
  2. Top-Down：自上而下，底层用 Stub 替代
  3. Bottom-Up：自下而上，上层用 Driver 替代
  4. Sandwich：上下同时推进，中间汇合（最常用）

SWE 实践要点

  • 使用 Testcontainer 启动真实数据库/Redis，而非内存模拟
  • 测试数据要做到「用例级隔离」：每个用例执行前后清表或回滚
  • 第三方接口用 Mock Server（WireMock / Mountebank）模拟

2.4 端到端测试（E2E / UI 测试）

  • 定位：模拟真实用户操作链路，验证系统全流程闭环
  • 工具选型：Playwright / Cypress（Web）、Appium（移动端）
  • 数量控制：只覆盖核心业务链路（如：注册→下单→支付→发货），一般 20~50 条足够
  • 稳定性治理：重试机制、合理等待、数据预埋、选择稳定的定位器

三、专项测试领域

3.1 性能测试家族

性能测试
├── 基准测试（Benchmark）：单接口基线性能
├── 负载测试（Load Test）：预期峰值下表现
├── 压力测试（Stress Test）：超出负载寻找极限点
├── 浸泡测试（Soak Test / Endurance Test）：长时间运行下的内存泄漏、连接泄漏
├── 尖峰测试（Spike Test）：突发流量冲击（秒杀场景）
└── 并发测试（Concurrency Test）：多用户同时操作的竞态问题

🌊 浸泡测试（Soak Test）—— 你提到的重点

为什么需要？

  • 内存泄漏：短时间看不出来，运行几小时/几天后 OOM
  • 连接泄漏：DB 连接、HTTP 连接池耗尽
  • 资源耗尽：文件句柄、线程池队列积压
  • 定时任务累积：日志膨胀、缓存数据过期逻辑异常

关键指标

  • 持续时长：通常 12h / 24h / 72h
  • 监控曲线：内存趋势（是否单调递增？）、GC 频率、响应时间漂移

SWE 可执行的最小实践：

压测脚本 + 监控看板跑一个周末，周一来观察内存曲线斜率。如果内存在持续上涨且 GC 不回收，十有八九有泄漏。

3.2 安全测试基础（SWE 应知应会）

风险类型开发侧防护点可自测手段
SQL 注入使用参数化查询，禁止字符串拼接 SQL输入 ' OR '1'='1 测查询接口
XSS输出转义、CSP 策略<script>alert(1)</script> 提交表单
CSRFToken 校验、SameSite Cookie构造第三方页面自动提交表单
越权访问接口必须校验资源归属改 URL 中的 ID 尝试访问他人数据
敏感数据泄露日志脱敏、传输加密检查日志/响应中有无明文密码、Token

3.3 混沌工程（Chaos Engineering）

「在生产环境注入故障，主动验证系统的弹性能力」

成熟度阶梯：

  1. 初级：手动杀死进程、断网，观察恢复能力
  2. 中级：用 Chaos Mesh / Gremlin 做故障演练（延迟、丢包、CPU 高负载）
  3. 高级：自动化故障注入 + 游戏日（Game Day）常态化

3.4 兼容性 & 回归测试

  • 兼容性测试：浏览器矩阵、OS 版本、分辨率、屏幕尺寸
  • 回归测试：每次上线前跑的「安全网」用例集，确认旧功能没被破坏
    • 回归用例不是越多越好，核心是高价值、高频用例
    • 自动化回归的覆盖率目标：核心链路 100%，重要功能 80%+

四、发布与实验体系

4.1 灰度测试（Grey Test / Canary Release）

核心思想

像金丝雀进煤矿，先让一小部分用户/流量进新版本，观察指标正常后再全量。

灰度维度

维度示例
用户维度按 userId 哈希、用户标签（内部员工/白名单/会员）、地理位置
流量维度按请求比例 1% → 5% → 20% → 50% → 100%
设备/版本iOS 先发、Android 后发；某个 App 版本以上才生效

SWE 实操要点

  • 可灰度配置：所有开关通过配置中心下发，禁止硬编码
  • 可观测性前置：灰度前先确保核心指标有监控（错误率、延迟、业务转化）
  • 回滚预案：一键关灰度开关比回滚代码快得多
  • 灰度时长：至少覆盖一个完整业务周期（一周含周末高峰）

4.2 A/B 测试

与灰度测试的区别

维度灰度测试A/B 测试
目的验证稳定性、发现 Bug验证业务方案优劣（数据驱动决策）
分组单维度渐进放量多组并行（对照组 vs 实验组）
时长天级别周/月级别（需统计显著性）
结果全量 / 回滚选择优胜方案

统计基础（SWE 也要懂）

  • 样本量估算：提前算好需要多少用户才能得出显著结论（避免过早下判断）
  • 统计显著性：p-value < 0.05 表示差异非偶然
  • 置信区间：指标的波动范围，比单点值更有参考意义
  • 辛普森悖论：整体结论和细分维度结论相反时要警惕（分流不均？）

SWE 职责

  • 埋点准确：实验组标识、事件上报、属性完整
  • 分流均匀：哈希算法要均匀，避免组间用户画像偏差
  • 防污染：不能让 A 组用户跑到 B 组（缓存问题？）

4.3 渗透率 & 核心指标监控

发布三板斧：

  1. 渗透率 = 新版本用户数 / 总活跃用户数
  2. 留存率 = 渗透率下的次日/7日留存是否下降
  3. 崩溃率 / 错误率 = 技术质量底线指标

📌 发布节奏：观察 → 判断 → 决策。放量后至少观察 24 小时再下一步。

4.4 发布策略对比

策略说明适用场景
蓝绿部署两套环境，流量一次性切快速回滚，但资源成本高
金丝雀（灰度）逐步放量大多数线上服务
滚动发布实例逐个替换对中断不敏感的服务
Feature Flag功能开关控制新功能、实验性功能

五、测试用例设计技术

5.1 黑盒设计方法（SWE 写用例也能用）

① 等价类划分

  • 有效等价类：符合规则的输入集合
  • 无效等价类：各种异常输入

例：手机号输入 → 有效：11位 1 开头；无效：空、10位、12位、以 2 开头、非数字...

② 边界值分析

错误往往发生在边界上。

  • 取 min-1, min, min+1, normal, max-1, max, max+1
  • 例：6~20 位密码 → 测 5、6、7、19、20、21 位

③ 决策表（多条件组合）

适合业务规则复杂的场景（如优惠叠加逻辑）。

  • 列出所有条件桩、动作桩
  • 穷举条件组合，化简无意义组合

④ 状态迁移测试

适合有限状态机（订单状态、工作流）。

  • 画状态转移图 → 覆盖所有合法/非法迁移路径

5.2 探索式测试（Exploratory Testing）

「同时学习、设计、执行测试」—— 不是乱点，是有章法的自由探索。

启发式漫游模型：

  • 商业区（核心功能）、历史区（老代码）、娱乐区（异常/极端操作）
  • 旅馆区（长时间停留、反复操作）
  • 穷街陋巷（边界、异常、并发）

💡 SWE 提测前花 30 分钟做一次探索式测试，可以拦截 30%+ 的低级 Bug。

六、测试工程实践

6.1 TDD（测试驱动开发）

红 → 绿 → 重构 循环

1. 红：写一个失败的测试（定义期望行为）
2. 绿：用最少的代码让测试通过
3. 重构：优化代码结构，保持测试通过

什么时候适合用 TDD？

  • ✅ 逻辑复杂、规则清晰的代码（计算、校验、算法）
  • ✅ Bug 修复：先写复现 Bug 的测试，再修（防止回归）
  • ❌ 探索性开发、原型开发（需求不停变化）
  • ❌ UI 层、胶水代码（收益低）

6.2 Mock / Stub / Fake / Spy 的区别

类型作用典型场景
Dummy占位对象，仅用于传参不需要实际被用到的参数
Stub返回预设数据，记录调用信息模拟 Service 依赖的 Repository 返回
Mock预设期望调用，验证交互发生验证某个方法必须被调用 X 次
Fake有真实逻辑但简化的实现内存数据库 H2 替代真实 MySQL
Spy包装真实对象，部分方法 Stub想调用真实逻辑但监控某个方法调用

⚠️ 不要滥用 Mock！Mock 过多会导致测试和实现高度耦合，重构噩梦。优先用真实依赖（集成测试），无法稳定获取时才 Mock。

6.3 测试覆盖率（Coverage）

四种覆盖维度：

语句覆盖 < 分支覆盖 < 条件覆盖 < 路径覆盖
（弱）───────────────────────────────→（强）

SWE 实践建议：

  • 新代码覆盖率目标 ≥ 80%，核心模块 ≥ 90%
  • 不要追求 100%：最后那几个点投入产出比极低
  • 更重要的是「业务语义覆盖」而非「代码行覆盖」（行覆盖高不代表场景覆盖全）
  • 覆盖率下降的 PR 要重点 Review

6.4 CI/CD 中的测试门禁

代码提交
   ↓
✅ 静态检查（Lint、类型检查）          ~10s
✅ 单元测试                          ~1min
✅ 代码扫描（SAST、依赖漏洞）         ~1min
✅ 构建镜像
✅ 集成测试（Testcontainer）          ~5min
✅ 部署到 Test 环境
⬜ 人工验证 / QA 回归
   ↓
合并主干 → 灰度发布

七、质量度量与持续改进

7.1 Bug 生命周期与分级

Bug 严重级别（Severity）：

  • S0 致命：核心流程完全不可用、数据丢失、安全漏洞 → 立即修复
  • S1 严重：主要功能异常、无替代方案 → 本版本修复
  • S2 一般：次要功能异常、有 Workaround → 下个版本修复
  • S3 轻微：UI 瑕疵、体验问题 → 排期修复

Bug 优先级（Priority）：

Severity 是影响面，Priority 是修复紧急度。两者相关但不等同。 例：按钮错别字（S3）但在首页广告位（P0）。

7.2 核心质量指标

指标公式 / 含义参考阈值
缺陷逃逸率线上 Bug 数 / (提测 Bug + 线上 Bug)< 5%（优秀），< 10%（合格）
重开率被 Reopen 的 Bug / 总 Bug< 5%
千行缺陷率Bug 数 / 千行代码因业务而异，趋势比绝对值重要
MTTR故障平均修复时间越短越好，核心服务 < 30min
测试执行率已执行用例 / 计划用例上线前 100%

7.3 SWE 的质量文化

预防 > 检测：

  • Code Review 是质量第一道防线（每一行代码至少两人看过）
  • 静态分析、类型系统是免费的 Bug 拦截器
  • 复杂逻辑写之前先画时序图 / 状态机，很多 Bug 在设计阶段就能避免

复盘文化：

  • 每个线上 P0/P1 Bug 写 Root Cause Analysis（RCA）
  • 三个经典问题：为什么没测出来？怎么避免再犯？如何自动检测？
  • 修复 Bug 的同时补测试用例（回归防护）

八、学习路线与实践建议

阶段 1：夯实基础（1~2 个月）

  • [ ] 将现有单测按 FIRST 原则重构优化 3~5 个模块
  • [ ] 为下一个需求提前写测试用例（等价类 + 边界值）
  • [ ] 了解 Jacoco / Jest Coverage 的四种覆盖维度差异

阶段 2：工程化能力（2~3 个月）

  • [ ] 写一次集成测试（用 Testcontainer 启真实 DB）
  • [ ] 参与一次 Feature Flag 灰度发布，观察监控指标
  • [ ] 用 JMeter / k6 对自己写的接口做一次压测

阶段 3：专项深入（长期）

  • [ ] 跑一次 24h 浸泡测试，观察内存/连接曲线
  • [ ] 尝试 TDD 写一个算法/计算类需求
  • [ ] 设计并执行一次 A/B 测试（埋点 → 分流 → 统计分析）
  • [ ] 做一次混沌工程实验：杀死 Pod、注入延迟，观察恢复

阶段 4：方法论沉淀

  • [ ] 对一个线上 Bug 做完整 RCA 并补充回归用例
  • [ ] 沉淀团队的「单测规范」「集成测试规范」
  • [ ] 优化 CI 流水线中的测试门禁（并行、分片、增量）

九、自动化测试

通用三段式结构（Given / When / Then）

  • 环境清理 / 数据准备（Arrange / Given）
  • 主体执行（Act / When）
  • 断言验证（Assert / Then）
