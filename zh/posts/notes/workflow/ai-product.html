AI 产品经理的 SOP

技能来源：SpaceZephyr/pm-skills —— 本文所有 pm-* skill 均出自此仓库（13 个执行工具箱 + 7 个专家顾问团 + pm-master 总控），各阶段「方法与工具」直接映射到对应 skill。

主线：读完能拿到一套「AI 原生」的产品经理工作 SOP——以 AI 方法论为主线，从「这个场景该不该用 AI」一路走到「上线后怎么迭代」，把传统 PM 工作（PRD、评审、排期、复盘）吸收为其中的步骤。每个阶段都写清：先做什么后做什么（工作流）、和谁开什么会（跨部门协同）、产出什么（核心产出）、用哪个方法/工具（skill 映射）。

状态：初稿完成——阶段零~六已成文；「🔗 扩展预留」标记的话题待后续独立成篇或展开为小节。

全程可用：pm-master（分诊 / 路由 / 编排）、pm-advisory-board（多视角评审）。

贯穿全程的三个横切主题（不单列成章，散入各阶段）：数据策略、合规与伦理、版本管理。

阶段零：战略对齐与 AI 适用性初筛

这一阶段回答：这个场景到底该不该用 AI？

为什么要先做这一步

AI 功能自带一笔传统功能没有的账：token 成本、评测集建设、失败兜底、内容安全与合规、持续的模型与 Prompt 维护。同样一个需求，用规则引擎几行代码能解决，用大模型可能要每月烧掉一笔推理费，还附带幻觉风险和返工。

所以在写任何 PRD、画任何原型之前，先回答一个问题：这个场景真的需要 AI 吗？

这一步最常见的坑是「拿着锤子找钉子」——先决定了要用 AI，再回头找理由。阶段零的意义就是反过来：先看问题和账，再决定要不要动用 AI。

工作流

步骤 1：业务目标拆解

先写清这个需求要改变的 outcome 是什么，而不是要做的功能是什么。

  • 业务目标：一句话说清「上线后，哪个指标应该往哪动」，如「客服单均处理时长下降 30%」。
  • 拆到可验证：目标要能落成一个事后可用数据验证的「北极星指标」（North Star Metric）——衡量业务结果的单一指标，而不是一堆过程指标。
  • 明确约束：时间、人力、预算、谁为结果负责。
  • 向上对齐：把目标陈述和老板、业务方的 OKR 对上，确认你要推的指标正是他们真正关心的结果。不然后面做得再对，也会被一句「这不是我要的」打回重来。

这一步的产出是一句「目标陈述」，它是后面所有取舍的锚点。

步骤 2：场景扫描

把目标涉及的流程拆成一个个具体任务，用四条信号逐一过筛，判断哪些任务天然适合 AI：

信号判断问题说明
高频这件事一天发生多少次？次数越多，AI 的复用收益越大
重复每次做的是不是同一套动作？重复性高，才有「样本」可学、可评测
非结构化输入输出是不是非结构化（文字、语音、图片）？结构化、可枚举的直接用规则，不必上 AI
需推理是否涉及判断、归纳、生成，而非查表匹配？纯查表、纯计算用规则更便宜

把候选场景列成清单，每个场景标注命中了哪几条信号。

步骤 3：AI 适配度判断

用一张表给每个候选场景打分，把「该不该用 AI」从感觉变成可复核的结论：

场景高频重复非结构化需推理容错要求数据可得性适配结论
客服话术起草✓✓✓✓中（有人审）有历史工单适合
价格计算✓✓✗✗零容错—用规则

三条硬规则（命中任意一条，基本判定「不用 AI 或暂缓」）：

  1. 规则能解决的，不用 AI。能枚举、能穷举、能查表的结构化问题，规则引擎更便宜、更稳定、零幻觉。
  2. 零容错、高风险、不可逆的操作，AI 只做建议不做执行。涉及资金、人身安全、法律后果的动作，AI 输出必须有人确认或直接走规则。
  3. 数据或标注人力不具备，就不启动。没有可用数据、也没有预算去标注，AI 能力再强也是无米之炊。

步骤 4：ROI 粗估

只做数量级估算，不为精确。把账分成两栏：

  • 成本侧（一次性 + 持续）：token / API 调用、数据采集与标注、人工兜底、监控运维、内容安全合规。
  • 收益侧：替代的人力成本、效率提升带来的吞吐、新增收入。

判断标准不是「能不能省钱」，而是「省下的钱是否显著大于 AI 带来的持续成本和风险」。粗估算不平的，上线后通常也算不平。

两笔容易被忽略的账：

  • 机会成本：同样的人力和预算，拿去做别的需求是不是更值。AI 需求排他性强，占了资源就做不了别的。
  • 回收期：算一个「多久回本」的数量级，作为和老板谈判的锚点。

这一步本质是向上管理的起点——预期管理：账算不平就提前摆到桌面，别等上线后才发现亏。

步骤 5：Go / No-Go 决策

综合上面四步，给出三种结论之一：

  • 做：进入阶段一，开始深入调研与定义。
  • 不做：终止，记录原因，避免日后重复论证。
  • 用规则替代：不引入 AI，改用规则引擎 / 模板 / 脚本实现，成本更低。

三种结论里，「不做」和「用规则替代」最考验向上管理。说「不做」不是能力不行，而是把账算清楚后替老板挡掉一次亏损——用 ROI 和机会成本说话，不用「感觉做不成」。决策要落到文字记录（场景 + 结论 + 依据），并让能「拍板」的人确认，否则「以后再议」会变成反复开会的黑洞。

核心产出

  • 场景优先级清单：候选场景 + 四类信号命中 + 适配结论 + 优先级。
  • AI 机会画布：一页纸，把「业务目标 → 场景 → 适配度 → 粗算账 → 结论」串成一条线，用于对齐老板和业务方。
  • Go / No-Go 决策记录：每个场景的最终结论与依据，留档可追溯。

边界与反例

这一阶段最容易翻车的，是把「能做」误当成「该做」。几个典型反例：

  • 反例一：用大模型做结构化查表。字段匹配、价格计算、固定模板渲染，规则引擎又快又稳，用 AI 反而引入幻觉和延迟。
  • 反例二：零容错场景让 AI 直接执行。资金划转、合同盖章、医疗处方，AI 只能出建议，执行必须走规则或人工。
  • 反例三：没有数据也要上。训练 / 微调 / 检索都没有数据来源，标注预算也没有，最后只能靠提示词硬撑，效果和可维护性都失控。
  • 反例四：为单次低价值的长尾场景上 AI。一年用不了几次、每次价值又低的场景，AI 的持续成本会吃掉全部收益。

判断层工具

  • pm-advisor-cagan：用「值不值得做」四问（价值风险 / 可用性风险 / 可行性风险 / 商业风险）在阶段零预演一次，把后面阶段要踩的坑提前暴露。
  • pm-advisor-yujun：用「用户价值 = 新体验 − 旧体验 − 替换成本」算这个场景是否真的产生增量价值，而不是「有 AI 就更好」的错觉。

向上汇报与对齐

阶段零最贵的产出不是结论，而是让结论被接受。三个动作：

  • 预期管理：把风险和账提前暴露，报忧不报喜。老板最怕的不是「这个做不成」，而是「做完才发现做不成」。
  • 用账对齐：拿 AI 机会画布和老板、业务方「拉齐」，把「值不值得上 AI」变成多方共识，而不是 PM 的一家之言。
  • 会签留痕：Go / No-Go 结论走一次「会签」，留档。日后翻旧账时，有「当初说好不做」的凭证，而不是各执一词。

阶段一：洞察与发现

这一阶段回答：有什么值得做的真问题，数据与合规上可不可行？

为什么要先做这一步

阶段零定了「值得做」的场景，但「值得做」不等于「做对了」。这一步要做的是把模糊的「用户需要 AI」变成具体的「用户在哪一刻、因为什么、愿意为哪件事付费或花时间」——也就是逼近产品市场契合（PMF，Product-Market Fit）：先确认方向对不对，再谈做多好。

AI 产品在这一步多出一个变量：数据。传统产品调研问的是「有没有需求」，AI 产品还要问「有没有数据喂它、能不能合法地喂它」。数据和合规判断错了，后面阶段做得再漂亮，上线时也会被卡住。

工作流

步骤 1：需求反馈收集

先把已有的信号捞干净，别急着访谈。反馈来源分三类：

  • 被动来源：客服工单、用户投诉、NPS、评论、社媒。这些是「已经痛到说出来」的需求，优先级天然高。
  • 主动来源：埋点行为数据、漏斗流失点。行为不会撒谎，但不会告诉你「为什么」，需要访谈补充。
  • 内部来源：运营、销售、客服的一线反馈。他们是「高信噪比」的信号源——真实、具体、带情绪，但容易把「个别抱怨」误当「普遍需求」。

这一步产出「需求池」：每条需求记三样——来源、出现频次、用户原话。频次就是去噪用的，别让一个嗓门大的用户顶十个沉默的用户。

步骤 2：用户调研与访谈

带着阶段零的「目标陈述」和需求池去访谈，目标是验证假设，不是收集需求清单。这一节的核心纪律是去诱导（详见扩展预留「用户调研与访谈」）：

  • 问行为，不问意愿。「你上次怎么解决的」比「你会不会用」值钱一百倍，因为后者天然诱导用户说好听话。
  • 问过去，不问未来。让人描述真实发生过的事，而不是想象未来会怎么做。
  • 找反例。主动追问「什么情况下你不会用」，逼出真实边界。

访谈要挖的不是「用户想要什么功能」，而是「用户在什么场景下，为了完成什么任务（JTBD，Jobs To Be Done），不得不忍受什么」。JTBD 的核心假设：用户不是买产品，而是「雇佣」产品去完成一个任务。

同时分清痛点、爽点、痒点三个层次：痛点是必须解决的，爽点是超出预期的，痒点是锦上添花但不致命的。访谈时别把痒点当痛点记，否则需求清单会越列越长、越做越散。

每次访谈结束，记一条「可证伪的假设」：这句话如果为真，我们就做；如果被证伪，就砍。

步骤 3：竞品拆解

竞品是别人替你做过的实验。拆解的目标不是「抄功能」，而是「借结论」——别人踩过的坑、验证过的需求、放弃过的路，都能直接成为你的判断输入。

SOP 层面回答三个问题（详见扩展预留「竞品拆解」）：

  1. 它解决了什么：竞品到底在服务哪个问题，和阶段零的目标陈述对不对得上。
  2. 哪些能抄：已被市场验证、且你的用户画像和它重叠的部分。关键是分辨竞品的「护城河」和「功能堆砌」——护城河（数据壁垒、生态锁定、规模效应）抄不动，功能堆砌可以抄，甚至要绕开。
  3. 哪些不能抄：它的用户结构、资源、时机和你不同，抄了会水土不服的部分。

「功能对表」是最常用的手法：把竞品功能逐项列成表，标注它对应解决了什么问题、你的用户是否也有这个问题。对表不是为了抄，是为了找空位——竞品没覆盖、但你的用户真实需要的那个空位。

步骤 4：数据可获得性评估

这是 AI 产品特有的硬闸口。三个来源逐一确认：

  • 内部数据：业务系统里有没有现成的历史数据？结构化程度如何？
  • 外部数据：公开数据、采购数据、第三方 API 是否可得，成本几何。
  • 标注数据：没有现成数据时，能不能标注出来？标注成本、周期、质量能不能兜住（详见扩展预留「数据可获得性评估」）。

结论落成「数据可行性报告（初版）」：每个候选场景标注「数据充足 / 可标注 / 不可得」。不可得的场景，要么砍，要么退到「用规则 + 少量 AI」。

步骤 5：数据合规初判

在投入之前，先排掉合规雷（详见横切主题「合规与伦理」）：

  • 个人信息：用的数据里有没有可识别到个人的信息，是否需要授权、脱敏。
  • 版权：训练 / 检索 / 生成的素材有没有版权归属问题。
  • 敏感行业：金融、医疗、教育等强监管行业，数据使用有没有额外的资质或备案要求。

初判的目的不是给结论，而是标注风险等级：绿的直接走，黄的要法务确认，红的一票否决。

步骤 6：沉淀「真问题」清单

把前面五步收敛成一份清单。每条「真问题」必须满足：

  • 是问题不是方案：写「睡眠数据区分度不够，看不出哪天睡得好」，不写「睡眠柱状图用紫色细长矩形」。
  • 有频次或证据：来自多少条反馈、多少比例的用户、什么行为数据。
  • 有验证假设：这条问题对应的可证伪假设是什么。
  • 有数据与合规标注：数据可得性、合规风险等级。

问题要拆到可决策的颗粒度：太粗（「用户觉得不好用」）无法验证，太细（「按钮颜色不对」）又掉回方案层。真问题是关于用户「心智」的——用户心里怎么理解这件事、卡在哪一步，而不是我们怎么设想这件事。

这份清单是阶段二的输入，也是以后砍需求时翻旧账的依据。

核心产出

  • 真问题清单：每条含问题、频次 / 证据、验证假设、数据与合规标注。
  • 数据可行性报告（初版）：候选场景 × 数据充足 / 可标注 / 不可得。
  • 合规初判记录：风险分级（绿 / 黄 / 红）。

边界与反例

  • 反例一：把「用户说想要」当「真需求」。诱导式提问问出来的「想要」，落地后往往是「没人用」。用行为数据和「上次怎么解决」校准。
  • 反例二：竞品做了什么就做什么。竞品的功能是它的答案，不是你的问题。抄之前先问「我的用户是不是同一个问题」。
  • 反例三：数据不可得还要硬上。没有数据、标注不起，却坚持做微调 / 检索，最后只能靠提示词硬撑，效果不可控。
  • 反例四：合规后置。阶段一不排合规雷，到阶段五上线前才发现要备案、要授权，返工成本是初判成本的几十倍。

判断层工具

  • pm-method-mom-test：把所有访谈问题改成「问过去、问行为、问反例」的版本，去掉诱导。
  • pm-advisor-torres：把收集到的散点需求挂到「机会解决方案树」上，逼自己区分「机会」和「方案」。
  • pm-advisor-yujun：用「用户价值 = 新体验 − 旧体验 − 替换成本」复核每条真问题的价值量级。

向上汇报与对齐

调研结论的价值，一半在做对，一半在讲明白。三个动作：

  • 一句话洞察向上同步：把一堆访谈浓缩成「一句话洞察 + 数据证据」，让老板在电梯里就听懂，而不是甩一份用户原话清单。周报、1on1 都是这个动作的常规载体。
  • 跨部门拉齐：需求池和真问题清单先和运营、销售、客服「对齐」，确认这不是 PM 闭门造车的想象。
  • 预期管理：数据不可得、合规红灯这类发现，要第一时间向上「同步」，别拖到阶段四才发现做不下去。

🔗 扩展预留

  • 用户调研与访谈：提纲设计 / Mom Test 去诱导提问 / 样本与招募 / 信号提取编码 —— 可独立成篇
  • 竞品拆解：四维拆解框架 / 能抄 vs 不能抄 / 对标矩阵 —— 可独立成篇
  • 数据可获得性评估：内外部数据源盘点 / 标注可行性测算 —— 可展开为小节

阶段二：定义与设计

这一阶段回答：怎么把问题变成一个「算得清账、守得住边界」的 AI 方案？

为什么要先做这一步

阶段一沉淀了「真问题」清单，但问题离方案还差一步：同一个问题可以有一百种解法，其中只有一两种是「算得清账、守得住边界」的。

AI 产品在这一步的特殊性在于：它要同时做产品设计和工程设计。传统产品经理画完页面就能交给开发，AI 产品经理还必须把模型、数据、Agent、成本、兜底这些「工程性」变量在方案里定清楚——漏掉一个，开发阶段就会失控。

一个贯穿全程的判断是「80% 的智能体本质是数据工程」：模型本身是通用的，真正决定效果的是喂给它的结构化上下文（指标口径、业务规则、实体维度、参考示例）。所以这一步不是「把需求翻译成功能」，而是「把业务问题翻译成模型能执行的结构化规格」。

工作流

步骤 1：定义「问题 + 验收标准」

先把「要解决什么」和「怎样算解决」锁死，再谈方案。

  • 问题陈述：继承阶段一的真问题，一句话说清「谁、在什么场景、卡在哪一步」。
  • 验收标准：写成「给定输入 X，输出 Y，满足条件 Z」，且 Z 可测。对 AI 来说，验收标准往往是一组评测指标 + 阈值，而不是「看起来对」（兑现方式见阶段四）。
  • 只锁问题，不锁方案：这一步锁定「问题和验收」，不锁「用哪个模型、界面长什么样」。方案留在后面，因为方案可换、问题不可换。

步骤 2：模型选型与能力评估

选模型不是选「最强的」，是选「够用且划算的」。三个维度同时看（详见扩展预留「模型选型与能力评估」）：

  • 效果：能力够不够覆盖这个场景（推理、长文本、多模态、工具调用）。
  • 成本：单次调用成本、并发量、延迟。
  • 可控性：闭源 vs 开源、能不能微调、数据出不出域。

一个可以前置的做法是「模型路由」思路：常规任务走小模型，难例才走大模型，而不是所有请求都砸最贵的那个。

步骤 3：Agent 工作流设计

如果场景需要 Agent（多步推理 + 工具调用），这一步要把「Agent 怎么干活」画出来，核心是四个决定（详见《Agent 开发专项》）：

  • 权限分层：L1 问答 → L2 协作 → L3 伴随 → L4 托管，权限越高，评测和护栏越严。
  • 工具调用约束：每个工具能读什么、能写什么、参数怎么校验。
  • 多步验证点：关键步骤后是否需要人工确认。
  • 失败恢复：超时、工具不可用、结果冲突时怎么回滚或降级。

产出「Agent 拓扑图 + 工具权限矩阵 + 人机 RACI 表」——谁在哪个环节干什么、出了事谁负责，一张图说清。

步骤 4：数据规格定义

模型是发动机，数据是油。这一步把「要喂什么油」定清楚（详见扩展预留「数据规格定义」）：

  • 量：训练 / 微调 / 检索各需要多少样本，从哪来。
  • 质：字段口径、格式、去重、清洗标准。
  • 标注标准：如果需要标注，标注规范是什么、一致性怎么保证。

产出「数据规格文档」，它决定阶段四能不能做出合格的评测集和黄金集。

步骤 5：不确定性兜底与降级设计

AI 会出错，方案必须预设「出错时怎么办」。三个层次（详见扩展预留「不确定性兜底设计」）：

  • 置信度阈值：模型置信度低于阈值时，不直接给结论，改走澄清或人工。
  • 降级策略：AI 不可用时退回什么（规则、模板、人工、上一版本）。
  • human-in-the-loop：哪些环节必须有人确认（资金、外发、高风险操作）。

核心原则一句话：AI 负责快，人负责对。让 AI 在擅长的部分全速跑，在不擅长的部分乖乖交给人。

步骤 6：成本治理

从阶段零的「粗估」升级到「建模」，三张表（详见扩展预留「成本治理」）：

  • TCO 拆解：API 调用 + 数据标注 + 推理延迟 + 人工兜底 + 监控运维，逐项估。
  • 单位经济模型：单次任务成本 vs 替代人力成本 vs 用户愿付价，三者放一张表看毛利正负。
  • 成本优化策略：模型路由（难例走大模型）、缓存（相同问题不重复调）、Prompt 压缩（省 token）。

成本不是阶段六才看的事，它在这一步就是设计约束——一个上线就亏的产品，做得再好也是负债。

步骤 7：合规设计

把阶段一的合规初判升级成设计约束（详见横切主题「合规与伦理」）：

  • 偏见风险：训练数据、Prompt 里有没有可能放大性别、地域、群体偏见。
  • 可解释性：输出能不能追溯「为什么这么答」，高风险场景必须能解释。
  • 内容安全：生成内容要不要过护栏、过滤。

步骤 8：原型验证 → 写 PRD

方案在脑子里成立，不等于用户觉得成立。先用 AI 快速出原型验证（产品定义 → 设计规范 → AI 生成 → AI 评审 → 优化），跑通「用户能不能看懂、愿不愿意用」，再落到 PRD。

PRD 一个实用的拆法：业务主 PRD + 前端 demo PRD 分开写。业务主 PRD 写字段、规则、状态、边界（给开发和算法看），前端 demo PRD 写页面和交互（给前端和设计看）。混在一起写，两边都看不懂。

核心产出

  • PRD（业务主 PRD + 前端 demo PRD）
  • Agent 拓扑图 / 工具权限矩阵 / 人机 RACI 表
  • 单位经济模型表
  • 数据规格文档
  • 合规风险清单

边界与反例

  • 反例一：方案先行，问题后补。先定了「用某模型 + 某界面」，再回头找问题，结果做成一个没人要的功能。
  • 反例二：用最贵的模型撑全部场景。所有请求都走最强大模型，上线后 token 成本爆炸，单位经济算不平。
  • 反例三：把兜底当成「上线后再想」。没有预设降级和 human-in-the-loop，模型一出错就是线上事故。
  • 反例四：PRD 只写页面不写边界。字段、异常流程、埋点、非功能需求全缺，开发阶段反复被打回。

判断层工具

  • pm-method-story-mapping：把方案拆成故事地图，找出「能发布的最小切片」（MVP），而不是一次做完所有功能。
  • pm-method-build-trap：检查自己是不是在「堆功能」——每加一个功能，问一句「它连回哪个 outcome」。

向上汇报与对齐

  • 用单位经济模型向上对齐：方案能不能做，先拿「单次成本 vs 替代人力成本」给老板看，让他拍板「这个账值不值得算」。
  • 风险前置同步：模型选型、数据规格、合规红灯这些决定，要在写 PRD 前就和技术、法务「拉齐」，别等 PRD 写完才被告知「模型不支持」「数据不能出域」。

🔗 扩展预留

  • 模型选型与能力评估：模型对比 / 能力边界测试 / benchmark 选型 —— 可独立成篇
  • 成本治理：TCO 建模 / 单位经济测算 / 模型路由与缓存优化 —— 可独立成篇
  • 不确定性兜底设计：降级策略 / human-in-the-loop 模式 —— 可展开为小节
  • 数据规格定义：数据量与质量标准 / 标注规范 —— 可展开为小节

阶段三：评审与排期

这一阶段回答：方案对不对、值不值得现在做、按什么顺序做？

为什么要先做这一步

PRD 写完，最危险的不是「被否定」，而是「没人认真看」。需求评审会上的沉默，上线后会变成返工。这一步的本质是：在投入开发之前，把所有角色的顾虑逼出来。

AI 产品的评审比传统多两类角色：算法（模型能不能做）和数据（数据能不能喂）。少请一个，就多一个上线前的坑。

工作流

步骤 1：评审预演

上会之前，先自己把会演一遍。用 pm-review-board 模拟 6 个角色（研发、测试、设计、运营、算法、老板）同时喷需求，把能提前回答的问题先答掉。这一步的价值是：会上只需要「确认」，不需要「救场」。

步骤 2：需求评审会

把 PRD 过一遍，目标是「各方明确职责和交付标准」。会上的核心不是「好不好」，是「清不清楚」——开发、测试、UI、算法，每个人知道自己要交付什么、怎么算完成。

步骤 3：技术评审会

AI 需求必须单独开技术评审，因为它的技术方案和传统功能不同（详见扩展预留「技术评审会」）。会上对齐三件事：

  • 模型方案：选哪个模型、要不要微调、走不走 RAG。
  • 工程方案：harness、服务链路、兜底、回滚怎么搭。
  • 成本预估：并发量、token 消耗、延迟能否兜住。

步骤 4：数据管道规划

如果方案依赖数据，这一步把「数据从哪来、怎么流到模型」画出来（详见扩展预留「数据管道规划」）：采集 → 清洗 → 标注 → 入库。产出「数据管道方案」，明确每一环的负责人和周期。

步骤 5：优先级排序

手里一堆需求，但资源有限。用「价值 ÷ 成本 ÷ 不确定性」三列打分（详见扩展预留「优先级排序」）：

  • 价值：不做会多痛苦？
  • 成本：要花多久、多少人？
  • 不确定性：我清不清楚怎么做？

价值高、成本低、确定性高的排前面；三者都差的进「待砍区」。

步骤 6：砍需求

俞军那句话值得贴在墙上：「决定不做什么，往往比决定做什么更重要」。给每个候选需求写一句「如果这个不做，我会失去什么」。你会发现很多「想要」其实是「没有也死不了」。

砍需求不是能力不行，是替团队省下做错事的成本。砍掉的需求记进「砍需求坟场」，注明砍掉的原因，避免日后有人又翻出来重新论证一遍。

步骤 7：路线图与排期

把留下来的需求排成路线图：谁先谁后、每个迭代交付什么。AI 需求排期要额外留两样缓冲：模型联调的来回、评测集建设的时间——这两样最容易低估。

核心产出

  • 评审结论（各方确认）
  • 数据管道方案
  • 优先级清单
  • 路线图 / 排期表

边界与反例

  • 反例一：评审会开成「介绍会」。PM 一个人讲，下面没人看，上线后各方才说「我当时没听清」。
  • 反例二：技术评审缺席算法和数据。传统评审只请研发，AI 需求漏了算法和数据，模型方案和数据可得性没人把关。
  • 反例三：排序靠感觉。没有打分标准，需求顺序随老板心情变，反复纠结。
  • 反例四：不敢砍。需求只进不出，团队被范围蔓延拖死。

判断层工具

  • pm-advisor-cagan：复核四大风险（价值 / 可用性 / 可行性 / 商业），确认方案没有致命盲区。

向上汇报与对齐

  • 用打分表向上汇报：优先级不是「我觉得」，而是「价值 ÷ 成本 ÷ 不确定性」算出来的。给老板看打分表，比解释一百句「这个先做」有效。
  • 砍需求要向上对齐：砍掉老板喜欢的需求，要拿「不做会失去什么 + 机会成本」说话，而不是硬顶。

🔗 扩展预留

  • 技术评审会：技术方案评审清单 / 模型与工程评审维度 —— 可展开为小节
  • 优先级排序：RICE / ICE / Kano 对比与适用场景 —— 可展开为小节
  • 数据管道规划：采集清洗标注入库的自动化链路 —— 可展开为小节

阶段四：开发与评测

这一阶段回答：怎么把方案做成「质量达标、可上线」的产品？

为什么要先做这一步

AI 产品和传统产品的最大分水岭在这里：传统功能测「对不对」，AI 功能测「好不好」。一个按钮点下去跳转对了就通过，一个 AI 回答「看起来对但其实是幻觉」却很难一眼发现。

所以这一步的评测不是上线前的一次性动作，而是分三层、贯穿开发全程的系统工程（详见扩展预留「评测体系」）。

工作流

步骤 1：埋点与数据体系 / 看板规划建设

上线前先想好「怎么量」，不然上线后就是睁眼瞎。用 pm-tracking-spec-writer 把用户链路拆成埋点事件，规划好看板看哪些指标。埋点要能回答三个问题：用户用了没、用了之后效果怎样、卡在哪一步。

步骤 2：标注流程管理、黄金集构建

评测靠什么？靠「标准答案」。黄金集就是一批「输入 + 标准答案」的样本，是评测的地基（详见扩展预留「标注流程管理」）：

  • 标注规范先定清楚，再开始标。
  • 多人标注要过一致性检验（两人对同一题答案的一致率）。
  • 黄金集随业务演进而更新，不是一次建好就永远用。

步骤 3：harness 搭建与调试

harness 是把模型接进业务的最小可跑通路：输入 → 模型 → 输出。这一步的目标不是「功能完整」，是「能稳定地跑起来、能反复调」——先跑通逻辑，再打磨细节。很多人在这步想一步到位，结果卡死在联调上。

步骤 4：三层评测

评测分三层，各自回答不同的问题（详见扩展预留「评测体系」）：

层级时机核心关注
离线评测上线前黄金集回归、版本间对比、防负向优化
在线评测灰度 / 全量A/B 测试、真实用户行为、任务完成率
运行时评测推理中Guardrails 实时拦截、高风险操作二次校验

三层缺一层就有一个盲区：只做离线，不知道真实用户买不买账；只做在线，模型改坏了才发现；不做运行时，风险操作没人拦。

步骤 5：评测维度

「准确率」不够用。AI 产品至少要盯六个维度：

  • 指令遵循率：让干什么就干什么了吗？
  • 幻觉率：有没有一本正经地胡说？
  • 安全性：有没有输出有害内容？
  • 延迟：等多久才出结果？
  • Token 成本：每次调用烧多少？
  • 人工接管率：多少次最后还得人来兜底？

不同场景权重不同：客服场景幻觉率一票否决，内部工具场景延迟比幻觉更致命。

步骤 6：非确定性验收

AI 产品的验收标准不是「输出等于某值」，而是「评测集通过率达到阈值」。所以 PRD 里的验收标准，在这一步兑现成：评测集 + 通过率阈值 + 一票否决项。达不到阈值就不上线，没有「差不多得了」。

步骤 7：A/B 实验设计

用 pm-experiment-designer 把实验方案定死：假设是什么、分流怎么分、样本量够不够、止损规则是什么、判定标准在实验开始前就定好。判定标准不能事后定，否则人总会把数据解释成自己想要的。

核心产出

  • 评测集 / 黄金集 / badcase 库
  • 评测报告（三层 + 六维）
  • 验收结论

边界与反例

  • 反例一：只有离线评测就上线。黄金集高分，上线被真实用户骂，因为评测集没覆盖真实场景。
  • 反例二：验收标准含糊。PRD 写「效果良好」，开发问「什么算良好」，最后扯皮。
  • 反例三：badcase 只记不治。收集了一堆 badcase，却没有回流进黄金集和迭代，等于白记。
  • 反例四：实验判定标准事后定。上线后发现数据不显著，改个口径让结果「看起来显著」。

向上汇报与对齐

  • 用评测报告向上汇报：阶段四的产出是一份「三层 + 六维」评测报告，它是阶段五上线评审的入场券。给老板看「通过了什么、没通过什么」，比说「我测过了」有力得多。
  • 验收结论要各方会签：算法、数据、QA 对「能不能上线」的结论要一致，别让 PM 一个人拍板。

🔗 扩展预留

  • 评测体系：三层评测 / 六维指标 / 黄金集构建方法论 —— 分量最重，强烈建议独立成篇
  • 标注流程管理：标注规范 / 质量控制 / 一致性检验 —— 可展开为小节

阶段五：上线与发布

这一阶段回答：怎么安全上线，并让用户真的用起来？

为什么要先做这一步

AI 产品上线后，最大的风险往往不是技术，而是两件事：模型在真实环境里出错，和用户不信它、不用它。前者靠灰度和监控兜住，后者靠用户采纳设计。上线不是终点，而是「从 demo 到生产」的跨越——demo 能跑通，生产要扛住真实流量和真实用户。

工作流

步骤 1：灰度与回滚方案

先小范围放，再逐步扩大。灰度要定清楚（详见扩展预留「灰度与回滚」）：

  • 灰度范围（哪些用户、多少比例）
  • 观察指标（错误率、延迟、人工接管率）
  • 回滚触发条件（什么情况下立刻切回旧版）

没有回滚预案的灰度，等于没有安全带。

步骤 2：上线评审（go / no-go）

上线前开一次「上线评审」，把阶段四的评测报告、合规检查、灰度方案、回滚预案摆到桌面上，各方确认「可以上」。AI 需求的 go/no-go 要多问一句：出错了会怎样，有没有兜底。

步骤 3：合规验收

把阶段一到阶段三积累的合规事项，在上线前一次性验收（详见横切主题「合规与伦理」）：内容安全护栏有没有生效、AIGC 标识有没有加、备案手续有没有走完、数据授权有没有到位。合规是「一票否决项」，不是「尽量做好」。

步骤 4：线上监控与 badcase 监控

上线后进入盯盘模式：核心指标、错误率、badcase 实时看。badcase 要沉淀成库，作为下一轮迭代和黄金集更新的输入。

步骤 5：AI 能力多场景接入落地

一个 AI 能力做出来后，价值在于「多场景接入」——把它推到运营、销售、客服等更多场景去复用。这一步是跨部门协同的活儿：和各个业务方「对齐」，找到他们的场景，把能力嵌进去。

步骤 6：用户采纳（用户教育 / 信任建立 / 变革管理）

AI 产品上线后最大的隐性成本是「用户不用」。三件事（详见扩展预留「用户采纳与信任建立」）：

  • 用户教育：让用户理解 AI 的能力边界，避免期望过高（「它什么都能干」）或过低（「它什么都干不好」）。
  • 信任建立：渐进式授权（先辅助后托管），透明化展示 AI 的推理依据——让用户看得懂 AI 为什么这么答。
  • 变革管理：如果 AI 替代了某些人工环节，要设计过渡方案，别让被替代的人成为阻力。

核心产出

  • 合规检查清单
  • 上线检查单
  • 用户引导手册
  • 信任建立路线图
  • 采纳率监控指标

边界与反例

  • 反例一：没有回滚预案就全量。模型一出错，线上事故，只能靠紧急下架。
  • 反例二：把「能跑」当「能上」。demo 跑通就上线，没扛住真实流量和边界 case。
  • 反例三：只管上线不管采纳。功能上线了，用户不知道、不信、不用，等于白做。
  • 反例四：合规验收走形式。上线后被监管点名，下架整改，损失远大于当初的合规成本。

向上汇报与对齐

  • 上线前向上要「拍板」：go/no-go 不是 PM 自己说了算，要让能拍板的人确认「出事谁负责」。
  • 采纳率要向上同步：上线后的效果（采纳率、任务完成率）要定期向上汇报，这是阶段六的输入。

🔗 扩展预留

  • 用户采纳与信任建立：渐进授权 / 推理透明化 / 变革管理 —— 可独立成篇
  • 灰度与回滚：灰度策略 / 回滚触发条件 —— 可展开为小节

阶段六：跟进与迭代

这一阶段回答：上线后有没有达到预期，下一步改什么？

为什么要先做这一步

上线不是结束，而是「验证的开始」。阶段零设的北极星指标，要在这里兑现成「到底动了没有」。这一步的本质是：把「做完了」变成「做成了」——用数据验证假设，用复盘沉淀经验，再回到阶段零开始下一轮。

工作流

步骤 1：数据看板监控

盯阶段四规划好的看板：北极星指标动了没、核心漏斗卡在哪、badcase 涨了没。监控的目标不是「看数据」，是「发现问题」。

步骤 2：数据分析归因

数据跌了或没涨，找原因。用 pm-analytics 一套走完：是流量问题、转化问题、还是模型效果问题？归因要落到「哪个环节、哪类用户、什么原因」，而不是一句「效果不好」。

步骤 3：实验验证

用阶段四设计的 A/B 实验，验证「改动有没有用」。判定标准在实验前就定好了，这里只是执行和读结果。不显著的改动要敢承认，别为了「显得有产出」硬解释。

步骤 4：badcase 分析

把线上收集的 badcase 拿出来分类：是模型能力不够、数据不够、还是 Prompt 设计有问题。分类决定下一步是换模型、补数据、还是调 Prompt。badcase 是免费的训练数据，别浪费。

步骤 5：反馈闭环

把 badcase、用户反馈、实验结论回流到数据飞轮（详见扩展预留「数据反馈闭环」）：

  • 高频 badcase → 补进训练 / 微调数据 → SFT
  • 用户偏好信号 → 反馈到 RLHF
  • 业务规则变化 → 更新结构化上下文

数据飞轮转起来，产品才会越用越聪明；转不起来，就是「每次出错都靠人肉兜底」。

步骤 6：复盘

用 pm-postmortem-writer 做复盘：5-Why 归因到根因，行动项强制分级（谁、做什么、截止时间、验证指标）。复盘不是「总结报告」，是「下次不犯同样的错」。

步骤 7：回到阶段零 / 一

复盘之后，把新发现的问题和机会，重新投入阶段零的「该不该做」判断。SOP 是一个闭环，不是一条直线——每一轮迭代都在重复「判断 → 设计 → 验证 → 复盘」的循环。

核心产出

  • 复盘报告
  • 版本对照表 / 变更日志 / 回滚预案
  • 迭代需求（进入下一轮）

边界与反例

  • 反例一：上线就撒手。上线后不盯数据，问题积累到爆发才回来处理。
  • 反例二：归因拍脑袋。数据不好就怪模型，其实可能是流量质量、场景错配。
  • 反例三：复盘写成流水账。记了一堆过程，没有根因和行动项，下次照样犯。
  • 反例四：badcase 不回流。收集了 badcase 却不用来迭代，等于把免费训练数据扔了。

判断层工具

  • pm-method-build-trap：检查团队是不是又掉进了「功能陷阱」——做了很多功能，outcome 没变。这个时候该做的是砍，不是加。

向上汇报与对齐

  • 用「北极星指标动了没」向上汇报：阶段六的汇报不是「我做了多少事」，而是「目标指标动了多少、为什么」。老板关心结果，不关心工作量。
  • 复盘结论要沉淀成共识：复盘不是 PM 一个人的总结，要把「根因 + 行动项」和团队、上级对齐，让下一次迭代有据可依。

🔗 扩展预留

  • 数据反馈闭环：数据飞轮 / SFT / RLHF 的落地路径 —— 可独立成篇
