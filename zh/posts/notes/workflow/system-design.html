需求分析与技术方案设计

vexillium2026/8/11大约 8 分钟后端开发软件工程技术设计需求分析Tech Spec架构设计

定位

写代码之前的一切：把「做什么」和「怎么做」想清楚。 本文件沉淀从需求输入到可执行技术设计稿（Tech Spec）的完整 SOP，每个环节均包含 AI/Agent 增强实践。

  • 产出物：Tech Spec、架构图、API 契约（OpenAPI）、表结构初稿
  • 下游：api-dev（API 开发）、testing（测试）、deploy-mantain（部署运维）

一、需求分析

1.1 需求理解

  • 阅读 PRD / 需求文档，标注不明确的点
  • 识别业务目标（最多 3 条）与非目标（Out of Scope，防止范围蔓延）
  • 列出所有角色（Actor）与核心 User Story

1.2 需求拆解

将大需求拆解为可验收的用户故事，验收标准使用 Gherkin 格式：

Given 用户已登录且账户余额充足
When 用户提交订单
Then 订单创建成功，返回订单号
And 扣减账户余额

1.3 需求澄清

  • 汇总疑问清单，约产品 / 设计评审
  • 评审产出：修改后的 PRD + 会议纪要
  • 未澄清的需求不做实现，避免返工

1.4 范围确认

  • 明确本期做 / 不做 / 延后
  • 与产品确认 MVP 边界

二、技术方案设计（Tech Spec）

2.1 Tech Spec 模板

## 1. 背景与目标
### 1.1 背景
### 1.2 目标（可量化：QPS、延迟、可用性）
### 1.3 非目标（Out of Scope）

## 2. 需求分析
### 2.1 业务流程（时序图 / 流程图）
### 2.2 功能清单（编号 / 功能点 / 优先级）
### 2.3 非功能需求（性能 / 可用性 / 安全）

## 3. 技术方案
### 3.1 整体架构（架构图）
### 3.2 方案对比（多方案维度矩阵）
### 3.3 详细设计（数据库 / API 契约 / 核心流程）

## 4. 风险评估（风险 × 概率 × 影响 × 缓解）

## 5. 排期与里程碑

## 6. 监控告警与回滚方案

2.2 方案对比

多候选方案用维度矩阵对比：

维度方案 A方案 B最终选择
开发成本（人天）低高A
性能表现中高
运维复杂度低高
可扩展性中高
技术风险低中

2.3 评审会 SOP

  1. 会前：提前 1 天发 Tech Spec 与关键图，参会人提前阅读
  2. 会上：按「背景 → 方案 → 详细设计 → 风险」逐模块过，记录决策
  3. 会后：更新文档，遗留项分配 Owner 与 DDL，评审结论同步团队

三、架构设计可视化（画图）

3.1 图的选型

不要为了画图而画图，每种图解决特定问题。推荐 draw.io。

图类型解决什么问题适用时机
用例图 Use Case理清多角色 × 复杂业务功能点关系角色 ≥ 2、需求复杂
数据流图 Data Flow Diagram数据来源、处理、去向数据链路复杂
时序图 Sequence Diagram用户 / 系统间时间线上的数据流向与交互顺序涉及 ≥ 3 参与者
状态图 State Diagram对象状态转换规则订单、审批流
流程图 Flowchart通用业务逻辑，含条件分支任何 if/else 逻辑

3.2 流程图绘制规范

  • 基本图形：椭圆（起止）、矩形（操作）、菱形（判断）、圆柱体（数据库）
  • 箭头：条件写注释「是否」、操作写「调用」
  • 颜色：字体黑色；方块用低饱和度的黄、灰、湖蓝、粉红、绿

四、数据库设计

4.1 ER 建模与范式

  • 用 ER 图表达实体、属性、关系
  • 范式权衡：第三范式减少冗余；反范式用于读多写少的查询场景
  • 每条业务规则都能落到一张表 / 一组字段上

4.2 表结构设计

  • 字段类型选择（避免隐式转换，注意长度与精度）
  • 默认值、非空约束、唯一约束
  • 软删除字段、创建 / 更新时间字段
  • 主键策略：自增 vs Snowflake vs UUID

4.3 索引设计

  • 聚簇索引 vs 非聚簇索引
  • 覆盖索引：查询列包含在索引中，避免回表
  • 最左前缀匹配：联合索引字段顺序 = 查询条件热度顺序
  • 索引失效场景：函数运算、隐式类型转换、like '%xx'

4.4 事务与隔离级别

  • ACID 与四种隔离级别（读未提交 → 可串行化）
  • MVCC 实现机制
  • 乐观锁（版本号）vs 悲观锁（for update）

4.5 分库分表（概述）

  • 垂直拆分：按业务域拆分库
  • 水平拆分：Range / Hash / Consistent Hash 分片
  • 分布式事务：2PC / TCC / Saga / 本地消息表

五、容量预估

5.1 估算公式

  • QPS 峰值 = 日活用户 × 人均请求数 ÷ 86400 × 峰值系数（3~10）
  • 存储 = 单条数据大小 × 每日新增 × 保留周期
  • 带宽 = 平均响应体大小 × QPS

5.2 结果反哺选型

指标阈值信号架构应对
读 QPS 高> 5000引入缓存 / 读写分离
写峰值高突发流量引入 MQ 削峰
数据量大单表接近千万级分库分表 / 归档

5.3 🤖 Agent 增强实践

给定业务参数：
- 日活：10 万
- 人均日请求：50
- 单条记录大小：1KB
- 数据保留周期：1 年

请估算峰值 QPS、年存储量、带宽，并给出架构建议。

六、API 契约设计

6.1 OpenAPI 规范

  • 用 OpenAPI 3.0 定义：路径、方法、参数、响应、错误码
  • 契约先行：前后端 / 服务间按契约并行开发

6.2 错误码体系

  • 统一返回结构：{ code, message, data }
  • 业务码分段规划（如 1xxxx 参数、2xxxx 权限、3xxxx 业务、5xxxx 系统）
  • 维护 HTTP 状态码与业务码的映射表

6.3 版本策略

  • URL 版本：/api/v1/...
  • 向后兼容：新增字段不影响老客户端；破坏性变更升版本

七、AI 写技术文档

需求文档、Tech Spec、评审纪要不是「打字」出来的，而是「想清楚 + 让 AI 扩写润色」出来的。

核心 Prompt

你是一名资深开发工程师，擅长写出流畅、富有深度的技术文档。
我希望你能仔细设计并扩充一下下面这段文字，要求：
- 重视叙述方式，分段要按照技术的实际情况分类，不要进行简略的举例，
  这样会让内容空洞，按照严谨的技术博客方向书写
- 不要介绍技术背后的公司、人物、年份等，注重实践实用性
- 以 markdown 格式输出
