并发正确性有一个硬性判据：**并发执行的结果，必须与按某个串行顺序执行这些事务的结果相同**。这条判据叫可串行化，它不关心实现，只关心结果。

在这个判据之下，数据库有两条腿去实现它：**多版本**让读不必等待写，**锁**让写之间互相排斥。理解这两条腿各自能做什么、以及在什么情况下失效，就能回答绝大多数并发问题的提问：**这段代码在隔离级别 X 下会不会错、锁会等在哪**。

## 事务与 ACID：它真正保证什么

### ACID 四条各自的准确含义

- **原子性**：事务是不可分割的工作单位，其中的操作要么全部生效、要么全部不生效。实现手段是回滚日志——修改前先记下旧值，出错时反向恢复。
- **一致性**：事务执行的结果必须使数据库从**一个一致性状态**变到**另一个一致性状态**。一致性状态就是满足所有完整性约束的状态。
- **隔离性**：并发执行的事务之间互不干扰，各自感觉不到彼此的存在。
- **持久性**：事务一旦提交，对数据库的修改就是永久的。

最容易记混的是**一致性**。它不是"要么全做要么不做"——那是原子性。一致性描述的是**状态**：事务开始前数据满足所有约束，结束后依然满足。

原子性也有它做不到的地方：**某些语句会隐式提交当前事务，因此无法回滚**。典型的是 DDL——建表、改表、建索引都会让正在进行的事务提前提交。把 DDL 和业务写入混在同一个大事务里，是一个会直接导致"我明明回滚了，数据却没恢复"的错误。

### 一致性是目的，另外三条是手段

把四条放在一起看，会发现它们不对等：

**一致性是目的，原子性、隔离性、持久性是实现它的手段。**

这个区分有实际后果。数据库能保证的一致性，只是它能表达的那些约束——主键唯一、外键存在、非空、取值范围，以及并发层面的可串行化。**而业务语义上的一致性，数据库不认识**。例如"订单总额必须等于明细之和"、"账户余额不能为负"，这些规则既不在数据库的约束里，也不在隔离级别里，只能由应用自己维护。

所以"数据库有事务，所以我的数据一定一致"是错位的期望。事务保证的是**你不会看到中间状态**，不是**中间状态本身是合法的**。

### 事务边界：提交时机决定锁持有多久

事务的边界就是锁的生命周期。同一段逻辑，把提交放在循环内还是循环外，影响的不是原子性，而是**锁被持有多久、以及有多少并发会被挡在外面**。

一条实用规则：**事务里只放必须原子的写操作**。把远程调用、文件读写、消息发送、大批量计算都放进事务，会让锁的持有时间从毫秒级变成秒级；而锁等待是会传染的——一个事务等锁，它后面依赖它的请求也跟着堆积。

读操作是否放进事务要分开看：**快照读不需要事务边界来保护**，它读的是某个一致版本，不会阻塞任何人；而当前读和写操作必须由事务划清边界。

## 并发异常与可串行化：并发正确的唯一判据

### 四类并发异常：丢失修改、脏读、不可重复读、幻读

如果不加控制，并发会产出四类错误结果：

- **丢失修改**：两个事务都读到了同一个值，各自基于它计算后写回，后写的覆盖了先写的。这类异常的根源是"读"和"写"之间没有保护。
- **脏读**：一个事务读到了另一个事务**尚未提交**的修改，而那个事务随后回滚了——读到的是一个从未存在过的值。
- **不可重复读**：同一个事务内两次读同一行，得到不同的值，因为中间有另一个事务修改并提交了它。
- **幻读**：同一个事务内两次按同一条件读，**行数变了**，因为中间有另一个事务插入或删除了满足条件的行。

不可重复读与幻读的区别经常被说反，正确的划分依据是**变化发生在哪里**：

| 异常 | 变化的对象 | 典型操作 |
|---|---|---|
| 不可重复读 | 同一行的**内容**变了 | 其他事务 `UPDATE` 并提交 |
| 幻读 | 满足条件的**行集合**变了 | 其他事务 `INSERT` / `DELETE` 并提交 |

`UPDATE` 会把一行改得不一样，所以它触发的是不可重复读；`INSERT` 会让"满足条件的行"多出一条，所以它触发的是幻读。

### 可串行化：并发正确的判据，以及冲突操作

**调度的可串行化**：如果一组并发事务的执行结果，与把它们按某个串行顺序执行的结果相同，那么这个调度是可串行化的。可串行化是并发事务正确性的**准则**——只要调度可串行化，就不可能出现上面四类异常。

判断可串行化，先要定义什么操作"互相影响"：

**冲突操作**是不同事务对**同一数据**的读写组合——读-写、写-读、写-写。同一事务内部的操作不构成冲突；对不同数据的操作也不构成冲突。

由此得到判据：**如果通过反复交换相邻的、不冲突的操作，能够把一个调度变成串行调度，那么这个调度是冲突可串行化的**。交换的依据只有一条：不冲突的操作谁先谁后都不影响结果，所以可以自由挪动位置。

这条定义同时说明了一件事：**真正的敌人是"顺序"**。并发出错几乎总能归因到某个"读-写"或"写-写"对的顺序被颠倒了。

### 两段锁：充分条件，但仍然会死锁

**两段锁协议**是最经典的实现方式，它把事务的一生分成两段：

- **扩展阶段**：只加锁，不释放锁；
- **收缩阶段**：只释放锁，不再加锁。

一旦释放过任何一个锁，就不能再申请新的锁——这是它的全部约束。**遵守两段锁是可串行化的充分条件**：它保证不会出现"先拿了 A 再看 B、同时另一个事务先拿了 B 再看 A"这类交错。

它有两点必须记住：

- **它只是充分条件，不是必要条件**。存在不遵守两段锁但依然可串行化的调度，所以"没按两段锁写"不等于"一定出错"——但你不能依赖这一点。
- **它不能避免死锁**。遵守两段锁只是保证结果正确，并不保证不互相等待。死锁是**两段锁的固有副作用**，而不是违反协议的结果。这也是为什么应用必须能处理死锁重试。

## 隔离级别：四级承诺与实现差异

### 标准四级：各自的承诺与允许的异常

标准定义了四个级别，每一级允许的异常如下：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 不可能 | 可能 | 可能 |
| 可重复读 | 不可能 | 不可能 | 可能 |
| 串行化 | 不可能 | 不可能 | 不可能 |

理解这张表的方式是：**越往下，承诺越多，代价越大**。隔离性不是免费的，它直接体现为"还有多少并发能通过"，以及"要付多少锁与版本维护的成本"。

### InnoDB 的可重复读为什么基本避免幻读

这张标准表格里最需要打折扣的是可重复读那一行——**InnoDB 默认级别的实际行为比标准承诺更好**。原因是它用了两条不同的机制分别对付两类读：

- **快照读**（普通 `SELECT`）走多版本，读的是事务开始时的那个一致版本，其他事务新插入的行根本不在这个版本里，所以不会出现幻读；
- **当前读**（`SELECT ... FOR UPDATE`、以及所有写操作）读的是最新数据，为了不让别人在它读过的范围里插入，它对范围加**间隙锁**。

两条机制合起来，使得 InnoDB 在可重复读下基本观察不到幻读。但有一个序列值得知道，它不是 bug 而是语义的必然：

**一个事务先做快照读，另一个事务随后插入并提交，第一个事务再做当前读——它会看到新插入的行。** 因为当前读的语义就是"读最新版本并加锁"，它不给旧版本让路。此时同一事务内两种读法看到的数据不同，这是"快照读与当前读的职责划分"的直接结果。

### 读已提交为什么在很多系统里取代了可重复读

既然可重复读更强，为什么不少高并发的系统反而把它调低到读已提交？因为**间隙锁的代价通常大于可重复读带来的收益**：

- 间隙锁锁的是**范围**而不是行，它会让"看似不相关"的插入互相阻塞——两个事务往同一个区间插不同的值，也会互相等待；
- 间隙锁是死锁的主要来源之一；
- 在需要"读到最新已提交数据"的业务里（例如后台任务、报表、实时查询），可重复读的一致快照反而会造成困扰。

降到读已提交之后，**每次读都会生成新的快照**，因此能看到其他事务最新提交的数据；同时间隙锁在大部分场景下不再使用，只在唯一性检查时保留，并发与死锁情况都明显改善。代价是放弃了"同一事务内两次读结果相同"这个保证——**用一致性换了并发度**。

这个选择没有普适答案：**如果业务代码依赖"同一事务内重复读结果不变"，就不能降级**；如果业务一直在和"读到旧数据"作斗争，那就应该降。

## MVCC：读为什么不加锁

### 隐藏字段与版本链：旧版本存在哪里

每一行记录上都有几个用户看不见的字段：

- **事务 ID**：最后一次修改这一行的事务；
- **回滚指针**：指向这条记录的上一个版本；
- **隐藏行 ID**：这张表既没有主键、也没有合适的唯一非空索引时，才会出现的隐藏主键。

**回滚指针**把同一行的所有历史版本串成一条**版本链**，挂在回滚日志上。所以"多版本"并不是把每一行复制多份存在数据页里，而是**当前版本在数据页上，旧版本在回滚日志里，用指针连起来**。

这也解释了一件容易被误判的事：**版本链会随着并发读的存在而变长**。只要还有更早的读视图需要旧版本，对应的回滚日志就不能回收。所以长事务的危害不止是持锁久，它还会让旧版本堆积、拖慢整个回收链。

### ReadView：可见性判断的四个字段

读取一行时，到底该看到版本链上的哪一个版本？这由**读视图**决定。一个读视图记录四件事：

| 字段 | 含义 |
|---|---|
| 活跃事务集合 | 生成读视图时**尚未提交**的事务 ID 列表 |
| 最小活跃事务 ID | 上面那个集合里的最小值 |
| 下一个事务 ID | 系统即将分配给新事务的 ID，可作为"上限" |
| 创建者事务 ID | 创建这个读视图的事务自己 |

判断一个版本是否可见，看它的**事务 ID**：

1. 等于创建者自己 —— 可见（是自己改的）；
2. 小于最小活跃事务 ID —— 可见（在它之前就已提交）；
3. 大于等于下一个事务 ID —— 不可见（它在读视图生成之后才开始）；
4. 落在两者之间 —— 查活跃事务集合：**在集合里说明当时还没提交，不可见；不在集合里说明已提交，可见**。

如果链头版本不可见，就顺着回滚指针往前找，直到找到第一个可见版本。**这个判断不涉及任何加锁**——这正是"读不阻塞写、写不阻塞读"的来源。

需要划清一个边界：**多版本只解决读与写的冲突，不解决写与写的冲突**。两个事务修改同一行，仍然要靠锁串行化。看到"MVCC 实现了并发"就以为写操作不需要锁，是理解上最常见的偏差。

### 读已提交与可重复读的差别只在快照生成时机

两个级别的机制完全相同，差别只有一个：**读视图什么时候生成**。

- **读已提交**：每一条快照读语句都生成一个新的读视图，所以能看到其他事务最新提交的修改；
- **可重复读**：事务内**第一次**快照读时生成一次读视图，之后整个事务复用它，所以看不到别人后来的提交。

这句话值得反复回看，因为它把"隔离级别"从一个需要背诵的表格变成了一个可推导的机制：**级联表里那些"可能/不可能"，全部是"读视图何时生成"的直接推论**。

### 快照读与当前读：同一个事务里两种读法

把读写分成两类之后，前面所有零散的结论都能归位：

- **快照读**：普通 `SELECT`。不加锁，走读视图，读某个一致版本。它不会阻塞任何人，也不会被别人阻塞。
- **当前读**：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`，以及 `INSERT`、`UPDATE`、`DELETE`。读最新版本并加锁。

`SELECT ... FOR UPDATE` 在行上加的是**排他锁**，同时在表上加意向排他锁；`SELECT ... LOCK IN SHARE MODE` 加的是共享锁。两者读的都是最新数据，区别只在锁的强度。

这两类读在同一个事务里可以共存，而且**看到的数据可以不同**——快照读看自己的版本，当前读看最新版本。前面提到的"先快照读、再当前读会看到新插入的行"，就是这条规则的具体表现。

## 锁加在索引上：写的影响范围由索引决定

### 记录锁、间隙锁与 next-key lock

InnoDB 的行级锁有三种形态，它们的对象都是**索引记录**，而不是"行"。与直觉相反，InnoDB 从来没有"锁住这一行数据"这回事——它锁的是索引项。

- **记录锁**：锁住一条索引记录；
- **间隙锁**：锁住两条索引记录**之间**的间隙，不包含记录本身，作用是阻止别人往这个间隙里插入；
- **next-key lock**：记录锁加上它前面的间隙锁，锁住一个左开右闭的区间。**这是 InnoDB 默认的加锁单位。**

理解这三者的关键，是接受一句话：**锁是加在索引项上的**。这不是实现细节，它直接决定了"我的 UPDATE 到底锁了多少东西"。

### 加锁范围由索引决定：三种典型情形

同一句 `SELECT ... FOR UPDATE` 或 `UPDATE`，加锁范围会随索引的形态剧烈变化：

| 情形 | 加锁结果 |
|---|---|
| 唯一索引等值查询，记录**存在** | 退化为**记录锁**——唯一性已经排除了插入同一键的可能，不需要间隙锁 |
| 唯一索引等值查询，记录**不存在** | 退化为**间隙锁**——锁住这个键本该所在的间隙，防止别人插进来 |
| 非唯一索引等值查询 | 加 **next-key lock**，并向右扫描到第一个不满足条件的记录，这条记录的锁退化为间隙锁 |
| 范围查询 | 对范围覆盖的记录加 next-key lock，会一直扫到第一个不满足条件的记录为止 |

```sql
-- 情形一：主键等值且命中，只锁这一条记录
SELECT * FROM part WHERE part_no = 'P1001' FOR UPDATE;

-- 情形二：条件落在非唯一索引上，锁住匹配的行，并连带锁住它们前面的间隙
SELECT * FROM part WHERE category_no = 7 FOR UPDATE;

-- 情形三：条件没有可用索引，全表扫描，扫描过的每条记录都被加锁
UPDATE part SET price = price + 1 WHERE model_name = 'X';
```

这几条规则合起来解释了一个很常见的困惑：**为什么"只更新一行"的语句会阻塞别的插入**。因为当条件是范围或非唯一索引时，它锁的不是那一行，而是**一行加上它前面的那段间隙**。

### 没有索引时会发生什么

如果 `WHERE` 条件没有可用的索引，InnoDB 只能全表扫描，于是**对扫描过的每一条记录都加上 next-key lock**——效果等同于锁住整张表，而且还会拦住插入。

这就是"一个没走索引的 `UPDATE` 把整张表锁死"的完整机制。它也说明了一个重要的事：**加锁范围是可以设计的**。给 `WHERE` 条件建合适的索引，不只是为了查得快，更是为了**锁得少**。在并发写入的表上，后者往往比前者更重要。

### 意向锁与表级锁：为什么它们存在

意向锁是**表级**的，它本身不锁任何数据，只表达一个意图："这张表里我已经给某些行加了锁，别用表锁来检查我。"

没有它，一个 `LOCK TABLES ... WRITE` 就必须逐行检查整张表有没有行锁，成本无法接受。有了意向锁，表锁只要看一眼表上的意向锁就知道能不能立刻获取。

- **意向共享锁**：即将在某些行上加共享锁；
- **意向排他锁**：即将在某些行上加排他锁。

兼容关系上要注意：**意向锁之间互相兼容**，它们只与表级的共享锁、排他锁冲突。所以"行锁不会阻塞表锁"这个说法是错的——行锁会通过意向排他锁与表级写锁互斥，只是它与表级读锁可以共存。

### 元数据锁：DDL 与查询之间的冲突

除了数据锁，还有一层**元数据锁**保护表结构本身：

- 执行 DML 时对表加**元数据读锁**；
- 执行 DDL 时对表加**元数据写锁**。

它们互斥。由此产生一个非常实际的线上事故模式：**一个长事务持有元数据读锁，DDL 申请元数据写锁被阻塞；而这个排在后面的写锁请求，又会把后续所有新的元数据读锁请求一起挡住**——于是整张表的查询开始堆积，看起来像数据库整体变慢，实际源头是一个 DDL 加一个长事务。

## 死锁与锁等待的诊断

### 死锁的三种典型成因

死锁是两条以上等待链首尾相接形成的环。数据库会主动检测并回滚其中代价较小的一个，所以它不会永久卡住，但被回滚的那个事务**必须由应用重试**。

常见的成因有三类：

- **加锁顺序不一致**。两个事务以不同顺序更新同一组行，各自持有对方需要的那把锁。这是最经典的一类，也是最容易通过代码规范消除的一类。
- **间隙锁交叉**。两个事务在同一个间隙里插入，各自的插入意向锁与对方的间隙锁冲突。它在可重复读下更常见，也是"降级到读已提交能减少死锁"的主要原因。
- **唯一键冲突下的并发插入**。两个事务同时插入相同的唯一键，先到的一方持有锁去检查唯一性，后到的一方等待；当先到的一方也需要对方持有的资源时，环就形成了。它表现为"明明是插入，却报了死锁"。

还有一类容易忽略：**两个事务分别走不同的索引路径去更新相同的行**。索引选择不同，加锁顺序就不同，于是两个事务各自持有对方需要的锁——冲突的根源不在数据，在访问路径。

### 锁等待排查：从三张表看出谁在等谁

排查锁问题需要三样东西，它们的分工是**事务、锁、等待关系**：

- **当前事务表**：正在运行的事务，包含事务状态、开始时间、已锁定行数、已修改行数。**开始时间和已锁定行数是判断"谁持锁太久"最快的两个字段。**
- **当前锁表**：当前的锁信息，包含锁所在的表、索引、锁类型与加锁的数据。
- **等待关系表**：谁在等谁的锁。它把上面两张表连起来，直接给出阻塞链。

```sql
-- 谁在等谁：阻塞链的直读
SELECT * FROM performance_schema.data_lock_waits;

-- 当前持有的锁落在哪张表、哪个索引、哪段数据上
SELECT * FROM performance_schema.data_locks;

-- 事务状态与开始时间，用来定位持锁最久的那个事务
SELECT trx_id, trx_state, trx_started, trx_rows_locked, trx_rows_modified
FROM information_schema.innodb_trx;
```

前两张表的位置随版本变过：较早的版本把它们放在 `information_schema` 下（名为 `innodb_locks` 与 `innodb_lock_waits`），较新的版本移到了 `performance_schema`；事务表的位置没有变。查不到时先确认版本对应的位置，比反复检查权限更快。

排查顺序是从等待关系出发：找到**等待链的源头**（那个不等待任何人、却持有锁的事务），再回到事务表看它为什么持有这么久。**多数情况下源头是一个长事务或一条没有走索引的写语句。**

### 处置：重试、缩短事务、固定加锁顺序

锁问题分成两类，处置方式不同：

**死锁**——不可能被完全消除，只能减少概率，并且**必须能在应用层重试**。减少概率的手段按收益排序：

- **固定加锁顺序**：批量更新前按主键排序，让所有事务以同一顺序加锁。这一条能消除最经典的那类死锁。
- **缩短事务**：把远程调用、计算、消息发送移出事务，让锁的持有时间尽量短。
- **减小加锁范围**：确保写操作的 `WHERE` 走索引，避免全表范围的 next-key lock。
- **考虑降低隔离级别**：读已提交会大幅减少间隙锁，从而减少间隙锁交叉那一类死锁。这是一个需要与业务一致性要求一起权衡的决定。

**锁等待（堆积）**——通常不是设计问题，而是某个环节变慢了。要查的是"源头事务为什么慢"，而不是去调锁参数。把等待超时时间调大只是在掩盖问题，它会让堆积更严重。

最后一条值得单独强调：**死锁不是异常，是正常现象**。任何用锁实现的并发控制都可能死锁，所以"如何重试"应该被当作事务设计的一部分，而不是出错时的补救。
