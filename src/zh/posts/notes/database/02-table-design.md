# 表设计：从函数依赖到反范式边界

表设计要回答的问题不是"该建几张表"，而是**这组业务规则允许出现哪些数据状态、不允许哪些**。函数依赖和范式是回答这个问题的工具：它们把业务规则翻译成对属性的约束，再推导出什么样的结构不会产生异常。

工具只解决一半。生产中有大量表并不满足第三范式，它们同样正确——因为它们用一致性成本换取了读取成本，而这个交换是有条件的。判断条件是否成立，比记住范式定义更重要。

全文用一个供应链场景贯穿：**产品由大部件构成，大部件又可以由其它部件或基本零件构成；每个基本零件可以由多个供应商供货，价格随供应商不同。**

## 关系模型：SQL 为什么可以非过程化

**关系模型**由三部分组成——**数据结构**（关系、元组、属性、域）、**数据操作**（关系代数）、**完整性约束**。这里只展开对表设计有后果的部分。

### 笛卡尔积与连接：拆开的表怎么合回来

关系代数只有五个基本运算，**笛卡尔积**是其中之一：两张表各取一行拼成一行，结果行数是两者行数之积。它本身几乎没有用，因为结果里绝大多数组合是荒谬的。

**连接是派生运算**，它的定义就是"笛卡尔积加上筛选条件"：先拼，再按条件过滤。记住这个定义就解释了一件事：**连接条件写错或漏写时，数据库不会报错**——它只是忠实地执行了笛卡尔积。行数爆炸不是 bug，是把派生运算退化成了基本运算。

三种常见形态各有它的陷阱：

- **等值连接**：连接条件是相等比较，最常用的一种。
- **自然连接**：按所有同名列自动匹配，并把重复的列去掉。它省掉手写条件，代价是**连接条件变成了"同名列"这件事本身，而不是你的意图**——两张表都有 `create_time` 时，它会把这一列也算进连接条件。
- **外连接**：在连接结果之外保留没有匹配上的行，未匹配的位置补空值；左外连接保留左表的全部行。它用于"包含空关联"的查询，而它与前两种混用错时的后果是**行数不对**——本该用左外连接的地方写成内连接，没有关联的行会直接消失。

### 声明式的代价：优化器获得了改写你 SQL 的权力

SQL 是**非过程化**的：你描述结果集合的形状，不指定存取路径。这个交换换来的是可移植性，代价是**你的 SQL 不是执行计划，只是一个待优化的表达式**。

优化器可以在语义等价的前提下重写它：调整连接顺序、把条件下推、展开子查询、换用别的索引。所以"同一条 SQL 昨天快今天慢"是会真实发生的，而且常常不是你改了 SQL，而是数据分布或统计信息变了。

对表设计的直接后果：**表结构和索引是在为优化器划定选择空间**。把一个高频过滤条件放进一个无法建索引的位置——比如把多个值拼进同一个字段——就等于把这个选择从优化器手里拿走，后面再怎么写 SQL 都补不回来。

### 逻辑独立性：视图与在线变更为什么能不动应用

数据库用三级描述把"数据的逻辑结构"和"数据如何存储"隔开：

| 层次 | 描述什么 | 数量 |
|---|---|---|
| 外模式（视图） | 某个用户能看到的数据视图 | 多个 |
| 模式（逻辑模式） | 全体数据的逻辑结构和特征 | 一个 |
| 内模式（存储模式） | 记录与索引按什么方式存储、组织 | 一个 |

两级映像负责隔离：**外模式/模式映像**让逻辑结构变化时可以只改映像、不动应用；**模式/内模式映像**让存储结构变化时不动逻辑结构。这就是**数据独立性**的来源，也是"重构数据库为什么可以不影响上层应用"的答案。

落到现代实现，逻辑独立性的主要载体是**视图、在线 DDL 和兼容层**。它的收益有边界：视图会被消解展开到查询里，分组视图通常不可更新，过于复杂的视图会让优化器失去选择空间。

### 关系模型不承诺什么：结果无序、无重复元组、NULL 破坏二值逻辑

三条容易忽略的语义，每一条都会变成生产事故。

**关系是集合，不是列表。** 元组没有顺序、没有重复。SQL 查询结果不保证顺序，`ORDER BY` 才是唯一的顺序保证。没有 `ORDER BY` 的分页结果是**不确定的**——同一句 SQL 在不同时刻可能返回不同的行，翻页时表现为重复或漏行：

```sql
-- 错：没有排序保证
SELECT part_no, part_name FROM part LIMIT 0, 20;
SELECT part_no, part_name FROM part LIMIT 20, 20;

-- 对：排序键要能唯一确定顺序，否则等值行之间仍然是任意的
SELECT part_no, part_name FROM part ORDER BY part_no LIMIT 0, 20;
```

**NULL 不是值，是"未知"。** 任何与 NULL 的比较返回 `UNKNOWN` 而不是真或假，`WHERE` 只在结果为真时保留该行。于是 `price <> 100` 会同时排除 `price = 100` 和 `price IS NULL` 的行。更隐蔽的是 `NOT IN`：

```sql
-- 子查询只要返回一行 NULL，这条查询的结果就是空集
SELECT part_no FROM part
WHERE part_no NOT IN (SELECT part_id FROM part_supplier WHERE supplier_id = 7);
```

`NOT IN` 的语义是"对子查询中的每一行，`part_no <> part_id` 都为真"。子查询里出现一个 NULL，比较结果就是 `UNKNOWN`，整个条件不可能成立。`NOT EXISTS` 没有这个问题。

**主键唯一不等于业务唯一。** 主键保证的是技术唯一性。如果业务规则是"零件型号不能重复"，必须显式建唯一索引——只靠自增主键，数据库会坦然接受两条型号相同的零件记录。

## 函数依赖：从业务规则推出候选码

### 函数依赖的方向：A→B 读作什么

$A \to B$ 表示：**任意两个元组，只要 A 上的取值相同，B 上的取值必然相同**。读作"A 决定 B"，或"B 函数依赖于 A"。

方向不能反。用场景验证：`供应商号 → 供应商名` 成立，因为一个供应商只有一个名字；反过来"供应商名决定供应商号"不成立，因为两家供应商可能重名。方向写反，后面所有推理都会错。

一个依赖是否成立，由**业务规则**决定，不由数据样本决定。样本里恰好没有反例，不等于依赖成立。

### 完全、部分与传递依赖怎么判定

- **完全函数依赖**：$X \to Y$，且 X 的**任何真子集**都不能决定 Y。
- **部分函数依赖**：$X \to Y$，但 X 的某个真子集就能决定 Y。只有当 X 由**多个属性**组成时才可能出现部分依赖，X 是单属性时不存在。
- **传递函数依赖**：$X \to Y$、$Y \to Z$，且 Y 不能决定 X。

在场景里各找一个：

| 依赖 | 类型 | 业务规则 |
|---|---|---|
| `(零件号, 供应商号) → 价格` | 完全依赖 | 价格由"哪个零件、哪个供应商"共同决定，单看任一个都不行 |
| `(零件号, 供应商号) → 供应商名` | 部分依赖 | 供应商名只由供应商号决定 |
| `零件号 → 类别号`、`类别号 → 类别名` | 传递依赖 | 类别名绕了一层 |

这两种"不完整"的依赖就是表里冗余的来源。

### 候选码求解：属性闭包算法

**超码**是能唯一标识元组的属性组合，允许包含多余属性；**候选码**是不含多余属性的超码，即它任何一个真子集都不是超码；从候选码里挑一个作为**主码**。求候选码靠**属性闭包**。

设关系 R 上的函数依赖集为 F，属性集 X 的闭包 $X^+$：

1. 令 $X^+ = X$。
2. 扫描 F 中每一条 $U \to V$：若 $U \subseteq X^+$，则 $X^+ = X^+ \cup V$。
3. 重复第 2 步，直到 $X^+$ 不再变化。

判断规则：$X^+$ 包含 R 的全部属性，则 X 是**超码**；若 X 是超码且任一真子集都不是超码，则 X 是**候选码**。

走一遍。取关系 `R(零件号, 供应商号, 供应商名, 价格)`，依赖集 `F = {供应商号 → 供应商名, (零件号, 供应商号) → 价格}`。

求 `(零件号, 供应商号)` 的闭包：初始为该两个属性；`供应商号 → 供应商名` 左部已包含，加入供应商名；`(零件号, 供应商号) → 价格` 左部已包含，加入价格。闭包等于全部属性，是超码。去掉任一属性后闭包都不再完整——`零件号` 单独推不出别的，`供应商号` 单独推不出零件号和价格。所以**唯一候选码是 (零件号, 供应商号)**。

再看这个关系里的 `供应商号 → 供应商名`：它的左部是候选码的真子集，**供应商名部分依赖于候选码**，这个关系不满足第二范式。

再看一个有多组候选码的情形。关系 `R(学生, 课程, 教师)`，依赖集 `F = {(学生, 课程) → 教师, 教师 → 课程}`：

- `(学生, 课程)` 的闭包含全部属性，真子集都不含全部属性，是候选码。
- `(学生, 教师)` 的闭包：由 `教师 → 课程` 得到课程，含全部属性；真子集都不行，也是候选码。

两个候选码**有重叠属性**（学生）。这种结构是 3NF 与 BCNF 分歧的来源。

### 最小依赖集：为什么它不唯一

一个函数依赖集可能含冗余。**最小依赖集**（最小覆盖）是与它等价且满足三个条件的依赖集：

1. 每条依赖的右部只有**一个属性**；
2. 没有任何一条依赖多余（去掉它，闭包会变）；
3. 没有任何一条依赖的左部含**多余属性**（去掉它，闭包不变）。

求解是逐条试删：先把右部拆成单属性，再依次尝试删除每条依赖、每个左部属性，删除后闭包不变就永久删除。

**结果不唯一。** 例如 $F = \{A \to B,\ B \to A,\ B \to C,\ A \to C\}$，`A → C` 是冗余的（可由 `A → B → C` 推出），删掉得到 $\{A \to B,\ B \to A,\ B \to C\}$；但也可以先删 `B → C`（由 `B → A → C` 推出），得到另一个同样最小、同样等价、内容却不同的依赖集。所以不要拿最小依赖集当"标准答案"去比对——它只保证等价和最小，不保证唯一。

## 范式：每一级消除了什么异常

### 冗余引发的四类异常：用产品零件清单走一遍

把场景里的信息塞进一张表：

```sql
CREATE TABLE product_part_supplier (
  product_no     VARCHAR(32),    -- 产品代号
  product_name   VARCHAR(64),    -- 产品名称
  part_no        VARCHAR(32),    -- 零件号
  part_name      VARCHAR(64),    -- 零件名称
  supplier_no    VARCHAR(32),    -- 供应商号
  supplier_name  VARCHAR(64),    -- 供应商名
  price          DECIMAL(12,2),  -- 该供应商对该零件的报价
  PRIMARY KEY (product_no, part_no, supplier_no)
);
```

这张表的第二范式都不满足（`supplier_name` 与 `part_name` 都部分依赖于主码），随之而来四类异常：

- **数据冗余**：一个供应商供应 500 种零件，它的名字就重复存 500 次。
- **更新异常**：供应商改名要更新多少行？取决于它供货的记录数。漏掉一行，同一个供应商就有了两个名字。
- **插入异常**：新签一家供应商但还没确定供货零件，插不进去——主码里必须有零件号。
- **删除异常**：删掉某个零件的最后一条供货记录，供应商本身的信息也跟着消失。

范式的价值就在这四类异常上。**记住定义没有用，能指出某个设计会产生哪一类异常才有用。**

### 1NF 到 BCNF：每一级消掉的是哪一类异常

- **1NF**：每个属性不可再分。反例是把多个供应商塞进一个字段，存成 `'S01,S02'`。代价是**这个字段无法建成可用的索引**，也无法用约束保证格式。现代争议是 JSON 列：它是自愿放弃 1NF，把结构藏进值里换取 schema 灵活性，代价是数据库无法约束其内部结构、大多数索引对它无效。这是**有意的反范式**，前提是你想清楚了谁来约束它。
- **2NF**：在 1NF 基础上，消除**非主属性对候选码的部分依赖**。上表拆出 `供应商(供应商号, 供应商名)` 后，`(零件号, 供应商号, 价格)` 里价格完全依赖于码。
- **3NF**：消除非主属性对码的**传递依赖**。`零件(零件号, 零件名, 类别号)` 配 `类别(类别号, 类别名)`。
- **BCNF**：每个决定因素都必须是超码。这是比 3NF 更强的条件。

3NF 与 BCNF 的差别只出现在一种情况：**决定因素不是超码，但它由主属性组成**。3NF 允许（因为被决定的也是主属性），BCNF 不允许。

### 多值依赖与 4NF：函数依赖管不到的那一类

函数依赖描述"一个 X 对应一个 Y"。有一类独立性与它不同：

```sql
-- 一个零件有多个适用标准，也有多个产地，两者互相独立
CREATE TABLE part_attribute (
  part_no  VARCHAR(32),
  standard VARCHAR(32),  -- 适用标准
  origin   VARCHAR(32),  -- 产地
  PRIMARY KEY (part_no, standard, origin)
);
```

零件 P 有两个适用标准 {S1, S2}、两个产地 {P1, P2}，但标准与产地并不成对。真实信息是 4 个独立事实，表里却要走 4 行；若标准增到 3 个、产地增到 3 个，就要存 9 行。这是**多值依赖**：`零件号 ↠ 适用标准`，它不能由任何函数依赖推出。

**4NF** 要求：对每一个非平凡的多值依赖 $X \twoheadrightarrow Y$，X 都必须是超码。上表不满足（零件号不是超码），拆成 `part_standard(零件号, 适用标准)` 与 `part_origin(零件号, 产地)` 即满足。判断口径很简单：**当两个"一对多"彼此独立时，不要把它们的多值放进同一张表。**

### 3NF 与 BCNF 的分歧：无损连接与保持依赖不能兼得

用前面那个关系 `R(学生, 课程, 教师)`，依赖集 `F = {(学生, 课程) → 教师, 教师 → 课程}`，候选码是 `(学生, 课程)` 和 `(学生, 教师)`。

`教师 → 课程` 的决定因素是教师。教师不是超码（它决定不了学生），所以**违反 BCNF**；但被决定的课程是主属性，所以**满足 3NF**。

把它拆成 `R1(学生, 教师)` 和 `R2(教师, 课程)`：两个关系都满足 BCNF，而且这个拆法是无损的。但原来 F 里的 `(学生, 课程) → 教师` **无法在这两个关系上表达**——学生和课程分别落在两个关系里，没有任何一个关系同时包含它们。这条业务规则失去了数据库层面的强制能力。

这是结构性的，不是算法不够好：**在一定条件下，满足 BCNF 的分解必然无法保持全部函数依赖**。所以工程上的选择是：

- 优先 **3NF**：保依赖且无损，代价是允许少量冗余（上述情形里 R 本身就是 3NF）；
- 坚持 **BCNF**：无损但丢依赖，丢失的规则必须在应用层补上，并且要写进文档，否则没人知道它丢了。

## 模式分解：无损连接与保持依赖的取舍

### 无损连接判定：表格法怎么走

拆表不可逆：数据结构一改，应用、索引、历史数据都要跟着动。所以拆完必须证明**还能通过连接还原出原来的关系**，这个性质叫**无损连接**。判定用表格法：

1. 建一张表，**行**是分解出的每个关系，**列**是原关系的全部属性；
2. 若属性 $A_j$ 属于第 $i$ 个关系，该格填区分符号 $a_j$，否则填 $b_{ij}$；
3. 对 F 中每一条 $U \to V$：找出行（至少两行）在 U 上取值相同的情况，把它们的 V 列改成一致——有 $a$ 就统一为 $a$，否则统一为同一个 $b$；
4. 重复第 3 步直到不再变化。**某一行变成全部为 $a$，则无损；否则有损。**

用前面那个关系 `R(零件号, 供应商号, 供应商名)`，依赖集 `F = {供应商号 → 供应商名}`，候选码是 `(零件号, 供应商号)`。

先看一个正确的拆法 `ρ1 = {R1(零件号, 供应商号), R2(供应商号, 供应商名)}`：

| 关系 | 零件号 | 供应商号 | 供应商名 |
|---|---|---|---|
| R1 | $a_1$ | $a_2$ | $b_{13}$ |
| R2 | $b_{21}$ | $a_2$ | $a_3$ |

两行在供应商号上都是 $a_2$，按 `供应商号 → 供应商名` 把供应商名列统一为 $a_3$，第一行变成 $(a_1, a_2, a_3)$——全 $a$，**无损**。

再看一个凭直觉同样合理的拆法 `ρ2 = {R1(零件号, 供应商名), R2(供应商号, 供应商名)}`：

| 关系 | 零件号 | 供应商号 | 供应商名 |
|---|---|---|---|
| R1 | $a_1$ | $b_{12}$ | $a_3$ |
| R2 | $b_{21}$ | $a_2$ | $a_3$ |

两行在供应商号上分别是 $b_{12}$ 和 $a_2$，不相等，规则无法应用；没有任何一行变成全 $a$，**有损**。直观上也说得通：这个拆法丢掉了"哪个零件由哪个供应商供货"，连接时只能用供应商名做笛卡尔积。

这就是表格法的作用——**判断一个看起来合理的拆法是否真的可还原**。

### 保持依赖：无损为什么还不够

无损只保证数据能还原，不保证**业务规则还能继续被强制**。

把 F 投影到每个分解出的关系上（只保留属性全部落在该关系内的依赖），得到 $F_i$。若 $\bigcup F_i$ 与 $F$ 等价，则分解**保持依赖**。

`ρ1` 的两个投影分别是空集和 `{供应商号 → 供应商名}`，合起来与 F 等价，保持依赖。

而前面那个关系 `R(学生, 课程, 教师)` 拆成 `R1(学生, 教师)` 和 `R2(教师, 课程)` 后，`(学生, 课程) → 教师` 在两个投影里都不存在，**无损但丢依赖**。

两个性质必须分别检验：**无损看数据能否还原，保依赖看规则能否继续生效**。只做前者是常见的疏漏——数据查得出来，脏数据从此却可以合法写入。

### 分解算法的选择：3NF 保依赖，BCNF 保无损

- **3NF 合成算法**：求最小依赖集 → 把左部相同的依赖合成一个关系 → 若没有任何关系包含候选码，补一个只含候选码的关系。结果**既保持依赖又无损**。
- **BCNF 分解算法**：反复找违反 BCNF 的依赖 $X \to Y$，把当前关系拆成 $X \cup Y$ 和 $R - Y$，直到全部满足 BCNF。结果**无损，但可能丢依赖**。

选择口径：**能用 3NF 达成就不要为了 BCNF 丢业务规则**。3NF 允许的冗余是"主属性之间的依赖"这一狭窄情形，代价通常可以接受；反过来，丢掉的依赖要靠在应用层补一句校验，而那句校验迟早会被绕过——脚本、手工修数、另一个服务都会绕过它。

一个真实的反面模式：很多团队的"拆表"并不基于依赖分析，只是把看起来相关的字段挪到一起。这种拆法既没消除异常，也没保住关联，问题要等到 join 之后行数不对才暴露，比如用 `INNER JOIN` 代替 `LEFT JOIN` 让数据消失。

## 反范式：什么时候故意违反范式是对的

### 反范式的三种动因：读放大、连接成本与跨服务边界

**反范式**是有意识地引入冗余，用一致性成本换读取成本。它在三种情形下成立：

1. **读放大**。产品零件清单要连接 4 张表才能渲染，而这个查询每次页面访问都要执行。把 `part_name` 冗余进 BOM 表，省掉一次连接。
2. **连接成本**。高频列表页、报表、C 端接口上，连接的 CPU 与随机 I/O 是真实成本，尤其在连接字段没有合适索引时。
3. **跨服务/跨库边界**。库或服务拆开之后，连接在物理上不再可能，只能冗余。订单里存商品名称快照是标准做法。

### 冗余的代价：一致性由谁保证

冗余一旦引入，**同一事实就有了多份副本，一致性必须由某个人负责**。三种方案，代价不同：

| 方案 | 一致性强度 | 延迟窗口 | 主要风险 |
|---|---|---|---|
| 应用层双写 | 取决于事务边界 | 无（同事务内） | 漏写一处就永久不一致；跨库双写没有原子性 |
| 触发器 | 强 | 无 | 逻辑隐蔽、难调试，拖慢写入路径，排查时容易被忽略 |
| 异步同步（binlog/CDC/消息） | 最终一致 | 有 | 延迟窗口内读到旧值；需要监控积压与补偿 |

决策变量只有两个：**业务能容忍多长时间的陈旧，不一致时谁来修**。答不上这两个问题，反范式就不该做。

### 先测再改：用执行计划判断反范式是否划算

反范式最常见的失败是"做了冗余，性能没变"，因为瓶颈根本不在连接。动手前先确认三件事：

- **瓶颈是不是连接**。用执行计划确认成本花在扫描、连接还是排序上。如果慢在扫描大量行，冗余字段不会让行数变少。
- **读写比**。冗余字段每次被更新都要同步所有副本，写多读少的字段做冗余是负收益。
- **变更频率**。几乎不变的事实（品牌、快照类）冗余接近无代价；高频变更的事实（库存、价格）冗余就是事故源。

三个具体的反例：

- **混淆快照语义与实时语义**。订单里存商品名是快照，用于展示历史成交信息；拿它去查"这个商品现在叫什么"就是错的用法。
- **用冗余字段做业务判断**。用冗余的库存字段决定能否下单，必然超卖——判断必须回到权威数据源。
- **冗余了但没建索引**。为了省一次连接而冗余字段，却没有为新的查询条件建索引，收益为零。

## 完整性约束：数据库该强制多少

### 实体完整性与参照完整性各自保证什么

- **实体完整性**：主码非空且唯一，DBMS 拒绝违反的插入和更新。它保证的是**技术唯一性**，业务唯一性必须用唯一索引单独表达，否则数据库会接受两条语义重复的记录。
- **参照完整性**：外码要么为空，要么等于被参照关系某个元组的主码。它保证**存在性**——子表不会引用不存在的父表记录，但不保证**正确性**：订单的 `user_id` 写成另一个真实存在的用户，外键完全允许。
- **用户定义完整性**：`NOT NULL`、`UNIQUE`、`CHECK`、`DEFAULT`。

`CHECK` 有一个必须知道的历史边界：**MySQL 8.0.16 之前会解析并静默忽略 `CHECK` 约束**。表结构里写了，不报错，也不生效。

### 外键在生产里为什么常被禁用

外键是最有效的参照完整性手段，但很多生产库不建外键。理由是真实的：

- **分库分表**：父表可能不在同一个实例上，物理上无法强制。
- **批量导入与数据迁移**：外键检查显著拖慢导入，在线 DDL 期间往往还要临时关闭。
- **锁竞争**：InnoDB 在插入或更新子表时会对父表对应的**记录加共享锁**。高并发下，热门父表记录会变成锁热点。
- **历史包袱与模板默认**：不少建表模板和 ORM 默认不生成外键。

禁用外键的代价必须显式承担：**存在性约束被搬到了应用层，而应用层是可以被绕过的**——数据修复脚本、手工 SQL、另一个服务都会绕过它。所以至少要补两件事：写明谁负责校验存在性；用巡检 SQL 定期发现已经产生的孤儿数据。

```sql
-- 找出引用了不存在零件的供货记录
SELECT ps.part_no, ps.supplier_no
FROM part_supplier ps
LEFT JOIN part p ON p.part_no = ps.part_no
WHERE p.part_no IS NULL;
```

### 约束下沉的分工：数据库、ORM 与应用层

| 约束类型 | 数据库 | ORM | 应用层 |
|---|---|---|---|
| 唯一性 | 唯一索引（最可靠） | 声明式生成 | 提供友好提示，不做最终保证 |
| 存在性 | 外键；禁用则需巡检 | 通常不生成 | 校验并记录孤儿数据 |
| 取值范围 | `NOT NULL` / `CHECK` / 字段类型 | 字段类型与校验注解 | 参数校验与错误信息 |
| 跨行/跨表业务规则 | 触发器（一般不建议） | 无法表达 | 事务内校验，这是唯一可行的位置 |

一条原则：**数据库约束是最后一道防线，不是唯一一道**。放在应用层的校验一定会被绕过，所以能下沉就下沉；但约束不是越多越好——每加一条都增加写入路径的失败面和运维复杂度，改数据、迁移、压测时都要临时处理。这是取舍，不是教条。

顺带明确一个边界：SQL 标准里的 `CREATE ASSERTION` 可以表达跨表约束，但主流实现都不支持，跨表规则只能落在触发器或应用层。

范式给的是下界：它保证你不会造出必然产生异常的结构。反范式给的是上界的取舍：你愿意用多少一致性成本换读取成本。两者之间没有通用答案，只有能被验证的判断——而验证的起点是执行计划，不是直觉。
