一条 SQL 从接收到返回，会在四层结构上留下痕迹：**磁盘上的页**、**按主键组织的 B+ 树**、**内存里的缓冲池**、**顺序追加的日志**。这四层各自解决一个物理问题——数据放哪、怎么快速定位、怎么避免随机 I/O、怎么保证掉电不丢。

理解它们的顺序是"从底往上"：先看数据在磁盘上长什么样，再看索引如何在一堆页里定位，再看内存如何把磁盘访问变少，最后看日志如何把随机写变成顺序写。把四层拼起来，就是一条 SQL 的真实路径。

这条路径也解释了索引的边界：**索引存在不等于会被使用**，而"不被使用"有时是优化器的正确决策，有时才是设计错误。

## 行与页：InnoDB 如何把表放进磁盘

### 行格式与行溢出：一行为什么会跨越多个页

InnoDB 的页默认 16KB，表数据按行存进页里。一行在页内的布局依次是：**变长字段长度列表**（每个变长列记多长，超过 255 字节的用 2 字节表示）、**NULL 标志位图**（每个允许为 NULL 的列占 1 bit）、**记录头**、**列值**。

两个直接推论：

- **允许为 NULL 的列本身不占数据空间**（只在标志位图里占 1 bit），但它会在索引与约束上留下代价。
- **当一行太大放不进一个页，InnoDB 会把大字段挪到溢出页**（off-page），行内只留一个 20 字节指针。这就是 `TEXT`/`BLOB`/超长 `varchar` 的真实代价：它不只是占空间，而是让**同一行的读取变成两次 I/O**，并且把该行所在页能容纳的行数压下来。

一条经验判据比背数字有用：**页要能装下足够多的行**。一页如果只能放一两行，扫描这张表的 I/O 次数就与行数同阶，缓冲区也更容易被冲掉。所以设计上常见的做法是**把大字段拆到独立的副表**，用主键一一对应——主表变窄之后，每页行数上升，索引与范围扫描都更快。

### 页、区、段、表空间：InnoDB 的四层容器

从大到小四层，理解它们的关键是**各自承担什么分配职责**：

| 层 | 大小 | 职责 |
|---|---|---|
| 表空间（tablespace） | 一个或多个文件 | 物理文件的容器：系统表空间 `ibdata1`、独立表空间 `表名.ibd`、通用表空间、undo 表空间、临时表空间 |
| 段（segment） | 按需增长 | 给一个逻辑对象（如一个索引）分配空间，每个索引通常占两个段：叶子节点段与非叶子节点段 |
| 区（extent） | 1MB = 64 个 16KB 页 | 空间分配的**基本单位**，按区申请以减少碎片 |
| 页（page） | 16KB | 磁盘与内存之间传输的**最小单位**；一页可能会承载多行 |

要抓住的两点：**页是 I/O 单位，区是分配单位**。读取永远以页为粒度，所以"只查一行"和"查同一页里的一百行"在 I/O 上几乎同价；反过来，只多要一行但那一行落在另一个页上，就要再付一整页的代价。

### 字段类型的选择：它决定了行有多宽

字段类型不是"哪个看起来更合适"的问题，而是**行宽**问题——行宽决定每页放多少行，进而决定整条路径上每一层的效率。

- **`char` 与 `varchar`**：定长列不需要长度列表项，但会用空格补齐；变长列省空间，代价是每行多 1 到 2 字节的长度记录。字符串长度基本固定的才用 `char`。
- **整数类型**：按取值范围选最小够用的。唯一例外是主键——它会被复制进每一个二级索引，所以主键要留足空间。
- **`decimal` 与浮点**：金额必须用 `decimal`。二进制浮点无法精确表示大多数十进制小数，`0.1 + 0.2` 不等于 `0.3`，用它做金额比较会得到错误结果。这是**表示能力**问题，不是精度调优问题。
- **时间类型**：`DATETIME` 存的是 **5 字节加上小数秒的增量**（`DATETIME(0)` 5 字节，`(6)` 才 8 字节），**原样存储、不做时区转换**；`TIMESTAMP` 存的是 UTC 秒数，**4 字节加上小数秒增量**（`(0)` 4 字节，`(6)` 7 字节），读取时按会话时区换算，范围上限到 2038 年。
- **两者的差别不是精度而是语义**：需要按用户时区自动换算、或者跨时区部署时，`TIMESTAMP` 的换算能力有用；需要原样记录一个"墙上时间"、或者要跨过 2038 年，就必须用 `DATETIME`。

## B+ 树与索引组织表

### B+ 树、B 树与 LSM：三种写读权衡

索引结构的选择本质是在**读放大、写放大、空间放大**三者之间取舍：

| 结构 | 等值查找 | 范围扫描 | 写入 | 代表 |
|---|---|---|---|---|
| 哈希 | 一次 | 不支持 | 追加/桶分裂 | Memory 引擎、自适应哈希索引 |
| B+ 树 | 树高次 | 叶子链表顺序扫描 | 原地更新，随机 I/O，页分裂 | InnoDB |
| LSM 树 | 多层查找，读放大 | 层内有序，可合并 | 顺序追加，写放大转移到后台合并 | RocksDB、TiKV |

B+ 树相对 B 树的关键差别：**只有叶子节点存完整数据，非叶子节点只存键和指针**。同样大小的非叶子页因此能放更多键，树更矮；叶子之间用双向链表相连，范围扫描只要找到起点然后顺序右移，不必回到上层做中序遍历。这正是"按范围查、按顺序取"这类需求在关系型数据库上高效的根本原因。

哈希不支持范围与排序，所以它只能做补充（InnoDB 的自适应哈希索引就是在 B+ 树之上、针对等值查询建的旁路），不能替代 B+ 树。

### 聚簇索引：表的数据就存在主键的 B+ 树里

InnoDB 把整张表的数据按主键顺序组织在 B+ 树的叶子里，这种表叫**索引组织表**。**聚簇索引就是这张表本身**，不是它上面的一个附属结构。

主键的确定顺序是：

1. 显式定义的主键；
2. 没有主键，就取第一个**非空唯一索引**；
3. 再没有，InnoDB 自动生成一个 6 字节的隐藏列作为聚簇索引键。

这个机制有一个容易被忽略的后果：**你选的不是"主键"，而是"整张表的物理组织顺序"**。换成第 2 或第 3 种情况时，表的数据顺序由那个唯一索引甚至隐藏列决定，这可能与你的查询模式完全无关。

### 二级索引与回表：为什么查一个字段要多跳一次

**二级索引的叶子节点存的是"索引列值 + 主键值"**，不是行的物理地址。原因是聚簇索引会因页分裂而移动数据，物理地址不稳定，而主键稳定。

所以通过二级索引查非索引列，需要两次树查找：

1. 在二级索引的 B+ 树里找到目标键，取出主键值；
2. 用主键值回到聚簇索引的 B+ 树里取出整行。这一步叫**回表**。

回表的次数等于**匹配到的二级索引记录数**（在没有条件下推的优化时），每一次都可能是一次随机 I/O。这就是"索引没少用，但查询还是慢"的常见原因——慢的不是定位，是回表。

**覆盖索引**正是为省掉第 2 步而存在：如果查询需要的所有列都已在索引里，就完全不必回表。有一个常被忘掉的推论：**因为二级索引叶子自带主键值，所以 `SELECT 主键 FROM 表 WHERE 二级索引列 = ?` 本身就是覆盖索引**，不需要额外建联合索引。

### 主键选型：自增、UUID 与雪花算法的代价

主键的代价不只在自己身上，**它被复制进每一个二级索引**。所以选主键时要同时算两笔账：插入时的页行为，以及所有二级索引的体积。

- **自增或趋势递增**：插入落在 B+ 树最右侧，顺序追加。页写满才分裂，页利用率高，索引碎片少。
- **纯随机（如 UUID v4）**：每次插入落到树的随机位置，频繁触发页分裂并留下页内空洞，同样的数据占更多页，缓冲池命中率随之下降。同时 16 字节的随机值比 8 字节整数大一倍，还要乘以二级索引的数量。
- **时间趋势递增（有序 UUID、雪花算法）**：兼顾分布式唯一与顺序插入，是分布式场景的常见解。代价是它**依赖时钟**——时钟回拨会导致重复或乱序，机器标识的分配也需要额外机制。

一个能直接用的判据：**如果一张表有很多二级索引，主键宽度的代价会被放大若干倍**。这也是"主键宁短勿长"这句话的真实来源。

## 缓冲池：随机 I/O 是怎么被消掉的

### 缓冲池：页的状态与改进的 LRU

**缓冲池**是 InnoDB 的主内存区域，以页为单位缓存磁盘页，读写都先经过它。页在其中有三种状态：

- **空闲页**：尚未被分配使用；
- **干净页**：内容与磁盘一致；
- **脏页**：已被修改，尚未写回磁盘。

淘汰策略不是普通 LRU，而是**改进的 LRU**：链表中段作为插入点，新读入的页先进入"老"区，只有被再次访问才升到"新"区。这个设计的目的是**让一次性的大范围扫描不要把整个缓冲池冲掉**——全表扫描读进来的页只被用一次，会待在老区被优先淘汰，不会挤走热数据。

缓冲池的空间是有限的，而**每个索引都要占一部分**。这就是"索引不是越多越好"在内存层面的依据：多一个索引，就多一棵树要和数据页争夺缓冲池。

### Change Buffer：非唯一二级索引的写为什么能缓

对二级索引的插入是**随机顺序**的，删除和更新还可能触及树上不相邻的多个二级索引页。如果每次写都要把对应页从磁盘读进来，随机 I/O 会非常可观。

**Change Buffer 的做法是把这些修改先缓在内存里**，等那个页因为别的原因被读进来时再合并（merge），从而把多次随机写合并成一次读入。

它有一个必须记住的边界：**只对非唯一的二级索引有效**。原因是唯一索引在插入时必须判断唯一性，而判断唯一性就必须把页读进来——既然页已经读进来了，缓冲就没有意义。这是"唯一索引写性能差"的真正机制，也是选唯一索引时要一起考虑的代价。

### 刷脏与双写缓冲：页什么时候写盘，写坏了怎么办

脏页不能无限积压，否则崩溃后恢复要重放太多日志。推动刷脏的力量有两个：**缓冲池脏页比例**与 **redo 日志的空间压力**。后者常被忽略——redo 是环形写入的，如果脏页迟迟不刷，redo 会写满，此时数据库必须停下来强制刷脏，表现为周期性的性能抖动。

页在写盘过程中可能因为掉电只写了一部分，这种**部分写**会让一个页既不是旧内容也不是新内容。**双写缓冲**的处理办法是：刷盘前先把整页顺序写到一块专门的区域，再写目标位置；崩溃后如果目标页损坏，可以用这块区域里的完整副本恢复。它牺牲一次顺序写，换来页级的写入原子性。

## 日志：为什么一次写入要记三份

### WAL：为什么必须先写日志再写数据页

随机写一页和顺序追加一条日志，成本相差很大。**WAL（Write-Ahead Logging）**就是利用这个差距：修改先在缓冲池里完成，同时把修改顺序写入日志并刷盘，数据页则由后台线程异步、批量写回。

于是事务提交时只需要保证**日志落盘**，而不需要等数据页落盘。持久性由日志保证，性能由延迟写数据页换来。

这里有一个必须知道的分档参数——`innodb_flush_log_at_trx_commit`，控制每次提交时日志刷到什么程度：

| 取值 | 事务提交时的行为 | 掉电会丢什么 |
|---|---|---|
| 1 | 写入并刷盘 | 不丢已提交事务（默认，也是最安全的） |
| 2 | 写入操作系统缓存，不刷盘 | 数据库进程崩溃不丢，**操作系统崩溃或断电会丢** |
| 0 | 交给后台每秒刷一次 | 进程崩溃就可能丢最近一秒 |

把 1 改成 2 或 0 能显著提高写入吞吐，代价是持久性从"事务级"降级为"秒级"。这是一个必须由业务来回答的取舍，不是性能调优参数。

### redo 与 undo：崩溃恢复和回滚各要什么

两者都叫日志，但解决的问题相反：

- **redo log**：记录"对这个页做了什么修改"，用于**崩溃后重做**已提交的事务。它是物理性的页级修改记录，因此重放是幂等的——同一条 redo 重放多次结果一致，这正是崩溃恢复可以重复执行的前提。
- **undo log**：记录反向操作，用于**事务回滚**，同时为多版本并发控制提供旧版本数据。

undo 的生命周期值得单独记：插入操作产生的 undo 在事务提交后即可回收；**更新和删除产生的 undo 不能立刻回收**，因为可能还有更早的读视图需要旧版本。这就是长事务的危害机制——它让 history list 无法收缩，undo 空间持续增长，并连带拖慢刷脏与 recovery。**长事务的真实代价不在于锁，而在于它拖住了整个版本回收链。**

### binlog 与两阶段提交：两套日志为什么必须同时存在

redo log 属于**存储引擎层**，binlog 属于**服务器层**，两者不能互相替代：

- redo 是物理的、幂等的，服务于**崩溃恢复**；
- binlog 是逻辑的、按事务顺序记录的，服务于**复制与时间点恢复**。引擎对 binlog 一无所知，所以 binlog 无法用来恢复引擎内部的数据页。

既然两套日志都要写，它们就必须一致，否则会出现"主库认为事务已提交、从库收到的是另一次修改"这类撕裂。**两阶段提交**解决这个问题：提交时先写 redo 并标记为 prepare，再写 binlog，最后把 redo 标记为 commit。崩溃恢复时的判定规则是：redo 处于 prepare 且对应的 binlog 完整，就提交；否则回滚。这个规则的实质是**以 binlog 的完整性作为事务是否真正成立的裁决依据**。

## 一条 SQL 的完整路径

### 读路径：一条二级索引查询经过哪些结构

以 `SELECT name FROM part WHERE part_no = 'P1001'` 为例，先不考虑 `name` 是否在索引里：

1. 连接层接收语句，权限校验；
2. 解析器做语法与语义分析，生成解析树；
3. 优化器决定用哪个索引——这一步只看代价估算，不看数据；
4. 执行器按计划驱动存储引擎；
5. InnoDB 在 `part_no` 的**二级索引 B+ 树**上从根走到叶，找到键值，取出主键值；
6. 用主键回到**聚簇索引 B+ 树**取整行，这就是回表；
7. 每一次树查找，如果目标页不在**缓冲池**，就从磁盘读入一页（16KB），并把淘汰出的脏页交给后台刷盘；
8. 如果优化器判断接下来会顺序访问，会触发**预读**，把后续的页一起读进来。

如果 `name` 也在索引里，第 6 步可以整步省掉。整条路径上**唯一昂贵的动作是第 7 步的磁盘读**，其他几乎都是内存操作——这解释了为什么优化索引的实质是"减少页的访问次数"，而不是"减少 CPU 运算"。

### 写路径：一条 UPDATE 要改几处地方

以 `UPDATE part SET name = 'X' WHERE part_no = 'P1001'` 为例：

1. 与读路径一样完成解析与优化，拿到要修改的行；
2. 先把**旧值写入 undo log**，这是回滚与旧版本读的基础；
3. 在**缓冲池**中直接修改该页，页被标记为**脏页**——注意，此时磁盘上的数据并没有变；
4. 把修改按顺序写入 **redo log**，并写入 **binlog**，以两阶段提交的次序完成；
5. 事务提交，按配置的刷盘档位保证 redo 落盘；
6. 之后由后台线程**异步批量**把脏页写回磁盘，写之前经过**双写缓冲**防止部分写；
7. 一个 UPDATE 若改了二级索引列，还要额外维护相应的二级索引页，这些页可能不在缓冲池里——此时 **Change Buffer** 能把随机写先缓起来（前提是索引非唯一）。

把 5 和 6 分开看是关键：**事务提交的代价与数据落盘的代价被解耦了**。这也是为什么"提交成功"不等于"数据已在磁盘上的最终位置"——它只意味着日志已经足够重放这次修改。

## 索引的边界：什么时候用不上、什么时候不该建

### 最左前缀与范围截断：联合索引什么时候只用得上前半段

联合索引 `(a, b, c)` 的键是**按 a、再按 b、再按 c 排序**的。查找时只能从最左边开始连续匹配：

- `WHERE a = ?`：用得上 a；
- `WHERE a = ? AND b = ?`：用得上 a、b；
- `WHERE b = ?`：**用不上**——因为索引先按 a 排序，b 的局部有序性无法在缺少 a 的情况下利用（8.0.13 之后有一种例外：当 a 的取值种类很少时优化器可能做跳过扫描，但那是依赖统计信息的退化用法，不能当作常规设计依据）；
- `WHERE a = ? AND b > ? AND c = ?`：a 用于定位，b 用于范围，**c 无法再用于定位与排序**。

最后一条是**范围截断**，也是最常被记错的一条：范围条件之后的列并非"索引失效"，而是从"定位列"降级为"过滤条件"。它仍然可以在存储引擎层被用来过滤（减少回表），但不会缩小索引的扫描范围，`key_len` 也不会包含它。**`>`、`<`、`>=`、`<=`、`BETWEEN`、`LIKE 'x%'` 都属于范围条件，没有例外**——把 `>=` 当作能规避截断的写法是流传很广的误解。

同理，`ORDER BY` 是否能用上索引的排序能力，取决于排序列是不是索引的连续前缀。一旦中间夹了范围条件，后面的有序性就用不上了。

### 索引列上的运算：函数、隐式转换与前缀匹配

索引树是按**列的原始值**排序的。一旦查询条件里对这个值做了变换，树上的顺序就无法对应：

- **对列使用函数或表达式**：`WHERE DATE(create_time) = '2024-01-01'`、`WHERE id + 1 = 5`，都让索引无法用于定位。前者的正确写法是把变换挪到常量一侧（改成范围条件），后者的正确写法是解出 `id`。
- **隐式类型转换**：`phone` 是 `varchar`，写成 `WHERE phone = 13800138000` 时，MySQL 会把**列**转换成数字再比较，索引因此失效。字符串列必须用引号。
- **字符集或排序规则不一致的连接**：两个列做连接时若字符集不同，比较前会发生转换，同样用不上索引。
- **前缀匹配**：`LIKE 'abc%'` 可以用索引；`LIKE '%abc'` 不可以，因为树从左往右排序，右边的部分无法定位。这类需求要靠全文索引或搜索引擎解决。
- **长字符串列**：可以只对前 n 个字符建索引。代价是它**不能被覆盖**——因为索引里只有前缀，取完整值必须回表比对。前缀长度的选择靠区分度实测，而不是拍一个数。

### 区分度与优化器：索引存在不等于会被使用

优化器选择索引是**按代价**的，不是按"有没有"。它会估算两条路的成本：走索引（索引树查找 + 逐行回表，回表是随机 I/O）与全表扫描（顺序读完整张表，一次读一页可拿多行）。

当条件命中的行占比不小的时候，全表扫描的顺序 I/O 反而更便宜，优化器会**主动放弃索引**。所以"这条 SQL 没走索引"要先分清两种性质完全不同的情况：

- **用不上的**：上面那些让树序失效的写法，是设计或写法问题；
- **不划算的**：区分度太低（例如只有两三个取值的状态列）、命中比例太高，优化器算出来全表扫描更便宜。这是**正确决策**，把索引"强制"用上通常更慢。

判断依据是区分度：`count(distinct 列) / count(*)`。越接近 1 越适合建索引；取值只有个位数的列，建了多半也不会被用，只是白付维护成本。

### NULL 与索引：唯一索引为什么不唯一

前面提到允许为 NULL 的列只占 1 bit，不占数据空间。但 NULL 在索引与约束上的行为会反过来咬人。

**索引项对 NULL 是建立的**，所以 `IS NULL` 本身是可以走索引的。至于 `IS NOT NULL`——它同样**可以**走索引，只是优化器经常放弃它，因为"非空"往往命中大部分行，按代价算不如全表扫描。所以"`IS NULL` 走索引、`IS NOT NULL` 不走索引"是个过度简化的说法，正确的表述是**两者都具备走索引的能力，是否真的走由选择度决定**。

真正需要单独记住的是这条：**唯一索引允许多个 NULL**。NULL 在 SQL 里表示"未知"，而"未知"不等于"未知"，所以唯一性检查不会把两个 NULL 视为冲突。后果是：

```sql
CREATE TABLE part (
  part_no  VARCHAR(32) NOT NULL,
  model_no VARCHAR(32) NULL,          -- 本想保证"型号不重复"
  UNIQUE KEY uk_part_model (model_no)
);

-- 下面这些插入全部成功，唯一索引一条都没拦住
INSERT INTO part VALUES ('P1', NULL);
INSERT INTO part VALUES ('P2', NULL);
INSERT INTO part VALUES ('P3', NULL);
```

只要这一列可为空，**唯一索引就不保证业务唯一**：绕过它只需要插 NULL。所以"业务唯一"的落法是**唯一索引 + `NOT NULL`**两件事一起做，缺一不可。

`NOT NULL` 因此不只是数据质量的偏好，它还有第二个作用：**让优化器确切知道这一列不会有 NULL**，从而在做索引选择与统计时少一层不确定性。所以"业务唯一"和"取值必填"这两件事，最好在同一个字段定义里一次说清。

最后顺带解开一个高频疑问：`count(*)` 与 `count(列)` 结果不同不是 bug——后者只统计该列**非 NULL** 的行。另外 InnoDB 不存储表的总行数，`count(*)` 必须实际扫描，它会选择**体积最小的二级索引**来扫，以减少要读的页数；这就是为什么 `count(*)` 通常比 `count(主键)` 和 `count(普通列)` 更快。

### 什么时候不该建索引

上面讲的是"索引为什么用不上"，还有一类问题反过来：**索引建了、也用了，但整体是负收益**。

- **区分度极低**：优化器多半不会用，只剩维护成本。
- **写多读少**：每一次插入、更新、删除都要同步维护所有索引。写入密集的表上，索引数量直接决定写入延迟。
- **表本身很小**：全表扫描只需要一两次 I/O，索引没有优化空间。
- **该列频繁被更新**：更新索引列往往等价于"删一条索引项再插一条"，代价高于更新普通列。
- **长字符串列直接建全列索引**：既占空间又拖慢写入，应该考虑前缀索引或改造查询。
- **查询普遍是 `SELECT *`**：覆盖索引永远无法生效，每次都要回表，索引的收益被大幅压缩。

还有一条容易被忽略：**索引占缓冲池**。多一棵树就和数据页争夺内存，可能让原本命中的热数据被挤出。所以"加索引"不是无成本的优化动作，它同时在写入路径、存储空间和内存三处收费。
