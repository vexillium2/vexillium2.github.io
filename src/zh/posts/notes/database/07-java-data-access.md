应用层是数据库唯一的调用方：数据库侧的优化——页的大小、索引的结构、执行计划的代价、锁的范围——最终都要经过应用层的一次调用才能发挥作用，也可能被它抵消。

这篇文章按"从下往上"看这个调用方由哪些层组成、每层负责什么：**JDBC 是唯一的真实通道，连接池决定连接怎么复用与限流，事务决定一致性单元的边界与连接的持有时间，ORM 与 SQL Mapper 决定内存对象和表之间怎么映射，读写分离决定读流量走哪里**。每层都在解决一个真实问题，也都在为这个解决方式付出代价；最后一节把这些结论收成一个判据。

有一类问题贯穿全文，先点出来：**最贵的性能问题往往在数据库内部看不到**——它不表现为一条慢 SQL，而是很多条各自都很快、快到不会进慢查询日志的 SQL。

## JDBC：应用层访问数据库的唯一通道

JDBC（Java Database Connectivity）是 Java 访问关系型数据库的标准 API。它解决的问题是：数据库各有各的线协议与驱动，而应用代码不应该关心自己连的是哪一家——JDBC 定义接口，每个数据库提供实现它的驱动。**所有持久层框架，最终都落到 JDBC 上。**

它对外只有三样东西：连接、语句、结果集。

### JDBC 的三件事：连接、语句、结果集

JDBC 的 API 面很大，但职责只有三块：

- **连接（`Connection`）**：一次数据库会话。它从 `DataSource` 或 `DriverManager` 取得；生产环境里一定来自连接池。
- **语句（`Statement` / `PreparedStatement`）**：要执行的 SQL。带参数时用 `PreparedStatement`。
- **结果集（`ResultSet`）**：查询返回的行。

围绕这三样东西的获取、使用与释放，就是应用层数据访问的日常。典型写法是把它们放进自动关闭的语法块：

```java
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement("SELECT name FROM users WHERE id = ?")) {
    ps.setLong(1, userId);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            // 处理每一行
        }
    }
}
```

这段代码平淡，但它同时暴露了三个成本：**连接的获取有多贵、参数怎么传才安全、结果集怎么读才不会把内存打爆**。

### 连接的成本：为什么必须池化

建立一个 JDBC 连接要经历 **TCP 握手加数据库认证**，还要在服务端为它分配会话状态。如果每个请求都新建、用完就关，会带来三重代价：

- **网络层**：大量短连接反复握手、关闭，留下大量处于等待关闭状态的连接，占用系统资源；
- **数据库层**：为每个连接建立与销毁会话相关的数据结构，这是纯开销；
- **应用层**：连接的创建与回收产生大量短命对象，把 GC 压力推高。

这三重代价与"这条 SQL 本身快不快"完全无关。所以**连接池不是性能优化选项，是必需的**——它把"每个请求付一次建连成本"变成"整个进程付一次，之后复用"。

### 预编译语句：参数化与预编译是两件事

JDBC 有三种语句对象：普通语句、预编译语句、存储过程调用。其中**预编译语句带来两件不同的事**，值得分开看：

- **参数化**：参数通过占位符传入，不参与 SQL 文本拼接。这从根本上消除了 SQL 注入（**前提是参数永远走占位符，而不是拼字符串**）；
- **预编译**：语句模板在数据库侧解析一次、复用执行计划，省掉重复的解析成本。

这里有一个容易误解的细节：**驱动默认可能并不使用服务端的预编译**。以 MySQL 驱动为例，服务端预编译需要显式开启，默认走的是客户端参数替换。所以"我用了预编译语句，所以数据库侧一定复用了执行计划"这个推断并不成立——**参数化带来的安全性是必然的，预编译带来的性能收益是条件性的**。

还有一件相关的错：把能用参数的场景写成字符串拼接，然后再靠转义来防注入。参数化是结构性的防护，转义是文本层面的对抗，后者迟早会有遗漏。

### 三种读取模式：一次性、流式与游标

**查询返回的数据要从服务端搬到客户端，这一段的内存与时间开销不受索引和计划的影响**，因此常被忽视。

默认行为是把**整个结果集一次性读进客户端内存**。行数少时它最简单也最快；行数上万之后，问题不在数据库而在应用——内存峰值、长时间的对象分配、以及 GC 停顿。轮询或数据修复类任务经常在这里出事故。

另外两种读取模式改变的是**数据传输的粒度**：

- **流式读取**：让驱动逐行或小批地从服务端取数据，不在客户端堆积。代价是**这条连接在结果集被读完之前被独占**——如果处理逻辑很慢，连接池里的可用连接会持续减少。它适合"边读边处理、且处理不慢"的场景。
- **游标读取**：在服务端建立游标，客户端按批取回。它在服务端保存了查询状态，对复杂查询更友好，但同样占用连接与数据库侧的临时资源。

选哪种取决于**结果集的规模与处理方式**，不是性能偏好：几百行的报表用一次性读取最省事；百万行的导出必须用流式或分页，否则迟早会因为内存问题挂掉。

### 连接泄漏：池化之后为什么必然耗尽

连接池让"忘记归还"变成了一个**必然耗尽**的资源问题：池里的连接是有限的，只要有一条代码路径在异常时没归还连接，池的可用量就会以每次调用的速度减少，直到全部占满，然后**整个应用的所有数据库操作一起挂住**。

避免方式是结构性的，不是靠仔细：**用自动关闭的语法块管理资源**，让连接、语句、结果集在作用域结束时一定被释放；在池上开启**泄漏检测**（超过阈值未归还就打印持有者堆栈），让问题在耗尽之前暴露出来。

要记住的是：**池化把"连接用完即走"的容错性换掉了**。以前漏一个连接只影响那个请求，现在漏一个连接会累积成全局故障。

## 连接池：把并发截断在数据库之外

连接池位于应用与数据库之间，做的是资源管理：启动时建立一批连接，请求来了借出、用完归还，而不是每次新建。它在代码里表现为一个 `DataSource`，因此对上层完全透明。

### 池的两个作用：复用与限流

连接池做两件事，第二件常被忽略：

- **复用**：把建立连接的成本摊到多次使用上；
- **限流**：为应用对数据库的并发量设置一个**上界**。

第二件事的意义比第一件大。数据库能承受的并发是有限的，它由 CPU 核数、磁盘 IO 能力、锁竞争程度共同决定。连接池把"无限并发"截断成"可控并发"，让超出部分在应用侧排队，而不是冲进数据库把锁竞争与上下文切换推到失控。**没有池，应用能对数据库发起的并发就没上限。**

### 池大小：从数据库的承受能力反推

这是连接池最重要也最反直觉的一条：**把池调大通常会让系统更慢**。

原因是数据库的并发处理存在一个饱和点。超过它之后，每个请求都要分享 CPU 时间片、抢同一批锁、争同一份缓冲池，结果是**每个请求都变慢、总吞吐反而下降**。连接数只是把等待从应用侧搬到了数据库侧，代价还更高——因为等待期间数据库仍在为这些连接做调度。

所以正确的推导方向是**从数据库能承受的并发反推池大小**，而不是按应用的线程数或用户数去配。经验上，一个较小的池（与 CPU 核数同量级、再按磁盘并行能力上浮一些）往往比一个过大的池吞吐更高。

同时必须核对一个乘法：**所有应用实例的池大小之和，必须明显小于数据库的最大连接数**。忘了这一步，扩容应用实例就会变成打垮数据库——这是"扩容反而更慢"最常见的原因。

另外，应用线程数与池大小也应当协调：线程数远大于池，大量线程会卡在"等连接"上，问题表现为应用超时而非数据库慢；线程数远小于池，池里会有大量闲置连接白占数据库资源。

### 连接池的生命周期与保活

数据库服务端会对空闲连接设一个超时（`wait_timeout`），到期就单方面关闭它。**问题在于这个关闭是静默的**：池里的连接对象还在，应用以为它是好的，直到拿它发请求才报错——表现为"偶发的、无法复现的连接异常"。

标准做法是把池的**最大生命周期设得比服务端的空闲超时更短**，让池主动在服务端清理之前把连接换掉。同时配置保活检测（拿连接时验证、或定期验证），把已经失效的连接提前淘汰。

这两个参数的关系是**必须成立的不等式**，不是可调优的选项：`maxLifetime` 小于 `wait_timeout`（并留出余量）。调错方向的后果不是变慢，而是随机失败。

### 连接池泄漏防范

泄漏排查不要从代码审计开始，先从**数据看**：

- 池的**活跃连接数**是否只升不降——这是泄漏最直接的信号；
- 泄漏检测打出的**堆栈**指向拿连接的那一行，这才是根因位置；
- 结合数据库侧的当前连接数与状态，确认这些连接是"空闲但未归还"还是"真的在执行"。

这三者能区分开三种完全不同的病因：**泄漏**（拿了不还）、**长事务**（还不了）、**慢查询堆积**（还没来得及还）。它们都表现为"连接数打满"，但修法完全不同。

### 连接池选型：HikariCP、Druid 与 Tomcat JDBC

池的参数是通用的，产品不是。选型的问题不是"哪个更快"，而是"你需要池本身，还是需要它附带的能力"。

Java 生态里能用的池不少，真正在选的是三个：

| 产品 | 定位 | 独有能力 | 代价 |
|---|---|---|---|
| **HikariCP** | 只做池，做到最快最轻 | 约 130KB；Spring Boot 2.x/3.x 默认；带泄漏检测 | 不带监控台、SQL 防火墙、密码加密 |
| **Druid** | 池 + 监控 + 防护的全能型 | 监控台（StatView）、SQL 防火墙（WallFilter）、数据库密码加密（ConfigFilter） | 体积与开销更大，同条件吞吐低于 HikariCP |
| **Tomcat JDBC Pool** | 从 Commons DBCP 演化而来的通用池 | 与 Tomcat 同源，支持异步获取连接、语句缓存 | 需显式替换默认池；性能与功能都不占两端 |

其余的池在新项目里基本只剩"历史依赖"这一个理由：Commons DBCP2 成熟但更慢，c3p0 是 Hibernate 早期的默认实现、早已被替换，BoneCP 已停止维护。

选型判据：

- 只要一个又快又省心的池，监控交给指标系统（Micrometer / JMX / Prometheus）→ **HikariCP**；
- 需要**应用内自带 SQL 监控台、SQL 防火墙、数据库密码加密**，或已经在阿里系生态里 → **Druid**。它的价值不在池本身，在池附带的那套东西；
- 已在 Tomcat 上、想要一个不额外引入依赖的成熟池 → **Tomcat JDBC Pool**。

还有一个容易混淆的层次：`pgbouncer`、`ProxySQL`、MySQL Router 这类**数据库前面的连接代理**，是在数据库一侧做池化与路由，与上面这些**应用内连接池**不是一回事——两者可以叠加，但解决的问题不同。

## 事务：一致性单元的边界划在哪里

事务定义一个**一致性单元**：一组操作要么一起生效，要么一起不生效。在应用层，它同时定义了两件更实际的东西——**锁的持有范围，和连接的持有时间**。

### 事务边界：声明式注解失效的三种来源

用声明式事务时，"我加了注解"不等于"事务真的生效了"。失效有三种典型来源：

- **同类内部自调用**。声明式事务靠代理实现，类内部直接调用自己的方法不经过代理，事务注解被跳过。这是最隐蔽的一种，因为代码看上去完全正确。
- **方法可见性不满足代理要求**。基于代理的实现对方法可见性有要求，不符合时注解不会生效。这条的具体边界随框架版本变化，遇到"注解没生效"时应把它列入排查项。
- **异常类型不在回滚范围内**。**默认只在非受检异常时回滚**，受检异常不会触发回滚——事务已经执行了一部分，然后提交了。这类 bug 不会报错，只会留下坏数据。

第三条的正确做法是**显式声明回滚条件**，不要依赖默认行为。事务里捕获异常后"吞掉不抛"也会产生同样的后果：异常被消化了，事务却以为一切正常。

### 事务禁区：远程调用与循环

事务的生命周期等于**锁的生命周期，也等于连接的持有时间**。所以放进事务的每一件慢事，都会成倍放大成并发损失。

三条明确不该进事务的操作：

- **远程调用**：网络抖动是秒级的，而事务里的锁在等它。一次下游超时就能把上游的写并发全部拖住。
- **消息发送**：它应该发生在**事务提交之后**。在事务内发送，会出现"消息发出去了但事务回滚了"的经典不一致。
- **循环里的单条读写**：一次事务里发 N 次查询，往返成本乘以 N。这类逻辑应该改成批量操作，让一次往返处理一批数据。

与之相关的是**只读事务**：如果一段逻辑只读，明确标记为只读，框架与数据库都可能省掉不必要的开销，也不会误占写锁。

### 长事务：为什么会耗尽连接池

这是一个跨层的因果链，值得单独走一遍：

**事务不结束 → 它绑定的连接不归还 → 池的可用连接减少 → 其他请求开始排队等连接 → 应用超时。**

它的表现极具误导性：数据库侧的慢查询日志可能是干净的（每个语句都很快），CPU 与 IO 都不高，但应用大面积超时。**根因是"事务开得太多、活得太久"，而不是"SQL 太慢"。**

所以定位"连接被打满"时，一定要先分清是三种里的哪一种：泄漏、长事务、还是慢查询堆积。把长事务当成连接数不够去扩容池，只会让更多长事务同时存在，情况更糟。

## 持久层框架：JDBC 之上的两种抽象

前面三层都是过程式的：你写 SQL、拿结果集、自己把列塞进对象。当对象模型变复杂，这段映射会占据大量代码，也容易写错。持久层框架就是为了消掉这段映射——但它们对"消掉多少"给了两个不同的答案。

### 映射问题的本质：内存结构与关系模型的鸿沟

要理解为什么会有两种答案，先要理解映射问题本身为什么难。

关系数据库和内存对象是两种不同的数据表示：**表是扁平的、由外键连接；内存对象是嵌套的、由引用连接**。而且内存结构比关系模型灵活得多——继承、多态、集合、双向引用在对象侧都很自然，在关系侧无处安放。映射就是在这两种表示之间来回同步。

难在三点：

- **结构性差异**：对象的引用关系要变成外键，集合要变成多行；
- **双向修改**：两边都可能在你的控制之外被改动，映射要保证它们一致；
- **并发**：多个线程或进程同时在改数据库，而内存里的对象改动不能一直占着事务不放。

这三条决定了：**任何映射框架都只能做到"足够好"，不可能无缝**。承认这一点，就能理解围绕它的争论——框架重、性能差、抽象漏——其实是同一件事的不同侧面：**问题本身难，不是工具懒**。所以真正的问题不是"要不要用框架"，而是"把映射交给框架换来的效率，值不值它带来的代价"。

### 对象映射（JPA）：对象状态怎么持久化

JPA（Hibernate 是它的参考实现）选择把映射尽量交给框架。它管理的是**对象的状态怎么持久化**，提供的这组能力全部落在写路径上：

- **工作单元**：一次事务里对多个对象的修改，在事务结束时统一算成变更、统一落库；
- **身份映射**：同一事务里同一个主键只对应一个对象实例，不会出现两份互相覆盖的副本；
- **脏检查**：你只改对象字段，不写 UPDATE，框架对比快照算出要更新什么；
- **实体生命周期与级联**：`persist` / `merge` / `remove` 有明确语义，级联把"保存订单时一并保存明细"表达成模型关系；
- **延迟加载**：关联对象在第一次被访问时才查；
- **JPQL**：从对象模型推导出来的查询语言。

这些能力让**复杂领域模型的写路径**显著变短：一个聚合的状态流转，在 JPA 里是"改对象 + 提交事务"，在 MyBatis 里是"手动维护每条 SQL 的时机和顺序"。

**案例（交易域）**：订单聚合包含订单主表、明细表、优惠记录，三者必须在一个事务里一致。JPA 的做法是给聚合根标 `@OneToMany(cascade = ALL)`，业务代码只操作聚合根，脏检查与级联负责生成并排序所有 SQL；MyBatis 的做法是手写三条 insert 并在 service 里保证顺序与事务——**能做，但模型每变一次就要同步改 SQL**。JPA 在这里的价值不是"不用写 SQL"，而是**模型与持久化共用同一份真相**。

### SQL 映射（MyBatis）：SQL 怎么执行与结果怎么映射

MyBatis 选择只做最薄的一层：你写 SQL，它负责参数绑定和结果映射，别的都不管。因为薄，它拿到了三样 JPA 拿不到的东西：

- **SQL 是一等产物**：SQL 写在 XML 或注解里，能进 git diff、能被 review、能被 EXPLAIN 回归测试；运行期由框架生成的 SQL 必须先被日志捕获，才成为可治理的对象。
- **结果映射的完全控制**：一条复杂查询可以直接映射到 DTO 或视图对象，不必先绕进实体模型再投影出来。
- **不假装自己是领域模型**：没有工作单元、没有脏检查、没有身份映射，也就没有"延迟加载在事务外爆炸""二级缓存脏读"这一类由抽象引入的事故。

**案例（报表与检索）**：一个订单检索页要按 8 个可选条件动态拼 SQL、join 四张表、分页并映射成 `OrderSearchDTO`。用 JPA 会退化成一大段 `nativeQuery` 字符串或一堆 `Specification`；用 MyBatis 是 `<if>` / `<where>` 动态 SQL 直接映射到 DTO，SQL 就在文件里，索引怎么走、要不要加覆盖索引，看一眼就知道。这里的优势是**控制权与可治理性**，代价是 SQL 要自己写、自己维护。

围绕 MyBatis 还有两个常和它一起出现的东西：**MyBatis-Plus** 在 MyBatis 之上叠一层约定，用 `BaseMapper` 提供通用 CRUD、`LambdaQueryWrapper` 拼类型安全的条件、分页插件、自动填充、逻辑删除，设计口号是"只做增强不做改变"；**MyBatis-X** 是 IntelliJ IDEA 插件，根据表结构生成 Entity / Mapper / Service、在接口方法与 XML 之间一键跳转、提供 SQL 补全，它不是运行时框架，是开发效率工具。要注意的是，MyBatis-Plus 把一部分 SQL 重新藏了回去——一个 `selectById` 背后的 SQL 你看不见，省掉样板代码的代价是控制力下降。

仓库地址：[mybatis/mybatis-3](https://github.com/mybatis/mybatis-3)、[baomidou/mybatis-plus](https://github.com/baomidou/mybatis-plus)、[baomidou/MyBatisX](https://github.com/baomidou/MyBatisX)、参考书 [mybatis-book/book](https://github.com/mybatis-book/book)。

### 两种抽象的代价：N+1、懒加载与不可见的 SQL

抽象换来的效率，代价集中在几处。

**N+1 查询**。这是应用层最典型的性能陷阱，也是最难在数据库侧看到的一类。看一个典型形态：查出一批订单，然后遍历它们取每个订单的客户名。如果关联属性是**懒加载**的，实际发生的 SQL 是**一条语句查出 N 个订单，然后每条订单各发一条语句查它的客户**——总共 N+1 次往返。

它的危害不在任何单条语句：每一条都走了主键索引，都很快，**都不会出现在慢查询日志里**。它的成本全在**往返次数**上：N+1 次网络往返、N+1 次解析与优化、N+1 次取连接。N 是 100 就是 101 次往返，而它本可以是一次连接查询。

```java
// N+1：一条语句查出订单，再为每个订单各查一次客户
List<Order> orders = orderMapper.selectByUser(userId);              // 1 次往返
for (Order o : orders) {
    o.setCustomerName(customerMapper.selectById(o.getCustomerId())  // N 次往返
            .getName());
}

// 显式批量查询：先收集主键，一次取回，再在内存里组装
Set<Long> ids = orders.stream().map(Order::getCustomerId).collect(toSet());
Map<Long, Customer> byId = customerMapper.selectByIds(ids).stream()
        .collect(toMap(Customer::getId, c -> c));                   // 1 次往返
orders.forEach(o -> o.setCustomerName(byId.get(o.getCustomerId()).getName()));
```

四类对策，按适用性排序：**一次连接取回**（用连接抓取 join fetch 把关联在一条语句里带出来；一对多关联被连接时结果会膨胀，去重与分页都要重新考虑）、**批量抓取**（把懒加载按批合并，一次取一批关联，例如每 100 个主键发一条查询，把 N+1 降到 1 + N/100）、**显式批量查询**（先收集关联 ID，再用一次带 `IN` 的查询取回，在应用侧组装）、**用缓存承接**（关联数据变化不频繁时放进本地或分布式缓存，把问题从"查询次数"变成"缓存命中率"，代价是引入失效逻辑）。检测手段比对策更重要：**开启 SQL 日志，统计单个请求产生的语句条数**。N+1 不会自己暴露，必须主动去数。

**懒加载与事务边界**。懒加载把"取数据"推迟到**属性被访问的那一刻**，带来两个后果：访问发生在事务之外时会失败（会话已关闭，框架无法再发起查询，于是抛异常——很多"偶发报错"来自这里，事务内没用到的属性在事务外被序列化时被触发）；访问发生在事务之外但会话尚未关闭时会反复申请连接（每次懒加载都是一轮独立的取连接、查询、归还，一个逻辑操作因此产生多次连接往返）。处理方式有两种取向：**要么在事务内一次性把需要的数据取全**并明确声明抓取策略，**要么把实体转成不含懒加载的传输对象再往外传**。

**批量操作与分页**。框架的抽象会掩盖两类操作的真实成本：批量更新与删除有时只是"在循环里逐条执行"，实际是 N 条语句、N 次往返，真正的批量应该落成一条语句或分批的多值语句；分页通常伴随一条额外的计数查询，深分页在 SQL 层的代价——要取出并丢弃前面所有行——不会因为换成框架的分页组件而消失。判断方法还是同一个：**看日志里实际生成了几条什么 SQL**。

**不可见的 SQL**。框架的收益是开发效率，代价是 **SQL 不再由你直接控制**。代价本身没问题，问题是很多人不知道代价发生在哪里。所以有一条几乎是硬性的工程要求：**框架生成的 SQL 必须可观测**——开发与测试环境**打开语句日志**，让每条生成的 SQL 都看得见；生产环境让这些 SQL **进入慢查询统计**，而不是绕过它；对关键接口统计**每个请求的语句条数**，把一个隐性的性能指标变成可监控的指标。

### 框架选型与混用

JPA 和 MyBatis 解决的不是同一个问题：**一个管对象状态怎么持久化，一个管 SQL 怎么执行与结果怎么映射**。所以选型不是二选一，而是先分清你要做的事落在哪一边。

三个问题基本能定位：

1. **你的主要工作是"沿对象图改状态"还是"写一条特定的 SQL"？** 前者 JPA，后者 MyBatis。
2. **复杂 SQL 占查询的比例？** 低于两成 → JPA 兜底、复杂处退回原生 SQL；高于四成 → SQL 优先。
3. **表结构由谁先行？** 实体先行、模型频繁迭代 → JPA 顺；DDL 先行、表已存在 → MyBatis 顺。

还有一条判据值得单列：**SQL 是否需要被当作需要评审和回归的一等产物**。需要（强 SQL 治理、CI 里有 SQL 门禁）→ MyBatis 结构上更顺；不需要、更看重开发速度 → JPA。这条判据取决于团队是否把 SQL 当一等产物，而不取决于有没有专职 DBA。

因为两者在不同层，混用不是"装两套框架"，真实形态有三种：

- **同栈高层 API + 手写 SQL**（最常见，严格说不算混框架）。`JpaRepository` 兜 CRUD、`@Query` 兜复杂查询；或 MyBatis-Plus `BaseMapper` 兜 CRUD、手写 XML 兜复杂查询。案例：绝大多数 Spring Boot 业务系统。
- **JPA 与 MyBatis 并存，按读写分**（CQRS 味道）。写模型（聚合、命令、事务）走 JPA；读模型（列表、报表、DTO）走 MyBatis 或 jOOQ，直接映射 DTO、绕过实体。案例：订单与账户聚合用 JPA 写，订单检索、流水查询、对账用 SQL 优先读。**红线**：两套栈要共用连接，写路径混用最容易翻车（JPA 一级缓存看不到 MyBatis 的写入、flush 顺序难控制），所以**写只走 JPA、读才走 MyBatis，同一事务里不要两边都写**。
- **按服务或按团队分**（组织级混用，最普遍）。不是同一个应用里混，而是不同微服务各选各的：交易域 MyBatis、用户或内容域 JPA。案例：国内互联网基本如此，一个公司内部两套栈并存是常态。

所以正确的问法是先分清要解决的是**对象状态持久化**还是**一条 SQL 的执行与映射**：前者只有 JPA 能给，后者只有 SQL 优先能给；两者都要的系统，自然落成"写用 JPA、读用 SQL 优先"，或"CRUD 用框架、复杂查询手写"。

## 读写分离与多数据源

单库能力到顶时，下一步是把读流量分出去，或者引入第二个数据源。这两件事都会把前面几层的假设打破，所以单独说。

### 读写分离的三种实现位置

读写分离把读流量分到从库，实现位置有三种，代价不同：

| 位置 | 做法 | 主要代价 |
|---|---|---|
| 驱动层 | 在 JDBC 层按语句类型路由到不同数据源 | 对应用透明，但路由规则只在当前进程内有效 |
| 代理层 | 应用连代理，由代理转发到主库或从库 | 对应用完全透明，多一跳网络与代理的运维成本 |
| 应用层 | 用注解或 AOP 显式指定走主库还是从库 | 控制力最强，但**每个开发者都要记得标注** |

三种都能用，选择依据是**团队愿意把复杂性放在哪里**：驱动与代理把复杂性集中在一个组件里，应用层则把它分散到每次调用上。

### 主从延迟：写后立刻读为什么读不到

只要用了从库，就必须面对一件事：**复制是异步的，延迟总是存在**。典型症状是"我刚保存，再查却查不到"。

这属于 **read-your-writes** 一致性的破坏——用户写入后立刻去读，应当能读到自己刚写的数据。标准补偿有几档：

- **写后一段时间内强制走主库**。实现简单，代价是把一部分读压回主库，需要设定时间窗口；
- **按标记路由**。写入后把这个请求（或这个会话）标记为"必须读主"，直到它成功读到自己的写；
- **在同一次业务操作内不切从库**。凡是与写属于同一逻辑单元、且需要看到该写的读，直接走主库。

要划清的边界同样重要：**事务内的读必须走主库**。如果在事务里把读路由到从库，会出现"事务内的读看不到本事务的写"这种更严重的错乱。

### 多数据源与事务的边界

引入第二个数据源时，最先要接受的事实是：**本地事务无法跨越两个数据源**。这不是实现问题，是本地事务的定义决定的——它的事务上下文属于某一个连接。

由此产生几种选择，代价逐级上升：

- **避免跨源写**：让每个事务只写一个数据源，跨源的一致性改由**最终一致**获得（本地事务写业务数据加一张待发送记录表，事务提交后再异步投递，由重试保证送达）。
- **两阶段提交**：由协调者保证原子性，代价是持锁时间变长、性能下降，且需要额外组件。
- **补偿型事务模式**：把一个分布式事务拆成若干本地事务加补偿动作，代价是**必须为每一步写出补偿逻辑**，并且要接受中间状态对外可见。

选择依据是业务对**中间状态**的容忍度，而不是对"强一致"这个说法的偏好。**能接受最终一致就不要引入两阶段提交**——后者带来的性能与可用性代价，通常在业务上换不到对应的收益。

## 边界：什么下沉到数据库，什么留在应用层

前面几节讲的都是应用层这一侧。最后把这些层的结论收成一个方向性问题：**一件事该在数据库做，还是留在应用做。**

### 应该下沉的：过滤、排序、聚合、约束

有一条判据可以覆盖大部分情况：**如果一件事能在数据库里用一条 SQL 表达，就应该在数据库里做。**

- **过滤**：把条件写进 `WHERE`，让索引有机会用上。把整表读进应用再筛选，等于主动放弃索引、放弃下推、放弃只读需要的那部分数据。
- **排序**：只有数据库知道索引的有序性，应用侧排序意味着先把数据全部搬过来。
- **聚合**：计数、求和、分组由数据库做，只返回结果行；应用侧做聚合意味着把明细全部搬运一遍。
- **约束**：唯一性与存在性尽量下沉，因为**应用层的校验会被绕过**——数据修复脚本、手工 SQL、另一个服务都会绕过它。

### 应该留在应用层的：跨服务聚合与业务规则

反向也要说清，否则会走向另一个极端：把所有逻辑塞进存储过程。以下三类更适合留在应用层：

- **跨服务的聚合**。数据在不同的服务或数据库里，数据库的 join 做不到，只能由应用组装。
- **需要外部系统的判断**。调用风控、调用配置中心、调用第三方，"是否允许下单"这类规则依赖数据库之外的信息。
- **频繁变化的业务规则**。规则用代码表达可以测试、评审、快速发布；写进存储过程会让它的变更流程与代码脱节。

所以边界不是"哪边更强"，而是**数据在哪里、变更频率如何、以及谁负责它的测试**。

### 判据：扫描行数与返回行数的比值

把上面这些结论压缩成一个可以在代码评审和监控里用的判据：

**核对每一次查询的"扫描行数"与"返回行数"的比值。** 扫描很多、返回很少，说明过滤没有下沉；扫描很多、返回也很多，说明**分页或聚合没有下沉**——这两类都能在数据库侧被消除，而现在它们消耗的是网络、应用内存与 GC。

这条判据的好处是它不依赖任何框架知识，也不需要在评审时读懂 SQL：**只要看一个比值，就能判断这段数据访问是在利用数据库，还是在绕过它。** 而它恰好也是那些"数据库侧看不到的性能问题"最可靠的检测手段——因为它们不会变成慢 SQL，只会变成很多条快 SQL。
