需求描述是用自然语言写的，关系模式是用键和外键写的，两者之间隔着一整套转换。这套转换里有几步是**不可逆的设计决策**：一只宠物是不是弱实体、一条联系是完全参与还是部分参与，都会决定后面哪些业务规则能被数据库强制、哪些必然落空。

所以概念设计要回答两个问题：**从这段需求里能读出哪些实体、联系和约束**，以及**读出来的东西映射成关系模式之后，还剩多少能被强制**。第二个问题比第一个更容易被忽略，但它才是设计质量的真正分水岭。

## 概念模型：实体、属性与联系

### 三个基本元素与它们的判据

概念模型只描述业务世界里有什么，与具体数据库无关。它由三个元素构成：

- **实体**：需要独立记录的对象；
- **属性**：描述实体的性质；
- **联系**：实体之间的关联。

实体与属性的划分经常被当成"看命名习惯"，其实有一条可操作的判据：**它需要被独立标识吗？**

以"诊所地址"为例。如果地址只是诊所的一个描述——不用单独查询、不用被别人引用、没有自己的生命周期——它就是**复合属性** `(city, street, postcode)`。反过来，如果多个诊所共用一个地址、而且地址本身还需要维护（比如要记录它的联系人、它的营业时间），那它就该升级成**实体**，需要自己的标识。

判据的另一面是：**把一个东西做成实体，代价是你要给它发一个键，并且所有引用它的地方都要改成外键。** 所以"升级为实体"不是一个免费的更规范的写法，它是一次有成本的设计决策。

### 联系的属性为什么挂不到任何一方实体上

有一类属性不属于任何一方实体，只属于**联系本身**。供应链场景里的典型例子是价格：一个零件可以由多个供应商供货，价格随供应商不同。这时：

- 价格不属于**零件**：同一个零件有多个报价；
- 价格不属于**供应商**：同一个供应商对不同的零件报不同的价。

**一个属性只能存一个值**，所以价格在两边都放不下——它只在"零件 + 供应商"这一对确定之后才有唯一值。这类属性就是联系的属性。

这也是多对多联系必须独立成表的**第一层原因**：不是因为"两边都存不下对方的键"，而是因为**联系自己的属性没有归宿**。即使联系上没有属性，多对多仍然要独立成表（否则一侧要存一个集合，而属性不能存集合），但"没有归宿的属性"是更直接的证据。

### 多值属性：ER 阶段就要决定升级为实体

**多值属性**是同一个实体上同时存在多个值的属性。例如"一位兽医有多个专业方向"，或者"一位主人有多个联系电话"。

它在关系模式里**根本放不下**——列是单值的。所以必须在概念设计阶段就把它处理掉，方式有两种：

| 处理方式 | 结果 | 适用 |
|---|---|---|
| 升级为独立关系 | `VetSpecialisation(empID*, specialisation)`，主键是实体键加值列 | 值的集合本身不是实体，不需要自己的标识 |
| 升级为实体并建立 M:N | 如果"专业方向"还需要自己的属性（编码、认证机构），它就是实体 | 值本身有生命周期 |

这里要区分两个容易混的形状：

- **多值属性**表达的是"一个实体的多个值"，独立成表时主键是 **（实体键, 值）**；
- **多对多联系**表达的是"两个实体之间的多个配对"，独立成表时主键是 **（键1, 键2）**。

判断方法是问一句：**这两个值之间有关系吗？** 兽医的专业方向和资格证书之间如果有独立关系，那是两个多值属性；如果"A 医生在 B 专业上持有 C 证书"是三元事实，那就是 M:N 之上的多元联系。

## 弱实体、部分码与识别联系

### 弱实体的判据：编号在谁的范围内重新开始

**弱实体**是没有独立完整标识的实体，它只能靠"上级实体的键 + 自己的部分码"来定位。

判据也只有一条，而且非常可操作：**它的编号在谁的范围内重新开始？**

- 宠物编号在**主人**内部是 1、2、3……两位主人可以都有 1 号宠物 —— 宠物是**相对于主人**的弱实体；
- 就诊编号在**宠物**内部是 1、2、3……两只宠物可以都有 1 号就诊 —— 就诊是**相对于宠物**的弱实体。

反过来，如果需求改成"每只宠物有一个全局唯一的档案号"，宠物立刻就是**强实体**。所以：

**弱实体是被编号方式决定的，不是被语义强弱的直觉决定的。**

这条判据的实际价值在于它反过来也成立——**你选择了编号方式，就等于选择了要不要弱实体**。而弱实体的建模会影响后面能表达哪些约束：一旦给了全局编号，"在主人在内连续编号"这条业务规则就再也没地方表达了。

### 部分码与识别联系

弱实体用来标识自己的那个属性叫**部分码**（也叫鉴别码），它只在上级实体内部唯一。

弱实体与它的上级实体之间的联系叫**识别联系**，上级实体叫**标识实体**。识别联系有三个固定性质，不需要额外判断就能写出来：

- 它一定是 **1 : N**（一个标识实体对应多个弱实体）；
- 弱实体一侧一定是**完全参与**（弱实体不能没有上级）；
- 弱实体一侧用**双矩形**表示，识别联系用**双菱形**表示。

**存在依赖**是弱实体的实质：上级不存在，下级就不能存在。映射到关系模式之后，它体现为**级联删除**——删掉主人，他的宠物记录必须一起消失。这也是弱实体在工程上的真正价值：**它把"这条记录属于谁"变成了结构的一部分，而不是应用层的一句约定**。

### 嵌套弱实体：键为什么越拉越长

弱实体本身还可以是另一个弱实体的标识实体。这时键会**逐层叠加**：

```
Owner ──(ownerID)──┐
                   │ 1
                ⟨Owns⟩ 识别联系
                   │ N
             Pet ──(ownerID, petNo)──┐
                                    │ 1
                              ⟨HasTreatment⟩ 识别联系
                                    │ N
                       Treatment ──(ownerID, petNo, treatmentNo)
```

- Pet 的键是 `(ownerID, petNo)`；
- Treatment 的键是 `(ownerID, petNo, treatmentNo)`。

治疗的部分码 `treatmentNo` 只在某只宠物内部唯一，而宠物又只在某位主人内部唯一，所以治疗的键必须把**整条链上的部分码全部带上**。漏掉 `ownerID` 是这类题最常见的错误——它会让"两位主人的 1 号宠物的 1 号就诊"撞成同一个键。

## 基数与参与约束

### 基数比与参与约束：上限与下限要分别读

这两个概念经常被合并成一句"几对几"，而它们回答的是不同的问题：

- **基数比**回答**上限**：一个实例最多能关联多少个实例。取值是 1:1、1:N、M:N。
- **参与约束**回答**下限**：一个实例**必须**关联至少一个吗。取值是**完全参与**（至少一个）与**部分参与**（可以零个）。

需求里的两句话，差别就在这个下限上：

| 需求描述 | 基数 | 参与约束 |
|---|---|---|
| 每个诊所雇佣**一名或多名**兽医 | 1:N | 诊所侧**完全** |
| 一个诊所**可以**雇佣兽医 | 1:N | 诊所侧**部分** |

**两句的表结构完全一样**（都是 1:N，外键放在兽医一侧），但它们的约束能力完全不同：前一句有一条"诊所不能没有兽医"的规则，后一句没有。而这条规则**在关系模式里表达不了**。

参与约束在 ER 图里用**双线**表示：连接到完全参与的那一侧画双线。

### 从题干里读出参与约束的信号词

需求描述不会直接写"完全参与"，但它的用词是高度规律的：

| 信号词 | 参与约束 |
|---|---|
| one or more / at least one / exactly one / must | **完全**参与 |
| zero or more / may / can / if any | **部分**参与 |
| 完全没有提及 | 按**部分**处理，并把它写进假设 |

最后一行是考试和评审里最容易被扣分的地方：**题目没说的，你要主动声明成假设**，而不是默默按某一种理解画图。一条"一个诊所可以暂时没有注册客户"的假设写出来，比画得再工整都更有价值。

### 双边完全参与的 1:N：不改变表结构，但会留下管不住的规则

有一种组合很少见但确实存在：**一个 1:N 联系的两侧都是完全参与**。

例如"每个诊所雇佣一名或多名兽医"，同时"每位兽医恰好在**一个**诊所工作"：

- 诊所侧完全参与（至少一名兽医）；
- 兽医侧完全参与（恰好一个诊所）。

它的表结构毫无特殊之处——仍然是 1:N，外键加在兽医一侧并声明为非空。**但两侧的"至少一个"和"恰好一个"命运不同**：

- 兽医侧"恰好一个"：靠外键非空，**可以**强制；
- 诊所侧"至少一名"：需要"另一张表里至少有一行指向我"，**任何键与外键都做不到**。

所以参与约束的结论可以浓缩成一句：**它不改变表结构的形状，但决定哪些业务规则在实现之后会落空。** 概念设计阶段标出完全参与，价值不在画图，而在于提前知道哪里会留一个必须由应用补上的洞。

## 从 ER 图到关系模式：映射规则

### 强实体与 1:N：外键放在"多"的那一侧

- **强实体**映射为一个关系，它的键就是主键。
- **1:N 联系**把"1"侧的键作为外键，放进**"N"侧**的关系里。如果 N 侧是完全参与，外键加非空约束；如果 N 侧是部分参与，外键允许为空。

反过来的做法——在"1"侧存一个集合——在关系模型里根本无法表达，因为属性是单值的。这条规则不是偏好，是模型的硬限制。

### 1:1：外键放在完全参与的那一侧

1:1 联系的外键可以放在任意一侧，选择依据是**哪一侧完全参与**：

- 放在完全参与的那一侧，外键可以声明非空，顺带把"必须有"这条规则表达出来；
- 外键要加**唯一约束**，否则 1:1 会退化成 1:N；
- 如果两侧都完全参与，也可以考虑**直接合并成一张关系**，避免多一次连接——这是"分表还是合表"里少见的可以有明确答案的一种情况。

### M:N 与弱实体：为什么一个必须独立成表、一个必须借上级的键

这两种构造的映射方式不同，原因也不同：

**M:N 必须独立成关系**。两侧的键都无法单独确定一行（同一个零件对应多个供应商），所以必须由两者的组合来定；联系自身的属性也只有这里能放。

**弱实体不能独立成关系**。它自己的部分码不足以定位一行，所以它的关系里必须**包含标识实体的键**，而这个键同时承担两个角色：**它既是外键，也是主键的一部分**。这是弱实体映射唯一需要记的一点——外键进了主键。

映射汇总：

| ER 构造 | 映射结果 | 键与外键 |
|---|---|---|
| 强实体 | 一个关系 | 实体的键 → 主键 |
| 1:N | 不新增关系 | "1"侧的键 → "N"侧的外键 |
| 1:1 | 不新增关系 | 外键放在完全参与的一侧，加唯一约束 |
| M:N | **新增一个关系** | 两侧键的组合 → 主键；联系的属性放这里 |
| 弱实体 | 一个关系 | 标识实体的键 → 外键，**并成为主键的一部分** |
| 多值属性 | 新增一个关系 | 实体键 + 值 → 主键 |

判断"要不要新增关系"的口诀很简单：**看这个构造能不能落在已有关系的单值属性上。** 能落下的（1:N、1:1）就不新增；落不下的（M:N、多值属性）就必须新增；弱实体是特例，它落在自己身上，但必须借用上级的键。

### 标准映射的副作用：循环外键

标准映射有一条容易踩的坑：**当 1:1 的两侧互相引用时，会形成循环外键。**

设想两个关系：诊所里存 `managerEmpID` 指向兽医，兽医里存 `clinicID` 指向诊所，而两个外键都非空。这时**第一行都插不进去**——插诊所需先有兽医，插兽医需先有诊所。

三条出路：

- **把那个 1:1 保留为独立关系**（例如 `Manages(clinicID, empID)`）。插入顺序变成 诊所 → 兽医 → 管理关系，循环被打断。这是最干净的做法，代价是多一张表。
- **让其中一个外键可为空**，分两步插入，之后再补上引用。
- **用延迟约束**，把外键检查推迟到事务提交时。不是所有数据库都支持。

这个例子的意义超出了 1:1 本身：**标准映射保证的是"逻辑上正确"，它不保证"插入顺序能成立"。** 拿到一个规范答案之后，还要再问一句"这个模式真的能写进数据吗"。

## 约束表达力的边界

### 外键永远管不了"至少一个"

外键的方向是单一的：它保证**"多"侧的每一行都指向一个存在的"一"侧**。它做不到反向的事——**保证"一"侧至少有一个"多"侧指向它**。

所以下面这些规则，用键和外键一个都表达不了：

- 每个诊所至少有一名兽医（删掉最后一名就违规）；
- 每位主人至少有一只宠物（删掉最后一只是违规）；
- 每个诊所至少有一次就诊记录。

`CHECK` 也救不了：它只能看**当前这一行**的值，不能对另一张表做存在性查询。

### 部分码的连续性与顺序

"宠物编号为 1、2、3……"看起来只是一句话，其实是三条独立的约束，而且它们的可表达性完全不同：

| 子约束 | 能否用键/外键表达 |
|---|---|
| 编号在主人内部唯一 | **能**——主键 `(ownerID, petNo)` 就保证了 |
| 编号从 1 开始、**连续无空洞** | **不能** |
| 就诊编号的大小顺序与就诊日期一致 | **不能** |

第二条和第三条都涉及"值之间的序列关系"，而键与外键只处理"值是否已经存在"，不处理"值应该是什么"。**唯一约束保证不重复，不保证不跳号。**

### 跨联系的子集约束：什么时候能改造成外键

还有一类约束跨越了两条联系。典型例子是"诊所的负责人必须是**在该诊所工作**的兽医"——它同时涉及"雇佣"和"管理"两条联系。

按标准映射，负责人存在诊所表、雇佣关系存在兽医表，是**两个彼此独立的外键**，数据库完全不知道它们应该一致，所以表达不了。

但它和前面两条不同：**它可以被改造成外键可表达的**。做法是利用一个已经在需求里的事实——每位兽医恰好在一个诊所工作，所以 `empID` 在雇佣关系里是唯一的。于是把雇佣关系独立出来：

```
WorksAt(empID 主键, clinicID 外键)   -- 每位兽医恰好在一个诊所工作，所以 empID 即主键
Manages(clinicID 主键, empID 外键)   -- clinicID 作主键：每个诊所恰好一位负责人
       外加复合外键 (empID, clinicID) → WorksAt(empID, clinicID)
```

被引用的 `(empID, clinicID)` 需要有唯一约束；由于 `empID` 本身已经是主键，这个组合天然唯一，只需把它显式声明出来。因为 `empID` 在 `WorksAt` 里唯一，这个复合外键会把"负责人所在诊所"钉死为"该兽医工作的诊所"，约束就落到了外键上，不需要触发器。

这个对比值得单独记住：**"外键表达不了"要先分清是模型表达力不足，还是这一次映射没设计好。** 最小基数是前者（外键的方向性决定的），跨联系的子集约束往往属于后者。

### 表达不了时用什么：四种机制与它们的代价

| 机制 | 能表达的范围 | 代价 |
|---|---|---|
| `CHECK` | 只能约束**本行**的列之间关系 | 跨表、跨行一律无解 |
| **触发器** | 跨表、跨行、序列关系都能写 | 逻辑隐蔽、拖慢写入路径、难调试；有些数据同步工具会默认禁用触发器 |
| `ASSERTION` | SQL 标准里可以写任意断言 | **主流 DBMS 都没有实现**，只能停留在纸面 |
| **应用层事务 + 行锁** | 理论上没有限制 | 可以被绕过：数据修复脚本、手工 SQL、另一个服务都会绕过它 |
| **巡检 SQL** | 不阻止违规，只事后发现 | 违规数据已经产生过；它是兜底，不是约束 |

这张表里有一条规律：**约束越靠近数据，越难被绕过，但表达力越弱。** 键与外键最靠近数据，但只能表达"存在性"和"唯一性"；应用层表达力最强，但任何能写数据的人都能绕过它。

由此得到设计时的分工原则：

- 能用键与外键表达的，**绝不下沉到应用层**；
- 表达不了的，**明确写出"由谁负责校验"**，并配一条巡检把已经产生的违规数据捞出来；
- 需要触发器时，先确认它带来的写入路径代价和排查难度是否可以接受——很多团队最终宁可用应用层加巡检，也不愿意在写入路径上挂一个隐形的触发器。

## 练习：兽医诊所链

### 题目

一家连锁兽医诊所要建立数据模型。公司运营多个诊所；一个诊所由 clinicID 标识，有地址（city、street、postcode）和一个电话号码。每个诊所雇佣一名或多名兽医；一位兽医由 empID 标识，有姓名、专业方向和薪水，且**恰好在一个**诊所工作。每个诊所由**恰好一位**兽医管理，这位管理者必须是**在该诊所工作**的兽医之一，而一位兽医最多管理一个诊所。

主人**恰好在一个**诊所注册。一位主人由 ownerID 标识，有姓名、电话和邮箱。一位主人拥有一只或多只宠物；宠物在**各自主人内部**编号为 1、2、3……（两位主人可以都有 1 号宠物），每只宠物有名字、物种和出生日期。一只宠物可以被就诊多次；某只宠物的就诊记录在**该宠物内部**按时间顺序编号为 1、2、3……，记录日期、诊断和费用，且每次就诊由**恰好一位**兽医执行。一次就诊可以使用零种、一种或多种药品；一种药品由 medCode 标识，有名称和单价，就诊中使用该药品的**数量**也要记录。

(a) 列出实体类型及其属性与键。对每个弱实体类型给出它的部分码、识别联系，并指出标识（拥有者）实体类型。
(b) 列出联系类型及其基数比与参与约束，画出 ER 图。说明你做的每一个假设。
(c) 给出标准 ER→关系模式映射产生的关系模式。主键加下划线，外键加星号，并说明哪些联系类型会成为独立的关系以及为什么。
(d) 给出本应用中**两条**仅靠键与外键约束无法强制实施的约束，并说明需要什么机制。

### (a) 实体类型、属性与键

| 实体类型 | 键 | 属性 | 弱实体信息 |
|---|---|---|---|
| **Clinic** | clinicID | clinicID, city, street, postcode, phone | — |
| **Veterinarian** | empID | empID, name, specialisation, salary | — |
| **Owner** | ownerID | ownerID, name, phone, email | — |
| **Medication** | medCode | medCode, name, unitPrice | — |
| **Pet** | `(ownerID, petNo)` | petNo, name, species, dateOfBirth | **弱实体**；部分码 `petNo`；识别联系 **Owns**；标识实体 **Owner** |
| **Treatment** | `(ownerID, petNo, treatmentNo)` | treatmentNo, date, diagnosis, fee | **弱实体**；部分码 `treatmentNo`；识别联系 **HasTreatment**；标识实体 **Pet** |

注意 Treatment 的键：它的部分码只在宠物内部唯一，而宠物本身又是弱实体，所以键必须带上整条链。

### (b) 联系类型、基数与参与约束

| 联系 | 参与实体 | 基数 | 参与约束 | 联系上的属性 |
|---|---|---|---|---|
| **Employs** | Clinic — Veterinarian | **1 : N** | Clinic **完全**；Veterinarian **完全** | — |
| **Manages** | Clinic — Veterinarian | **1 : 1** | Clinic **完全**；Veterinarian **部分** | — |
| **RegistersAt** | Clinic — Owner | **1 : N** | Clinic **部分**；Owner **完全** | — |
| **Owns**（识别） | Owner — Pet | **1 : N** | Owner **完全**；Pet **完全** | — |
| **HasTreatment**（识别） | Pet — Treatment | **1 : N** | Pet **部分**；Treatment **完全** | — |
| **PerformedBy** | Veterinarian — Treatment | **1 : N** | Veterinarian **部分**；Treatment **完全** | — |
| **Uses** | Treatment — Medication | **M : N** | 两侧均**部分** | **quantity** |

**图（边列表形式，每条边是一个联系）**：

```
Medication  ──M──⟨Uses {quantity}⟩──N── Treatment
Treatment   ──N──⟨HasTreatment⟩识别──1── Pet
Pet         ──N──⟨Owns⟩识别────────1── Owner
Owner       ──N──⟨RegistersAt⟩─────1── Clinic
Clinic      ──1──⟨Employs⟩─────────N── Veterinarian
Veterinarian──N──⟨PerformedBy⟩─────1── Treatment
Clinic      ──1──⟨Manages⟩─────────1── Veterinarian
```

画成正式 ER 图时，`Owns`、`HasTreatment`、`PerformedBy` 的"多"侧以及 `Employs` 的"多"侧、`RegistersAt` 的"多"侧都要画**双线**（完全参与）；`Pet` 与 `Treatment` 用**双矩形**；`Owns` 与 `HasTreatment` 用**双菱形**。

**假设**：

1. 地址是 Clinic 的**复合属性**，不是独立实体——它没有独立标识，也不需要被单独维护。
2. `phone`、`email` 是**单值**属性（题目用单数）。若允许多个号码，它们是多值属性，需要各自独立成关系。
3. `specialisation` 每位兽医只有一个值。
4. Clinic 在 RegistersAt 中是**部分参与**——一个诊所可以暂时没有注册客户（题目只约束了 owner 一侧）。
5. Clinic 在 HasTreatment 中是**部分参与**——可以没有任何就诊记录。
6. Veterinarian 在 PerformedBy 中是**部分参与**——可以没有执行过任何就诊。
7. Medication 在 Uses 中是**部分参与**——可以有从未被使用过的药品。
8. 姓名不保证唯一，只有题目给定的键能标识实体。
9. 一只宠物只属于一位主人，一次就诊只属于一只宠物（由"在各自范围内编号"隐含）。
10. 药品按 medCode 全局标识，不区分诊所。

### (c) 关系模式

标记：<u>下划线</u>为主键，`*` 为外键。

**Clinic**(<u>clinicID</u>, city, street, postcode, phone, managerEmpID*)
　`managerEmpID` → Veterinarian(empID)，**UNIQUE**（一位兽医最多管一个诊所），**NOT NULL**（每个诊所必有负责人）

**Veterinarian**(<u>empID</u>, name, specialisation, salary, clinicID*)
　`clinicID` → Clinic(clinicID)，**NOT NULL**（完全参与）

**Owner**(<u>ownerID</u>, name, phone, email, clinicID*)
　`clinicID` → Clinic(clinicID)，**NOT NULL**（完全参与）

**Pet**(<u>ownerID*</u>, <u>petNo</u>, name, species, dateOfBirth)
　`ownerID` → Owner(ownerID)；主键 `(ownerID, petNo)`；删除 Owner 时级联删除

**Treatment**(<u>ownerID*</u>, <u>petNo*</u>, <u>treatmentNo</u>, date, diagnosis, fee, empID*)
　`(ownerID, petNo)` → Pet；`empID` → Veterinarian(empID)，NOT NULL；主键 `(ownerID, petNo, treatmentNo)`；删除 Pet 时级联删除

**Medication**(<u>medCode</u>, name, unitPrice)

**Uses**(<u>ownerID*</u>, <u>petNo*</u>, <u>treatmentNo*</u>, <u>medCode*</u>, quantity)
　`(ownerID, petNo, treatmentNo)` → Treatment；`medCode` → Medication；主键为四列组合

**哪些联系成为独立关系**：只有 **Uses**。它是 M:N——任何一侧的键都无法单独确定一行，而 `quantity` 是联系的属性，在两边的实体关系里都没有位置。

其余六个都不独立成关系，但分三类处理：**Employs / RegistersAt / PerformedBy** 是 1:N，把"1"侧的键并入"N"侧；**Owns / HasTreatment** 是识别联系，把标识实体的键并入弱实体并成为主键的一部分；**Manages** 是 1:1，把外键并入完全参与的一侧（Clinic）并加唯一约束。

**这里有一个标准映射没解决的问题**：`Clinic.managerEmpID` 与 `Veterinarian.clinicID` 互相引用，两个外键都非空，于是**第一行插不进去**。工程上的做法是把 Manages 保留为独立关系：

**Manages**(<u>clinicID*</u>, empID*)
　`clinicID` → Clinic(clinicID)（作为主键，每个诊所恰好一位负责人）；`empID` → Veterinarian(empID)，**UNIQUE**（一位兽医最多管一个诊所）

插入顺序变成 Clinic → Veterinarian → Manages，循环被打断。

### (d) 键与外键表达不了的两条约束

**约束一：每个诊所至少有一名兽医。**

外键只能保证"兽医指向一个存在的诊所"，无法保证"诊所至少有一名兽医指向它"。所以可以建一个没有任何兽医的诊所，也可以把某诊所的最后一名兽医删除或调走。

这说明**最小基数（存在性）约束**是键与外键方向性决定的盲区。

**需要的机制**：在 Veterinarian 的删除与更新上写**触发器**，拒绝"删掉最后一个"的操作；或用 SQL 标准的 `ASSERTION`（标准有，主流 DBMS 不实现）；或放在应用层的同一事务里，先用 `SELECT ... FOR UPDATE` 锁住父行再删。三者都不如外键那样不可绕过，所以实践中很多团队选择接受它，改用**巡检 SQL** 定期查出"没有兽医的诊所"。

**约束二：宠物与就诊的编号必须从 1 开始、连续、且就诊编号与就诊日期同序。**

模式能保证 `(ownerID, petNo)` 与 `(ownerID, petNo, treatmentNo)` 唯一，但唯一约束**只保证不重复，不保证不跳号**：插入 `petNo = 7` 而在 `2` 处空缺是合法的；删掉 `petNo = 2` 留下空洞也是合法的。更隐蔽的一条是就诊编号与日期的顺序一致性——完全可能插入编号为 3 但日期更早的就诊。

**需要的机制**：编号必须在应用层事务内分配（读取当前最大值加一，同时靠行锁或唯一索引防并发）；"连续"与"同序"只能靠触发器或应用逻辑维护。另一种做法是放弃存储编号、在查询时用窗口函数动态生成序号——但那等于取消了这条约束，而不是表达它。

### 这道题埋了哪些陷阱

1. **Treatment 的键要带整条链**。漏掉 `ownerID` 会让两位主人的"1 号宠物的 1 号就诊"撞键。嵌套弱实体的键是逐层叠加的。
2. **弱实体由编号方式决定，不由语义直觉决定**。题目说"在各自主人内部编号"，这就是唯一原因。如果改成全局唯一档案号，Pet 立刻是强实体。
3. **Employs 是双边完全参与的 1:N**。这很少见，但题目确实这么写（诊所至少一名兽医、兽医恰好一个诊所）。漏掉任一侧的完全参与，都会丢掉一条约束。
4. **只标基数、漏标参与约束**。"one or more" 与不写，表结构相同，约束能力不同。这是 (b) 最常见的失分点。
5. **Manages 上有一条子集约束**（负责人必须是该诊所雇员）。ER 图里要标出它，标准映射表达不了它；但如前面所说，它**可以被改造成外键可表达**——这是 (d) 之外的一个加分点。
6. **只有 Uses 独立成关系**。很多人会把 Manages 也做成表——那是可选的工程改进（用来打破循环外键），不是标准映射的产物。
7. **(d) 只答"CHECK 不行"是不够的**，题目要求说明**需要什么机制**，所以要给出触发器、断言、应用层事务、巡检这几种替代方案及各自的代价。
8. **模式能建出来 ≠ 能写进数据**。如果按标准映射把 `managerEmpID` 放进 Clinic，循环外键会让第一条记录插不进去。
