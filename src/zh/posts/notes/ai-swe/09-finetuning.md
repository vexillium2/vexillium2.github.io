这一章用应用工程师的视角讲微调，而不是把损失函数再推一遍。**微调改的是模型参数，本质是改写"这个模型默认擅长什么"**——它不像提示词那样每次请求注入，而是把期望的行为烙进参数里，成为新的先验。因此微调在生产里有三个不同于训练实验室的特征：成本前置（要攒数据、花 GPU、做回归评估）、不可逆（调一次坏，下游所有 Prompt 全部跟着变）、以及最容易被低估的遗忘风险（专精领域时把通用能力调没了）。全章主线是工程闭环而不是算法演进：先回答"到底要不要微调"，再依次讲决定微调上限的 SFT 数据工程、决定成本与破坏面的参数高效微调与偏好对齐、把流程跑起来的工具链、以及最容易翻车的"调完怎么验证怎么上线"，最后落到 Embedding、Rerank、蒸馏三类最常见的任务微调案例。两句话贯穿全章：**数据决定上限，配方决定下限，评估决定你敢不敢上线**。具名模型与工具按"机制与取舍"描述，易过时的榜单与价格按"该看什么维度"处理。

## 一、何时微调：先分清"知识缺口"与"行为缺口"

### 微调改的是行为分布，不是给模型补知识

模型表现不达预期，第一步永远是归因：问题是"它不知道"还是"它做不到"。前者是知识缺口——事实性、私有信息、时效内容不在参数里，给上下文或接检索就能补，因为这类知识会过期、要溯源，放在可替换的数据侧比烙进参数便宜得多；后者是行为缺口——模型"知道"但行为不稳定：输出不符合协议与格式、话术不像目标领域、工具调用总填错参数、该收敛时继续绕。**提示词能临时给出期望，微调改变的是"默认行为"**：示例和指令只在一段上下文里锚定行为，输入一变、上下文一长就回落；微调把行为变成先验，让模型在没有提示词托底时也稳定地按这个方式行动。判断"该不该微调"，本质是判断问题属于哪一种缺口。

### 升级到微调的四个信号

- **同一类偏差反复出现，且示例外推无效**。把典型反例和正例写进 Prompt 只能短期压制，换一批输入又复发——说明问题出在行为先验，不在即时上下文。
- **输出必须服从严格协议**。工具调用 schema、领域报文、JSON 契约这类"格式稳定性"诉求，靠 Prompt 约束会偶尔破格，微调能把格式服从率顶上去。
- **预算要求换成更小的模型**。让 7B 级模型承载 70B 级模型的某个具体分布（领域问答、特定格式转换），用领域数据微调把"性价比模型"推到主场景，是微调最扎实的 ROI 场景之一。
- **手里有真实任务分布**。能拿到线上对话日志、bad case、真实产出样本，也就有了把"期望行为"批量成数据的基础——没有数据源，讨论微调没有意义。

### 四个"不该微调"的反例

- **用参数装私有知识**。把知识库灌进参数要付训练成本，换来的是会遗忘、会过期、无法溯源的知识副本，更新一次重训一轮。可检索、会更新的知识放数据侧；微调只负责"拿到知识后怎么组织行为"。
- **目标模糊或样本过少**。微调的下限不是"有没有几十条样例"，而是"数据能不能代表你要的行为分布"。数据太少时，SFT 只会把通用分布往少量样本的噪声方向拉，症状是复读、模板化、一遇分布外输入就崩。
- **问题根本不在模型**。工具参数拼错、检索链路脏、后处理逻辑缺失时去微调，等于给产品缺陷打补丁——换个场景就失效，而且让真正的缺陷更难被定位。
- **内容时效强、更新频繁**。微调承担"常新知识"的更新频率，会把每次发布都变成一次训练 + 回归 + 上线的长周期，性价比远低于把高频变化留在数据侧。

### 成本与数据门槛的现实刻度

一次微调的真实成本要按整条链路算：GPU 时间只是其中一项，还有数据收集与清洗的人天、通用 + 领域的双份回归评估、以及上线后的监控与回滚预案。数据量没有普适数字，但经验刻度可作参考：**风格、格式、协议类"行为迁移"，几百到几千条高质量示范就能看到显著变化；想让模型在某个领域的复杂推理或事实覆盖上真正变强，数据量与质量要求高一个量级**。自测方法是先收敛 bad case：连续收集一两周真实失败样本，如果能从中抽出稳定、可复现的行为模式，才有资格谈微调；抽不出来，说明问题在别处。

## 二、SFT 数据工程：上限在数据，不在训练脚本

SFT（监督微调）干的事是让模型模仿一批示范的条件分布。损失函数与训练脚本各框架都差不多，**模型最终长什么样，几乎全由喂进去的数据决定**。这一节把数据工程里最值钱的几个点讲透。

### 质量 > 数量不是口号，是三件可执行的事

- **坏样本的污染效率远高于好样本的增益效率**。模型拟合重复模式极快，混入一条错答、前后矛盾或脱离任务分布的数据，它会被当成分布学进去，症状是"平时好好的，一遇到训练集里那类输入就复读坏答案"。清洗不是可选项：去重（含近似重复）、修错、剔除标注噪声，优先级高于"再多造一万条"。
- **有效信息是"覆盖面"而不是"条数"**。十条同构样本的边际增益趋近于零，真正有用的是多样性：任务类型、难度梯度、输入长度、格式形态、语言与领域术语的覆盖。堆量堆不出覆盖，覆盖要刻意设计。
- **分布决定泛化方向**。合成数据可以快速放大规模，但若全由单一来源生成，会自带同质化与偏差（自肥），微调出来"像生成器、不像真实用户"。

### 三个数据来源按真实度排优先级

- **线上真实日志**最接近任务分布，是首选底料——但要清洗"失败的示范"：对话里模型答错又被纠正的片段，需要人工或自动把回答改写成正确示范，否则会把错误行为也学进去。
- **人工标注与改写**质量最高、成本最高，适合做小批量高质量种子（几百条）去定义"期望行为到底长什么样"。
- **大模型合成**负责扩规模与造难度梯度（构造更长尾的样本、更难的负例），但必须配合人工抽检与去重，且只适合合成"示范"，不适合合成"事实"——事实错误会被学生照单全收。

工程上常用的闭环是：**真实日志定分布、人工种子定行为、合成补覆盖，上线后再把新 bad case 回流进下一版训练集**。微调数据不是一次性产物，而是一条随线上反馈持续更新的回路。

### 格式模板：训练怎么拼，上线就得怎么拼

SFT 最容易翻车的不是训练本身，而是**模板不一致**。训练样本必须用与线上推理完全相同的对话模板渲染：system 段怎么放、角色标记（user / assistant）怎么写、特殊 token 的位置、是否带 BOS/EOS。训练时图省事用"裸拼接"，上线走官方 chat template，两边 token 分布对不上，微调学到的行为就"搭不上车"——离线指标好看，线上对话却表现得像没训过。**模板一致性要用同一段渲染代码在训练与推理两侧分别做校验来保证，而不是靠肉眼比对**。

另一个常被忽略的工程细节是 **loss masking**：一般只对 assistant 回复部分的 token 计算损失，user/system 内容不参与。如果对所有 token 一起算 loss，模型学到的任务变成"复述输入"，生成时倾向重复用户的话或把整段上下文背出来。用现成框架时，务必核对训练配置里的 mask 范围，而不是相信默认值。

### 去污染与切分：别让评测"开卷"

把接近线上问题的样本塞进训练集、又拿同源的样本当评测集，得到的分数是"背题分"而不是能力分。**训练 / 验证 / 测试三份切分要在内容层面去重**（近似重复也算），测试集要"锁死"：不进训练、不做人工修错的参考、不被合成流程复用。数据版本与训练配置（seed、采样比例、清洗规则）要随模型一起留档，否则复现与回归都无从谈起——这套纪律和代码的版本管理是同一件事。

## 三、参数高效微调：LoRA / QLoRA 与"怎么改最划算"

### 为什么默认不碰全参微调

全参微调更新每一个权重，工程上有三笔账不划算：**显存**——除了参数本身，还要存梯度与优化器状态（Adam 系要 2 份动量，通常是参数量的数倍开销）；**部署**——每个任务一份全量权重副本，切任务等于换模型文件；**破坏面**——全局更新最容易把预训练积累的通用能力冲掉，领域专精后通用能力掉点，多数发生在全参场景。所以生产里默认从参数高效微调（PEFT）起步，全参只在数据量足够大、确需彻底改写行为、且能承担回归成本时才考虑。

### LoRA：把"任务修改"压进低秩子空间

LoRA 的思路是冻结原始权重 W，只学一个低秩增量 ΔW = B·A（A 把输入压到 rank=r 的中间维度，B 再映射回去），训练时只更新 A/B 两个小矩阵。它的前提假设是：**单个任务的适配修改主要落在少数几个方向上，可以被低秩矩阵近似**。这个假设在数据规模不大时近乎成立，也是 LoRA 能"以极小的可训练参数量逼近全参效果"的原因；数据量极大、任务极复杂时低秩假设会碰到表达上限，但与全参的差距通常是可接受的代价而非质变。

LoRA 有两个参数最容易让人照抄出问题：

- **rank（r）**决定适配器容量。r 太小表达力不足（格式/风格这类浅层行为 r=8~16 往往够用），r 太大不是线性变好，而是容量浪费 + 过拟合风险上升（领域覆盖广或多任务时再考虑 32~64 量级）。**正确做法是把 r 当超参做步进实验，用验证集对比，而不是抄一篇博客的固定值**。
- **alpha 与缩放**：合并时增量按 alpha/r 缩放，alpha 控制注入幅度。改了 r 却不调 alpha，等效于静默改学习率刻度。任何超参变动后都要重跑回归，而不是只看训练 loss。

推理侧 LoRA 有一个隐蔽优点：**可以把增量合并回原权重（merge），线上零额外延迟**；代价是合并后 base 与 adapter 绑死成一个文件，base 模型一升级，adapter 要重训或至少复验。不 merge、以 adapter 方式部署则要管理 base 与 adapter 的版本配对与并发加载——这两条路各有版本管理账，别默认其中一种不需要。

### QLoRA：把基座压到 4bit 再训练

QLoRA 是在 LoRA 上加一层"基座量化"：把冻结的预训练权重量化到 4bit（NF4），反传时反量化回 bf16 算 LoRA 梯度，配合分页优化器进一步省显存，让更大的模型能在单卡或消费级显卡上微调。它把"训练显存"压到最低，换来两个代价：**数值精度损失与训练速度下降**。对多数 SFT 任务影响可忽略，但对吃精细数值的任务（数学推理、长代码）可能掉点——这种差别要**用多次采样和独立验证集对比确认，而不是看一两个样例下结论**。还要分清两件事：QLoRA 的 4bit 是**训练手段**，训完 merge 回 bf16 权重再部署是常规路径；把 adapter 直接并进 4bit 权重会叠误差，属于该避免的操作。

### 方法对比与实操反例

| 方法 | 可训练参数 | 训练显存 | 通用能力风险 | 典型适用 |
|---|---|---|---|---|
| 全参微调 | 100% | 高（含优化器状态） | 最高 | 数据量大、需彻底改写行为 |
| LoRA | 约 0.1% ~ 1% | 中 | 低 | 默认首选，行为/格式/领域适配 |
| QLoRA | 约 0.1% ~ 1% | 最低 | 低（基座 4bit 有精度损耗） | 显存受限时的 LoRA 替代 |

实操里三个高频反例：**小数据上全参微调**（几个 epoch 就把训练集背下来，通用能力大幅滑坡，还误以为"效果很好"）；**只加 rank 不加数据**（容量变大但没新信息可学，净增过拟合）；**用训练 loss 当效果指标**（loss 降只说明拟合了训练集，与任务效果好坏是两回事，效果要回到独立评估看）。

## 四、偏好对齐：从"会模仿"到"按偏好作答"

### SFT 与对齐的分工

SFT 教模型模仿示范里的条件分布，学的是"示范的平均行为"，不区分示范之间的好坏层次。偏好对齐则显式引入"哪些回答更被偏好"的信号——目标不是让模型更像某条示范，而是让整体倾向偏向被偏好的方向（格式更稳、话术更合口味、更会拒绝越界、推理更可复核）。应用视角下的流水线是**先 SFT 把行为学会，再做偏好对齐把行为倾向掰正**：多数领域任务止步于 SFT；只有涉及安全边界、风格取舍、"答案之间的排序"时，对齐才值得上。直接拿偏好数据跳过 SFT 训练，模型连基本行为都还没定型，对齐效果会很不稳。

### DPO：用离线偏好对做隐式奖励优化

DPO 的工程价值在于把对齐成本降了一个量级：它不需要单独训练奖励模型，也不需要在线采样做强化学习，直接用离线的**偏好对（chosen / rejected）**隐式完成奖励优化，训练稳定、实现简单，适合应用团队自己跑。省事不等于省心，DPO 的坑全在数据与超参上：

- **偏好标注的可靠性决定上限**。chosen / rejected 的标签必须一致可靠，标注者主观分歧大的噪声会直接进损失——先做标注一致性校验，比调 beta 更值钱。
- **模型会走捷径：学长度、学模板，而不是学好坏**。偏好对里 chosen 普遍更长或格式更花哨时，模型学到的是"写长、写得像那么回事"而非"答得对"。构造偏好对时要刻意控制长度、格式等无关变量，让 pair 之间的差异只落在真正想优化的维度上。
- **beta 与过拟合**。beta 控制"偏离 SFT 的代价"，过大学不动、过小漂移太远；对齐在偏好集上过拟合的症状是模板化开头、空话套话变多。兜底手段是保留通用能力评估，别只盯对齐指标。

反例值得记住一个：**用"更长 = 更好"这类廉价自动规则生成偏好对，训练出来的模型会变成话痨**——它忠实地拟合了你的偷懒信号。

### GRPO：让"可判分"的任务自己教自己

GRPO 面向的是另一类场景：**任务结果可以程序化判分**——数学题有确定答案、代码能跑测试、格式能规则校验。它不再需要人类偏好对或奖励模型，而是让策略对同一问题多次采样，用**组内相对优劣**估计每个样本的 Advantage，再配合 KL 约束做策略优化：模型在"反复试 + 知道哪些对"中把推理准确率顶上去，非常适合把数学、代码这类"答案可验证"的任务调到高水准。

它的工程风险也来自"可判分"本身：**reward hacking**——模型会去钻奖励函数的空子（输出貌似符合格式、把相似答案重复刷一遍提高命中、迎合判分的表面特征而不是真正解题）。防法是把奖励函数设计得难钻空子、采样温度保证组内多样性、并用**与奖励函数无关的独立测试集**做最终验收——用奖励函数自己给自己打分，等于开卷考试。

### 三类方法的定位

| 方法 | 训练信号 | 需要的额外组件 | 主要风险 | 适用场景 |
|---|---|---|---|---|
| SFT | 正确示范 | 无 | 模仿噪声、复读坏样本 | 行为/格式/领域适配 |
| DPO | 离线偏好对 | 偏好标注 | 长度/模板捷径、过拟合偏好集 | 有可靠偏好信号的对齐 |
| GRPO | 规则/程序判分 | 打分器 | reward hacking | 答案可验证的推理任务 |

## 五、训练工具链：框架是"配方执行器"，不是"炼丹免责声明"

### 工具链替你省掉的是流程样板

自己从零搭一条微调流水线，要手写的样板很多：数据集加载与模板渲染、dataloader 与分布式启动、优化器与调度、训练中评估与 checkpoint 管理、训练后的 adapter 合并与量化、再接推理服务。主流训练框架把这串流程集成成标准路径：**数据集配置 → 模板渲染 → 训练（SFT/DPO/LoRA）→ 评估 → 导出/合并 → 部署**。它们的定位是"配方执行器"：你负责数据与评估这两件真正决定效果的事，框架负责让配方被正确、省力地跑完。

### 三个具名样本的机制差异

- **LLaMA-Factory**：覆盖面最均衡的代表——支持主流开源模型与全参/LoRA/QLoRA/DPO 等方法，用数据集配置文件声明数据与字段映射，训练后提供导出与合并，命令行与 WebUI 双入口，社区资料多，是多数人入门微调的第一站。
- **ms-swift**（ModelScope 系）：走"训练 + 推理 + 评测一条龙"路线，与魔搭模型库及国产模型生态联动，多模态支持较全，训练完能直接衔接 vLLM 部署，适合在阿里系/境内环境里做完整闭环。
- **unsloth**：专注把 LoRA/QLoRA 训练本身做"更快、更省显存"（底层算子与显存优化），API 兼容主流训练接口，适合算力紧张、想在消费级显卡上把更大模型跑起来的人；它刻意不做重平台功能，取舍在"单点性能极值"而非"全流程覆盖"。

### 挑选工具链按五个维度自测

具体版本与能力随时间演化，选型别背说明书，按维度现场核：

1. **方法与格式覆盖**：你要的 SFT/DPO/GRPO 是否都支持？数据集格式约定是否与你手头数据的形状匹配？
2. **模板与 mask 透明度**：框架是否自动套官方 chat template？**能否预览渲染后的训练样本、能否核对 loss mask 只落在 assistant 段**——这两点决定"离线对、上线崩"类事故会不会被框架默认值藏起来。
3. **导出与部署衔接**：adapter 合并、量化导出、推理服务（vLLM 一类）是否顺畅，还是训练完还要自己再写一遍转换脚本。
4. **评估钩子**：能否挂自己的评测集做训练中/训练后评估，而不是只能看框架默认演示集。
5. **生态与维护**：社区活跃度、issue 响应、与底层库（transformers 等）的版本绑定是否激进。

反例永远集中在"把工具当免责声明"：**一键默认配置跑完，不看渲染样本、不核对 mask、用框架自带的演示指标当效果结论**——工具只负责执行，数据对不对、效果好不好、模板一致不一致，责任仍在你自己身上。

## 六、微调后的评估与部署：把"调好了"和"调坏了"同时测出来

微调的评估只有一个原则：**效果是"分维度同时测"测出来的，不是"领域指标"一个数测出来的**。微调特有的评估问题不是通用方法论，而是三类训练自带的病——过拟合到训练集、灾难性遗忘、量化把微调效果抹掉。围绕它们建三组信号。

### 过拟合检测：loss 在降，不代表模型在变好

训练 loss 持续下降而独立评估不再提升甚至恶化，是过拟合最直接的信号。除此之外有两个微调特有的症状值得主动去测：

- **背诵检测**：抽查模型对训练集样本的复现能力——若能把训练集里的句子逐字背出来，说明模型在"记忆"而不是"学会"。做法是拿训练集样本与同分布的改写样本对比提问：记忆型模型在训练集原题上答得好，一改措辞就崩。
- **模板化信号**：回复格式整齐划一、开头套话变多、内容同质化，是模型在拟合训练集的"表面结构"。这类退化领域分可能不降反升，单看领域指标发现不了。

### 灾难性遗忘：专精的同时，通用能力在悄悄掉

领域微调最常见的隐性代价，是把模型的通用能力（指令遵循、常识推理、安全拒绝、代码/数学、多语言）冲掉一部分。检测方法只有一条：**建一张"领域 + 通用"双份的能力看板，训练前后与每次迭代都全量跑**，把通用分当发布门禁，而不是出了问题才补测。缓解手段按破坏面从小到大排列：**参数高效微调（LoRA 本身就在隔离破坏面）→ 数据混合（领域与通用按比例混训）→ 学习率与早停控制 → 全参慎用**。反例是"只测领域分就上线"：线上通用问答崩了好几天，团队还以为是模型供应商的问题。

### 与基座的 A/B：微调效果要能归因

微调效果好坏的判定必须回到对照：**微调版 vs 基座/上一版，在相同 Prompt、相同采样参数下多次采样对比**。生成有方差，单看几个样例下结论会误判；报告至少分四维：目标任务质量、格式/协议正确率、通用能力回归、安全与拒绝合规。任何一次超参、数据或方法变动，都重跑这张对照，而不是信任"看起来变好了"。

### 部署：模型是发布物，要走代码那套纪律

- **量化与微调的关系最容易在部署环节翻车**。微调后权重再量化（GPTQ/AWQ/GGUF 一类），量化误差可能恰好抹掉微调学会的边缘行为——**量化后的模型必须重跑关键评估**，并与未量化版本做抽样 A/B，而不是假设"量化只损失一点点"。
- **版本与可复现**：权重、adapter 与 base 的配对、数据版本、训练 seed 与超参要一起留档；模型版本与代码版本同库管理。
- **发布流程**：构建模型制品 → 自动化评估门禁（领域 + 通用 + 合规三张表过线）→ 灰度放量 → 线上监控（输出长度、格式合规率、拒绝率、用户反馈采样）。**微调版回复分布漂移是常态，把它当监控信号而不是事故**：漂移的 bad case 回流进下一版训练数据，形成"评估 → 回流 → 再训练"的闭环。

## 七、三类特殊任务微调：Embedding、Rerank 与蒸馏

生成式对话的微调逻辑不能直接搬到检索与排序模型上——它们的"行为"不是说话，而是排序。这三类任务各自的训练目标与坑，比算法细节更值得记住。

### Embedding 微调：改的是"距离"，不是"话术"

Embedding 模型把文本映射成向量，微调的目标是**让相关对在向量空间里更近、不相关对更远**，效果最终看检索质量（recall、MRR），不看生成质量。数据工程是它的胜负手：

- **困难负样本决定上限**。只用"不相关的随机文档"当负样本，模型很快退化成学词面匹配。真正逼出语义理解的是困难负样本：在召回 TopK 里表面相关、实际不相关的文档——模型必须学会"为什么它们不该被召回"。没有困难负样本的 embedding 微调，收益会明显缩水。
- **向量空间一变，索引必须重建**。微调后 embedding 分布整体位移，旧索引里的向量全部失效——**重新向量化并重建索引是部署的必要步骤**，不是可选项。
- **两个反例**：只看训练分布内 query 的 recall，得到的是背题分；模型把大量输入挤进向量空间的窄区域（表示退化），用相似度分布监测而不是只信排行榜。

### Rerank 微调：给精排装"领域耳朵"

Rerank 用交叉编码器把 query 与候选文档拼接打分，比双塔 embedding 更准、但不能预先索引，只用于对召回 TopK 精排。它的训练有一个隐蔽的**分布错配陷阱**：推理时精排吃的是召回阶段带噪声的候选，训练时若只喂"金标相关文档 + 随机负样本"，模型学到的判别口径与线上输入对不上。正确做法是在训练中注入**模拟召回结果**——从召回器 TopK 里采正负样本（包括假阳性与难负例），让训练分布贴着推理分布。领域术语越重（医药、法务、代码），通用 Rerank 越容易把"看似相关、实则无关"判错，微调收益越明显；评测用候选集上的 nDCG/MRR，而不是单点准确率。

### 蒸馏：用小模型继承大模型的分布

蒸馏的场景是成本与约束驱动的：用大模型（或 API 服务）当 teacher，把它的知识与行为迁移给更小、更快、可私有化的 student。应用工程里最常见的形态是**离线蒸馏**：teacher 批量产出示范或标注，student 用这些数据做 SFT/KD。两个必须记住的边界：

- **蒸馏不能超过 teacher**。student 的天花板是"teacher 的能力 × 数据能传递的信息量"，期望小模型比大模型老师更强，属于违背因果。学生容量有限时，与其灌大而全的数据，不如聚焦一个窄任务分布把它学透。
- **teacher 的错误会被放大**。teacher 的幻觉与过度自信会作为"标准答案"被 student 学走，合成数据侧的一致性过滤与人工抽检不能省；文本标签之外，软标签/中间层蒸馏能多传一些信息，但实现与调参成本高，收益要先量化再投入。

### 把全章收束成一条判断线

微调作为工程可控与否，取决于三个要素是否错配：**数据（分布对不对）、配方（PEFT/对齐方法匹配目标吗）、验证（领域 + 通用 + 合规的评估纪律有没有）**。任务类型不同，这三要素的口径也不同——生成式任务看行为、Embedding 看检索、Rerank 看排序、蒸馏看与 teacher 的相对差距，而高频反例几乎全是错配：拿生成思路调检索模型、用领域分掩盖遗忘、期望蒸馏出 teacher 没有的能力。回到最初的归因就能避开大多数坑：**先分清是知识缺口还是行为缺口，再决定要不要微调、调哪个组件、用什么配方、拿什么尺子量**。
