## 前言：三个判断

> 这份笔记回答的不是"AI 能干什么"，而是"手上这件活，该不该交给它、交成什么、用多重的流程做"。

关于 AI 使用的文章，多数在回答"它能干什么"。这个问题每半年要重答一次，因为工具在换。更耐用的问法是另一组：手上这件活，落在能力的哪一侧？就算能做，该交付成什么形态？该用多重的流程做？

这三个判断决定了后面所有具体做法。它们不保证做对，但能挡掉大部分"用了 AI 反而更慢"的情况。

### 边界：能力是锯齿状的

2023 年，Dell'Acqua 等人在 BCG 做了一次随机对照实验。758 名顾问，两组任务：一组落在模型能力圈内，是创意、分析、写作、说服这类活；另一组落在圈外，是必须交叉核对表格与访谈记录才能成立的商业案例。

圈内，用 GPT-4 的一组完成任务多 12.2%、快 25.1%、质量高 40%。圈外，用 AI 的一组给出正确答案的概率低了 19 个百分点。

还有第三个结果：即使答错，用 AI 的那组在表达质量上的得分依然更高。

这三条合起来，就是"锯齿状前沿"。模型能力不随任务难度平滑下降，它在看起来差不多的任务之间突然断裂。判断一件事能不能交，靠"这题难不难"没用，得靠"这类活有没有被可靠完成过"。

失败的样子也因此变了。模型被训练成输出连贯、自信、结构完整的文本，它很少给出明显的垃圾，更多是给出一段读起来没问题的东西：引用格式正确但来源不存在，代码结构漂亮但边界没处理，方案逻辑自洽但前提是错的。**表达流畅不是证据**，一段文字越顺，越需要单独确认它的事实层。

三种成本决定了这件事值不值得交出去。

| 成本 | 低 | 高 |
|---|---|---|
| 验证成本 | 能跑测试、能复算、能对着原文核 | 只能靠专家判断，或只能等上线 |
| 上下文成本 | 通用知识，一句就懂 | 大量内部事实、历史决策、隐含约定 |
| 返工成本 | 改一处即可 | 牵一发动全身，要重做整条链路 |

三项都低，直接交。有一项高，就要在设计流程时单独处理：验证成本高就加人工 gate，上下文成本高就先补上下文资产，返工成本高就拆小步。

有三样东西不能外包。**领域事实**——模型不知道你司的组织结构、历史包袱、老板的偏好；**判断**——它可以列选项，但不能替你承担选错的后果；**责任**——它可以起草，签字的是人。

数据边界也要单独说。能进对话框的是公开资料、脱敏样本、已发布内容、自编测试数据；不能进的是客户个人信息、密钥凭证、未公开代码与合同、内部财务数据。"私有部署"解决的是数据不出域，不解决模型会不会把敏感信息写进日志、缓存或下游工具调用。它是成本问题，不是安全承诺；合规要看整条链路的数据流，不是部署方式这一个选项。

### 形态：同一答案的四种交付

Karpathy 在 2026 年 10 月给过一条输出形态的阶梯，每一级都比上一级更好读：用 ASD-STE100 写、画成图、输出 HTML、做成解释视频。

ASD-STE100 是航空维护手册用的受控英语，1979 年起源于欧洲航司的要求：让非母语的机械师读手册时不误读。它的规则很硬——句子短、一个词一个意思、动词形式受限。Karpathy 自己也只说"到 80% 的程度"，因为完整规范会把手感磨没。收益是歧义少：一句话只表达一个意思，读者不用猜代词指谁。

图表的收益是关系可见，代价是条件与例外。一张图讲不清"如果 A 且非 B，则 C"。HTML 的收益是自包含、可交互、可打印，代价是多一层构建与样式。视频的收益是带宽，代价是修改：改一句话要重录，改一个镜头要重渲染。

这条阶梯有个容易忽略的地方：它解决的是理解带宽，不是正确性。Karpathy 那条帖子附了一张 ASD-STE100 的一页速查图，有人逐条对照规范后发现，图里有三条词典规则是错的。这不是嘲讽，它恰好演示了阶梯本身的风险：**格式越顺滑，错误越容易被相信**。

所以选形态的问题不是"哪个更高级"，而是"这个形态允许读者检查什么"。

| 读者要做的事 | 合适的形态 |
|---|---|
| 复算数字、对比多组数据 | 表格 |
| 判断流程、找缺失环节 | 图 |
| 演示交互、反复查阅 | HTML |
| 对外讲解、传播 | 视频 |
| 逐条执行 | 清单或 runbook |

### 任务形态：三个开关

METR 在 2025 年用"人类做这件事要多久"来度量模型能力：50% 成功率下的任务时长中位数，过去六年大约每七个月翻一倍。数字会变，但它给了一个实用的提问方式：这件事能不能在一次会话里收口？

能，就是短程：一次做完，最后验一次，失败模式是"看起来对"。不能，就是长程：需要 spec、检查点、上下文管理和中途的人工 gate，失败模式是"越走越偏"。

第二个开关是 skill。满足三个条件才值得写：会重复、输入稳定、有明确的验收标准。缺一个，写成提示词片段就够了。写成 skill 的成本不在写，在维护——模型一升级，里面写死的参数和工具名就可能失效。

第三个开关是 eval。判断标准是：错了的代价大，而且判断不稳定。两个条件同时成立，才值得建评测集。代价大但判断稳定，写一条检查规则即可；判断不稳定但代价小，人工看一眼更便宜。

| | 短程 | 长程 |
|---|---|---|
| 低风险 | 直接做，最后看一眼 | 分步做，中途人工盯 |
| 高风险 | 加一道可执行的校验 | 上管线，设 gate 与基线 |

读、做、造这三类任务的分工，就落在这张表上。

## 一、判断方向

方向错了，后面每一步都在放大错误。判断阶段的工作不是让 AI 给答案，是让它把问题问清楚。

### 1.1 让 AI 反过来问你

最常见的失败不是"它不会做"，是"它做出来的不是你要的"。你以为自己说清了，看到产出才发现差得很远。这类错在人和人协作里同样常见，只是 AI 不会在动手前追问一句"你确定吗"。

所以第一步是把它放到提问的位置上。一次只问一个问题，每个问题自带一个推荐答案和简短理由；先把一个分支问到底，再开下一个；能从代码、文档、已有材料里读到的，就不要问人。问题类型可以固定成几组：范围（什么在内、什么明确在外）、依赖（这件事依赖哪些还没定义的东西）、失败模式（先坏的是哪里）、被否掉的替代方案（为什么不是另一种做法）、成功标准（怎么知道成了）、可逆性（什么难以撤销）、归属（出问题谁负责）。

Claude Code 的官方最佳实践把这件事写成了标准动作：给一个最小的描述，让它反过来面试你，问技术实现、交互、边界情况、取舍，一直问到没有新问题，然后写一份自包含的 spec——点名涉及的文件与接口，写清 out of scope，结尾放一条端到端的验证步骤。写完 spec 之后**换一个新会话执行**。

换会话这一步容易被省掉，但它是有意义的：追问会话里装满了讨论过程、被否掉的方案、你的犹豫；执行会话只需要 spec。把两者混在一起，执行时会被一堆无关的上下文拖慢，也容易把"讨论过的选项"当成"已定的结论"。

追问的产出必须是文件，不是"聊清楚了"的感觉。感觉没法交接，spec 可以。

它的边界也要说清：这是投入之前用的动作。投入之后再用，它就变成了对既有方案的辩护——你已经写了两千字，它再问"要不要考虑另一种做法"，你只会烦。

### 1.2 产品判断：三层

产品类判断有一套现成的分层，来自 pm-skills 那类 skill 库：一个总控负责分诊和路由，一组执行型 skill 负责把模糊描述变成可评审的文档，一组顾问型 skill 负责在"该不该做"上提供不同视角。

执行型包括 PRD 写作、评审预演、优先级打分、埋点设计、实验设计、复盘。顾问型包括 Cagan 的四大风险、Torres 的机会树、俞军的用户价值公式，以及 Mom Test、Story Mapping、Build Trap 这几套方法论。

选择哪一层，看问题卡在哪。**不知道该不该做**，用顾问层，让分歧提前出现；**决定要做但没想清**，用执行层，把异常流、埋点、非功能需求补上；**多个需求抢资源**，用优先级工具，把打分标准显式化。

一个常见的误用是拿顾问层去解决执行问题。顾问层产出的是视角和分歧，不是决定；你会在一次评审里收到四种互相不兼容的意见，然后更不知道该怎么办。反过来，拿执行层去回答"该不该做"也不行——PRD 写得再完整，也只是更高效地做错事。

### 1.3 方案判断：Tech Spec 是待审文档

技术方案最常见的错误，是把它当成"待实现的结论"。写完就开始排期，评审变成走过场。

换一个定位：Tech Spec 是一份待审文档，评审要回答三个问题。

**什么情况下会失败？** 不是"有没有风险"这种空问法，是具体到：流量涨十倍先坏哪里、依赖的服务挂了怎么办、数据迁移到一半失败怎么恢复。

**失败之后怎么回滚？** 有没有开关、有没有备份、回滚要多久、回滚会不会丢数据。没有回滚路径的方案，等于把一次发布变成一次赌博。

**出问题谁负责？** 不是追责，是确认每个环节都有明确的人。归属不清的地方，通常也是设计最模糊的地方。

还有一节最容易被跳过：非目标。写清"这次不做什么"，比写清"这次做什么"更能防止范围蔓延。没有非目标，执行中每遇到一个相关问题，都会被顺手加进来。

### 1.4 判断的验收

判断阶段结束前，用三个问题自检：

- 有没有明确的非目标？
- 这个判断能不能被证伪——什么结果出现，说明它错了？
- 有没有回滚路径？

三个都答不上来，说明还停在愿望阶段。愿望可以开工，但不该排期。

## 二、读：搜索调研

调研不是一种活。四种品类的证据等级、可接受来源、失效方式都不同；混在一起写，只能写成工具清单。

### 2.1 四种品类

| 品类 | 可接受来源 | 证据强度 | 典型失效 |
|---|---|---|---|
| 事实核查 | 原始文件、官方公告、法规原文 | 高 | 二手转述失真，来源不可追溯 |
| 学术 | 同行评议论文、DOI、arXiv | 高 | 预印本未经审稿，引用断章取义 |
| 市场 | 一手数据、审计报告、财报 | 中 | 口径不可比，样本有偏 |
| 用户 | 原话、录音、行为数据 | 中 | 引导性提问，把客套当需求 |

同一份调研报告里，这四类证据不能混着加权。一份访谈里的"用户说愿意付费"和一份财报里的"这个品类客单价 39 元"，不是同一种东西；把它们放进同一个结论，结论就不可信了。

### 2.2 学术检索：先建候选集

学术调研的第一步不是让模型总结，是让它把候选集建出来。

关键词要扩：同义词、近邻术语、反义词、不同学派对同一现象的不同叫法。只用一个词搜，召回率会低得离谱。扩完之后走 API 检索——Semantic Scholar 覆盖两亿多篇，返回的是论文 ID、DOI、引用数，不是一段摘要。拿到 ID 之后再按年份、引用数、venue 过滤，去重，最后用 OpenAlex 之类的另一个源交叉验证一遍，防止单一索引漏掉或错标。

这里有个容易犯的错：把"搜索"当成"一次查询"。真正的深度调研是多轮的——后一轮的问题由前一轮的结果决定。搜到"这个方向有三种主流做法"，下一轮才去分别查这三种做法的原始论文；搜到"某篇高引论文的结论和另一篇冲突"，下一轮才去查这两篇的方法差异。一次查询只能给你关键词的回声，多轮才能给你地图。

这一阶段的产出是候选集，不是综述。综述是精读之后的事。

### 2.3 精读：五档与台账

精读可以按投入分五档：快速（主旨加三条支撑）、深入（论证树、证据、假设、反例）、地图（节点与关系）、费曼（合上书讲一遍，标出讲不通的地方）、整本（章节地图与主线）。

不管哪一档，都要落一本证据台账：每个结论对应哪段原文、哪一页、哪个时间戳。台账的作用不是引用好看，是让你在写的时候能回到原话，而不是回到自己上一轮的转述。

材料超过九千词，按语义边界切，不要按 token 数硬切。切在章节、小节、论点的边界上，每一段的分析才能独立成立；切在句子中间，模型会补出原文没有的因果关系。

精读的目标不是把长文变短，是把作者的论证重新搭起来：他主张什么、用什么支撑、哪里是假设、哪里是跳跃。

### 2.4 市场与竞品：口径先于结论

市场数字最危险的地方不是不准，是不可比。两个来源都写"市场规模 500 亿"，一个按出厂价算，一个按零售价算，加起来就是错的。

所以先问口径：TAM 是自上而下算的，还是自下而上算的？SAM 的边界按地域、按行业、还是按客群？SOM 的假设是什么？口径不同，数字就不能放进同一张表。

竞品分析也一样。按什么轴切分——价格、场景、交付形态、客户规模？轴不同，结论就不同。五力模型不是五个框各填一句，是找出**当前真正卡住你的那一股力**：是供应商集中，是买方议价，是新进入者，是替代品，还是现有竞争。五股力都写"中等"，等于没分析。

### 2.5 用户访谈：原话回到时间戳

用户调研的产物不是"用户想要 X"，是"第 3 位受访者在 12:40 说了这句话，对应的场景是 Y"。

访谈转写之后要做编码：把原话切成片段，标主题，标情绪，标场景。每个主题下面必须挂着原话；没有原话的主题，是研究者的投射。引文要能回到时间戳，这一条能挡掉大部分"我觉得用户会喜欢"。

提问方式也会污染结论。问"你会用这个功能吗"，得到的多半是客气；问"你上一次遇到这个问题是什么时候，当时怎么解决的"，得到的才是行为。这是 Mom Test 那套方法的核心：问过去，不问未来；问具体，不问假设。

### 2.6 调研的验收

调研收口时，检查四件事：

- 每个关键结论有没有两个独立来源？
- 来源冲突时，有没有回到官方或原始文件？
- 结论有没有标置信度，证据不足的地方有没有写出来？
- 输出的是"主张 + 来源 + 置信度"，还是一段读起来很顺的话？

最后一条最容易被忽略。一段没有出处的流畅综述，比一段标注了"证据不足"的粗糙笔记更危险，因为它看起来已经完成了。

## 三、做：不累积资产的任务

做的判断标准是"做完就结束"。翻译一段话、核对一个结论、跑一次脚本，交付完这次就完了，下一次从头开始。没有中间资产留下来，所以不需要管线；成功标准只有两条：一次做对，当场能验。

### 3.1 什么算做

翻译、核对结论、一次性脚本、格式转换、单次问答，都属于这一类。

它们的共同点是**没有下一次**。你不会在三天后接着改这段翻译，也不会在下周继续跑同一条命令。既然没有"接着改"，就不需要 spec、基线、检查点这些为长程准备的东西；多设一道 gate 反而更慢。

### 3.2 翻译：术语表先行

翻译的质量瓶颈不在句子流畅度，在术语一致性。同一个词在三段里译成三个说法，读者会以为是三个概念。

顺序是：先建术语表——原文术语、选定译法、禁用译法、出处；再分段翻；再出双语对照；最后人审。术语表放在最前面，是因为它一旦定错，后面每一段都会错，而且错得很一致，反而不容易被发现。

机器翻译出错有规律：否定范围（"不是所有 A 都 B"译成"所有 A 都不是 B"）、修饰语归属、数字与单位、专有名词、以及看起来像术语的普通词。人审按这几类逐项过，比从头通读一遍有效。

跨语言找资料时，顺序要反过来：先用原文语言检索，再翻关键段落。用中文关键词去搜英文世界，召回率会差一个量级。

### 3.3 核对结论：证据链

核对一个结论，走三步：把它拆成可验证的主张，找到原始来源，逐条比对。

"AI 说对"不是证据。模型可以给出格式完美的引用而来源不存在，也可以引用一篇真实存在的论文而把结论改写。核对要回到原始文件，不是回到另一个模型。

重点核对五类东西：数字、日期、单位、人名、否定词。这五类最容易被"顺"过去，也最容易在转述中被悄悄改掉。

### 3.4 一次性执行

脚本、SQL、正则、shell 命令属于同一类：跑一下就知道对不对。

所以验收动作是**跑**，不是读。给它一个能返回通过或失败的命令，比让它解释一遍逻辑有效得多。反过来，如果没有可执行的验证，就不要让它直接动生产环境；不可逆的操作前面必须有人工 gate。

### 3.5 做的失败模式

三种：看起来对、过度解释、不可复现。

"看起来对"靠可执行验证挡；"过度解释"靠明确输出格式挡——要一条命令就给一条，不要附上三段说明；"不可复现"靠记录输入、版本、随机种子挡，尤其是数据处理和脚本类任务。

## 四、造：带资产的产出

造和做的分界不在产出的大小，在产出会不会累积成资产。写一套文档、做一个功能、拍一条片子、搭一条 Agent 工作流，中间产物会留下来，下一次在它上面继续改。有资产，才需要管线。

管线的形状在三个地方被反复描述过。产品开发里的 stage-gate 把阶段之间的人为决策点叫 gate，gate 只回答三件事：继续、停止、返工。影视和游戏生产把它切成 development / pre-production / production / post-production。Agent 工程把自动检查和人工拍板分开：guardrail 管前者，human review 管后者。

管线的一个核心设计目标，是让错误在修复成本还低的时候暴露。错误越晚被发现，返工通常越贵，但这不是铁律——有些问题只有成片或上线之后才看得见。流程能做的是把能提前暴露的尽量提前。

### 4.1 七段：按任务查表

拿到一个任务，先按列找到它，再按行看每一段该产出什么。

| 阶段 | 代码 | 文档 | AI 应用 | 视频 | 演示 | 游戏资产 |
|---|---|---|---|---|---|---|
| 意图 | issue、spec | 读者与决策 | 用户与任务边界 | 品牌与转化目标 | 受众与决策 | 目标玩法 |
| 分解 | 任务、接口、验收命令 | 章节、论点、证据 | 能力清单、工具图 | 镜号、时长、景别 | 叙事骨架 | 逆向 spec |
| 一致性资产 | 接口、schema、CONTEXT.md | 术语表、大纲 | tool schema、memory | 参考图、设定图 | 视觉方向、模板 | 资产清单、规格 |
| 人工评审 | plan review、dry-run | 骨架评审 | approval gate | 分镜图、低清小样 | 单页草图 | 可玩原型 |
| 生成 | 实现 | 扩写 | 执行 | 逐镜生成 | 全 deck | 逐系统重建 |
| 收尾 | PR、CI | 统稿 | 结果整合、回滚 | 剪辑、配乐 | 排版、校验 | 集成、对照 |
| 回收 | lint 规则、skill | 模板 | eval 集、playbook | shot 模式 | 校验器 | 拆解方法 |

七段不是必须走满。一条 15 秒的演示可以只走意图、生成、收尾。判断标准是**返工成本与流程成本的比值**：返工越贵，越值得多设 gate；返工只是重跑一遍，设 gate 反而更贵。

七段也不必在一个会话里完成。把调研、写指令、执行、判拆开，目的不是分工好看，是让每个会话的上下文只装它需要的东西。

| 会话 | 只做一件事 | 产出 | 分开的理由 |
|---|---|---|---|
| 调研 | 查同类做法、既有参考、硬约束 | 约束清单 | 调研会引入大量无关信息，留在执行会话里会稀释指令 |
| 写指令 | 把 brief 变成可执行的规格或 prompt | 指令稿 | 改指令和改产物是两种反馈，混在一起会互相带偏 |
| 执行 | 按指令产出 | 初稿、素材 | 执行需要干净的上下文 |
| 判 | 按判据验收 | 过、退回、局部修 | 作者视角会替自己的产出找理由 |

会话之间的交接物是**文件**，不是聊天记录。规格、指令稿、判据、基线，都要落到可以被下一个会话直接读取的地方；靠"它还记得上文"，换一个会话就断了。

### 4.2 意图与分解

brief 的典型反例是形容词堆叠：「高级感、年轻化、有科技感」。这类词不可执行，因为两个人对它的判断可以完全相反，模型只能猜；模型猜的部分，就是后面要重来的部分。

可执行的 brief 至少包含：受众、渠道、时长、必须出现的元素、明确不要的元素，以及一句"这次交付用来让谁做什么决定"。

意图阶段先跑调研会话。它查同类做法、既有参考、硬约束，产出不是灵感，是**约束清单**——哪些必须遵守、哪些已经被别人证明不行。约束清单直接进入分解，不进入执行会话。

分解的产物是执行清单。清单粒度只有一条标准：**每一项都能被单独执行、单独验收**。视频里是镜号、时长、景别、运镜、主体动作、字幕位、音效点；文档里是章节、论点、证据、篇幅；代码里是任务、接口、验收命令。缺一项，执行时就要靠猜。

写指令的会话和执行会话要分开。指令会话只改指令，执行会话只产出。两边混在一起，改指令时会被已有产物带偏，执行时又会迁就旧指令。

### 4.3 一致性资产

这一阶段解决的是跨项一致性：第 N 项和第 1 项还是不是同一个东西。

术语表、schema、接口定义、参考图、CLAUDE.md 属于同一类资产。它们不直接构成交付物，却决定了所有产出物能不能拼在一起。长文档里它叫术语表，代码里它叫契约，视频里它叫参考图。

参考图要分工：主参考定"是谁"——产品、角色、场景；风格参考定"长什么样"——光、色、质感、镜头。两类混用，最常见的后果是主体被风格吃掉。

### 4.4 人工评审：先定判据，再判

评审不是打分，是判。判的输出只有三种：过、退回重做、局部修。只给"再优化一下"，等于没有判。

**判据要在生成之前定。** 看完产物再定标准，标准会不自觉地迁就产物。

判据的来源可以拆成两步：先让 AI 起草一版，人会嫌它列得太多、太抽象；再逐条删，只留下**可观察**的条目。可观察的意思是，能指着具体位置说"这里不对"。不说"高级感"，说"主体在三个镜头里保持同一张脸、同一套服装"。留下的条目分两级：必过项一条不达标就退回，加分项不阻塞。

判据还要用样本校准。给两条"过"的、两条"不过"的例子，判据才算落地；只给文字标准，不同会话会判出不同结果。

判要独立于生成。新会话、换角色、只给产物与判据，不给生成过程。同一个会话里判自己的产出，模型倾向于为已经写下的思路辩护；换一个会话、只给它结果，它才容易说出"这里不对"。

每一类任务在评审阶段都有一处最容易漏掉的东西：视频是主体一致性，文档是术语漂移，代码是验证信号缺失，Agent 是副作用发生前没有 gate。评审把这一处当成必查项，而不是顺带看一眼。

### 4.5 生成与收尾：检验与局部修复

生成阶段真正的风险不是做不出来，是做出来了，但每一项都不完全一样。到收尾时，看到的是：大部分对，少数几处差一点，还有几个小 bug。全部重做的代价最大，也最容易把对的改坏。

收尾的核心动作是**定位、局部修复、回归**，不是"再优化一版"。

**定位**：把"不对"说成坐标——第几镜、第几节、哪个函数、哪条断言。说"整体感觉差点意思"，模型只能重写，重写就会带上已经对的部分。

**冻结**：把已经确认的部分标成不可改——基线文件、已批准镜头、通过的测试。修复只动未确认区。

**小步**：一次只改一处，改完立刻验。多处一起改，出错时无法判断是哪一处引起的。

**回归**：改完对照基线，确认没把对的改坏。视频是抽帧对照，文档是术语与结论对照，代码是测试与 diff。

**粒度**：点修（一处措辞、一个参数）、段修（一节、一个镜头、一个函数）、重做（整段）。按代价选，不要默认重做。

修复放在独立会话里做，带上基线和坐标。执行会话的上下文里全是它自己刚做过的东西，在那里顺手改，等于让它替自己辩护。

有一个反向信号：如果每次修复都在扩大改动范围，说明问题不在执行，而在意图或评审阶段没对齐。这时候继续修只会越修越远，应该退回去重新对齐，而不是加大 prompt 的力度。

### 4.6 回收与迁移

值得回收的不是 prompt。prompt 会随模型失效，值得留下的是三样：**模式**（哪类任务、什么参数、什么资产组合）、**清单**（验收时逐项检查什么）、**触发条件**（什么任务该走这条线）。一个 skill 就是这三样的打包。

这套管线搬到别的产出上，只换每一段的具体物：

| 阶段 | 代码 | 文档 | AI 应用 / Agent |
|---|---|---|---|
| 意图 | issue、验收标准 | 读者、决策、非目标 | 任务定义、权限边界 |
| 分解 | 任务清单、接口 | 章节大纲、论证顺序 | 能力清单、工具图 |
| 一致性资产 | 接口、schema、CONTEXT.md | 术语表、体例 | tool schema、memory、系统提示 |
| 人工评审 | plan review、dry-run | 骨架评审 | 副作用前的 approval |
| 生成 | 实现 | 扩写 | 执行 |
| 收尾 | PR、CI、回归 | 统稿、交叉引用 | 结果整合、回滚 |
| 回收 | lint 规则、skill | 模板、术语库 | eval 集、playbook |

## 五、验收与沉淀

验收不是最后一步，是每一段的出口。沉淀也不是写总结，是把这次做对的东西变成下次的起点。

### 5.1 验证强度与监督程度成正比

你盯得越少，验证越要硬。这是一条比"多检查几遍"更可操作的规则：先看自己实际投入了多少注意力，再决定验收做到什么程度。

| 监督程度 | 验收手段 |
|---|---|
| 全程盯着 | 读一遍，发现问题当场改 |
| 偶尔看 | 跑测试、构建、schema 校验 |
| 完全不管 | 独立验证、对抗评审、可回滚 |

关键不在于验几遍，在于**有没有一个能返回通过或失败的东西**。读一遍觉得行，是判断；跑一条命令得到退出码，是验证。前者会疲劳，后者不会。

### 5.2 AI 自查的三种失效

让模型检查自己的产出，会遇到三种系统性偏差。

**自评偏高**：模型给自己的输出打分，往往高于外部评审。它倾向于把"符合指令"当成"符合标准"。

**同会话辩护**：在生成它的同一个上下文里让它自查，它会为已经写下的思路找理由。你问"这里有没有问题"，它更容易回答"整体是合理的，但可以补充……"，而不是"第三段错了"。

**覆盖不全**：它只检查自己想到过的维度。没想到的类别，它不会主动去查——比如数字对不对、单位有没有换、否定词有没有丢。

对应的做法是三条：自查只当第一道筛；判放到新会话，换角色，只给产物和判据；能用可执行检查的，不靠模型判断。对抗评审也属于这一类——让一个没有参与生成的会话去尝试推翻结论，比让它"再看看"有效。

### 5.3 workslop：不透明的使用比使用本身更贵

HBR 在 2025 年让一个词进入主流讨论，workslop：看起来像完成品、实际没有推进任务的 AI 生成内容。

一项调查里，40% 的美国员工在过去一个月收到过同事发来的 workslop，平均处理一次要花近两个小时；按一万人规模估算，一年损失的生产力以百万美元计。另一项覆盖 47 国、三万多名员工的调查里，66% 的人不核对就使用 AI 输出，61% 会隐瞒自己用了 AI。

这两个数字放在一起看，问题就不在"AI 写得好不好"，在**错误没有被标记**。一个人用 AI 生成了看起来完整的文档，另一个人以为那是想过的结论，花两小时去核对，才发现里面没有可执行的内容。隐瞒使用让这件事更难被发现，也更难被纠正。

所以使用 AI 的规范里，最该写进去的一条不是"要检查"，是**标注哪部分是 AI 生成的、哪部分是人确认过的**。透明本身不提高质量，但它让质量问题的发现成本降下来。

### 5.4 沉淀：skill 的三件套

值得沉淀的不是 prompt，是流程。一个可复用的 skill 至少包含三样东西：

**SOP**：这类任务分几步、每步的产出是什么、哪一步要停下来等人判。

**触发条件**：什么任务该用它。这一段通常写在 name 和 description 里，常驻在系统提示中，不占正文的上下文。

**检查脚本**：验收时跑什么。能写成脚本的，就不要写成"请仔细检查"。

Agent Skills 的加载方式是渐进式披露：元数据常驻，正文按需读，附带资源再按需取。所以 skill 的写法要反过来——把"什么时候用"写短写准，把详细的步骤和参考放到正文与附件里。正文写得太长，反而会让模型忽略其中一半。

最后是判断值不值得写。三个条件：会重复、输入稳定、有明确的验收标准。缺一个，写成提示词片段就够了。写成 skill 的成本不在写，在维护——模型升级、工具改名、接口变更，都会让里面写死的东西失效；维护跟不上，skill 就会从资产变成负债。
