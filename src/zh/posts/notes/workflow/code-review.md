## 定位

> CR 的目的不是挑错，而是**集体提升代码质量 + 知识共享**，让 PR 保持干净和清晰。
> 核心原则：**你 PR 的代码，最终 owner 还是你**——AI 可以辅助，但看懂、负责是你的事。

- **上游**：api-dev（API 开发）
- **下游**：testing（测试）

## 提交者自检（Before CR）

### 自检清单

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | Self-review 自己的 diff | 确认没有 debug 代码、注释掉的代码、临时代码 |
| 2 | 敏感信息检查 | 无密码、密钥、Token 硬编码，日志无敏感数据 |
| 3 | 单测通过 + 覆盖率 | 核心逻辑覆盖，关键边界 case 有测试 |
| 4 | Commit message 规范 | Conventional Commits：feat / fix / docs / refactor 等 |
| 5 | 本地冒烟测试 | 关键链路自己跑一遍 |
| 6 | PR 描述完整 | 背景、改动点、影响范围、测试方法 |

### PR 描述模板

```markdown
## 背景
为什么做这个改动？

## 改动点
- 新增 / 修改了哪些模块和接口

## 影响范围
- 影响的接口、表、前端页面

## 测试
- 单测：xx 个用例
- 手工验证：xx 场景

## 相关文档
- 技术方案：[链接]
```

## Reviewer 审核清单

### 七大维度

| 维度 | 检查项 |
|------|--------|
| **正确性** | 业务逻辑符合需求、边界 case 处理、错误处理 |
| **安全性** | SQL 注入 / XSS / 越权、敏感数据脱敏、依赖漏洞 |
| **性能** | N+1 查询、循环内 DB/网络调用、索引合理性 |
| **可读性** | 命名清晰、函数不过长、注释恰当 |
| **可维护性** | 无重复代码、低耦合、设计模式合理 |
| **测试** | 核心逻辑有单测、关键边界有覆盖 |
| **兼容性** | API 向后兼容、数据迁移脚本、配置兼容旧版 |

### Reviewer 操作 SOP

1. **先看 PR 描述**，理解背景和目标，再进代码
2. **按影响面排序**：先核心逻辑，再安全 / 性能，最后风格
3. **区分 Blocking / Non-blocking 意见**：
   - 🚨 Blocking：必须改，否则拒绝合并（bug、安全问题、重大性能问题）
   - ⚠️ Nitpick：建议改，可后续跟进（命名、风格、小优化）
4. **评论写清理由**，不只说"这里不对"，要说"为什么不对 + 怎么改"
5. **回复每条评论**：Accept / 说明理由 / 修改后标注 Done
6. **合并标准**：无 Blocking 意见 + 单测通过

### 🤖 Agent 增强实践：AI 预审

```text
请以资深 Reviewer 视角 review 这个 PR：

[粘贴 PR 描述 + git diff]

按以下格式输出：
🚨 阻断性问题（必须改，附原因和修改建议）：
⚠️ 建议性改进：
💡 最佳实践提醒：
```

### 案例：怎么说清楚一个问题

```text
❌ 不好的评论：「这里写得有问题」

✅ 好的评论：
「第 88 行用 double 存金额会有精度丢失，建议改成 BigDecimal。
   当前下单流程可能触发 0.1 + 0.2 = 0.30000000000000004 的 bug，
   参考支付模块 PaymentUtil 的写法。」

包含四个要素：位置 + 问题 + 后果 + 改法（含参考实现）
```

## 4.3 AI 辅助 CR 的实战技巧

> 实践认知：AI 是 CR 的杠杆。几千行的 PR 人工很难看完，但可以让 AI 先做影响面分析和问题清单，人再复核。一两次严格 review 之后，提交者的 PR 质量会明显提升，之后越来越干净。

### 技巧 1：大 PR 先做影响面分析

几千行 diff 直接看会淹没在细节里。先让 AI 分层：

```text
这个 PR 改了哪些模块？按影响程度高→低排序。
哪些文件是核心逻辑改动？哪些只是格式化 / 重命名？
可能影响哪些功能？有没有隐性的调用方受影响？
```

拿到影响面地图后，按模块分批次 review，而不是从头滚到尾。

### 技巧 2：AI 出清单，人做裁决

- AI 列出的问题不要全信，逐条判断：真的错？还是误报？
- 把 AI 清单 + 自己发现的问题合并去重，输出结构化 Review 意见
- 误报也要反馈给 AI，让它在同一会话内记住你的标准，越用越准

### 技巧 3：规范类检查交给 AI，人专注业务

- 是否符合团队 convention、命名规范、是否复制粘贴 → AI
- 业务语义、架构取舍、产品意图 → 人

### 技巧 4：建立 CR 反馈循环

第一次被丢回几十条意见不要慌。把高频问题整理成团队 CR 检查单，下次自检先过一遍。一两次以后，提交者和 Reviewer 的沟通成本会显著下降。

### 案例：大 PR 处理流程

```text
场景：同事提了一个 3000 行的 PR，涉及订单模块重构。

第 1 步：让 AI 做影响面分析
→ 输出：改动集中在 3 个模块，其中支付接口是核心逻辑，
  其余是 DTO 重命名和测试更新

第 2 步：让 AI 分模块出问题清单
→ 支付接口发现 2 个阻断问题（并发扣款未加锁、金额精度用 double）
→ 其余模块发现 8 条建议性改进

第 3 步：人复核 AI 结论
→ 确认 2 个阻断问题属实，8 条建议中 5 条采纳
→ 合并自己发现的 1 个业务问题（优惠券状态机缺状态）

第 4 步：输出 Review 意见给作者
→ 2 个 Blocking + 6 条建议，附上原因和改法

第 5 步：作者修改后二次 review，通过合并
```

### 案例：AI 误报处理

```text
场景：AI 报了一条「资源未关闭，存在连接泄漏」，指向 try-with-resources 代码。

人的处理：
1. 核对代码 —— 实际已用 try-with-resources 正确关闭，属误报
2. 回复 AI：「这里已通过 try-with-resources 自动关闭，不是泄漏，
   之后遇到 try-with-resources 请跳过该检查」
3. 后续同一会话中，同类误报不再出现

原则：AI 是助手不是法官，最终裁决权在人。
```
